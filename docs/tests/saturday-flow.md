# 試験計画: saturday-flow（土曜運用 通し結合試験）

- 前提となる設計書: なし（既存 5 集約の結合シナリオ。個別設計は
  `docs/designs/{meal-plan-core,shopping-list-core,pantry-core,dashboard}.md` を参照）
- レベル: L2（新規ドメイン/契約なし。既存 UseCase 集約の端から端までの結合確認）
- 位置づけ: Sprint 6 タスク1「全体結合テスト（土曜運用の通しテスト）」の試験台本。
  2 人での実運用（Sprint 6 完了条件）の手順書を兼ね、将来の Playwright E2E 自動化の準拠元とする。

## 試験種別

- **結合（E2E シナリオ）**が主。献立 → 買い物リスト → 買い物 → 在庫 → 平日消費 の 1 本の
  ハッピーパスを端から端まで通し、Presentation の配線（フォーム・Hono RPC・Server Component・
  画面間遷移）と集約をまたぐ状態遷移（MealPlan.status / ShoppingList.status → Pantry 反映）が
  破綻なく繋がることを見る。
- 各集約内部のビジネスロジック・境界値・防御性は既存の単体/結合試験で担保済み
  （`docs/tests/{meal-plan-core,shopping-list-core,pantry-core,...}.md`）。本計画はそれらを
  **再実装せず**、通しの結節点と画面遷移に観点を絞る。
- **実行環境**: アプリ + DB が必要なため、緑判定は原則ローカル（`pnpm --filter @cookpit/web e2e`）
  または 2 人での実機運用で行う。リモート（エフェメラル）環境は `DATABASE_URL` 未設定のため
  自動実行不可（`docs/07-dev-rules.md §環境の既知の事実`）。本計画作成時点では自動 spec は未実装
  （E2E は `apps/web/e2e/` にハッピーパス 1 本のみ。追加はこの台本を準拠元に別タスクで行う）。

## 前提データ（試験データ）

| 種別       | 内容                                                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------- |
| 店舗マスタ | 2 店舗以上（例: スーパーA / スーパーB）。買い物の実購入店舗・推奨店舗変更に必要                                           |
| レシピ     | 材料を持つレシピ 1 件以上（買い物リストに品目が載る前提）。`/recipes` で作成（既存 `recipe-crud.smoke.spec.ts` がカバー） |
| 商品マスタ | 価格比較ビュー確認用に、価格履歴が 2 店舗以上ある商品 1 件（任意観点 I-10 用）                                            |
| 週         | 「今週」（`currentWeekIdentifier`）に既存の献立が無い状態から開始                                                         |

| E-01 | 空の献立から買い物リスト生成          | 献立にレシピ 0 件                 | 「買い物リストを作る」                                     | リスト遷移後、品目 0（EmptyState「リストにアイテムがありません」）。クラッシュしない                    | 境界 |

## 特性観点

- **権限**: 認証なし MVP1 のため対象外（ログインユーザー概念なし。出典: `docs/03-architecture.md`）。
- **データ整合性**: 集約をまたぐ状態遷移が一方向で保たれること — MealPlan(draft→…) →
  ShoppingList(active→completed) → Pantry へ在庫反映、の順序で前段完了が後段の前提になる（I-03/I-07/I-08）。
  買い物完了前に在庫は生成されない。
- **冪等性**: 通しシナリオでは重複押下の主対象は「購入記録」「買い物完了」「消費」。各ハンドラは
  `submittingItemId`/`completeSubmitting`/`submittingStockId` で多重実行を抑止する（画面ガード）。
  UseCase レベルの冪等性は各集約の単体/結合試験で担保済みのため本計画では**画面ガードの確認のみ**。
- **障害系（外部 I/O）**: 対象外に近い — DB 以外の外部 API 連携は MVP1 に無い。ネットワーク断は
  E-04/E-05 とオフライン（下記 FE）でカバー。
- **フロントエンド（apps/web）**:
  - ローディング: 各ボタンの submitting 表示（「作成中」・disabled）・「更新」ボタン。
  - エラー表示: E-04 のバナー。エラーバウンダリは各画面 `error.tsx`（別途担保）。
  - 楽観的更新ロールバック: E-05（購入記録の `useOptimistic`）。
  - **オフライン再訪問（O-01）**: 買い物中に `/shopping-lists/{id}` をオフライン再表示できること。
    Service Worker（`src/app/sw.ts`）が当該詳細ページと `GET /api/shopping-lists/{id}` を
    NetworkFirst で runtime cache する設計。**本番ビルド + 実機が必要**（`next build` 経由でのみ
    Serwist 有効化。dev は素の Turbopack で SW 無効）→ ローカル/実機でのみ検証可（MB-10〜12）。
- **防御性（Domain）**: 本計画は結合シナリオのため対象外（Entity/VO の防御性は各集約の
  単体試験で担保）。
