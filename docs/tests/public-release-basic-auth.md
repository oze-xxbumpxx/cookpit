## 重要な設計上の注記: `proxy()` と `config.matcher` の責務分離

設計書の疑似実装は、除外パス判定を **`config.matcher` の否定 lookahead 1 箇所にのみ**委ねており、
`proxy()` 関数本体にはパス判定コードが無い。つまり:

- `proxy()` を Vitest から直接呼び出すユニットテストは、**どの pathname を渡しても同じ認証ロジック**
  （環境変数確認 → Authorization ヘッダ検証）が走る。除外パス（`manifest.webmanifest` 等）を
  `proxy()` に直接渡しても 401 判定ロジックがそのまま実行されるため、「除外パスは 401 にならない」
  という振る舞いは **`proxy()` の単体テストでは検証できない**。実際に除外されるかどうかは
  Next.js が `config.matcher` を見て `proxy()` を呼び出すかどうかを決める段階の話であり、
  Vitest はこの Next.js 内部のルーティング判定を再現しない。
- 設計書テスト方針節は「対象パス・除外パスの実挙動は proxy の単体テストで担保する」と述べているが、
  上記の理由により、これは `config.matcher` の**パターン文字列**を対象にした構造テスト（後述）でしか
  近似できない。最終的な実挙動確認は設計書「移行とリリース」手順4の実機確認、および `pnpm build` に
  よる matcher 構文の静的検証（設計書「未決事項」節）に委ねられる。本試験計画はこの区別を明示する。

したがって単体試験観点を 2 系統に分ける。

1. `proxy()` の認証ロジック（pathname に依存しない）。
2. `config.matcher` のパターン文字列（正規表現として妥当か、想定パスをマッチ/除外するか）の構造テスト。
   Next.js の path-to-regexp コンパイル結果そのものではなく、パターン文字列を素の `RegExp` として
   評価する近似テストであることを明記する（Next.js 実挙動と完全一致する保証はない）。

## Orchestrator 判断: matcher の実挙動は実サーバで確認する

上記の指摘（構造テストは Next.js の実コンパイルとの一致を保証しない）を受けた確定判断。
**設計 D-2（除外を `config.matcher` に置く）は変更しない。** 理由は、除外を
`proxy()` 内の関数へ移すと `_next/static` 等への全リクエストで Proxy が
起動し、D-2 が除外理由として挙げた実行コスト削減を失うため。

代わりに、近似テストを実挙動の根拠に**しない**。matcher の正解判定は次の 2 つで行う。

1. `pnpm --filter @cookpit/web build` の成功（Next.js が matcher を静的検証する）。
2. **本番相当のサーバを実際に起動した black-box 確認**（実装ステップとして必須）。
   `BASIC_AUTH_USER` / `BASIC_AUTH_PASSWORD` を設定して `next start` を起動し、
   以下を curl で確認して結果を実装報告に記録する。localhost への接続のみで完結する。

   | パス                                    | 期待                                           |
   | --------------------------------------- | ---------------------------------------------- |
   | `/`                                     | 401 + `WWW-Authenticate`                       |
   | `/api/pantry`                           | 401                                            |
   | `/manifest.webmanifest`                 | 401 でない                                     |
   | `/api/cron/expiry-alerts`               | 401 でない（`CRON_SECRET` 側の判定に到達する） |
   | `/_next/static/...`（実在するアセット） | 401 でない                                     |
   | `/` + 正しい資格情報                    | 200                                            |

MW-M01〜MW-M12 の構造テストは**破棄せず残す**。Next の実コンパイルとは別物だが、
パターン文字列のタイプミス（例: `manifest.webmanifest` の綴り間違い）を CI で
継続的に検出する価値があるため。ただし完了条件としての重み付けは上記 2 点が上位で、
構造テストが通っただけでは matcher が正しいとは見なさない。

## 特性観点

- 権限: 資格情報は 2 名で共有する単一アカウントであり、ユーザーごとの権限差・ID 分離はない
  （B-05）。試験は「資格情報が一致するか否か」のみを判定対象とし、ロールベースの追加観点は不要。
- データ整合性: `proxy.ts` は DB・永続状態を持たない（DB 設計は対象外）。認証チェックは
  `process.env` の読み取りのみで完結する純粋なリクエスト処理であり、リクエスト間で状態を共有しない。
- 冪等性: 同一リクエストを何度実行しても結果は変わらない（環境変数のみを参照するステートレスな
  処理で、書き込み系の副作用が無いため）。連続した誤り資格情報（MW-04〜06 相当）を繰り返しても
  ロックアウトや状態変化は発生しない設計であることを確認する（ブルートフォース対策は設計上スコープ外、
  「ログと監視」節に明記）。
- 障害系（外部 I/O）: 対象外。DB・外部 API・外部ストレージへの新規 I/O はない
  （設計書「エラー処理」節のトリガー不成立）。
- フロントエンド固有: 対象外。画面・コンポーネントの変更はない。
- 防御性（Entity/VO ではないため観点を以下のように再解釈して適用する）:
  - 不変条件: `proxy()` はリクエストを変更しない（ヘッダの読み取りのみ）。MW-01/02 で
    `NextRequest` の入力がそのまま次段へ渡ること（書き換えが無いこと）を確認する。
  - 防御的コピー: 対象外（配列・Date 等の可変オブジェクトを返すゲッターは存在しない）。
  - 副作用の検証: 401 応答時は資格情報やエラー詳細をログに残さない（設計書「ログと監視」節）。
    503 応答時のみ `console.error` が 1 回呼ばれること、かつログ出力に資格情報の値そのものが
    含まれないことを確認する（MW-19 に付随する観点として実装時に追加、必須ではなく推奨）。
  - 不正引数の伝搬: MW-07〜MW-11 のとおり、ヘッダが欠落・スキーム不正・base64 破損・区切り文字なし
    のいずれであっても例外を投げず 401 に正規化されること（未捕捉例外により 500 に落ちないこと）を
    必須観点として含む。
