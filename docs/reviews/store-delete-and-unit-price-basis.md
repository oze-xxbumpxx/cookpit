## アーキテクチャ原則の確認

- 依存方向: `packages/domain` の追加は `StoreId` の型参照のみで、外部パッケージへの依存は増えていない。
  Drizzle・HTTP の型は Domain に入っていない。
- 集約境界: 参照件数の取得は各集約のリポジトリに置き、**集約をまたぐ判断は
  `DeleteStoreUseCase`（Application 層）が束ねる**。集約インスタンスを別集約に持たせていない。
- `create()` / `reconstruct()`: 新規エンティティ生成は無く、既存の入口を変えていない。
- 1 UseCase = 1 クラス・`execute()`・手動 DI（コンストラクタ注入）を守っている。
- `any` なし / default export なし / `import type` / `===` / 「値なし」は `null`。
- 新規の公開 API（UseCase・エラー・Repository メソッド）に JSDoc を付け、
  **型に表せない契約のみ**（何を数えるか・`@throws`・冪等性）を書いた。

## 機械検証の結果

### 既存ルートの回帰（DELETE 追加でパスが食い合わないか）

`products.ts` は `DELETE /:id` と `DELETE /:id/price-records/:priceRecordId` を併存させる。
セグメント数が異なるため衝突しない。既存の WH-P-01〜05 が**無変更で通ること**を確認した。
`stores.ts` は今回ルートテストを新設し、`GET /` と `POST /` の既存挙動（WH-S-01/02）も
同時に固定した。

### Hono RPC の型に 404 / 422 が現れない件

`app.ts` の共通 `onError` 由来のステータスは RPC の戻り型に含まれず、
`response.status !== 404` が「型に重なりが無い」比較としてコンパイルエラーになる。
`shopping-list-client.tsx` の既存対処（`const status: number = response.status;`）と
同じ形に揃えた。**新しい回避策を発明していない。**

### 死んだ公開 API の除去

`formatUnitPrice` 導入後、`unitPriceBasisLabel` の本番呼び出しがゼロになった
（金額とラベルは常に対で出るため）。テストだけが参照する公開関数を残さないよう削除し、
PF-06 / PF-06b は `formatUnitPrice` 経由の検証へ移した。

### テスト用 InMemory リポジトリの追随

リポジトリインターフェースへのメソッド追加により 6 箇所がコンパイルエラーになることを
意図的に発生させ、`pnpm type-check` の出力を潰す形で追随した（実装計画 手順 1）。
追随漏れが型で検出されることを確認済み。

### スコープ外変更の混入

差分に含まれる「要求に直接無い」変更は 1 点のみ。**「最近の記録」の各行に内容量
（`3001kg` 等）を表示するようにした。** これは「どの記録が誤入力か」を画面で見分けられないと
削除機能が使えないための追加で、要求②の達成に必要と判断した（PDC-03 で固定）。
それ以外のリファクタリング・改善は入れていない。

## Should

### S1: 同一商品の記録行で表示基準が混在し得る

300g で記録した行は `99円 / 100g`、1kg で記録した行は `298円 / 1kg` と並ぶ。
**行同士の目視比較がしづらい。** 比較の本体である「最安店舗」カードは正準値で判定しており
結果は正しいので、実害は「一覧を眺めたときの読みにくさ」に留まる。
今回はユーザーが「入力した単位に合わせる」を明示的に選択したため現状のままとする。
実運用で気になるようなら、商品ごとに表示単位を持たせる案（要件で不採用にした案）を再検討する。

### S2: kg / L 表示は保存値の丸め誤差が 10 倍に増幅される

保存値は 0.1 円単位に丸められている（`UnitPriceCalculator`）。kg 表示ではそれを 10 倍するため、
真値との差が最大 0.5 円/kg になり得る（例: 3kg 1,000 円 → 保存 33.3 → 表示 333 円、真値 333.3 円）。
`priceAmount / packageSizeValue` から直接計算すれば誤差ゼロにできるが、
`CheapestStoreResultDto` は `packageSizeValue` を持たないため**カードと記録行で計算経路が
分かれてしまう**。一貫性を優先して正準値 × 倍率に統一した。
価格帯（数百円）に対して 0.5 円の差は判断に影響しない。

### S3: 参照ゼロ確認と削除が別トランザクション

確認と削除の間に他方の端末が価格を記録すると、`price_records` の FK（`restrict`）が
最後の砦として働き 500 になる。2 人利用で同時操作がほぼ起きないため追加のロックは入れていない。
ADR-0012 §Consequences に既知の制約として記載済み。

## Nice

### N1: 422 の内訳件数が UI に出ない

`StoreInUseError` は件数を保持しているが、`onError` の共通変換が `{ error: message }`（英語）
しか返さないため、UI は固定の日本語文言を出している。件数を出すには
エラーレスポンス形の拡張（全エンドポイントに波及）が要るので見送った。
件数はサーバーのメッセージとテスト（DSU-05 / WH-S-05）に残っている。

### N2: 店舗のリネームが無いため「使用中の打ち間違い店舗」は救えない

名前を間違えたまま価格を記録すると、その店舗は参照ありで削除できず、直す手段も無い。
ADR-0012 で受容したトレードオフ。必要になったら `PUT /api/stores/:id` を別タスクで足す。

2. 店舗管理パネルの一覧が、店舗数が多いときに縦に伸びすぎないか（現状は件数制限なし）。

## 本レビューの限界（申し送り）

- 本番データの `3001kg` が実際に消せることは、**ユーザーが実画面で操作するまで未検証**。
  API・UseCase・リポジトリの経路は PGlite（IR-P-10/11）とルートテスト（WH-P-06）で
  通っているが、本番 DB に対しては実行していない。
- 店舗プルダウンの「変なの」が何であるかは特定していない。参照ゼロなら削除でき、
  参照ありなら 422 で理由が出る、という形で**どちらでもユーザーが状況を把握できる**
  ようにした。
