# ADR-003: MVP1 は認証なしで運用する

**ステータス**: 採択
**決定日**: 2026-05

## 背景

当初は Better Auth（最新トレンドの認証ライブラリ）を MVP1 から導入する想定だった。しかし、以下の点を考慮して再検討。

- 利用者は2名のみ（家庭内利用）
- アプリの本質機能は献立・買い物・在庫であり、認証は本質ではない
- Better Auth の導入は学びになるが、MVP1 のスコープを増やす
- ドメインモデル上の `userId` 管理は実装の複雑性を増す

## 検討した選択肢

- A. 認証なし（URL 共有のみ、最シンプル）
- B. Basic 認証のみ（パスワード共有）
- C. Better Auth を MVP1 から入れる

## 決定

**A. 認証なし** で MVP1 を運用する。Vercel の URL を 2 名で共有する。

Phase 2 以降、必要に応じて Basic 認証 → Better Auth と段階的に追加する選択肢を残す。

## 決定の理由

1. **2人利用の本質に合致**：家庭内の共有家計簿や共有メモに近い感覚で、誰の操作かを区別する価値が薄い
2. **MVP1 を本質機能に集中させる**：認証実装に Sprint を割かずに済む
3. **PWA 体験の阻害がない**：ログイン画面が間に挟まらず、ホーム画面から即起動
4. **後から段階的に追加可能**：Phase 2 で Basic 認証で簡易保護、必要になったら Better Auth、というパスが取れる
5. **Vercel URL の推測難度はそこそこ高い**：完璧ではないが、家庭内利用としては実用上の安全性が確保される

## 帰結

### ポジティブ

- MVP1 のスコープ縮小
- ドメインモデル簡素化（[ADR-004](./004-no-user-in-domain.md) 参照）
- 開発速度向上

### ネガティブ

- URL がバレた場合に第三者が編集できる（家庭内利用なので実害は小さい）
- Better Auth の学習機会を MVP1 では得られない（Phase 2 で取得可能）
- 「最初から認証あり」の場合より、後から導入する移行コストが発生する

## 移行パスの想定

Phase 2 で認証を導入する場合の手順：

1. Better Auth を導入してユーザーテーブル作成
2. 大関さんと彼女の 2 名分のアカウントを発行
3. middleware で全ルート保護
4. （必要なら）既存データに `created_by` カラムを追加して埋める

ドメインモデル変更ではなく、インフラ層の変更で対応可能な構造を維持する（[ADR-004](./004-no-user-in-domain.md)）。

## フォローアップ

- Phase 2 移行時に、本 ADR をステータス「廃止」に変更し、新たな ADR を作成する
- 「最初から認証なし、後から導入」のパターンは業務でも遭遇する状況なので、移行時の経験を業務に還元する
