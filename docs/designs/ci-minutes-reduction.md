## 背景

2026-07-25、GitHub Actions が課金停止でジョブを起動しなくなり CI が全面停止した
（メッセージ: “The job was not started because recent account payments have failed or your
spending limit needs to be increased.”）。`oze-xxbumpxx/cookpit` は **private リポジトリ**の
ため Actions の実行時間が従量制であり、無料枠を超えると停止する。

`docs/01-overview.md` の技術制約は「継続費用なし」「無料枠で完結」を掲げている。
したがって課金枠の引き上げより先に、**CI の消費分数そのものを減らす**のが筋である。

### 現状の実測（直近の成功した PR run）

GitHub Actions は**ジョブ単位で分単位に切り上げ**課金される。

| ジョブ           | 実時間 | うちセットアップ | 課金      |
| ---------------- | ------ | ---------------- | --------- |
| Format Check     | 47 秒  | 21 秒            | 1 分      |
| Lint             | 49 秒  | 23 秒            | 1 分      |
| Type Check       | 54 秒  | 28 秒            | 1 分      |
| Dependency Audit | 23 秒  | 14 秒            | 1 分      |
| Build            | 75 秒  | 30 秒            | 2 分      |
| Test             | 139 秒 | 20 秒            | 3 分      |
| E2E Smoke        | 95 秒  | 22 秒            | 2 分      |
| **合計**         |        | **約 2.5 分**    | **11 分** |

7 ジョブが同じ checkout + `pnpm install` を繰り返しており、**run あたり約 2.5 分が
重複セットアップ**に消えている。

### 変更の種類の分布（直近マージ 25 PR の実測）

| 判定                                                                            | 件数         |
| ------------------------------------------------------------------------------- | ------------ |
| ドキュメントのみ（`docs/` `logs/` `notes/` とルート直下 `*.md`）                | 3 件（12%）  |
| コードを含む                                                                    | 22 件（88%） |
| 依存定義（`package.json` / `pnpm-lock.yaml` / `pnpm-workspace.yaml`）の変更あり | 6 件（24%）  |

## 目的

CI の**検証内容を落とさずに**、課金対象の実行分数を減らす。

## 要件

1. main は常にフル検証された状態を保つ（main への push では全ゲートを実行する）。
2. コードを含む PR の検証項目を減らさない（lint / type-check / build / test / E2E / audit）。
3. Markdown の整形検証はドキュメントのみの変更でも維持する（`format:check` は md も対象）。
4. 依存を変えていない変更に対する新規アドバイザリの検知手段を失わない。

## 対象範囲

`.github/workflows/ci.yml` のみ。

## 対象外

- `weekly-maintenance.yml`（週次のドリフト検査。本設計の安全網として現状維持）。
- Turbo のリモートキャッシュ導入、Playwright ブラウザのキャッシュ。
  効果はあるが、前者は外部サービス連携、後者は削減が分単位に届かない（95 秒 → 65 秒でも 2 分）。
- 課金枠の引き上げ、リポジトリの public 化、self-hosted runner。いずれも運用判断のため対象外。
- Dependency Audit が現在 main で失敗している件（推移的依存の high 3 件）。本変更とは独立。

## 変更後構成

ジョブを **7 個 → 2 個**にする。

### quality（Quality Gates）

1 ジョブに集約し、ステップを**安い順**に並べる。失敗すると後続がスキップされるため、
lint の失敗で build / test の分を払わずに済む（fail-fast をコスト最適化として使う）。

```
checkout(fetch-depth: 0) → setup → 変更範囲を判定
  → format:check（常に）
  → lint / type-check / build / test（docs_only でなければ）
  → Node 22 + pnpm 11 へ切替 → audit（deps_changed のときだけ）
  → 実行範囲のサマリ
```

- **依存監査を最後に置く理由**: `packageManager` を pnpm 11 に書き換えるため、
  後続ステップに影響させない。pnpm 11 は Node >= 22.13 を要求するので、この直前でだけ
  Node を 22 に上げる（`.nvmrc` は 20 のまま据え置き）。
- **`fetch-depth: 0` が必要な理由**: base との差分で変更範囲を判定するため。

### e2e（E2E Smoke）

`needs: quality` とし、PR かつ `docs_only != true` のときだけ実行する。

## 変更範囲の判定

PR では `git diff --name-only <base sha> HEAD` の結果で 2 つのフラグを立てる。

**`docs_only`**

- 条件: 変更ファイルが**すべて** `docs/` `logs/` `notes/` のいずれかで始まるか、
  ルート直下の Markdown（スラッシュを含まない `*.md`）である。
- 効果: lint / type-check / build / test と E2E ジョブをスキップする。

**`deps_changed`**

- 条件: `package.json` / `pnpm-lock.yaml` / `pnpm-workspace.yaml` のいずれかを含む。
- 効果: 依存監査のステップ群を実行する。

判定の設計上の選択：

- **`.claude/` 配下は「コード扱い」**。Hook（`.mjs`）やスクリプト（`.sh`）を含み、
  壊れると開発フロー全体に影響するため、安全側に倒して全ゲートを回す。
- **配下の Markdown（例 `apps/web/README.md`）もコード扱い**。ルート直下の `*.md` だけを
  ドキュメント扱いにする。判定を単純に保ち、誤ってスキップしないことを優先した。
- **main への push は常に全ゲート**。`docs_only=false` / `deps_changed=true` を固定で返す。
- **差分が空のときは全ゲート**（安全側フォールバック）。

### 重要な限界：PR 単位でしか効かない

PR の CI は「前回 push からの差分」ではなく **base からの差分**を見る。したがって
コードを含む PR にドキュメントだけを追加 push しても `docs_only` にはならず、
全ゲートが実行される。**恩恵を受けるのは PR 全体がドキュメントのみの場合（実測 12%）**。

「直前の push からの差分」で判定すれば追加 push を軽くできるが、**採用しない**。
`concurrency.cancel-in-progress: true` により、コードを含む push の run が後続 push に
キャンセルされ得るため、「前の run が検証済み」という前提が成り立たない。
コードが一度も検証されないままマージされる穴が開く。

## 期待効果

| ケース                         | 変更前 | 変更後 | 削減 |
| ------------------------------ | ------ | ------ | ---- |
| コードを含む PR の 1 run       | 11 分  | 6 分   | −45% |
| 依存も変える PR の 1 run       | 11 分  | 7 分   | −36% |
| ドキュメントのみの PR の 1 run | 11 分  | 1 分   | −91% |
| main への push                 | 9 分   | 5 分   | −44% |

削減の主因はジョブ統合（全 run に効く）。ドキュメントスキップは PR 全体が
ドキュメントのみのとき（12%）に大きく効く。依存監査のゲートは 76% の PR で 1 分を節約する。

## データフロー / API 設計 / DB 設計 / セキュリティ

いずれも **対象外**（CI 設定のみの変更。アプリケーションのコード・契約・スキーマは不変）。

セキュリティについて 1 点補足すると、依存監査を「依存定義が変わったときだけ」に絞るため、
依存を変えない期間に公開された新規アドバイザリは PR では検知されなくなる。
これは `weekly-maintenance.yml` の週次監査（毎週月曜 06:00 JST・main 全依存・high 以上で失敗）が
引き続き担う。要件 4 はこれで満たす。

## エラー処理

外部 I/O を伴う新規処理は無いため、リトライ・タイムアウト・冪等性・部分失敗・
フォールバックの 5 項目は **対象外**。判定スクリプトは `set -euo pipefail` で失敗時に
ジョブを落とす（判定不能なまま検証をスキップしない）。

## ログと監視

`GITHUB_STEP_SUMMARY` に「ドキュメントのみの変更か」「依存定義の変更か」と、
スキップした場合はその旨を出力する。**何がスキップされたかが run の画面から一目で分かる**
ようにし、スキップが暗黙にならないようにする。

## 性能

CI の実時間（wall-clock）は次のとおり変化する。

- 変更前のクリティカルパス: Type Check(54 秒) → Build(75 秒) → Test(139 秒) ≈ 4.5 分、
  E2E は Build の後に並列で開始。
- 変更後: quality(約 4 分) → E2E(約 1.5 分) ≈ 5.5 分。

**E2E の開始が約 2 分遅くなる**（従来は Build 完了後に開始できたが、Test 完了まで待つ）。
個人開発でありコスト制約を優先するため、この遅延は受容する。

## テスト方針

CI ワークフロー自身の変更であり、アプリケーションのコードは変わらないため Vitest の
追加対象は無い。また Actions が課金停止中で CI を回して確かめられないため、
ローカルで完結する 3 段の検証（静的検証 / 判定ロジックの単体検証 / 実履歴による検証）を行う。

確認項目と結果、およびマージ後に実地で確認する項目は
**docs/tests/ci-minutes-reduction.md** を正とする。

なおこの PR 自体は `.github/` と `docs/` を変更するため `docs_only=false` と判定され、
新しいワークフローで全ゲートが実行される（変更後のワークフローが自分自身を検証する）。

## 移行とリリース

- データ移行なし。マージした時点から新しいワークフローが有効になる。
- `main` に branch protection は設定されていない（`protected: false` を API で確認済み）ため、
  ジョブ名の変更（`Format Check` / `Lint` / … → `Quality Gates`）による
  required status checks への影響は無い。

## リスク

| リスク                                                  | 対応                                                                                                                 |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| ドキュメント判定を誤り、コードが未検証でマージされる    | 判定は「全ファイルがドキュメント」のときだけ true。差分が空・判定不能は全ゲート。`.claude/` と配下の md はコード扱い |
| 依存監査の頻度低下で脆弱性の検知が遅れる                | `weekly-maintenance.yml` の週次監査（main・全依存・high 以上で失敗）が引き続き担う                                   |
| 1 ジョブ化でどのゲートが落ちたか分かりにくい            | ステップ名を明示し、Actions の画面でステップ単位に結果が出る。サマリにも実行範囲を出力                               |
| 失敗の局所性が下がる（lint 失敗で test 結果が見えない） | fail-fast は**コスト最適化として意図的**。原因を直せば次の run で先へ進む                                            |
| E2E の開始が約 2 分遅れる                               | 個人開発のためコスト優先で受容（「性能」節に記載）                                                                   |
