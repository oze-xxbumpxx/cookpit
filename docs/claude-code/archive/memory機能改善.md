# 継続的なAgent改善機構の追加要件

> **ARCHIVED（2026-07-02）**: このファイルは初期構築時の依頼文（歴史的記録）であり、
> 現在の正典ではない。運用の正典は `docs/claude-code/`（usage-guide.md ほか）、
> Agent 実体は `.claude/agents/`、Skill は `.claude/skills/` を参照すること。
> このファイルへの参照は新規に追加しない。

既存のマルチエージェント構成に、Claude CodeのAuto Memory、Subagent Memory、Skills、Hooksを利用した継続的改善機構を追加してください。

目的は、タスクの実行結果、ユーザーからの修正、レビュー指摘、テスト失敗、手戻りを蓄積し、エージェント構成を段階的に改善することです。

ただし、エージェントが自分自身の重要な設定を無制限に変更する完全自動型にはしないでください。

改善候補の収集と評価は自動化し、重要な設定変更はOpusまたは人間による承認を必要とする半自動型としてください。

## 1. 改善サイクル

以下の改善サイクルを構築してください。

1. タスクを実行する
2. Reviewerが成果物を評価する
3. Reflection Agentが振り返りを作成する
4. 再利用可能な知見をMemory候補として抽出する
5. 改善候補をBacklogへ保存する
6. 複数タスクの候補をAgent Improvement Managerが横断分析する
7. Agent、Skill、Rule、CLAUDE.md、Hookの変更案を作成する
8. 過去の代表タスクで回帰評価する
9. 改善前後の結果を比較する
10. 承認された変更だけを正式に反映する
11. 変更理由と評価結果を記録する

## 2. 追加するAgents

### reflection-agent

モデル：

```yaml
model: claude-sonnet-4-6
```

責務：

- タスク完了後の振り返り
- 手戻りの抽出
- ユーザーから受けた修正の抽出
- Reviewerの指摘分析
- テスト失敗の分析
- Agent間の認識不一致の抽出
- 成功した手順の抽出
- 再利用可能な知見の抽出
- Memory候補の作成
- 改善候補の作成

このAgentは、CLAUDE.md、Agent定義、Skills、Rules、Hooksを直接変更してはいけません。

出力先：

```text
docs/claude-code/improvements/candidates/<task-id>.md
```

### agent-improvement-manager

モデル：

```yaml
model: claude-opus-4-8
```

責務：

- 複数タスクの振り返りを横断分析する
- 一時的な問題と恒久的な問題を区別する
- 重複する改善候補を統合する
- 知見の保存先を決定する
- Agentプロンプト変更案を作成する
- Skill変更案を作成する
- Rules変更案を作成する
- CLAUDE.md変更案を作成する
- Hook変更案を作成する
- 変更による副作用を分析する
- 回帰評価の対象を決定する
- 改善提案書を作成する

このAgentは、デフォルトでは重要な設定を直接変更せず、差分または提案書を作成してください。

出力先：

```text
docs/claude-code/improvements/proposals/<proposal-id>.md
```

### agent-evaluator

モデル：

```yaml
model: claude-sonnet-4-6
```

責務：

- 改善前後のAgent構成を比較する
- 過去の代表タスクを使って回帰評価する
- 要件の見落としを評価する
- 設計漏れを評価する
- 不要な質問回数を評価する
- 実装計画と実装の不一致を評価する
- テスト漏れを評価する
- レビュー指摘数を評価する
- ドキュメント不足を評価する
- トークン消費とAgent呼び出し回数を評価する
- 改善による悪化がないか確認する

出力先：

```text
docs/claude-code/improvements/evaluations/<proposal-id>.md
```

## 3. Memoryの分類

知見の性質に応じて、保存先を分類してください。

### Auto Memory

以下を保存します。

- ビルドコマンド
- デバッグ時に判明した注意点
- ユーザーから受けた修正
- プロジェクト固有のパターン
- 一時的または検証中の知見

### Subagent固有Memory

以下を保存します。

- Agent固有の成功パターン
- Agent固有の失敗パターン
- 担当領域固有の注意点
- 頻出するレビュー指摘
- 担当領域の調査方法

### CLAUDE.md

以下のみを保存します。

- 全セッションで必ず必要な原則
- 全Agentが知る必要があるルール
- 長期間有効なプロジェクト方針
- 複数回再現した重要な注意事項

### .claude/rules

以下を保存します。

- 特定ディレクトリにだけ適用するルール
- フロントエンド固有ルール
- バックエンド固有ルール
- DB固有ルール
- テスト固有ルール

### Skills

以下を保存します。

- 複数ステップの作業手順
- 再利用可能なチェックリスト
- 成功した設計手順
- 成功した実装手順
- 成功したレビュー手順
- 成果物テンプレート

### Hooks

以下に使用します。

- 必ず実行する必要がある検証
- 保護対象ファイルへの変更制御
- 必須成果物の存在確認
- テスト実行確認
- Agent設定変更時の構文検証
- 改善プロセスを開始するトリガー

## 4. 知見の昇格条件

Auto Memoryで得た知見を、無条件にCLAUDE.mdやSkillsへ反映してはいけません。

以下のいずれかを満たした場合に改善候補へ昇格してください。

- 同じ問題が3回以上発生した
- ユーザーから同じ修正を2回以上受けた
- Reviewerから同種の重大指摘を複数回受けた
- 本番障害または重大な試験不具合につながった
- 複数Agentで同じ認識不足が発生した
- 作業時間またはトークンを継続的に浪費している
- 明確な成功パターンが複数タスクで再現した

昇格時は以下を記録してください。

- 観測した事象
- 発生回数
- 対象タスク
- 原因仮説
- 改善案
- 変更対象
- 想定される副作用
- 評価方法

## 5. 改善記録

次のディレクトリを作成してください。

```text
docs/claude-code/improvements/
├── README.md
├── improvement-backlog.md
├── candidates/
├── proposals/
├── evaluations/
├── accepted/
├── rejected/
└── incidents/
```

各改善案には一意なIDを付与してください。

例：

```text
IMP-2026-001
```

改善案には最低限、以下を含めてください。

- タイトル
- ステータス
- 対象AgentまたはSkill
- 背景
- 観測事象
- 原因
- 変更案
- 変更差分
- リスク
- 評価方法
- 評価結果
- 採用または却下理由
- ロールバック方法

## 6. 自動反映の制限

以下は自動実行可能です。

- Auto Memory候補の整理
- 振り返り作成
- 改善候補作成
- 評価レポート作成
- 重複候補の統合
- フォーマット修正
- リンク切れ修正

以下はAgent Improvement Managerのレビュー後に反映可能です。

- Skillのチェック項目追加
- テンプレートの改善
- Agent descriptionの軽微な改善
- 非破壊的なRules追加

以下は人間の承認なしに変更してはいけません。

- CLAUDE.md
- Agentの責務
- Agentのモデル
- Agentのツール権限
- Hookのブロック条件
- 自動実行するシェルコマンド
- セキュリティルール
- 成果物の省略条件
- 本番環境へ影響する設定

## 7. Hooks

以下のHook構成を検討してください。

### SubagentStop

各Subagentの完了時に以下を記録します。

- Agent名
- 担当タスク
- 成果
- 失敗
- 未解決事項
- 他Agentへ渡す情報
- Memory候補
- 改善候補

### Stop

メインタスク終了時に以下を確認します。

- 必須成果物が存在する
- テストが実行されている
- Reviewerが実行されている
- Reflection Agentが振り返りを作成している
- 未解決事項が記録されている
- 改善候補が必要な場合に作成されている

### PostToolUse

以下が変更された場合に構文と整合性を検証します。

```text
CLAUDE.md
.claude/agents/**
.claude/skills/**
.claude/rules/**
.claude/settings.json
```

確認内容：

- YAML frontmatterが有効
- モデル指定が正しい
- Agent名が重複していない
- 存在しないAgentを参照していない
- ツール権限が過剰でない
- Skillの参照先が存在する
- HookのJSONが有効
- 保護対象ファイルが未承認で変更されていない

重要な制御はCommand Hookで実装し、LLMによる判断が必要な部分だけPrompt HookまたはAgent Hookを使用してください。

## 8. 評価用タスク

エージェント改善の回帰評価用として、代表的なタスクセットを作成してください。

```text
.claude/evals/
├── cases/
│   ├── small-bug-fix.md
│   ├── api-field-addition.md
│   ├── database-schema-change.md
│   ├── frontend-screen-addition.md
│   ├── aws-integration-change.md
│   └── refactoring.md
├── rubrics/
└── results/
```

各タスクでは以下を採点してください。

- 要件理解
- 影響範囲調査
- 設計品質
- 実装計画品質
- 実装整合性
- テスト網羅性
- レビュー品質
- ドキュメント品質
- 不要な作業量
- トークン効率

Agent設定を変更する前後で同じ評価ケースを実行し、品質が悪化した場合は変更を採用しないでください。

## 9. 改善の実行タイミング

以下のいずれかでAgent Improvement Managerを実行してください。

- 5タスク完了ごと
- 同種の問題が3件蓄積した場合
- 重大インシデント発生時
- ユーザーが改善を要求した場合
- Agent設定を変更する前
- Agent設定変更後の回帰評価時

毎タスクAgent定義を書き換えることは禁止してください。

短期的な事象に過剰適応せず、複数タスクで再現した傾向だけを正式設定へ反映してください。

## 10. 最終報告

構築後、以下を報告してください。

- Memoryの保存方針
- 各AgentのMemoryスコープ
- 改善候補の作成条件
- 改善案の承認フロー
- 自動変更可能な範囲
- 人間の承認が必要な範囲
- 回帰評価方法
- ロールバック方法
- Memory肥大化への対策
- 誤った知見が保存された場合の削除方法
- 改善ループによる想定トークン消費

特に重要な設計判断

この構成で最も重要なのは、次の3点です。

1. Memoryは「学習済みモデル」ではない

Memoryはモデル自体を再学習する機能ではなく、次回セッションに読み込まれる永続的なコンテキストです。そのため、誤った内容を保存すれば、次回以降も誤りを参照する可能性があります。

2. 毎回Agent定義を変更しない

1回の失敗だけでAgentプロンプトを修正すると、特定の事例へ過剰適応します。

単発の事象 → Memory
繰り返す事象 → 改善候補
検証済みの事象 → Agent・Skill・Rule

という段階を設けるべきです。

3. 改善前後を評価する

単に指示を増やすだけでは、Agentは改善しません。

指示が増えすぎると、

判断が遅くなる
指示同士が競合する
毎回不要な作業をする
トークン消費が増える
重要な指示が埋もれる

という問題が起きます。

したがって、改善とは指示を追加することではなく、不要な指示を削り、適切な場所へ移動することも含むと定義するのがよいです。
