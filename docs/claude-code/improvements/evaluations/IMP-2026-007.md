## 効率改善の確認（「改善を期待」軸）

提案の目的は「L3 設計フェーズの非効率解消（Agent 呼び出し効率 / トークン効率の改善）」。

| 軸 | 改善A（before→after） | 改善B（before→after） | A+B |
|---|---|---|---|
| Agent 呼び出し効率（database-schema-change: before=3） | 3→3（0差分） | 3→3（0差分） | 3→3（0差分） |
| Agent 呼び出し効率（aws-integration-change: before=3） | 3→3（0差分） | 3→3（0差分） | 3→3（0差分） |
| トークン効率（database-schema-change: before=4） | 4→4（0差分） | 4→4（0差分・純増リスク留意） | 4→4 |
| トークン効率（aws-integration-change: before=4） | 4→4（0差分） | 4→4（0差分・純増リスク留意） | 4→4 |

**効率改善は eval ケース上では確認できなかった（全パターン 0 差分）。**

理由の分析:
1. **改善Aのガード発動**: database-schema-change（集約未確定→並列化なし）と
   aws-integration-change（グレーゾーンで並列化が発動するかは不確定）という選定ケースで、
   改善Aの主効果（並列化によるフロー短縮）が顕在化しにくい。改善Aが最もよく機能する
   ケース（「契約骨子が既存スキーマから確定できる L3」例: フィールド追加系の L3）は
   今回の評価対象外。
2. **rubric の軸定義**: rubric の Agent 呼び出し効率は「レベルに対し必要最小の Agent だけ起動」
   を測る。並列化はフロー「時間」を短縮するが Agent 「起動数」は変わらない。rubric 定義上、
   並列化は Agent 呼び出し効率軸には反映されない（Agent 数不変）。改善AがスコアUPにつながる
   rubric 軸が定義されていない可能性がある。
3. **トークン効率の定量未確認**: 改善Bの重複削減効果は実測なしには確認できない。

## 総合判定

### 改善A（設計系 Subagent の並列化）

**採用推奨（条件付き）**

- **悪化軸なし**: 全 3 ケース × 15 軸でスコア低下ゼロ。劣化指標増加なし。
- **効率改善の未確認**: 評価対象ケースでは Agent 呼び出し効率・トークン効率の向上が
  rubric スコアに現れなかった。これは:
  - 選定ケースで「ガード発動（並列化なし）」が多かったため（database-schema-change 確定、
    aws-integration-change 不確定）。
  - rubric の Agent 呼び出し効率が「起動数」ベースのため、並列化（同数起動の時間短縮）が
    スコアに反映されない構造的限界がある。
- **条件付き採用推奨の根拠**: 悪化なし・ガード機能の正常動作確認・既存の §並列実行の指針
  の拡張（指示純増でなく既存節の拡張）。ただし以下の実タスク確認を推奨:
  - 並列化が「実際に発動する L3 ケース」での所要時間計測（フロー時間の短縮確認）。
  - aws-integration-change 類似タスクでの「追送機構」の動作確認（設計確定差分の追送漏れがないか）。
- **懸念事項**: contract-designer 並列化時の「追送漏れリスク」が定性懸念として残る。
  実タスクで 1 件も追送漏れが確認されなければ懸念は解消される。

### 改善B（orchestrator 先行調査の共有）

**採用推奨（条件付き）**

- **悪化軸なし**: 全 3 ケース × 15 軸でスコア低下ゼロ。劣化指標増加なし。
- **L2 誤発火なし確認**: refactoring（L2）で「L3 のみ・任意」「L1/L2 では行わない」の
  二重条件が機能し、不要な作業量・トークン効率の悪化なし。rubric 非推奨パターン
  （指示追加のみでトークン・質問増）に当たらないことを確認。
- **効率改善の未確認**: トークン効率の改善（Subagent 重複削減 > orchestrator 先読み増）が
  定量確認できない。純増リスクが消えていない。
- **条件付き採用推奨の根拠**: 悪化なし・L3 限定の正常機能確認・所在情報のみという制約の
  明示（設計品質への影響なし）。ただし以下の実タスク確認を推奨:
  - L3 タスクでの「orchestrator の先読み + Subagent の重複削減」が合計 tool use 数を
    減少させるかの計測（純増でないことの確認）。
  - 要約が各 Subagent の委譲指示に適切に埋め込まれているか（過長・不完全でないか）の確認。

### 改善A + 改善B 同時適用

**採用推奨（条件付き）**

- **悪化軸なし**: 全 3 ケース × 15 軸でスコア低下ゼロ。劣化指標増加なし。
- 改善Aと改善Bは独立して設計されており、同時適用での追加リスクは定性評価の範囲では
  確認されない。
- **条件**: 改善A・改善B それぞれの実タスク確認（追送漏れなし・トークン純増なし）が揃ってから
  採用することを推奨。両方の懸念が実タスクで解消されれば A+B 採用が可能。
  一方のみ実タスク確認が取れた場合は確認済みの片方を先行採用することも選択肢。

## 重要な補足: eval ケース選定と効率改善の測定限界

今回の評価ケース（database-schema-change・aws-integration-change）は「品質軸の悪化がないか」
の確認に適している一方、「改善Aが最も効果を発揮する L3（契約骨子が既存スキーマから確定
できるケース）」は今回の評価対象外だった。

提案書が評価ケースとして選定した根拠（「改善Aの contract 並列化と改善Bの schema 先読みの
効果/悪化が最も現れる」）と評価結果（ガード発動によりケースで改善Aが発動しなかった）の
間に乖離がある。これは評価の失敗ではなく「ガードが正しく動いた」という正の確認ではあるが、
「並列化が実際に起きたときの効果・リスク」の評価は未完了のまま残る。

rubric の Agent 呼び出し効率軸が「Agent 起動数」ベースのため、並列化による「フロー時間短縮」
というオリジナルの改善目的が rubric スコアに直接反映されない構造的限界もある。

**採用・却下の最終決定は提案者 manager および人間承認者に委ねる（承認区分：人間承認必須）。**
定性評価では悪化なしを確認した。効率改善の定量確認（実タスク計測）を採用前の条件として
推奨する。
