## ケース別 before / after 採点根拠

### ケース 1: external-service-failure（L2/L3）

**before の問題点**
Skill の本文に冪等性・障害系の具体チェック項目がなかった。「冪等性」は標題に登場するが、「同一操作の多重実行・タイムアウト・リトライ・部分失敗・フォールバック」を試験計画に含めるよう明示する手順が欠けていた。結果として test-designer がこのケースで試験計画を書く際、障害設計固有の観点（タイムアウト値・リトライ/バックオフ・部分失敗時の整合性・冪等性キー）を抜かす蓋然性が高く、INDEX.md ベースラインでテスト網羅性 2 が記録された。

**after の変化**
手順 4(4)(5) が追加された。(5) 障害系の適用条件は「Infrastructure 経由の外部 I/O（DB 以外の外部 API/ストレージ）を含む場合」であり、このケースは条件に正確に合致する。選択基準表でも Infrastructure 行の(4)(5)が「必須」と明示されている。test-designer はこれを参照して冪等性・タイムアウト・リトライ・部分失敗・フォールバックを試験計画に含める構造的な後押しを得る。テスト網羅性は 2 → 4 と評価する（観点の構造的な追加があり、異常系・冪等性・障害系をほぼ網羅できる根拠が Skill に揃った。残る限界は実行検証の不可のみ）。

他軸への影響：手順の選択基準が明確化され、Skill が長くなるが焦点を絞った記述であるため不要作業量・トークン効率の悪化はない。他軸は実質 Skill 変更の直接対象外であり中立。

### ケース 2: refactoring（L2）

**before の問題点**
リファクタリングは「振る舞い不変の構造変更」であり、試験計画の核心は回帰観点（入出力が変わっていないこと）の確認。before の Skill では回帰試験範囲の定義は手順 4（現 after では手順 5）に含まれていたが、「L2/L3 リファクタでは回帰観点を最優先にし、冪等性・障害系・FE 固有は任意」という選択指針がなかった。test-designer が試験計画の重点を回帰確認に集中させる構造的なガイドが不足しており、テスト網羅性スコアは 2（ベースライン）。

**after の変化**
選択基準表の「L2/L3 リファクタ（振る舞い不変）」行が「回帰観点（入出力不変）を最優先」と明記し、(4)(5)(6)は「任意」とした。回帰観点に集中する根拠が Skill に明示され、試験計画で入出力不変の確認ケースを優先配置する構造的な後押しを得る。テスト網羅性は 2 → 3 と評価する（回帰観点が最優先と明示されたことで観点の抜けが減るが、「振る舞い不変の全ケースを網羅」するには実際のコード量・公開 API の列挙が必要であり、Skill 変更だけで完全解消はできないため 5 ではなく 3 が妥当）。

不要作業量・トークン効率：選択基準で「任意」と示されているため、リファクタに不要な障害系・FE 固有の観点が膨らむリスクが抑制されている。中立を維持。

### ケース 3: small-bug-fix（L1）

**before の状態**
L1 ケースでは Skill に余分な観点が少なかった分、テスト網羅性は 2（Domain 純粋ロジックのバリデーション修正という性質上、試験計画の観点が薄くなりやすい）。不要作業量・トークン効率は共に 5（ベースライン）。

**after の変化**
選択基準表に「L1（単一ファイル軽微修正）は(4)(5)(6)が原則対象外。直す対象の観点のみ。膨らませない」と明記された。Domain 純粋ロジック行でも(5)(6)は「対象外」と示されている。test-designer が L1 ケースを受けた際、Skill の選択基準を参照することで追加観点を適用しない判断を明示的に正当化できる。

テスト網羅性：L1 の Domain バリデーション修正では「正常系・異常系・境界値」が核心観点であり、これらは before も after も同様に手順 3 で求められる。after で新たに追加された(4)(5)(6)は「原則対象外」とされ適用されないため、テスト網羅性は 2 → 2（中立）。改善を期待しない軸であり期待どおりの結果。

不要作業量・トークン効率：after では Skill の記述が増えた（選択基準表・追加観点の説明）が、test-designer への指示は「L1 は膨らませない・原則対象外」と簡潔に限定されており、L1 ケースで試験計画が肥大化する構造的な誘因がない。test-designer の呼び出し回数・生成する試験計画の量は変化しない（むしろ「飛ばす」判断の根拠が与えられ過剰適用が防がれる）。不要作業量 5 → 5、トークン効率 5 → 5（中立）と評価する。

## 総合判定

- **判定**: 採用推奨
- **理由**:
  1. **全ケース・全軸で悪化ゼロ。** 3 ケース × 全軸を採点した結果、スコアが低下した軸は 1 軸もない。劣化指標もすべて「横ばい or 改善」。
  2. **テスト網羅性が改善対象ケースで向上した。** external-service-failure で +2（2→4）、refactoring で +1（2→3）。いずれも Skill に具体的チェック項目と選択基準が追加されたことによる構造的な改善であり、偶発的ではない。
  3. **L1 過剰適用が防がれている。** small-bug-fix（L1）で不要作業量 5→5・トークン効率 4→4・テスト網羅性 2→2 のすべてが中立。「観点の選択基準」表の「L1 は原則対象外」記述が過剰適用を抑止する構造になっており、指示追加が工数増につながっていない。
  4. **「追加と限定の同時実施」設計が機能している。** 観点を追加しつつ選択基準で適用範囲を絞るという設計意図が、評価結果（改善は L2/L3 の適切なケースに限定、L1 は中立）として現れている。scoring-rubric.md の判定ルール「全軸が before 以上かつ劣化指標がすべて減少 or 横ばい」を満たす。
- **前提・限界の再確認**: 本評価はすべて定性評価（実 Agent 実行なし）。実際のモデルが「選択基準を正しく解釈して適用するか」は実行時のモデル応答に依存し、本評価では検証できない。採用後の実タスクで過剰適用が観測された場合はロールバックを検討すること。
