## 発見（スコアの根拠）

### (a) implementer.md: 正味のトークン増加

before は `.claude/agents/implementer.md` 内に規約サマリ（約15行、依存方向・create/reconstruct・
`any`/default export 禁止と例外・コメント方針）を**常時システムプロンプトに焼き込み済み**で、
追加の Read 呼び出しなしに規約遵守が担保されていた。

after は同サマリを削除し「実装着手前に `coding-standards.md`（47行）と `domain-layer.md`
（35行）を Read してから着手する（`apps/web/` を触る場合は `presentation-layer.md` 28行も）」
という**無条件**の指示に置き換える。実測行数（`cat -n` 実測）:

| ファイル                              | 行数  |
| ------------------------------------- | ----- |
| `.claude/rules/coding-standards.md`   | 47 行 |
| `.claude/rules/domain-layer.md`       | 35 行 |
| `.claude/rules/presentation-layer.md` | 28 行 |

domain 層を触らない frontend-screen-addition や、apps/web を触らない小規模ドメイン修正でも
`domain-layer.md` / `presentation-layer.md` の Read は無条件に発火する文言になっており、
実装対象に無関係なファイルまで読む場面がある。結果として：

- 非 apps/web タスク: Read 2 回・82 行相当 vs 定義側の削減 約13行 → 正味 **+69 行相当・
  Read 呼び出し +2**
- apps/web タスク: Read 3 回・110 行相当 vs 定義側の削減 約13行 → 正味 **+97 行相当・
  Read 呼び出し +3**

これは提案書「リスク」節の「rules は28〜47行と小さく軽微」という評価が、複数ファイル同時
Read や呼び出し回数増を勘定に入れていないための過小評価だと判断する。

### (b) small-bug-fix（L1）への影響が最も大きい

rubric は L1 で「不要な作業量・トークン効率・過剰な質問の抑制を重視」と明記している。
small-bug-fix は before で `packages/domain` 内の Entity/VO バリデーション修正に必要な規約
（create/reconstruct・ドメインロジックの閉じ込め）が既に inline サマリと CLAUDE.md の双方で
無料（追加コストゼロ）で満たされていた。after は同じ情報を得るために **無条件で** 2 回の
Read 呼び出しを強制し、L1 の軽微修正であることに対するスコープ調整（除外条件）が指示文に
無い。これは rubric が明示的に非推奨とする「指示追加だけでトークン消費が増える」パターンに
該当する。

### (c) database-schema-change では実装整合性・設計品質が改善する

before の implementer.md / architecture-designer.md の inline サマリは、いずれも
「DB スキーマ形 ⇔ ドメインモデル形の変換責任は **Repository 実装**が持つ。Domain 層は DB の
形を知らない」という `domain-layer.md` 固有の規定（19-23行目）を**要約から落としている**
（CLAUDE.md §アーキテクチャ原則にも同記述は無い）。このケースの失敗パターンとして eval
ケース自体が「Domain 層に Drizzle 型を持ち込む」を明記しており、before はこの規定を拾えない
経路がある。after は正典 `domain-layer.md` を無条件で Read するため、この抜け漏れが埋まる
方向に働く。トークン効率は (a)(b) と同様に低下するが、設計品質・実装整合性はこのケースに限り
改善方向。

### (d) reviewer.md は無関係（コントロール）

`.claude/agents/reviewer.md` は本提案の対象外で、before/after いずれも `.claude/rules/` を
直接 Read する運用のまま変わらない。レビュー品質軸は3ケースとも変化しない。

## 総合判定

- **判定**: **採用非推奨**
- **理由**:
  1. rubric の判定規律「1 軸でも悪化（スコア低下・劣化指標の増加）があれば不採用推奨」に
     該当する。3 eval ケース全てで「トークン効率」が -1、うち frontend-screen-addition と
     small-bug-fix では「不要な作業量」も -1。劣化指標「Agent 呼び出し回数・トークン消費」も
     3 ケース全てで増加。
  2. rubric は「指示を追加しただけで質問回数・トークン消費だけが増えた提案は非推奨」と
     明記している。本提案は agent 定義の文字数は減らすが、実行時の Read 呼び出しが
     `.claude/rules/coding-standards.md`（47行）・`domain-layer.md`（35行）・
     `presentation-layer.md`（28行）に対して無条件（タスクの実際の変更範囲を問わず）で
     発生するよう置き換わっており、定義削減（約13〜18行）を上回る正味のトークン増加
     （+69〜+97行相当 + Read 呼び出し2〜3回）を生む。特に L1（small-bug-fix）は rubric が
     最重視する「不要な作業量・トークン効率」の軸を直撃しており、L1 向けの除外条件が
     指示文に存在しない点が設計上の欠陥である。
  3. タスク指定の観点(1)（page.tsx default export の誤判定回避）は before の時点で既に
     CLAUDE.md（IMP-2026-020 適用済み）で解決済みのため、本提案による追加の便益ではない。
     観点(2)（domain 規約遵守）は database-schema-change に限り明確な改善（設計品質・
     実装整合性 各+1）があるが、これは全 3 軸中 2 軸のみで、他 2 ケースでの効率低下を
     相殺しない（rubric は軸ごとの悪化を個別に見るため、ケース間の相殺は認めない）。

### 改善提案（参考。可否判断はしない）

- database-schema-change で確認された「Repository 変換責任」の実装整合性改善は価値がある。
  ただし実現方法として、agent 定義から規約全文を削除して**無条件**の複数ファイル Read に
  置き換えるのではなく、(i) 触るディレクトリ（`packages/domain/` か `apps/web/` か）に応じた
  **条件付き** Read 指示にする、または (ii) inline サマリは維持しつつ「Repository 変換責任」
  など漏れていた1〜2行だけを追記する、といった**最小差分での欠落補完**の方が、今回発見した
  トークン効率の悪化を避けられる可能性がある。次回提案時の検討材料として記録する。

### 総合判定（v2）

- **判定**: **採用推奨**（ただし残存リスクを限定条件付きで付記）
- **理由**:
  1. v1 で確認された 2 種類の悪化（3 eval ケース全ての「トークン効率」-1、および
     frontend-screen-addition / small-bug-fix の「不要な作業量」-1、劣化指標「Agent 呼び出し
     回数・トークン消費」の増加）は、v2 が無条件 Read を一切追加しないことにより **全て解消**
     された。3 eval ケース・全軸で before を下回るスコアは確認されなかった（rubric の
     「採用推奨: after の全軸が before 以上、かつ劣化指標がすべて減少 or 横ばい」を満たす）。
  2. database-schema-change の Repository 変換責任に関する v1 の改善（+1×2 軸）は v2 では
     再現しない。これは v2 が implementer.md / architecture-designer.md の domain-layer.md
     関連 bullet を変更していないため（v2 の diff は default export bullet と、
     architecture-designer の既存進め方 3 への一本化のみが対象）。ただしこれは before 水準への
     回帰であって、before を下回る「悪化」ではないため、rubric の判定規律には抵触しない。
  3. 残存リスクとして、default export 例外の完全なファイル一覧（loading.tsx / error.tsx /
     not-found.tsx / template.tsx / default.tsx）が implementer.md から削除され、CLAUDE.md の
     簡略な例示（「page.tsx / layout.tsx 等」）と条件付き参照指示（「例外の有無が判断に関わる
     場合は必ず coding-standards.md を確認する」）に委ねられる点は、page.tsx 以外の特殊
     ファイルを扱うタスクに対する**決定的な担保から非決定的な担保への変化**である。現行の
     3 eval ケースはこのリスクを顕在化させる構成になっておらず（frontend-screen-addition は
     page.tsx 相当の判断のみ）、**今回の評価では劣化として観測されていない**が、この提案の
     採用可否を最終判断する際は「評価できていない」ことを前提として記録する。
  4. 上記 3 の残存リスクは L1/L2 の一般的な frontend タスクでは低頻度（loading.tsx /
     error.tsx を新規作成する画面追加は本 eval セットに含まれない）と見積もるが、恒久的に
     問題ないと保証するものではない。次回の eval ケース拡充（App Router 特殊ファイルを含む
     ケース追加）で継続確認することを推奨する。

### 改善提案（参考。可否判断はしない）

- 残存リスク（観点 2）を埋める最小差分として、CLAUDE.md §アーキテクチャ原則の default
  export 例外の記述を「page.tsx / layout.tsx **等**」のままにせず、v1 diff で implementer.md
  から削除された完全な App Router 特殊ファイル一覧を CLAUDE.md 側（唯一の要約）に転記する

  CLAUDE.md の肥大化とのトレードオフがあるため、次回提案時の検討材料として記録するに留める。
