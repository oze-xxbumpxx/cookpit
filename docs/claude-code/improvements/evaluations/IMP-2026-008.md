## 評価の前提：追加差分の性質

提案差分で orchestrator.md に追加されるのは以下の 2 ステップのみ。

- **手順 3-2**: Sub-agent を background 委譲する前に、`inflight-agents.json` への追記を
  Write 可能な Sub-agent へ指示する。単一 Sub-agent への委譲は同期待機を既定とする。
- **手順 4-2**: resume 直後に `inflight-agents.json` の各エントリの成果物存在を確認し、
  完了 or 再委譲を判定する。「完了待ちループに入らない」ことを明記する。

orchestration-policy.md には「stop/resume を跨ぐ委譲の扱い（通知非依存）」節が追加され、
3-2 / 4-2 の条件詳細をここへ集約することで orchestrator.md 側は参照に留める設計になっている。

通常フロー（stop なし）では手順 3-2 は「background 委譲の前に Sub-agent へ 1 ファイルへの
追記を依頼する指示」が増えるだけであり、4-2 は「resume 直後」という条件付きで発動するため
stop しないセッションでは事実上スキップされる。

### トークン効率の悪化分析（database-schema-change）

通常フローにおいて手順 3-2 が実際に行う動作は：

「background で委譲する全 Sub-agent を起動する都度、Write 可能な Sub-agent に対して
`inflight-agents.json` への追記を付加指示する」

L3 フルフローでは background 委譲のタイミングが複数存在し得る。例として：

- requirements-analyst への委譲時 → inflight-agents.json 追記指示
- architecture-designer への委譲時 → 同上
- planner / test-designer 並列委譲時 → 同上（2 件）
- implementer 委譲時 → 同上
- reviewer 委譲時 → 同上（Write 可能かは定義次第）

提案書の「B（同期待機を既定、background は明示的並列化に限定）」により、単一 Sub-agent への
委譲は同期待機（background なし）となる場合、inflight-agents.json への追記が減る可能性がある。
ただし提案差分には「単一 Sub-agent の委譲は原則同期待機とし、background は明示的に並列化する
複数 Sub-agent に限定する」とのみ書かれており、「通常フローで background を使う頻度がどの程度
減るか」が不明確である。

現状（before）でも orchestrator.md には background 使用に関する明示的制約がなく、orchestrator が
各 Sub-agent を background で委譲するかどうかは実行時の判断に委ねられていた。
after では「単一委譲 = 同期待機」が明示されることで background 使用が絞られ、その分
inflight-agents.json の追記コストが減る方向ではある。

しかし問題は、停止しない通常フローでの inflight-agents.json 追記は「完全に無駄な副作用」
となる点である。追記のコストは小さいが、orchestrator が Write を持たないため Sub-agent へ
追記を指示する分のコンテキスト増・Sub-agent の追記作業が毎回 background 委譲のたびに
発生する。IMP-2026-007 評価で示した「指示追加のみでトークン・質問が増えた」という
rubric 非推奨パターンに一致するリスクがある。

定性評価では「小さな純増リスク」として -1 を付与する。定量確認（実 L3 タスクでの
tool use 数計測）なしに純増でないことを証明できない点で before より条件が悪化している。

なお IMP-2026-007 評価（改善B）でもトークン純増リスクが懸念として残ったが、同評価では
「L3 限定の条件付き」かつ「Subagent 重複削減との収支」という緩和要因があった。
本提案の場合は stop なし通常フローにおける純追加コストであり、緩和要因が薄い。

### L2 での影響分析（frontend-screen-addition）

提案差分の手順 3-2 は「Sub-agent を background で委譲する前に」という条件を持つ。

手順 B（「単一 Sub-agent の委譲は原則同期待機」）が機能する場合、L2 の逐次委譲フローでは
background を使わないため inflight-agents.json の追記が発生しない。これにより L2 では
追加コストが発生しない可能性が高い。

ただし orchestrator が L2 でも architecture-designer を background で起動するケース（planner と
並列化しない場合を含む）では追記が発生し得る。差分に L2/L3 の適用条件の明示がないため、
「L2 では発動しない」という保証が得られない。

定性評価として、通常フロー（stop なし）かつ L2 の単一逐次フローでは追記コストが
限定的になると想定し 0 差分とした。しかし L2 への適用範囲を明示的に除外する記述がなく、
これは設計上の明確性欠如として記録する（劣化指標「設計漏れ」の懸念参照）。

### 設計漏れの内容

以下の点が提案差分に明示されておらず、設計上の抜けとして記録する。

1. **L2 への適用範囲の非明示**: 手順 3-2 が L2 フローでも発動するかどうか差分から不明。
   L2 では background 委譲が多用されないが、適用除外の明記がなければ
   orchestrator が L2 でも inflight-agents.json 追記を行うリスクがある。

2. **inflight-agents.json のクリアタイミング**: 提案書本文には「feature 完了時にクリアしないと
   古いエントリで誤判定するリスク」が記載されているが、クリアを誰が・いつ・どの指示で行うかが
   差分に含まれていない。この設計漏れは古いエントリによる誤判定という実運用リスクを生む。

3. **Write を持つ Sub-agent が inflight-agents.json を追記する設計の非明示**: 提案では orchestrator が
   Write を持たないため、Write 可能な Sub-agent へ「追記指示を付加する」形をとる。しかし
   各 Sub-agent が inflight-agents.json を（自身の本来の成果物作業に加えて）追記する責務を
   持つことは Sub-agent 定義に記載がなく、委譲指示に「追記指示を付加する」ルールだけで
   担保しようとする設計は実運用での漏れリスクがある。

### トークン消費の純増リスクの詳細

stop しない通常フロー（L3 フルフロー）において：

- 手順 3-2: background で委譲する都度、Sub-agent へ inflight-agents.json 追記指示を付加する。
  この指示文・追記作業が通常フローでは完全に無駄な副作用コストとなる。
- 手順 4-2: 「resume 直後」という条件だが、orchestrator のプロンプト処理時には常に
  「resume 直後かどうか」を判断するコンテキストが発生する。

提案書自体が「副作用: 状態ファイルの読み書きが増え、orchestrator の起動直後処理でトークンが
微増する」と認めている。rubric の判定ルール「指示追加のみでトークン・質問が増えた提案は
非推奨とする」に照らすと、stop なし通常フローでのトークン純増（緩和要因なし）は問題となる。

## 総合判定

**採用非推奨（条件付き再提案を推奨）**

### 判定根拠

rubric の判定ルール「1 軸でも悪化（スコア低下・劣化指標の増加）があれば採用非推奨」に
従い、以下の悪化を確認した。

1. **トークン効率の悪化（L3 ケース 2 件で -1）**: database-schema-change および
   external-service-failure において、L3 通常フロー（stop なし）での inflight-agents.json
   追記コスト（Sub-agent への付加指示 + 追記作業）が純増となる。提案書自身が「トークン微増」
   を副作用として認めており、定量緩和要因がない状態では before より悪化と判定する。

2. **劣化指標「設計漏れ」の増加**: L2 適用範囲の非明示・inflight-agents.json のクリア
   タイミング未定義・Sub-agent 追記責務の非明示という 3 点の設計漏れが before では
   存在しなかった問題として追加されている。

### 本提案の価値の認識

stop/resume 後の手動オーケストレーション化という重大インシデント（事象 1）への対応として
本提案の問題設定は正しく、解決の方向性（通知非依存の冪等判定）も妥当である。
採用非推奨は「問題設定・解決方針が誤っている」という判断ではなく、
「現在の差分設計が通常フローでのトークン純増リスクと設計漏れを解消できていない」という判断である。

### 再提案に向けた修正案

以下の修正を施したうえで再評価することを推奨する。

**修正 1: L3 / background 限定の明示（不要な作業量・トークン効率の悪化回避）**

```diff
- 3-2. Sub-agent を background で委譲する前に、起動する Write 可能な Subagent へ
-     「起動する Sub-agent 名 / 目的 / 期待成果物パス」を `.claude/state/inflight-agents.json`
-     へ追記するよう指示する（通知非依存の再開判定用）。単一 Sub-agent の委譲は原則
-     同期待機とし、background は明示的に並列化する複数 Sub-agent に限定する。
+ 3-2. L3 で Sub-agent を background で委譲する場合に限り（L1/L2 および単一 Sub-agent の
+     同期委譲では不要）、起動する Write 可能な Subagent へ
+     「起動する Sub-agent 名 / 目的 / 期待成果物パス」を `.claude/state/inflight-agents.json`
+     へ追記するよう指示する（通知非依存の再開判定用）。feature 完了時に reflection-agent
+     または orchestrator が同ファイルを空にする（古いエントリの誤判定防止）。
```

**修正 2: 適用タイミングを resume 限定に絞る（通常フローへの副作用排除）**

手順 4-2 は「resume 直後」という条件付きであり現状も限定的だが、手順 3-2 の
inflight-agents.json 追記が通常フローで毎回発生する点が問題の核心である。
修正 1 の「L3 + background 委譲時のみ」という限定により追記頻度を大幅に下げられる。

**修正 3: orchestration-policy.md への適用範囲・クリア運用の明記**

orchestration-policy.md の新節に以下を追加する：

- 適用レベル: L3 のみ（L1/L2 では inflight-agents.json を使わない）
- クリアタイミング: reflection-agent 起動時、または feature 完了報告前
- 追記責務: 委譲指示の禁止事項に「inflight-agents.json の追記を成果物確定前に行わない」を明記

v1 指摘：L3 通常フロー（stop なし）において background 委譲のたびに追記指示が付加され、完全に無駄な副作用コストが純増する。

評価：v2 の限定により、background 委譲が発生する場面が「意図的な並列化（planner ∥ test-designer など）」に絞られた。v1 の問題点「条件不明のまま全 background 委譲で追記が発生する」という性格は変化している。

ただし L3 通常フローの標準ステップである planner ∥ test-designer 並列委譲では background が使われ、追記コストが残る。この追記が「完全に無駄な副作用」（v1 の指摘の核心）から「L3 並列化という意図的な場面でのコスト」に性格が変わっており、stop/resume 解消という利得の対価として合理性がある。
