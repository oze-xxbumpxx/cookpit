## ケース別 before/after 採点

### ケース 1: api-field-addition（L2）

**採点根拠（before）**

ベースライン（`INDEX-2026-06-24-post-phase3.md`）の絶対採点値を before として使用する。
契約品質 before=3 の根拠：現在の orchestrator.md は「〔契約変更あれば contract-designer〕」と
曖昧な条件で書いており、L2 の「任意フィールド追加（Zod スキーマへの `servings?: number`
追加）」が contract-designer 起動に値するかの判定が orchestrator の裁量に委ねられる。
一見「軽微な任意追加」として architecture-designer 止まりになりうる構造が残り、
nullability・後方互換・エラー形式・契約テスト方針が設計書の Contract 節に落ちないまま
スコア 3（「契約は妥当だが浅い」）に沈む。

影響範囲調査 before=3 の根拠：Zod 契約 → Domain → Application → Infrastructure →
Presentation の 5 層を「具体パスで特定」することが期待されるが、contract-designer が起動
しない場合、契約→ドメイン→Repository の連鎖確認が architecture-designer 単体では
網羅しにくい。波及の「具体パス洗い出し」が不完全なため 3（「主要な層・ファイルを特定」）
に留まる。

**採点根拠（after）**

after では orchestration-policy.md に「必須起動トリガー」小節が追加される：

> 「1. `packages/api-contract`（Zod）のスキーマにフィールドの追加/変更/削除がある」

api-field-addition のシナリオ（Recipe に任意項目 `servings` を追加、対象は `packages/api-contract`
の Zod 契約）は条件 1 に明確に該当する。また「判断に迷うフィールド変更は『契約変更あり』側
に倒し起動する」という明文化により、「任意項目追加は軽微かも」という誤判断も防がれる。

contract-designer が必ず起動することで、nullability（`null` 許容・デフォルト値）・後方互換・
エラー形式・Hono RPC 入出力型の整合・契約テスト方針が設計書の Contract 節に構造的に落ちる。
→ 契約品質: 3 → 4（+1）

contract-designer 起動により Zod 契約→ドメイン→Repository のパスを明示的にトレースする
工程が確保される。影響範囲調査の「波及（契約・移行・回帰）まで具体パスで特定」が
より確実になる。
→ 影響範囲調査: 3 → 4（+1）

Agent 呼び出し効率について：before では contract-designer が任意起動で「起動しない」ことも

## 過剰起動チェック（契約の形が変わらない変更への不要起動がないか）

refactoring ケース（Application 層内部整理・公開 API/契約不変）において、after の変更差分が
「起動しない」条件を明文化していることを確認した。

refactoring シナリオは「Zod スキーマ・Drizzle スキーマ・Hono RPC 型・DTO の形は変更しない」
と明記されており、必須起動トリガーの条件 1〜5 のいずれにも該当しない。

不要な作業量・Agent 呼び出し効率・トークン効率の各軸で悪化なし（スコア維持）。
「指示を追加しただけで Agent 呼び出しが増えた」という rubric の非推奨パターンに
当たらないと判断する。

## 追加検討: orchestrator.md の注記置き換えによる単一情報源化

before では orchestrator.md 委譲フロー早見に：

> 「contract-designer は **契約（Zod / Drizzle スキーマ / Hono RPC 型 / DTO / 外部連携）の
> 新設・変更があるときだけ**起動する。」

と定性的一文があった。after では：

> 「contract-designer の起動は orchestration-policy.md §contract-designer の必須起動トリガー
> に従う。...L2 でも必ず起動...」

という参照形式に置き換わる。この変更は：

- 定義の二重管理を解消し、orchestration-policy.md が単一情報源になる（指示の純増ではなく
  移動・明確化）。
- orchestrator.md の注記自体は削除ではなく参照に置き換えであり、情報量は減らない（むしろ
  具体化される）。

この置き換えは「指示の純増でトークン・質問が増える」には当たらず、むしろ将来の乖離リスク
（二重定義の不整合）を防ぐ構造改善である。軸別スコアへの悪影響なし。

## 前提と限界の整理

1. **定性評価のみ**: 実コード実行・実 Agent 起動なし。変更差分と eval ケース定義の照合による
   推論評価。実際のモデル応答品質・確率的判断のブレは含まれない。
2. **実タスク未発生**: L2 の Zod フィールド追加に contract-designer が必ず起動するかの実地
   確認は未実施。根拠はベースライン採点（2 回の全軸採点で同一要因が再現）と
   reflection-agent の Memory 留め記録に限られる。
3. **契約品質の改善幅**: api-field-addition の +1（3 → 4）は「起動条件の明文化により
   orchestrator の誤判断を防ぎ、Contract 節が設計書に落ちる確率が上がる」という推論に
   基づく。モデルが before 構成でも正しく contract-designer を起動する可能性を排除できない。
   ただし 2 回のベースラインで同一要因（起動条件の裁量依存）が 3 として記録されており、
   構造的問題の根拠として採用する。
4. **影響範囲調査の改善幅**: api-field-addition の +1（3 → 4）は「contract-designer の起動が
   Zod → Domain → Repository のパス洗い出しを誘導する」という推論。実際の誘導効果は
   contract-designer.md の記述内容にも依存するが、本提案は contract-designer.md を変更しない。
   すでに contract-designer が起動している contract-validation-change で影響範囲調査 4 を
   達成していることから、起動確定が 4 水準に引き上げる根拠として合理的と判断した。
5. **Agent 呼び出し効率の評価**: api-field-addition で contract-designer が「必ず」起動する
   before からの差分（任意 → 必須）は、1 本の追加起動をもたらす。rubric は「レベルに対し
   必要最小の Agent だけ起動」を 5 とするため、「必要な 1 本を確定」は 4 維持が妥当（不要
   起動増加ではなく必要起動の確定）。

## 総合判定

**採用推奨**

**理由**: 評価対象 3 ケース・15 軸のすべてにおいてスコア低下なし。劣化指標に増加なし。
過剰起動チェック（refactoring・契約不変 L2）でも Agent 呼び出し効率・トークン効率・
不要作業量の悪化なし。

改善は L2 で Zod フィールド追加を含む api-field-addition に限定して現れ（契約品質 3 → 4・
影響範囲調査 3 → 4）、契約不変の refactoring では不要起動が発生しない。
「必須トリガー」と「起動しない条件」の両建てが意図どおりに機能しており、
「指示追加のみでトークン・質問が増える」という rubric の非推奨パターンに当たらない。

また orchestrator.md の注記を policy 参照に置き換えることで定義の単一情報源化も達成され、
将来の乖離リスクを構造的に抑制している。

rubric 判定ルール「after の全軸が before 以上、かつ劣化指標がすべて減少 or 横ばい」を満たす。

なお、採用・却下の最終決定は提案者 manager および人間承認者に委ねる（承認区分：人間承認必須）。
