## 背景

`docs/reviews/<feature>.md` への受け入れレビュー記録は L3 の完了条件（正本）であり、複数 Task の
feature では Task 単位で追記すると、definition-of-done.md（64-66 行）・orchestration-policy.md
（92-96 行）・review-codex-implementation Skill（56-61 行）が明記している。この**テキストポリシーの
統一は IMP-2026-020（2026-07-14 適用）で完了済み**。

にもかかわらず、その **2 日後**の pantry-core で同型の記録欠落が再発した。現在の
`docs/reviews/pantry-core.md` には Task 1・Task 4 のみ記録され、**main へマージ済みの
Task 2（Infrastructure・PR #67）・Task 3（Application・PR #68）の受け入れレビュー記録が欠落**して
いる。`.claude/state/quality-gates-log.jsonl` にも該当 2 ブランチの実行記録が無い。テキストで
「書くべき」と規範を明示しても、記録漏れは機械的に防げていない。

## 観測事象（根拠）

| 事象                                                           | 再現タスク                                           | 累計回数                              | 昇格条件                                     |
| -------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------- | -------------------------------------------- |
| docs/reviews への Task 単位記録欠落（main マージ済み Task 分） | shopping-list-core Task 3/4/5 → pantry-core Task 2/3 | 5 相当                                | 同じ問題が 3 回以上を大きく超過              |
| テキストポリシー統一（IMP-2026-020）**適用後 2 日で再発**      | pantry-core                                          | 1（テキスト是正では不十分の実地証拠） | 検証済み対策が効かず次段階（機械制御）へ昇格 |

## 原因

**恒久的・構造的**。段階原則（memory-policy.md「検証済み → Hook（機械的制御）」）に照らすと、
テキストポリシー（規範）は「検証済みだが効かなかった」段階にあり、機械制御へ昇格すべき。
効かなかった理由を 2 点に分解する。

1. **既存の機械チェックが存在確認どまりで Task 網羅を見ていない**。Stop hook
   `check-improvement-cycle.mjs`（172-176 行）は `docs/reviews/<feature>.md` の**ファイル存在**のみを
   warn 条件にしている。pantry-core は Task 1 の記録でファイルが存在するため、Task 2/3 が欠けていても
   **沈黙する**。「ファイルがある = 網羅されている」ではない。
2. **Stop hook はレビュー実施セッションの停止時にしか発火しない**。git 経緯（`.git/logs/HEAD`）上、
   Task 2/3 の PR マージは本セッションのローカル操作を経由せず成立した形跡がある（shopping-list-core
   事象 7 と同型の「PR 作成・マージ主体の暗黙受け渡し」）。Task 完了と Stop イベントが一致しない場合が
   あり、Stop hook 単独では捕捉に構造的な穴がある。

## 変更案

1 根本原因（Task 単位の記録網羅を機械的に担保する仕組みが無い）に対し、**非ブロッキング**から
段階導入する。過剰反応（いきなりブロック）を避け、まず警告＋チェックリストで再発を測ってから、
再発した場合のみ強い担保へ escalate する。指示の追加ではなく、**既存の存在チェックを網羅チェックへ
格上げ**するのが主眼。

### Change 1（機械・非ブロッキング）: Stop hook の reviews チェックを Task 網羅へ格上げ

再利用可能なヘルパー `.claude/scripts/check-review-coverage.mjs` を新設し、Codex ルート feature
（`docs/tasks/codex/<feature>/` が存在）を検出したら、Task ブリーフ `NN-<layer>.md`（README 除く）を
列挙して Task 番号を取り出し、`docs/reviews/<feature>.md` の `## Task N` 見出しと突き合わせる。
ブリーフはあるが受け入れレビュー見出しが無い Task 番号を列挙して**警告**する（常に exit 0）。
未着手 Task の誤警告を避けるため、文言は「未着手 Task は無視可」と添える。`check-improvement-cycle.mjs`
はこのヘルパーを呼び、従来の「ファイル存在のみ」判定を置き換える。

> 精度 vs 単純さ: 「どの Task が main マージ済みか」をローカルファイルのみで厳密に判定するのは
> quality-gates-log.jsonl がエフェメラル環境で欠落しうる（本事象でも欠落）ため脆い。よって厳密判定は
> せず、**ブリーフ有り × レビュー見出し無し**の全 Task を非ブロッキングで列挙し、着手/未着手の判断は
> 人間・Orchestrator に委ねる（誤検知の実害は低い＝非ブロッキング + 「無視可」明記）。

### Change 2（工程）: close-session チェックリストに明示項目を追加

Stop hook の「発火タイミングが Task 完了と一致しない」穴（原因 2）を塞ぐため、**セッション締め**で
必ず走る close-session Skill に「複数 Task Codex feature では、main マージ済み Task 分の
`docs/reviews/<feature>.md` 記録が揃っているか `check-review-coverage.mjs` で確認する」を明示項目として
追加する。セッション締めは Task 完了タイミングに依存せず必ず通るため、Stop hook の穴を補完する。

### Change 3（escalation・今回は提案のみ・適用しない）

Change 1/2 を適用しても次の複数 Task Codex feature で再発した場合に限り、PR 作成前 / pre-commit
ゲート（lefthook）でのブロック格上げを検討する。**今回はブロックを提案しない**（マージがセッション外で
成立するためローカルのブロックゲートでは確実に intercept できず、過剰反応になりやすい）。再発回数を
測ってから判断する。

```diff
# .claude/scripts/check-review-coverage.mjs（新規）— Codex Task ブリーフと reviews 見出しの網羅照合
+#!/usr/bin/env node
+// check-review-coverage.mjs — Codex ルート feature の受け入れレビュー記録の Task 網羅を照合する
+// 使い方: node .claude/scripts/check-review-coverage.mjs <feature>
+// 出力: ブリーフはあるが docs/reviews/<feature>.md に「## Task N」見出しが無い Task 番号の配列（JSON）
+// 非ブロッキング前提（呼び出し側が警告表示に使う）。exit は常に 0。
+import { readdirSync, existsSync, readFileSync } from 'node:fs';
+import { join } from 'node:path';
+const ROOT = process.env.CLAUDE_PROJECT_DIR || process.cwd();
+const feature = process.argv[2];
+function uncovered(feature) {
+  const tasksDir = join(ROOT, `docs/tasks/codex/${feature}`);
+  if (!feature || !existsSync(tasksDir)) return [];              // Codex ルートでなければ対象外
+  const briefTasks = readdirSync(tasksDir)
+    .map((f) => f.match(/^(\d{2})-.+\.md$/))                     // NN-<layer>.md（README 除外）
+    .filter(Boolean)
+    .map((m) => Number(m[1]));
+  const reviewPath = join(ROOT, `docs/reviews/${feature}.md`);
+  const review = existsSync(reviewPath) ? readFileSync(reviewPath, 'utf8') : '';
+  const recorded = new Set(
+    [...review.matchAll(/^##\s*Task\s*(\d+)/gim)].map((m) => Number(m[1])),
+  );
+  return briefTasks.filter((n) => !recorded.has(n)).sort((a, b) => a - b);
+}
+process.stdout.write(JSON.stringify(uncovered(feature)));
```

## リスク

- **副作用（誤検知）**: 実装途中の最後の Task（未着手・作業中）を「記録なし」と警告しうる。→ 非
  ブロッキング + 「未着手 Task は無視可」明記で実害を抑える。厳密なマージ判定はあえて行わない
  （quality-gates-log がエフェメラル環境で欠落するため脆く、複雑化が新たな穴を生む）。
- **副作用（記録形式依存）**: `## Task N` 見出し規約に依存する。review-codex-implementation Skill の
  良い例（shopping-list-core Task 1・2）はこの形式で、pantry-core もこの形式のため実運用と整合。
  形式が揺れると誤検知するが、非ブロッキングのため実害は低い。
- **指示過多の懸念**: 純増は close-session の 1 チェック項目 + 小さなヘルパー 1 本。既存の存在
  チェックを網羅チェックに**置き換える**ため Stop hook の警告数は増えない（むしろ的確化）。判断遅延・
  トークン増は生じにくい。
