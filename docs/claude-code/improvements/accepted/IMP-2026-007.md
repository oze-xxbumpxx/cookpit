## 背景

Sprint 2（product-master）の L3 設計フェーズで、orchestrator の進め方に起因する非効率が
計測された。通常の昇格条件（再発 3 回等）は満たさないが、**ユーザー指定の必須改善項目**として
proposal 化する（候補ファイル冒頭・backlog の「必須昇格」マークに準拠）。

改善は 2 案セットだが、**依存関係と採否を独立に判断できるよう別々の差分**として記述する。
改善 A（並列化）と改善 B（先行調査共有）は互いに独立して適用・評価できる。両方適用も、
片方のみ適用も可能。

## 観測事象（根拠）

| 事象                                                                                    | 再現タスク                              | 累計回数       | 昇格条件                                         |
| --------------------------------------------------------------------------------------- | --------------------------------------- | -------------- | ------------------------------------------------ |
| L3 設計フェーズが約 20 分（duration_ms: 1,169,584）・tool uses 191 回・トークン 176,022 | product-master（Sprint 2 設計フェーズ） | 1 回（初計測） | **ユーザー指定の必須昇格**（通常条件を待たない） |
| 設計系 Subagent が直列実行され後段が前段完了を待つ（並列可能工程の逐次化）              | product-master 設計フェーズ             | 1 回           | 同上                                             |
| 各 Subagent がコードベースを個別に再探索（同一ファイルの重複読取り）                    | product-master 設計フェーズ             | 1 回           | 同上                                             |

> **限界（単発計測である点を明記）**: 本事象は Sprint 2 の 1 タスクでの初計測であり、再現タスクは
> まだ無い。L2 recipe-edit-screen（5 Subagent）では問題化せず、L3（6 Subagent）で顕在化した。
> 恒久ルール化の根拠は「再発回数」ではなく**ユーザー指定の必須項目**である点に依拠する。
> このため回帰評価で悪化が出れば即不採用とし、効果が確認できない場合は backlog に差し戻す
> （単発事象への過剰適応を避ける）。

## 原因

**恒久的・構造的原因。** 現在の orchestrator.md / orchestration-policy.md は次の 2 点で
非効率を生んでいる。

1. **逐次実行の指示**: orchestration-policy.md §委譲フロー（レベル別）と §並列実行の指針は、
   `implementation-planner ∥ test-designer` の並列だけを明記し、**`architecture-designer` と
   `contract-designer`、および `performance-designer` の並列余地を活かす記述が無い**。
   結果として orchestrator が設計系 Subagent を直列に呼び出し、後段が前段完了を待つ。
2. **重複探索の構造**: 各 Subagent に「コードベースを自分で調査せよ」と委ねる設計のため、
   `schema.ts` / 既存 repository / api-contract といった**主要ファイルを複数 Subagent が
   それぞれ読む**。orchestrator が調査結果を先取りして渡す仕組みが無い。

> 一時的問題（環境・単発ツール障害）ではなく、委譲フロー定義そのものに起因する構造的問題。
> ただし「再現タスク 1 件」である点は上記のとおり評価で厳格に確認する。

## 変更案

最小変更で最大効果を狙う。**指示の純増を避け、既存の並列指針を拡張する**形にとどめる。
改善 A・改善 B は独立。1 提案だが**同一根本原因（L3 設計フェーズの非効率）に対する 2 つの
独立した修正**であり、採否は個別に判断してよい。

### 改善 A: 設計系 Subagent の並列化

- orchestration-policy.md §並列実行の指針に、`architecture-designer` 完了を待たずに
  `contract-designer` を**並列起動できる条件**を追記する。
- orchestrator.md の L3 委譲フロー早見に、並列実行の余地を注記する（フロー自体は変えず、
  並列可否の判断指針を 1 行加える）。

**contract-designer 並列化の緩和策（候補 §想定副作用・ユーザー指定の設計判断に対応）**:
contract-designer を architecture-designer と完全並列にすると、**contract-designer が
architecture-designer の最終成果物（`docs/designs/<feature>.md`）を参照できない**問題がある。
これを次のように緩和する。

- 並列にするのは「契約の骨子（既存 schema / api-contract から確定できる型・nullability・
  エラー形式）」を先行設計できる範囲に限定する。
- architecture-designer が**集約境界・新規 Entity・層責務を確定したら、その確定差分を
  orchestrator が contract-designer へ追送し、契約を再確認させる**（差し戻しではなく追補）。
- 契約書には設計書への参照リンク（「§集約設計は `docs/designs/<feature>.md` を参照」）を
  必ず入れ、設計確定後の整合チェックを orchestrator の統合フェーズで行う。
- **集約構造そのものが未確定で契約の骨子が立てられない L3**（新規ドメイン中心の変更）では
  並列化せず従来どおり直列にする（並列は「契約が設計に強く従属しない」ケース限定）。

### 改善 B: orchestrator 先行調査の共有

- orchestrator.md §起動直後に行うこと の後に「先行調査フェーズ（L3 のみ・任意）」を追加する。
- orchestrator が Read/Grep で**主要ファイルを限定的に**読み、要約を各 Subagent への委譲指示に
  埋め込む。これにより各 Subagent の重複探索を減らす。

**先行調査の対象ファイルを限定（候補 §想定副作用・ユーザー指定の設計判断に対応）**:
orchestrator 自身の Read/Grep 呼び出しが増えるため、**対象を 3 種に厳格に限定**する。

- 対象スキーマの `schema.ts`（Drizzle DB 契約）1 本
- 変更対象に最も近い既存 repository 実装 1 本
- 関連する `packages/api-contract`（Zod）1 本

> これ以上に手を広げない（orchestrator が設計を先取りして Subagent の責務を奪わない）。
> 要約は「どこに何があるか」の所在情報にとどめ、設計判断は各 Subagent に委ねる。
> 要約が不完全でも後段が誤前提で動かないよう、要約には「これは所在情報であり設計判断は
> 各 Subagent が一次情報を確認すること」と明記する。

> **削除・移動の検討（改善＝指示追加ではない原則）**: 本提案は指示を純増させる。これを抑えるため
> 改善 A は新規節を作らず既存の §並列実行の指針を**拡張**し、改善 B は L3 限定・対象 3 ファイル
> 限定とした。並列化により各 Subagent の「個別調査」量は減るため、トークンの純増は限定的と見込む。

## リスク

- **副作用（改善 A）**: contract-designer を並列先行させると、設計確定前の契約骨子が
  architecture-designer の最終成果物とずれる可能性。→ 設計確定差分の追送＋統合フェーズでの
  整合チェック＋設計書参照リンクで緩和。**集約未確定の L3 では並列化しない**ガードを入れた。
  並列分離で contract 品質が落ちないかは回帰評価で必ず確認する。
- **副作用（改善 B）**: orchestrator の Read/Grep が増え、orchestrator 自身のトークンが増える。
  → 対象を 3 ファイルに限定し L3 のみとした。各 Subagent の重複探索減と相殺し、合計トークンが
  増えないことを回帰評価で確認する（**合計トークンが増えるだけなら不採用**）。
- **副作用（改善 B）**: 要約が不完全だと後段 Subagent が誤前提で動くリスク。→ 要約を所在情報に
  限定し「一次情報は各 Subagent が確認」と明記。orchestrator が設計を先取りして Subagent の
  責務を奪わないよう範囲を制限した。
- **指示過多の懸念**: 本提案は指示を純増させる。改善 A は既存節の拡張にとどめ、改善 B は
  L3 限定・3 ファイル限定として最小化した。判断遅延・指示競合（既存 §並列実行の指針との矛盾）が
  起きないよう、改善 A は既存記述に追記する形で単一情報源を保つ。
- **ワークフロー破壊の懸念**: 並列化により Subagent の起動順前提（planner は設計確定後等）が
  崩れないよう、改善 A は「契約骨子が立つ場合限定」とし、設計に従属する工程の順序は変えない。

### 主な発見事項

- **設計品質・契約品質の悪化なし**: 全パターン・全ケースで悪化ゼロ。品質軸（設計品質・
  契約品質・レビュー品質・ドキュメント品質）は before を維持。最重点確認事項をクリア。
- **L2 誤発火なし確認（改善B）**: refactoring（L2）での先行調査誤発火なし。
  「L3 のみ・任意」「L1/L2 では行わない」の二重条件が正常機能。rubric 非推奨パターン
  （指示追加のみでトークン・質問増）に当たらないことを確認。
- **改善Aのガード正常動作**: database-schema-change（集約未確定=新規 Entity）でガード発動・
  直列維持。設計品質劣化なし。
- **効率改善の定量未確認**: Agent 呼び出し効率・トークン効率は全ケース 0 差分。
  - 改善A: 今回の評価ケースではガード発動（並列化なし）が多く、並列化が実際に発動する
    ケース（「契約骨子が既存スキーマから確定できる L3」）での効果測定が未完了。
  - 改善B: トークン純減（Subagent 重複削減 > orchestrator 先読み増）が定性評価では確認不能。
  - rubric の Agent 呼び出し効率軸が「Agent 起動数」ベースのため、並列化による「フロー時間
    短縮」が rubric スコアに直接反映されない構造的限界も確認。

### 条件付き採用推奨の根拠と実タスク確認事項

採用前に実タスクで確認することを推奨:

1. **改善A**: 並列化が「実際に発動する L3 ケース」（フィールド追加系 L3 等）での所要時間計測。
   追送機構の動作確認（設計確定差分の追送漏れがないか）。
2. **改善B**: L3 タスクでの合計 tool use 数の計測（orchestrator 先読み増 vs. Subagent 重複削減
   の収支が純増でないことの確認）。
3. **A+B**: 上記両方の確認が揃ってから同時採用を推奨。

## 採用または却下理由

**決定: 採用（A+B・2026-07-08 人間承認）**

判断根拠:

1. 定性評価（evaluations/IMP-2026-007.md）で 3 ケース × 3 パターンすべて悪化軸ゼロ。
2. 計測阻害要因だった stop/resume 通知待ちループは IMP-2026-008 で解消済み。
3. 効率の定量 before/after は次の正常 L3 で追記する条件付き採用とする（評価の構造的限界を認める）。
4. ユーザーがハーネス改善 1→3 の実装依頼で採否を明示承認。

採用後の監視:

- 次の正常 L3 で `duration_ms` / `tool uses` / 合計トークンを reflection-agent が記録し、

- 契約品質の低下（追送漏れ）やトークン純増が観測されたら当該側をロールバックする。

判断者: 人間（Agent 定義変更のため人間承認必須）。
