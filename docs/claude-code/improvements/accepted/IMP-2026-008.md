# IMP-2026-008: orchestrator の stop/resume 後 Sub-agent notification 待ちループの解消

> agent-improvement-manager が複数候補を横断分析して起票。重要設定は本適用せず差分を残す。
> 承認境界は [../../improvement-cycle.md](../../improvement-cycle.md) §承認境界 を参照。

- **ステータス**: accepted
- **対象 Agent または Skill**: Agent: orchestrator / docs: orchestration-policy.md / 運用: `.claude/state/`
- **承認区分**: 人間承認必須（Agent 責務・委譲フローの構造変更のため）
- **起票日**: 2026-07-01
- **元候補**: candidates/store-master.md（事象 1・2・6）

## 背景

L3 タスク store-master（Sprint 2 Unit A）で、orchestrator が Sub-agent を background で
起動した後に自身が stop すると、resume 後に Sub-agent の完了通知（notification）を受け取れず
「完了待ち」ループから抜けられない事象が観測された。結果としてメイン会話が orchestrator の
代わりに各 Subagent を手動起動する「手動オーケストレーション」に陥り、二重起動（事象 2）や
IMP-2026-007 計測の歪み（事象 6）を副次的に引き起こした。

これは並列化改善（IMP-2026-007）が想定する「notification 待ちループ」そのものであり、
並列化の恩恵を測る前に解決すべき前提条件である。

## 観測事象（根拠）

| 事象                                                            | 再現タスク   | 累計回数                  | 昇格条件                          |
| --------------------------------------------------------------- | ------------ | ------------------------- | --------------------------------- |
| orchestrator stop/resume 後の Sub-agent 通知断絶 → 無限待機     | store-master | 1（初観測・重大機能不全） | 重大インシデントは 1 回で昇格対象 |
| 手動オーケストレーション化に伴う architecture-designer 二重起動 | store-master | 1（事象 1 の副産物）      | 事象 1 解消で自然消滅             |
| IMP-2026-007 の before 計測が異常ケースになり使用不可           | store-master | 1                         | 事象 1 が計測前提を破壊           |

## 原因

**恒久的・構造的原因**。Claude Code の background Agent 起動と stop/resume の組み合わせにより、
resume 後のセッションコンテキストに Sub-agent の実行状態が引き継がれない。orchestrator は
「Sub-agent の完了通知待ち」という揮発的な状態を resume 後に復元できず、通知にも到達しない
ため待機が解けない。通知に依存する現行フローが単一障害点になっている。

## 変更案

最小変更で「通知非依存」にする。既存の `.claude/state/current-feature` 運用を拡張し、
起動済み Sub-agent とその期待成果物（出力先ファイル）を状態ファイルに記録、resume 時は
通知ではなく**成果物の存在**で完了を冪等判定する。

方針の優先順位（A を主案、B を補助原則とする）:

- **A（状態ファイル + 冪等再開）**: **L3 の background 委譲時のみ**、その前に「起動済み
  Sub-agent / 目的 / 期待成果物パス」を `.claude/state/inflight-agents.json` に追記。resume 時に
  未処理エントリがあればこのファイルを読み、期待成果物が存在すれば「完了」とみなして次工程へ、
  無ければ再起動または同期待機に切り替える。通知に依存しない。L1/L2 および単一 Sub-agent の
  同期委譲では本ファイルを使わないため、通常フロー（stop なし）への副作用を生まない。
- **B（既定を同期委譲に）**: 単一 Sub-agent へ委譲する局面では background を使わず同期的に
  完了を待つことを既定とし、background は「明示的に並列化する複数 Sub-agent」に限定する。
  これにより stop を跨ぐ揮発状態を最小化する。

指示は「追加」だけでなく、orchestration-policy.md の並列指針に **A/B の適用条件** を移して
一元化し、orchestrator.md 側は参照に留めることで指示の分散を避ける（削除・移動を含む）。

## 変更差分

```diff
# .claude/agents/orchestrator.md（「実行手順」節・提案。本適用前の差分）
   3. 作業単位の `feature-name`（kebab-case）を決める。自分は Write を持たないため、
      L2/L3 で最初に起動する Write 可能な Subagent（L3: requirements-analyst、
      L2: architecture-designer）に対し、成果物作成とあわせて
      `.claude/state/current-feature` へ feature-name を 1 行で書き込むよう指示する。
      Level 1 ではこのファイルを設定しない（Hook を黙らせ誤検知を防ぐため）。
+  3-2. **L3 で** Sub-agent を **background で** 委譲する場合に限り（L1/L2 および単一
+      Sub-agent の同期委譲では不要）、起動する Write 可能な Subagent へ「起動する Sub-agent 名 /
+      目的 / 期待成果物パス」を `.claude/state/inflight-agents.json` へ追記するよう指示する
+      （通知非依存の再開判定用）。単一 Sub-agent の委譲は原則同期待機とし、background は
+      明示的に並列化する複数 Sub-agent に限定する。feature 完了時（reflection-agent 起動時
+      または完了報告前）に同ファイルを空にする（古いエントリの誤判定防止）。
   4. 各 Subagent へ委譲する。委譲時は必ず以下を明示する。
      - 目的 / 対象範囲 / 対象外 / 参照すべきファイル / 期待する成果物 / 出力先 /
        完了条件 / 禁止事項
+  4-2. resume（会話再開）直後**かつ inflight-agents.json に未処理エントリがある場合のみ**、
+      notification を待たず各エントリの期待成果物の存在を確認する。存在すれば完了とみなし
+      当該エントリを除去して次工程へ進む。存在しなければ再委譲する。「完了待ちループ」に
+      入らない。stop していない通常フローでは本手順は発動しない。
   5. 成果物を統合し、矛盾があれば該当 Subagent へ差し戻す。
```

# docs/claude-code/orchestration-policy.md（並列指針節・提案）

+
+ - **適用レベル: L3 のみ**（L1/L2 では inflight-agents.json を使わない）。
+ - **background 委譲時のみ**、その前に `.claude/state/inflight-agents.json` へ
+   { agent, purpose, expected_outputs[] } を追記する。単一 Sub-agent の同期委譲では追記しない。

+ - **クリアタイミング**: reflection-agent 起動時、または feature 完了報告前に空にする。

## リスク

- 副作用: 状態ファイルの読み書きが増える。**v2 では追記を「L3 + background 委譲時のみ」に
  限定し、resume 手順を「未処理エントリがある場合のみ」に絞った**ため、L1/L2 および stop なし
  通常フローではトークン増が発生しない（v1 で指摘された L3 通常フローの純増を回避）。クリア手順
  （reflection-agent 起動時／完了報告前）を運用ルールに明記済み。
- 指示過多の懸念: orchestrator.md への手順追加は 2 ステップに留め、詳細条件は
  orchestration-policy.md へ移すことで分散を防ぐ。B（同期既定）は IMP-2026-007（並列化）と
  トレードオフの関係にあるため、両者の適用条件を policy 側で一元管理する。
- 未検証点: background 停止時に「成果物が部分書き込みで存在する」ケースの完了誤判定。
  Write 可能 Subagent が成果物を atomically に確定する（完了時にのみ出力先へ書く）前提を
  委譲時の禁止事項に明記して緩和する。

## 評価方法

- 対象 eval ケース: `.claude/evals/cases/`（L3 オーケストレーション代表ケース。store-master
  相当のフローを再生する新規ケース追加を検討）
- 観測軸: 不要作業量（手動オーケストレーション有無）/ トークン効率 / 実装整合性 / 設計品質
- 実タスク検証: 次の L3 タスクで orchestrator が background 委譲後に stop → resume した際、
  手動オーケストレーションなしに Sub-agent 完了を検知して次工程へ進めるかを確認する。
  あわせて IMP-2026-007 の before 値をこのタスクで再取得する（事象 6 の解消）。

## 評価結果

- **v1（初版・2026-07-01）**: agent-evaluator 回帰評価（3 ケース）で **2 軸悪化**。トークン効率が
  L3 2 ケース（database-schema-change / external-service-failure）で 4→3、劣化指標「設計漏れ」3 点
  追加。→ 採用非推奨。詳細は [evaluations/IMP-2026-008.md](../evaluations/IMP-2026-008.md)。
- **v2（改訂・2026-07-01）**: 評価の修正 1〜3 を反映。再評価待ち。

## 採用または却下理由

**採用（2026-07-01・人間承認）**。v1 は回帰評価で 2 軸悪化（トークン効率 L3 2 ケース・設計漏れ
3 点）のため不採用。修正 1〜3 を反映した v2 を同一 3 ケースで再評価した結果、**悪化軸ゼロ・
劣化指標の純増なし**（条件付き採用推奨）。人間承認者が本適用を承認し、`.claude/agents/orchestrator.md`
と `docs/claude-code/orchestration-policy.md` へ適用済み。

残条件（採用の障壁ではない・後続で解消）:

1. 定量検証: 次の L3 実タスクでトークン計測を実施し IMP-2026-007 の before 値も再取得する。
2. Sub-agent 定義への追記責務の明記（追加改善候補として記録）。
3. `inflight-agents.json` の具体スキーマ確定（初回 L3 background 委譲時に確定）。
