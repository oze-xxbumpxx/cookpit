# IMP-2026-003: reviewer に「障害設計レビュー観点」を追加（外部 I/O / 障害系タスク限定で適用）

> agent-improvement-manager が複数候補を横断分析して起票。重要設定は本適用せず差分を残す。
> 承認境界は [../../improvement-cycle.md](../../improvement-cycle.md) §承認境界 を参照。

- **ステータス**: accepted（人間承認済み・本適用済み 2026-06-25）
- **対象 Agent または Skill**: Agent: reviewer（`.claude/agents/reviewer.md`）
- **承認区分**: 人間承認必須（Agent の責務に観点を追加するため。非破壊の観点追記でも本適用しない）
- **起票日**: 2026-06-25
- **元候補**: ベースライン採点（`.claude/evals/baselines/INDEX.md` / `INDEX-2026-06-24-post-phase3.md`「今後の弱点優先順位 §3」）

## 背景

全軸再採点（新ベースライン `INDEX-2026-06-24-post-phase3.md`）でレビュー品質は平均 3.7 のまま据え置き、
弱軸として残った。元 INDEX.md・新 INDEX 双方が要因を同一に特定している。

> 「レビュー品質: reviewer 定義に障害設計固有観点（リトライ嵐・冪等性欠如）が不足。
> L3 の external-service-failure でスコア 3 にとどまる。」（INDEX-2026-06-24-post-phase3.md §弱い軸）

reviewer.md の現「観点」リストは「エラー処理・セキュリティ・性能」を一行で挙げるにとどまり、
外部 I/O を伴う障害設計に固有の落とし穴（リトライ嵐・指数バックオフ欠如・タイムアウト未設定・
冪等性欠如・部分失敗時の整合性・秘密情報のログ漏れ）を**具体的なチェック項目として持たない**。
eval ケース `external-service-failure.md` は「reviewer はエラー処理・リトライ嵐・タイムアウト未設定・
冪等性欠如・秘密情報の漏えいを指摘」することを期待しているが、現定義はそれを構造的に誘導しない。

## 観測事象（根拠）

| 事象 | 再現タスク | 累計回数 | 昇格条件 |
| --- | --- | --- | --- |
| レビュー品質が弱軸（平均 3.7）で再採点後も据え置き | ベースライン採点（8 ケース横断、2 回の全軸採点）| 2 回のベースラインで同一値・同一要因 | 同種要因が複数ベースラインで再現 |
| `external-service-failure` でレビュー品質 3 止まり（障害系観点の欠落が要因と明記） | 元 INDEX.md / post-phase3 INDEX | 2 回の採点で連続 3 | 障害系の構造的観点欠落として記録 |
| `small-bug-fix` でレビュー品質 3（L1 で reviewer 観点が薄い）| 元 INDEX.md / post-phase3 INDEX | 2 回連続 | （本提案の対象外。L1 は障害系と無関係） |

> 単発事象ではなく、**2 回の全軸ベースライン採点で同一要因（障害設計観点の欠落）が再現**しており、
> 構造的原因として扱える。なお元データはベースライン採点由来であり、実タスクでの障害系開発は
> 未発生（external-service-failure は外部連携未導入のため設計・レビュー観点の質を採点するモード）。
> この限界は評価レポートにも明記する。

## 原因

**恒久的・構造的原因。** reviewer.md の「観点」セクションが汎用レビュー観点（要件充足・責務分離・
エラー処理・セキュリティ・性能・テスト不足・ドキュメント漏れ）の粒度で書かれており、外部 I/O を
含む障害設計タスクに固有の失敗モードが具体化されていない。reviewer は「エラー処理を見る」とは
書いてあるが、「リトライに上限と指数バックオフがあるか」「タイムアウトが設定されているか」
「書き込みに冪等性キーがあるか」「部分失敗時にデータ整合性が保たれるか」「秘密情報がログ/エラー
本文に漏れていないか」という**チェックリスト粒度**を持たないため、観点が抜けやすい。

## 変更案

最小変更で最大効果を狙い、変更対象は `reviewer.md` の **1 ファイルのみ**。
**指示を「増やすだけ」にしない**ため、追加観点には IMP-2026-001 と同じ思想で**適用条件**を付け、
「対象タスクに外部 I/O / 障害設計が含まれる場合のみ」適用する。L1 や純粋ロジック修正、外部 I/O を
持たない変更には適用しないことを明文化し、L1 への過剰適用（不要な指摘・トークン増・重要指摘の
埋没）を防ぐ。

- 「観点」セクションの「エラー処理、セキュリティ、性能」を、**外部 I/O / 障害設計を含む場合に限り**
  展開する障害設計チェックリスト（小見出し）へ分岐させる。
- チェック項目: (a) リトライに上限と指数バックオフ（リトライ嵐の防止）、(b) タイムアウト設定の
  有無、(c) 書き込みの冪等性キー、(d) 部分失敗時のデータ整合性・補償、(e) フォールバック/縮退、
  (f) 秘密情報がログ・エラー本文・例外メッセージに漏れていないか。
- 各項目に**適用条件**（「Infrastructure 経由の外部 API/ストレージ I/O を含む場合」）を併記し、
  該当しないタスクでは適用しない旨を明記する。指示の追加と同時に**適用範囲を限定**する。
- 既存の汎用観点（責務分離・テスト不足・ドキュメント漏れ）は変更しない。tools / model / 制約
  （コードを直接修正しない等）には一切触れない。

> CLAUDE.md・Hook・セキュリティルール・他 Agent には触れない。reviewer の責務「観点」への
> チェックリスト追加であり、責務カテゴリ（レビュー）自体は不変だが、Agent 定義の責務記述変更に
> 該当するため承認区分は **人間承認必須**。proposal に差分を書くにとどめ、本適用しない。

## 変更差分

```diff
--- a/.claude/agents/reviewer.md
+++ b/.claude/agents/reviewer.md
@@ ## 観点
 - 要件充足性（requirements / 設計 / 実装が同じものを指しているか）
 - 設計との整合性、実装計画との整合性
 - コード品質、責務分離（層・集約の境界を越えていないか）
 - エラー処理、セキュリティ、性能
 - テスト不足（試験観点に対する実装の網羅）
 - ドキュメント更新漏れ
+
+### 障害設計の追加観点（対象タスクに外部 I/O / 障害設計が含まれる場合のみ）
+
+次のいずれかを含む変更のときだけ適用する。該当しない L1・純粋ロジック修正・外部 I/O を
+持たない変更では**適用しない**（過剰な指摘・トークン増・重要指摘の埋没を避ける）。
+適用条件: Infrastructure 経由の外部 API / 外部ストレージ I/O・タイムアウト/リトライ・
+書き込みの再送/重複処理・部分失敗が起こりうる多段処理を含む場合。
+
+- (a) リトライ嵐の防止: リトライに**上限回数**と**指数バックオフ**があるか（無限/即時リトライで
+  障害を増幅していないか）。
+- (b) タイムアウト: 外部呼び出しにタイムアウトが**設定されているか**（未設定でハングしないか）。
+- (c) 冪等性: 書き込み/再送のある操作に冪等性キー等の重複防止があるか。
+- (d) 部分失敗時の整合性: 多段処理の途中失敗でデータ不整合が残らないか（補償/ロールバック方針）。
+- (e) フォールバック/縮退: 外部依存ダウン時のユーザー向け挙動が設計されているか。
+- (f) 秘密情報の漏えい: ログ・エラー本文・例外メッセージにトークン/認証情報/個人情報が
+  出ていないか（安全性とも関連）。
```

## リスク

- 副作用: 他 Agent への破壊的影響なし。reviewer.md のみの変更で、orchestration-policy.md・
  他 Subagent・Hook・CLAUDE.md を参照／変更しない。reviewer は障害系チェックを **Should/Nice の
  重大度**で扱えばよく、既存の出力フォーマット（重大度・該当箇所・理由・修正案）と整合する。
- 指示過多の懸念: 観点を**無条件追加**すると L1・純粋ロジック・外部 I/O 無しの変更で reviewer が
  無関係なチェックを並べ、不要な指摘・トークン増・本質的指摘の埋没を招く。これを「適用条件
  （外部 I/O / 障害設計を含む場合のみ）」で打ち消す。IMP-2026-001 と同じく「追加と限定を同一提案に
  含める」設計でネットの指示負荷増を抑える。
- 評価の限界: external-service-failure は外部連携未導入のため設計・レビュー観点の質を採点する
  モードであり、実コード実行・実 Agent 起動を伴わない定性評価である。

## 評価方法

- 対象 eval ケース:
  - `.claude/evals/cases/external-service-failure.md`（障害設計が核心 → レビュー品質向上を確認）
  - `.claude/evals/cases/aws-integration-change.md`（外部 API/ストレージ → 障害観点の適用を確認）
  - `.claude/evals/cases/small-bug-fix.md`（L1・外部 I/O 無し → 過剰適用が起きていないか＝不要作業量・
    トークン効率・不要な質問の悪化が無いかの回帰確認）
- 観測軸: レビュー品質（改善期待）/ 安全性（秘密情報漏えい観点で中立〜微増）/ 不要な作業量・
  トークン効率（悪化しないこと）/ 要件理解・実装整合性（中立であること）。
- 判定ルール: improvement-cycle.md §回帰評価。**1 軸でも悪化があれば不採用。** 過剰適用
  （不要作業量・トークン効率の悪化）も必ずチェックする。

## 評価結果

agent-evaluator のレポート: [../evaluations/IMP-2026-003.md](../evaluations/IMP-2026-003.md)。

- `external-service-failure`: レビュー品質 3 → 4（+1）。障害設計チェックリストが構造的に観点を
  誘導。安全性 5 → 5（秘密情報漏えい観点が明示化されるが既に高水準で中立）。他軸中立、悪化なし。
- `aws-integration-change`: レビュー品質 4 → 4（中立、既に外部 I/O 観点をカバー）。悪化なし。
- `small-bug-fix`（L1 過剰適用チェック）: レビュー品質 3 → 3（中立）。不要作業量 5 → 5・
  トークン効率 4 → 4・不要な質問 中立（適用条件「外部 I/O / 障害設計を含む場合のみ」が機能し
  L1 で無関係チェックが起きない）。悪化なし。

**全ケース・全軸で悪化ゼロ。** 改善は障害系ケースに限定して現れ、L1 では中立。
適用条件による過剰適用防止が意図どおり機能した（評価レポート参照）。

## 別案（採用しなかった選択肢）と理由

  本案とし、Skill 化案は人間承認時の選択肢として記録する。
