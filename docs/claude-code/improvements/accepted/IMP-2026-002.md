# IMP-2026-002: Stop フックの反復ノイズを変更検知デバウンスで抑制

> 起票: ユーザーの明示改善要求（recipe-edit-screen トライアルの摩擦観測）に基づく。
> Hook 改修のため本適用せず差分を残す。承認境界は [../../improvement-cycle.md](../../improvement-cycle.md) §承認境界 を参照。

- **ステータス**: accepted（人間承認済み・本適用済み）
- **対象 Agent または Skill**: Hook: `.claude/hooks/check-deliverables.mjs` / `.claude/hooks/check-improvement-cycle.mjs`（＋新規 runtime state `.claude/state/hook-notice-state.json`）
- **承認区分**: **人間承認必須**（`.claude/hooks/*` の改修。非ブロッキング警告のみだが保護ファイル）
- **起票日**: 2026-06-24
- **元候補**: candidates/recipe-edit-screen.md（事象5: Stop フックの多段進行中ノイズ）

## 背景

recipe-edit-screen（L2・実機能トライアル）で orchestrator フルフロー（6 Agent）を回した際、
各 Subagent の完了待ちで手番を終えるたびに `Stop` フックが発火し、**十数回の同一警告**が出た。
警告内容（「設計書が未作成」等）はその時点では正しいが、工程進行中に成果物が段階的に揃う L2/L3 では
**完了するまで毎ターン鳴り続ける**。実害はトークン浪費と重要シグナルの埋没。

## 観測事象（根拠）

| 事象                                                   | 再現タスク         | 累計回数             | 昇格条件                                                                   |
| ------------------------------------------------------ | ------------------ | -------------------- | -------------------------------------------------------------------------- |
| Stop フックが多段 Agent 進行中に毎ターン同一警告を反復 | recipe-edit-screen | 1 タスク内で 10 回超 | ユーザーが改善を要求（improvement-cycle.md §実行タイミングの起票トリガー） |

> 単発タスクだが、L2/L3 の orchestrator フルフローでは**構造的に必ず再現**する（current-feature が
> 全工程で設定され、成果物が段階的に揃うため）。ユーザーの明示要求もあり proposal 化する。

## 原因

**恒久的・構造的原因。** `.claude/settings.json` の `Stop` イベントに `check-deliverables.mjs` と
`check-improvement-cycle.mjs` が紐づき、**毎ターン末に無条件発火**する。両フックは
「進行中」と「完了」を区別せず、`current-feature` が設定されていて成果物が未充足なら警告する。
Stop は「タスク完了」ではなく「毎手番の終わり」に発火するため、多段 Agent の待機ターンすべてで
同じ警告が出る。フック自体の判定は正しく、**問題は発火頻度（タイミング）にある**。

## 変更案

警告を**消さず**、「同じ警告は一度だけ」に変える（安全網＝言い忘れ検知は保持し、反復だけ殺す）。
指示の追加ではなく**フックの発火条件にデバウンスを足す**最小変更。

- 新規 runtime state `.claude/state/hook-notice-state.json`（`.claude/state/` は gitignore 済み＝
  マシンローカル。current-feature / subagent-log と同じ扱い）に、`(フック名, feature)` ごとの
  「直近に出した警告セットのハッシュ＋時刻」を保存。
- 各 Stop フックは警告算出後に `feature + ソート済み警告群` のハッシュを計算し、
  - **同一ハッシュ かつ クールダウン内（30分）→ 沈黙**
  - **ハッシュ変化（ギャップが開く/閉じる）／クールダウン経過 → 1回だけ emit し状態更新**
- これにより「新しい未充足が現れた時に一度通知 → 状態が変わるか30分経つまで沈黙」。
  完了時に未充足が残れば既に一度は表示済み。最終ゲートは validate-deliverables Skill / reviewer。

> スコープ外: `~/.claude/stop-hook-git-check.sh`（未コミット催促）は**ユーザーグローバル**フックで
> 本リポジトリ外。同じ毎ターン問題を持つが、このリポジトリの設定からは制御できない（別途マシン側で対応）。
> 本提案は Stop の2フックに限定。`check-deliverables.mjs` の PostToolUse 分岐（ソース編集時警告）は
> 痛みが小さいため対象外（必要なら同じヘルパで後日拡張可）。

## 変更差分

両フックに共通のデバウンスヘルパを追加し、`Stop` 分岐の `emit` をガードする。

+import { readFileSync, writeFileSync, mkdirSync, existsSync } from 'node:fs';
+import { join } from 'node:path';
+import { createHash } from 'node:crypto';
+
+const NOTICE_COOLDOWN_MS = 30 * 60 * 1000; // 同一警告セットを再掲しない窓（30分）
+
+// 同一の警告セットを毎ターン繰り返さないためのデバウンス。
+// 警告セットが変化したか、クールダウンを過ぎたときだけ true（＝emit すべき）。
+// state 読み書き失敗時は fail-open（true を返し従来どおり警告）。
+function shouldEmitNotice(key, feature, warnings) {
+  const statePath = join(ROOT, '.claude/state/hook-notice-state.json');
+  const hash = createHash('sha1')
+    .update(`${feature}\n${[...warnings].sort().join('\n')}`)
+    .digest('hex');
+  let state = {};
+  try {
+    if (existsSync(statePath)) state = JSON.parse(readFileSync(statePath, 'utf8')) || {};
+  } catch {
+    return true; // 読めない → 従来どおり出す
+  }
+  const prev = state[key];
+  const now = Date.now();
+  if (prev && prev.hash === hash && now - prev.ts < NOTICE_COOLDOWN_MS) return false;
+  state[key] = { hash, ts: now, feature };
+  try {
+    mkdirSync(join(ROOT, '.claude/state'), { recursive: true });
+    writeFileSync(statePath, JSON.stringify(state, null, 2));
+  } catch {
+    /* 書き込み失敗は致命でない。今回は出し、次回も出る（fail-open） */
+  }
+  return true;
+}

   if (event === 'Stop') {

## リスク

- **言い忘れの見逃し**: 同一警告は一度しか出ないが、(1) 初回に必ず出る (2) 状態変化で再掲
  (3) 30分で再掲 のため、完了時に未充足があれば最低一度は表示済み。最終ゲートは
  validate-deliverables Skill / reviewer であり、本フックは補助シグナル。見逃しリスクは小。
- **fail-open 設計**: state の読み書きに失敗したら従来どおり警告する（沈黙して隠さない）。
  新たな「警告が出ない」故障モードを作らない。
- **指示過多**: 指示文・成果物要件は不変。フックのコードのみ増。トークンはむしろ**減る**
  （反復警告が消えるため）。指示競合・ワークフロー破壊なし。

## 評価方法

eval ケース（agent 挙動の採点）は本件に**不適**（agent 定義・Skill・Rule を変えずフックの発火頻度のみ
変更するため）。代わりにスクリプト単体試験で before/after を確認する:

1. **初回は出る**: feature 設定・成果物欠如の状態で Stop 入力を流す → 警告が出る。
2. **同一連打は沈黙**: 同じ入力を再度流す → 出力なし（クールダウン内・ハッシュ一致）。
3. **状態変化で再掲**: 成果物を1つ作成し再度流す → 警告セットが変化し再び出る。
4. **feature 未設定は沈黙**: current-feature を空にして流す → 出力なし（既存挙動を維持）。

劣化指標: 反復警告回数（before: 毎ターン → after: 一度）。それ以外のフック挙動・他フックは不変。

## 評価結果

隔離 ROOT でのスクリプト単体試験を両フックで実施（2026-06-24）。全項目合格。

| 検証                   | check-deliverables    | check-improvement-cycle                    |
| ---------------------- | --------------------- | ------------------------------------------ |
| ① 初回は出る           | ✅ 警告出力           | ✅ 警告出力                                |
| ② 同一連打は沈黙       | ✅ 出力なし           | ✅ 出力なし                                |
| ③ 状態変化で再掲       | ✅ 成果物追加で再出力 | ✅ candidate 追加で再出力                  |
| ④ feature 未設定は沈黙 | ✅ 出力なし           | ✅（feature 必須分岐で同等・既存挙動維持） |

- 構文チェック（`node --check`）両フック OK。
- 劣化指標: 反復警告回数 = 毎ターン → 一度（状態変化/30分まで沈黙）。他フック・他挙動は不変。
- 回帰なし: emit 内容・判定ロジック・PostToolUse 分岐・guard-dangerous / validate-agent-config /
  record-subagent は無変更。fail-open のため「警告が出ない」新故障モードは発生しない。

## 採用または却下理由

**採用。** 判断者: 人間（ユーザー承認 2026-06-24）。承認区分「人間承認必須」を満たし、上記試験で
「初回は出る／反復は沈黙／状態変化で再掲／未設定は沈黙」を確認、他フック挙動に回帰なし。本適用済み
（`check-deliverables.mjs` / `check-improvement-cycle.mjs` を編集）。
