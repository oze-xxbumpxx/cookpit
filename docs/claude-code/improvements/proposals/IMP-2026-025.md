## 背景

Codex 委譲ルートの直近 3 連続 L3 ユニットで、Codex が着手する前に Claude が生成する
「設計書 + 実装計画 + ブリーフ」の総量が高水準で継続し、かつ実装計画とブリーフが**同じ確定
コードを二重に書き起こしている**ことが定量的に確認された。ユーザーの明示の問題意識は
「Codex 委譲ルートでは Claude の作業比重・usage を減らしたい」であり、二重生成はその阻害要因。

Codex ルートでは実装計画の実質的な読者が存在しない（`docs/tasks/codex/README.md` は実装計画を
「読み取り専用参照。実装の根拠が必要な場合のみ」と明記し、Codex の主入力はブリーフ）。にも
かかわらず `create-implementation-plan` Skill の完了条件は「**implementer** がこの計画だけで
実装に着手できる粒度」を要求しており、Codex ルートに存在しない implementer 読者を前提にした
重い粒度を課している。これが二重生成の構造原因。

## 原因

**恒久的・構造的**。実装ルートに関わらず「implementer が着手できる粒度」を実装計画に要求する
Skill 完了条件が、Codex ルートでは読者不在の重い文書を生む。ブリーフ側の「完成コードを貼る」
慣行は成功パターンとして 3 件継続しているが、一度も Skill テキストに明文化されないまま踏襲され、
実装計画との二重生成コストと、Application 層でのサンプルコード自体の潜在バグリスク（2 回）を
併発している。トレードオフ（後述）が明文化されていないため、削るべき箇所と残すべき箇所の
判断基準が現場に無い。

## 変更案

1 根本原因（Codex ルートが実装計画・ブリーフを implementer 前提の完全実装文書として二重に扱う）
に対し、リスク profile の異なる 2 段階で対応する。**usage 削減効果が最も大きく副作用が最小な
Phase 1 を優先**し、品質トレードオフを伴う Phase 2 は次の L2 で試験運用してから判断する。
「指示の追加」ではなく「二重生成の除去（削減）」と「層別に貼付コードを削る（削除）」が主眼。

### Phase 1（低リスク・usage 直接削減・優先）: 実装計画の Codex 軽量モード

Codex 委譲ルートの実装計画から、ブリーフと重複する「ファイル別の完成コード・詳細シグネチャ」を
外し、**タスク分解・依存順・Task 別完了条件・テストファイル対応・リスク・ロールバック**のみを
持たせる（ファイル別の実装内容はブリーフが正本）。完了条件の「implementer が着手できる粒度」を
実装ルート別に分岐させ、Codex ルートでは「ブリーフ生成の入力として十分な分解粒度」に緩める。
これは二重生成そのものの除去であり、実装計画÷ブリーフ比を構造的に下げる。品質への影響はほぼ
無い（実装内容はブリーフに残るため）。

> 完全省略案（Codex ルートでは実装計画書を作らずブリーフが兼ねる）も検討したが、(a) 実装途中で
> Orchestrator 経路へ切り替える場合の土台文書が失われる副作用、(b)「成果物の省略条件」の変更は
> より重い承認事項、の 2 点から、Phase 1 では**省略ではなく軽量化**を推奨する。省略を選ぶ場合は
> 本 proposal 内の別オプションとして人間が明示承認する。

### Phase 2（要注意・段階導入）: ブリーフの完成コードを層別に薄くする

事象 4（Domain/Infra はボイラープレート色が強く完成コード同梱で 3 件連続ゼロエラー）と
事象 3（Application はロジック絡みでサンプルコード自体に潜在バグ 2 回）を層別に扱う。

- **Domain / Infrastructure**: 現状維持（完成コード + 「命名・記法の注意」節）。ゼロエラー実証が
  あり、貼付コードの潜在バグリスクも低い。
- **Application / Presentation**: 公開シグネチャ + 不変条件/落とし穴 + テスト観点 + **公開識別子
  一覧（タイポ照合基準として必ず残す）**を主とし、メソッド本体の完成コード貼付を減らす。サンプル
  コード由来の潜在バグ（2 回とも Application 層）を構造的に減らす狙い。

この層別方針は現状どの Skill にも明文化されていない（「完成コードを貼る」慣行は暗黙）。Phase 2 で
初めて明文化する。

### トレードオフ（必須明記）

- 完成コード同梱ブリーフは **3 タスク連続で Codex の既知ミス型（識別子タイポ・結線漏れ）ゼロ**
  という実証効果がある。Phase 2 の薄化はこの効果を Application/Presentation で**どこまで手放すか**の
  判断である。
- 補償策: (1) **公開識別子一覧を必ず保持**（check-codex-implementation.mjs の識別子照合と目視照合の
  基準を維持）、(2) `review-codex-implementation` の機械検出（結線漏れ・'use client' 漏れは FAIL 検出）で
  貼付コードが減った分を後段で補う、(3) Domain/Infra は薄化しないため、効果が高い層の実証効果は温存。
- 逆に、完成コードを貼り続けると事象 3 の潜在バグ（Application ロジックのサンプル自体のバグ）が
  Codex に忠実にコピーされるリスクが残る。薄化はこのリスクを下げる方向にも働く。

### 運用注記（逐語一致基準）

いずれの Phase を採るにせよ、Orchestrator 統合クロスチェックの「契約書コード片と実装計画コードは
逐語一致」（logs/2026-07-15.md の運用実践・正典化はされていない）は、薄いブリーフ/軽量実装計画では
「逐語一致しない」ことが正常になる。採用時にこの合格基準を「シグネチャ・識別子の一致」に置き換える
注記を残す（policy 文書の変更ではなく運用注記。正典化されていないため diff 対象外）。

## リスク

- **副作用**: Phase 2 でブリーフを薄くすると、Application/Presentation で識別子・配線ミスが
  再燃する可能性（完成コード同梱のゼロエラー効果を一部手放すため）。→ 層別に限定（Domain/Infra は
  維持）+ 公開識別子一覧の保持 + review-codex-implementation の機械検出で補償し、次 L2 で試験。
- **副作用**: Phase 1 の実装計画軽量化により、実装途中で Orchestrator 経路へ切り替える場合の
  土台が薄くなる。→ 完全省略ではなく軽量化にとどめ、切替時は実装計画を補強する運用で対応。
- **指示過多の懸念**: 本 proposal は正味「削減・移動」寄り（実装計画からブリーフへ実装内容を一元化、
  貼付コードを層別に削る）。Skill テキストの純増は層別方針の明文化分のみで、判断遅延・トークン増は
  生じにくい。むしろ Claude の生成トークンを下げる方向。
