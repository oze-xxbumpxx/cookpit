## 背景

shopping-list-core（L3・Codex 委譲）で、`docs/reviews/shopping-list-core.md` に Task 1・2 の
受け入れレビューのみ記録され、Task 3・4・5 の記録が欠落した（同一問題が同一 feature 内で 3 回）。
一因は 2 文書の必須性の食い違い:

- `definition-of-done.md` L3: 「`docs/reviews/<feature>.md` にレビュー記録。」→ **条件なしの必須**。
- `orchestration-policy.md` §実装ルートの分岐（Codex）: 「結果（…）を **PR 本文または** `docs/reviews/`
  に記録する。」→ **OR 条件で緩和**。

この不一致により「PR 本文への記録で足りる」という判断が可能になり、docs/reviews/ への記録が
なし崩しに省略され得る構造がある。

## 観測事象（根拠）

| 事象                                               | 再現タスク                      | 累計回数             | 昇格条件                    |
| -------------------------------------------------- | ------------------------------- | -------------------- | --------------------------- |
| L3 受け入れレビュー記録が docs/reviews/ に残らない | shopping-list-core Task 3・4・5 | 3（同一 feature 内） | 同じ問題が 3 回以上発生した |

## 原因

**恒久的な構造的原因（文書間の文言不一致）**。加えて (b) 長尺セッションで最初の 1-2 タスクは
記録したが以降が途切れる運用のなし崩し。本 proposal は主因である文言不一致を解消する。
機械検出しにくい（PR 本文に書いたかはローカルから見えない）ため、記録先を検証可能な場所に
一本化することが構造的対処になる。

## 変更案（2 案の比較と推奨）

### 案 A（推奨）: docs/reviews/ を L3 必須に統一（orchestration-policy.md 側を締める）

- `orchestration-policy.md` の Codex 規律から「PR 本文または」の逃げ道を、L3 に限り除去する。
- `definition-of-done.md` L3 は既に docs/reviews/ 必須で正しいため**変更なし**（正典として維持）。
- L2 は definition-of-done.md でも docs/reviews/ を必須にしていない（reviewer 工程は「必要なら」）。
  Codex 規律も L2 は任意（PR 本文可）と明記して**レベル別に整合**させる。

**推奨理由**:

1. **検証可能性**: リモート/エフェメラル環境では PR 本文はローカル/Hook から検証できず機械検出
   不能。docs/reviews/ はリポジトリ内で追跡・横断参照でき、成果物欠落を後から確認できる（事象 6 の
   副作用に明記された問題を根本で解消）。
2. **非対称の解消**: orchestration-policy.md の L3 標準フローは reviewer 工程を
   「reviewer → docs/reviews/<feature>.md」と規定する。受け入れレビューは reviewer 工程の
   **代替**（省略ではない）なので、記録先も docs/reviews/ に揃えるのが一貫的。Codex ルートだけ
   PR 本文可にするのは非対称。
3. **正典を動かさない最小変更**: definition-of-done.md（正典）は既に正しく、緩い側 1 文書を
   締めるだけで整合する。

### 案 B: PR 本文記録で足りるとする（definition-of-done.md 側を緩める）

- `definition-of-done.md` L3 の「docs/reviews/ にレビュー記録」を「PR 本文または docs/reviews/ に
  レビュー記録」へ緩和し、orchestration-policy.md に合わせる。
- **却下理由**: (1) PR 本文は検証不能で、事象 6 の「機械検出しにくい」問題がそのまま残る。
  (2) L3 reviewer 工程（docs/reviews/ 必須）との非対称が残る。(3) 成果物要件を緩める方向は
  記録欠落の再発を許容することになり、改善の趣旨に反する。

### 推奨: **案 A**

## リスク

- 副作用: 記録の付け忘れが起きやすい構造自体は残る（Hook で機械検出しにくい）。ただし記録先を
  リポジトリ内の docs/reviews/ に一本化することで、少なくとも**事後の欠落検出は可能**になる。
  将来的に check-deliverables 系 Hook で L3 の docs/reviews/<feature>.md 存在確認を足す余地がある
  （本 proposal のスコープ外・別候補）。
- 指示過多の懸念: L2 を任意に据え置くことで過剰要求を避ける。L3 のみ締めるため肥大化しない。
- review-codex-implementation SKILL.md は `.claude/skills/` 配下で guard-dangerous の保護対象。
  適用にはマーカー承認が必要（下記）。
