## 背景

Anthropic が 2026-07-24、Claude Code のシステムプロンプトを 80% 以上削除しても社内
コーディング評価で計測可能な性能低下がなかったと公表した。解説記事
（`ai.zenken.co.jp/post/claude5-context-engineering/`）はこれを 6 つの転換として整理している。

1. ルール列挙 → 判断委任
2. 例示 → インターフェース設計（例が探索範囲を狭める）
3. 前置き一括 → 段階的開示
4. 繰り返し記述 → ツール記述への一本化
5. 手動メモリ → 自動メモリ
6. 単純仕様 → リッチ参照

> 403）。本提案は検索スニペットと転載・解説記事から再構成した内容にもとづく。一次情報の細部

## 原因

**恒久的・構造的**（変更 A）。`orchestration-policy.md` §モデル割り当ては「判断がいる」層に
`claude-opus-4-8` を固定値で書いており、モデル世代が更新されても追随する仕組みがない。
`.claude/evals/results/setup-audit-2026-07-04--regression.md` の C3 では実務 Agent 13 体を
`claude-sonnet-4-6` → `claude-sonnet-5` へ更新した際、orchestrator / agent-improvement-manager を
「opus-4-8 のまま」と明示的に据え置いており、Opus 側の更新経路が未整備のまま残った。

変更 B/C は**一時的・外部起点**。記事の主張に反応した変更であり、本リポジトリ内で反復観測された
問題ではない。

## 変更案

指示の追加は行わない。**A はモデル値の置換、B は削除、C は適用範囲の限定**であり、
いずれも指示の増量を伴わない（improvement-cycle.md コスト方針「削除・移動を含む改善」に合致）。

### 変更 A（適用を提案）: 上位 4 Agent のモデルを Claude 5 世代へ

`claude-opus-4-8` → `claude-opus-5`。対象は orchestrator / reviewer / security-reviewer /
agent-improvement-manager の 4 本と、同期文書。

**順序が重要**: 記事は「Claude 5 世代向けに指示を削れ」と言っている。前世代モデルのまま指示を
削ると、単に判断材料を失った状態になる。**A を適用してから B を評価する。**

### 変更 B（A 適用後・回帰評価を通過した場合のみ）: `implementer.md` の規約再掲を削除

`implementer.md` は `.claude/rules/` を必読と指示したうえで、同じ規約を 6 行再掲している。
再掲を消して参照一本にする（転換 4）。**単独では適用しない。**

### 変更 C（据え置き・適用しない）: audit-skills の「例」ポリシー

`audit-skills/SKILL.md:33` の「良い例・悪い例が最低 1 つずつあるか（例が挙動を最も強く規定する）」は
記事の転換 2 と正面から衝突する。ただし本リポジトリで実際に運用されている「例」は
**インライン擬似コードではなく実成果物へのパス参照**（`docs/designs/test-infra-expansion.md §4` 等）で、
これは記事の転換 6（リッチ参照）そのものであり、転換 2 が警告する few-shot とは別物。
**機械的な反転は行わない。** 将来変更するなら「インラインで手順を模倣させる例」だけに対象を絞る。

### 適用しないと明記するもの

- **アーキテクチャ原則の削減**（依存方向・`create()`/`reconstruct()`・集約間 ID 参照）。
  記事が言う「自明なこと」ではなく「自社固有の落とし穴」側であり、削減対象ではない。
- **転換 5（自動メモリ）への移行**。`memory-policy.md` の段階的昇格（単発 → Memory → 改善候補
  → Rule/Skill、CLAUDE.md 変更は人間承認必須）は、自動化より意図的に強い設計。誤情報の永続化
  リスクを踏まえた選択であり、記事に合わせて緩める理由がない。

## リスク

- **副作用（変更 A）**: Opus 5 は前世代と判断特性・出力量が異なる。reviewer の指摘粒度、
  orchestrator の委譲判断が変わりうる。コスト単価も変動する可能性がある。
- **副作用（変更 B）**: `.claude/rules/` を読まずに実装へ入った場合、規約違反が素通りする。
  再掲は冗長であると同時に**フェイルセーフでもある**。この二面性が B を単独適用しない理由。
- **指示過多の懸念**: 本提案はいずれも指示を増やさない（置換・削除・限定のみ）。
- **外部情報の不確実性**: 記事本文を直接検証できていない（ネットワークポリシーによる到達不可）。
  記事の主張そのものを根拠に設定を変えるのは変更 B/C のみで、それらは据え置き・評価前提とした。

## 評価方法

- 対象 eval ケース: `.claude/evals/cases/` から実装工程を含むケースを選定（manager が確定）

- 手順: ①変更 A 適用 → ②ベースライン取得 → ③変更 B 適用 → ④再評価
- 判定: improvement-cycle.md §回帰評価 のとおり **1 軸でも悪化があれば変更 B は採用しない**
