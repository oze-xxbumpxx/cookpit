# IMP-2026-029: 承認マーカーのリモートデッドロック解消（明示承認によるマーカー作成手順の正規化）

> 重要設定は本適用せず差分を残す。承認境界は

- **承認区分**: 人間承認必須（settings.json = Hook・権限まわりの保護構成ファイル）

## 背景

guard-dangerous.mjs のブロック格上げ（IMP-2026-013）により、保護構成ファイル
（CLAUDE.md / `.claude/{agents,hooks,rules,skills}/` / settings.json）への書き込みは
`.claude/state/config-change-approved` マーカーが無い限りブロックされる。ところがリモート
（エフェメラル）環境では、マーカー作成コマンド自体が権限クラシファイアに自動拒否されるため、
**人間がチャットで明示承認した変更ですら適用できない**デッドロックが反復している。
IMP-2026-025/026 の SKILL.md・Hook 計 4 ファイルが現に「ローカル適用待ち」で滞留中。

| 事象 | 再現タスク | 累計回数 | 昇格条件 |
| ---- | ---------- | -------- | -------- |

| ⑤（create-codex-brief モデル行・ユーザー承認済み）が再度適用不可を確認 | pantry-screens（logs/2026-07-19 セッション 2） | 3 | **充足**（backlog でも「再発条件充足」記載済み） |

## 原因

恒久的・構造的。安全機構（保護ファイルの書込ブロック）の設計時にリモート運用が想定されて
おらず、「人間承認 → マーカー作成 → 適用」のフローの第 2 步がリモートで実行不能。承認の
**有無**の問題ではなく、承認を機械に伝える**経路**の欠落。

## 変更案

**案 B（推奨）: 明示承認によるマーカー作成手順の正規化**

1. `.claude/settings.json` の `permissions.allow` へマーカーの作成・削除コマンドを追加し、
   権限クラシファイアの自動拒否を解消する。
2. improvement-cycle.md §承認境界へ「リモートセッションでの承認手順」を明文化する:
   - ユーザーがチャットで**当該変更を明示承認**した場合に限り、Claude がマーカーを作成してよい。
   - 適用は**承認された差分のみ**。適用後は直ちにマーカーを削除する。
   - 適用コミットのメッセージに承認の出典（日付・承認内容の要約）を記載する。
   - ユーザー承認なしのマーカー作成は従来どおり禁止（違反は guard ではなく監査
     （コミット履歴・validate-agent-config 警告）で検出する — 現行ローカル運用と同等の信頼モデル）。

**案 A（代替・非推奨）: PR レビュー承認方式** — 保護ファイルの書き込みを作業ブランチ上で
許可し、main マージ前の PR レビューを人間承認とみなす。guard の保護条件を「ブランチ」依存に
緩める必要があり、セッション内で未承認の構成変更が即時有効になる穴（hooks は作業ツリーから
実行される）が生じるため推奨しない。

**ブートストラップ制約**: settings.json 自体が保護ファイルのため、本 proposal の初回適用
だけはローカルセッションまたは人間の直接編集が必要（既存の「ローカル適用待ち」4 ファイルと
同じバッチで適用すると往復が 1 回で済む）。適用後は同型のデッドロックが解消する。

```diff
       "Bash(git branch)",

```

```diff
--- docs/claude-code/improvement-cycle.md（§承認境界「人間の承認なしに変更してはいけない」の直後へ追加）
+### リモートセッションでの承認手順（承認マーカーの運用）
+
+リモート（エフェメラル）環境で人間承認済みの保護ファイル変更を適用する場合の正規手順:
+
+1. ユーザーがチャットで**対象の変更を明示承認**する（proposal・差分の提示が前提）。
+2. Claude が `touch .claude/state/config-change-approved` でマーカーを作成する
+   （ユーザー承認のないマーカー作成は禁止。作成はこの手順のみ）。
+3. **承認された差分だけ**を適用し、適用後直ちに `rm` でマーカーを削除する。
+4. 適用コミットのメッセージに承認の出典（日付・承認内容の要約）を記載する。
+
+> 出典: IMP-2026-029（obsidian-vault-setup 事象 1 ほか累計 3 回のデッドロック解消）。
```

## リスク

- 副作用: マーカー作成コマンドが許可リストに入ることで、承認なしの自己承認が技術的には
  可能になる → 現行ローカル運用でも同じ（ローカルの Claude も touch を実行できる）。
  信頼モデルは「手順の遵守 + コミット履歴・validate-agent-config による監査」で従来と同等。
  手順違反（承認出典のない構成変更コミット）は棚卸し・レビューで検出できる。
- 指示過多の懸念: 承認境界へ約 10 行追加のみ。デッドロック起因の往復（リモート → ローカル
  再適用）が消えるため正味の運用コストは減る。

## 評価方法

- スモーク: リモートセッションで（ユーザー承認発言 → touch → 保護ファイル 1 件編集 →
  rm → コミット）の一連が guard にブロックされず完走すること。
- 実運用確認: 「ローカル適用待ち」滞留中の 4 ファイル（IMP-2026-025 の SKILL.md 2 件 +
  IMP-2026-026 の Hook / close-session）が本手順で適用できること。
- 観測軸: 不要作業量（適用待ち滞留・セッション往復の減少）。
