## 背景

`pnpm --filter @cookpit/web dev:pglite` + Playwright による実画面確認の自動化が、meal-plan-screens
（MB 8 項目）と shopping-list-screens（MB 12 項目 live PASS）の 2 タスク連続で成功した（成功
パターンの複数タスク再現＝昇格条件充足）。しかし各タスクで判明した個別コンポーネント固有の
落とし穴（searchbox ロール・Base UI SelectField のトリガー+popup 操作・Chromium executablePath
明示・スクリプト設置場所）は Skill に反映されず、candidate ファイルに散在している。あわせて
事象 4 で PWA/Service Worker が BLOCKED になる**具体的技術的理由**（本番ビルドの pglite dead code
除去）が言語化され、毎回のコードリーディングを省ける定型文候補となった。

## 観測事象（根拠）

| 事象                                           | 再現タスク                                | 累計回数 | 昇格条件                                      |
| ---------------------------------------------- | ----------------------------------------- | -------- | --------------------------------------------- |
| dev:pglite + Playwright 実画面確認自動化の成功 | meal-plan-screens / shopping-list-screens | 2        | 成功パターンが複数タスクで再現した            |
| PWA/SW BLOCKED の具体理由の言語化              | shopping-list-screens（事象 4）           | 1        | 単発（低コストな軽微追記として事象 3 に同梱） |

## 原因

**恒久的な構造的要因（成功手順と既知の落とし穴が Skill に未集約）**。自動化の一般化可能な型
（dev:pglite 起動 → role/label セレクタ → PASS/BLOCKED/FAIL 出力）と、UI ライブラリ固有の例外は
別物だが、どちらも Skill に無いため各タスクで再発見コストが生じている。事象 4 の PWA 理由も、
Skill の「環境制約の扱い」節が一般論（PWA は BLOCKED）にとどまり具体理由が無かった。

## 変更案

**1 Skill・追加のみ（非破壊）**。過剰肥大を避けるため、(a) 一般原則（自動化の型）と (b) ライブラリ
固有の例外（表形式で簡潔に）を分離し、後者は表で最小限にする。(c) PWA 理由は既存「環境制約の
扱い」節への 1 バレット追記にとどめる（新規節を作らない）。

## 変更差分

```diff
# .claude/skills/manual-browser-verify/SKILL.md  手順 4「環境制約の扱い」に 1 バレット追記
    - BLOCKED 項目は該当コードのコードリーディングで実装の正しさを確認し、
      「コード確認済み・DB 接続があれば PASS 見込み」と補足する
      （実例: `logs/2026-06-26.md` — 404 とキャンセルは live 確認、初期値/保存はコード確認で補完）。
+   - **PWA / Service Worker が BLOCKED になる具体理由**: 本番ビルドは DB クライアント
+     （`apps/web/src/db/client.ts`）の pglite 分岐を dead code として除去する設計（Neon 経路の保護）
+     のため、リモート環境で「本番ビルド + PGlite」の組み合わせが原理的に作れない。毎回コードを
+     読み直さず BLOCKED 理由としてこれを引用してよい（shopping-list-screens 事象 4）。

# 「## 良い例（実績）」の直前に 2 節を新設
+## 自動化の型（dev:pglite + Playwright）
+
+2 タスク連続で有効だった手順の型（meal-plan-screens → shopping-list-screens）。個別画面に依存しない:
+
+1. `pnpm --filter @cookpit/web dev:pglite` で DB あり dev サーバーを起動する。
+2. Playwright スクリプトで対象 URL を開き、**role / label ベースのセレクタ**で操作する
+   （CSS セレクタや文言直書きより壊れにくい）。
+3. 各確認項目を **PASS / BLOCKED(理由) / FAIL** として機械的に出力する。
+4. スクリプトは `apps/web/scripts/` 配下に置く。Chromium は `executablePath` を明示する
+   （同梱 Chromium のパス解決がリモートで失敗しうるため）。
+
+## UI ライブラリ固有の操作パターン（既知）
+
+一般原則（role/label ベース）で足りない、ライブラリ固有の落とし穴だけを表にする（肥大化させない）:
+
+| 対象 | 操作パターン |
+| --- | --- |
+| 検索入力 | `getByRole('searchbox')`（`textbox` ではない。meal-plan-screens 事象 3） |
+| Base UI `SelectField`（店舗変更等） | ネイティブ `<select>` ではなくトリガー button + popup。`getByLabel(ラベル).click()` → `getByRole('option', { name })`。`selectOption()` は使えない（shopping-list-screens 事象 3） |
+| Chromium 起動 | `executablePath` を明示する（同梱パスの自動解決に依存しない） |
+| スクリプト設置場所 | `apps/web/scripts/`（`setup-pglite-dev.mjs` と同ディレクトリ） |
```
