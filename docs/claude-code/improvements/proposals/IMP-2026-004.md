対照的に `contract-validation-change`（契約変更が題意で contract-designer 起動が明確）はスコア 5。
**起動条件が明示されているケースだけが高得点**で、orchestrator 裁量に委ねられる L2 のフィールド
追加・スキーマ変更系で 3 に沈む、という構造が 2 回の採点で再現している。

## 原因

**恒久的・構造的原因。** 現在の orchestration-policy.md と orchestrator.md は contract-designer を
「契約の新設・変更があるとき」起動と書くが、**「契約変更」の判定基準が定性的**で orchestrator の
裁量に委ねられている。とくに L2 の「API フィールド追加（Zod スキーマに任意項目を 1 つ足す）」は、
一見「軽微」に見えて contract-designer を呼ばずに architecture-designer 止まりで流れうる。その結果、
nullability・後方互換・エラー形式・契約テスト方針といった契約品質の核心が設計書に落ちず 3 に沈む。

判定が定性的なため、`packages/api-contract`（Zod）・Drizzle スキーマ・Hono RPC 型に**フィールドの
追加/変更/削除・必須⇔任意・nullability の変更**が入るケースで「必ず起動する」保証がない点が要因。

## 変更案

最小変更で最大効果を狙う。**起動条件の文言を、裁量依存から「客観的に判定できる必須トリガー」へ
具体化**する。指示の純増を避けるため、既存の曖昧な一文を**置き換える**（追加でなく置換・明確化）。

- orchestration-policy.md に **「contract-designer の必須起動トリガー」** を小節として定義し、
  次のいずれかに該当したら**レベルに関わらず必ず起動**すると明記する:
  1. `packages/api-contract`（Zod）のスキーマにフィールドの追加/変更/削除がある。
  2. Drizzle スキーマ（DB 契約）に列・制約・型の追加/変更/削除がある。
  3. Hono RPC の入出力型 / 層をまたぐ DTO の形が変わる。
  4. フィールドの必須⇔任意・nullability・enum 値・最大長などバリデーション境界が変わる。
  5. エラー形式・冪等性キーなど外部に観測される契約が変わる。
- 同時に**起動しない条件**（過剰工程の禁止）も明記して限定する: 契約の形が一切変わらない内部実装
  リファクタ・コメント/ドキュメントのみ・UI 文言のみ等。これにより「必ず起動」を強める一方で
  不要起動を抑え、Agent 呼び出し効率・トークン効率の悪化を防ぐ。
- orchestrator.md の委譲フロー早見にある〔契約変更あれば contract-designer〕の注記を、上記
  トリガー定義への**参照に置き換える**（同じ基準を二重定義しない＝単一情報源化）。

> CLAUDE.md・Hook・セキュリティルール・contract-designer 自身の責務には触れない。変更は委譲フロー
> （= どの条件で Subagent を起動するか）の規定であり、orchestrator の責務・委譲方針に関わるため
> 承認区分は **人間承認必須**。proposal に差分を書くにとどめ、本適用しない。

## リスク

- 副作用: contract-designer の起動回数が増えるケースがある（L2 の Zod フィールド追加で必ず起動）。
  これは契約品質の改善が目的であり意図どおりだが、**不要起動はトークン効率・Agent 呼び出し効率を
  悪化させうる**。そのため「起動しない条件」を同時に明記し、形が変わらない変更では従来どおり
  起動しない設計とした（純増ではなく条件の明確化）。
- 指示競合の懸念: orchestrator.md と orchestration-policy.md で基準を二重定義すると将来の更新で
  乖離する。これを避けるため orchestrator.md は policy への**参照に置き換え**、基準の単一情報源を
  policy 側に一本化した（指示の純増を抑える方向）。
- 評価の限界: 契約変更を伴う実タスクは未発生。external 連携・実コード実行を伴わない定性評価である。

## 評価方法

- 対象 eval ケース:
  - `.claude/evals/cases/api-field-addition.md`（L2 の Zod フィールド追加 → 必須起動で契約品質向上を確認）
  - `.claude/evals/cases/contract-validation-change.md`（起動条件が元々明確な対照群 → 維持＝悪化なしを確認）
  - `.claude/evals/cases/refactoring.md`（契約の形が変わらない L2 → 不要起動が起きていないか＝
    Agent 呼び出し効率・トークン効率・不要作業量の悪化が無いかの回帰確認）
- 観測軸: 契約品質（改善期待）/ Agent 呼び出し効率・トークン効率・不要な作業量（悪化しないこと）/
  影響範囲調査・設計品質（中立〜微増）。
- 判定ルール: improvement-cycle.md §回帰評価。**1 軸でも悪化があれば不採用。** 過剰起動による
  Agent 呼び出し効率・トークン効率の悪化を必ずチェックする。

## 評価結果

agent-evaluator のレポート: [../evaluations/IMP-2026-004.md](../evaluations/IMP-2026-004.md)。

- `api-field-addition`: 契約品質 3 → 4（+1）。L2 の Zod フィールド追加で contract-designer が必ず
  起動し、nullability・後方互換・エラー形式・契約テスト方針が設計書に落ちる。影響範囲調査 3 → 4
  （契約 → ドメイン → Repository の同期漏れ検出が向上）。Agent 呼び出し効率 4 → 4（必要な 1 本の
  追加起動であり過剰ではない）。悪化なし。
- `contract-validation-change`（対照群）: 契約品質 5 → 5（維持）。元々起動条件が明確なため変化なし。
  悪化なし。
- `refactoring`（不要起動チェック）: 契約品質 4 → 4・Agent 呼び出し効率 4 → 4・トークン効率 4 → 4・
  不要作業量 4 → 4。「起動しない条件（契約の形が変わらない）」が機能し contract-designer の
  不要起動が起きない。悪化なし。

**全ケース・全軸で悪化ゼロ。** 改善は契約変更を伴う L2 ケースに限定して現れ、契約不変のリファクタ
では不要起動なし。「必須トリガー」と「起動しない条件」の両建てが意図どおり機能した（評価レポート参照）。

## 採用または却下理由

**人間承認待ち（proposal どまり）。** 本提案は委譲フロー（Subagent 起動条件）の規定変更であり、
orchestrator の責務に関わるため承認区分「人間承認必須」に該当する。回帰評価で悪化ゼロのため
manager としては採用を推奨するが、本適用と `accepted/` への移動は**人間承認後**に行う。
1 軸でも悪化があれば不採用とし `rejected/` へ移す方針（今回の回帰評価では悪化なし）。
