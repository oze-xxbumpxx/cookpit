## 観測した事象（複数可）

### 事象 1: 本番の接続方式を検証しないまま基盤変更をマージし、本番障害が 3 回起きた

- **種類**: 手戻り / 本番障害
- **観測した事象**: 自動試験は PGlite のみで通っていたが、本番では 3 回落ちた。
  (1) PR #164 の WebSocket `Pool` 導入で**読み取りごと全断**（`/api/health` が `db:"error"`・約 16 秒）→ PR #168 でロールバック。
  (2) PR #171 再導入後、`globalThis` に持った Pool の使い回しで `Connection terminated unexpectedly` → PR #173。
  (3) PR #173 後、`ws` の `bufferutil` が空モジュールにエイリアスされ 48 バイト超のフレームで
  `b.mask is not a function` → 未捕捉例外でプロセス落ち → PR #174。
- **発生回数**: このタスク内 **3 回**（いずれも本番）
- **対象タスク**: uow
- **原因仮説**: 完了条件（`definition-of-done.md`）が lint / type-check / test の 3 ゲートで、
  **外部インフラ依存（DB ドライバ・接続方式・バンドル結果）の検証段を持たない**。
  PGlite はドライバも接続方式もバンドルも模擬しないので、この層の欠陥は原理的に検出できない。
- **改善案**: 「DB ドライバ・接続方式・`next.config.ts` のバンドル設定・サーバー実行時依存の追加」に
  触れる変更を対象に、**Preview デプロイでの読み取り + 書き込み一巡**を完了条件に加える。
  対象判定は変更ファイル（DB クライアント生成箇所 / `next.config.ts` / 依存追加）で機械的に絞れる。
- **変更対象**: docs/claude-code/definition-of-done.md（必要なら quality-gates Skill の対象条件）
- **想定される副作用**: Preview 一巡は時間がかかる。対象条件を広く取ると L1 の小変更まで重くなる。
  条件を「上記ファイル群に触れたときだけ」に狭く保つ必要がある
- **評価方法**: 次にドライバ・バンドル設定へ触れるタスクで Preview 一巡が実行されるか。
  併せて `.claude/evals` の代表タスクで工程増による悪化がないか agent-evaluator で確認する
- **昇格判定**: **昇格条件を満たす**（memory-policy「本番障害につながった」。3 回発生）→
  proposal 起票を推奨。ただし IMP 採番と適用は agent-improvement-manager の横断分析と
  PR レビューを経ること（早期昇格の原則禁止・IMP-2026-030 の趣旨に反しない範囲で）

### 事象 3: フラグで実行経路が分岐するのに、どちらを通ったか外形から判定できなかった

- **種類**: 手戻り
- **観測した事象**: `DB_WRITE_TRANSACTION` で読み取り経路と書き込み経路が分岐するが、
  `createTxConnection` に成功ログが無く「WS 経路が実際に走ったか」をログで一意に判定できない。
  08-16 はローカル `main` が origin より 8 コミット遅れていたことに気づくまで、本番で
  動いているコードの実体を誤認したまま切り分けを進めた。
- **発生回数**: このタスク内 1 回
- **対象タスク**: uow
- **原因仮説**: フィーチャーフラグで経路が変わる設計に、経路を一意に示す観測点を設けていない
- **改善案**: フラグで実行経路が変わる実装は、**経路を一意に判定できるログまたはヘルスチェック項目**を
  設計時に必須にする（本件は継続課題「`createTxConnection` に成功ログ 1 行」として残っている）
- **変更対象**: （まだ未定）create-design-document のチェックリスト候補
- **想定される副作用**: ログが増える。秘密情報を載せない範囲に限定する必要
- **評価方法**: 次にフラグ分岐を入れるタスクで、設計書に観測点の記述があるか
- **昇格判定**: Memory 留め（単発。同種が再発したら候補へ）
