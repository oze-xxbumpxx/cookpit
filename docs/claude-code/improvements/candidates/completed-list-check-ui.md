## 観測した事象

### 事象 1: サーバーのガードに対応する UI 側の抑止が設計・試験計画から漏れ、しかもテストが誤った挙動を固定していた

- **種類**: 逃げた欠陥（escaped defect・ユーザー報告）
- **観測した事象**: `ShoppingList` の `check` / `uncheck` / `markAsBought` / `reassignStore` は
  いずれも `assertActive` を持ち、`completed` のリストでは 422 を返す。しかし
  `ShoppingItemRow` は完了後もこれら 3 つの操作要素を操作可能なまま描画していた。
  さらに**テスト CB-11「完了後も item のチェックと店舗再割当 UI を残す」が、この誤った挙動を
  明示的に固定していた**（PR #109 で追加）。ユーザーが実機で触るまで検出されなかった。
- **発生回数**: このクラス（サーバーの状態ガード ⇔ UI の操作可否の不一致）は **1 回目**。
  ただし「`shopping-list-client` 系の UI 状態が試験計画から漏れる」という**より広いクラス**では
  累計 3 回目（shopping-list-screens 事象 2 / project-refactoring 事象 1 に続く）。
- **対象タスク**: completed-list-check-ui（今回）
- **原因仮説**: 設計書の「フロントエンド設計」節には**画面に何を出すか**を書くが、
  **ドメインのガードによって出してはいけない操作は何か**を書く欄が無い。
  ドメイン側の `assertActive` を追加した PR #109 の時点で、対応する UI 側の抑止が
  設計・試験の観点に載らなかった。
  加えて「1 集約 = 1 ステータス機械」を持つ画面では、**ステータス × 操作の可否表**が
  自然な試験観点になるが、正常系・異常系・境界値という既存の分類には載りにくい。
- **改善案**: 設計・試験の観点に「**ドメインのガード（`assertXxx` / 状態遷移の前提）に対して、
  UI 側で対応する操作が抑止されているか**」を加える。具体的には、Application 層の UseCase が
  投げ得る 422 系エラーを列挙し、それぞれについて「UI がその操作を出しているか／出すべきか」を
  1 行で判定する。ステータスを持つ集約の画面では**ステータス × 操作の可否表**を試験計画に置く。
- **変更対象**: `.claude/skills/create-test-plan/SKILL.md` および
  `.claude/skills/create-design-doc/SKILL.md`（フロントエンド設計節）
- **想定される副作用**: ステータスを持たない画面では不要な項目になる。
  適用条件を「対象 UseCase が状態ガード由来の 422 を投げ得る画面のみ」と明記する必要がある。
- **評価方法**: 次にステータスを持つ集約の画面を触るタスクで、設計書または試験計画に
  可否表が現れるか。および同種のユーザー報告が出るか。
- **昇格判定**: **昇格条件の判断を manager に委ねる**。単体のクラスとしては初回だが、
  (a) **ユーザーが実機で発見した escaped defect** である点、(b) 既存の事象 1 系
  （shopping-list-client 系の UI 状態が試験計画から漏れる）と**同一ファイル群での 3 回目**で
  あり、`create-test-plan` という同じ変更対象を指している点を重く見るなら昇格。

### 事象 2: テストが仕様を守った結果として不具合が残った

- **種類**: Agent 間の認識不一致（テストと実装の整合は取れているが、仕様自体が誤り）
- **観測した事象**: CB-11 は「完了後も UI を残す」を**正しく**固定しており、テストは緑だった。
  つまりテストの存在は「実装が仕様どおりか」は保証したが、
  「**その仕様がサーバー側の制約と整合するか**」は保証していなかった。
  修正では CB-11 の書き換え自体が成果物になった。
- **発生回数**: このタスク内 1 回（過去の candidate に同種の記録なし）。
- **対象タスク**: completed-list-check-ui
- **原因仮説**: Presentation 層のテストは API クライアントをモックするため、
  **サーバーが実際にどう応答するかを知らないまま**「UI がその操作を出す」ことを固定できる。
  モックが常に `ok: true` を返す限り、サーバーが 422 を返す状態でも緑になる。
- **改善案**: Client Component のテストで書き込み系の操作を扱うとき、
  **対応する API ルートのテスト（`src/server/routes/*.test.ts`）で 422 になる条件を確認し、
  その条件下で UI がどう振る舞うべきかを 1 ケース書く**。今回でいえば
  `shopping-lists.checked.test.ts` に「completed のとき 422」のケースが既にあったため、
  突き合わせれば設計時に気づけた。
- **変更対象**: `.claude/skills/create-test-plan/SKILL.md`（事象 1 と同じ変更対象）
- **想定される副作用**: 試験計画の作成時に API ルートのテストを読む手間が増える。
- **評価方法**: 次の画面タスクで、試験計画に「対応 API の異常系との突き合わせ」が現れるか。
- **昇格判定**: **Memory 留め（昇格せず）**。ただし事象 1 と同根であり、
  manager が事象 1 を昇格させる場合は同じ変更にまとめるのが妥当。

### 事象 3: ユーザー報告を「直前の変更の回帰」と決めつけず、先に切り分けた

- **種類**: 成功手順
- **観測した事象**: 報告のタイミングが PR #110（大規模リファクタリング）のマージ直後だったため
  回帰を疑う状況だったが、まず dev:pglite + API 直叩きで**現象そのものを再現**し、
  次に分岐元 `590dfc2` の実装にも同じガードがあることと、`assertActive('uncheck')` が
  PR #109（`ccb23d6`）由来であることを確認して、**リファクタリングとは無関係**と特定した。
  この切り分けを設計書の「回帰ではないことの確認」節に残した。
- **発生回数**: このタスク内 1 回。
- **対象タスク**: completed-list-check-ui
- **原因仮説**: 直前に大きな変更を入れていると、報告された不具合をその変更のせいだと
  仮定しやすい。仮定のまま修正に入ると、無関係な箇所を触ってしまう。
- **改善案**: バグ報告を受けたときの初動を「(a) 再現、(b) `git log -S` / 分岐元との比較で
  混入時点を特定、(c) 意図された仕様か否かの判定」の順で手順化する。
  今回は (c) で ADR-0009 に当たり、「意図された制約であり UI 側が誤り」と判定できた。
- **変更対象**: （まだ未定。単発のため Memory 留め）
- **想定される副作用**: なし（手順の追加のみ）。
- **評価方法**: 次のバグ報告タスクで、修正前に混入時点の特定が行われるか。
- **昇格判定**: **Memory 留め（昇格せず）**。

### 事象 4: 回帰テストを「旧挙動に戻して落ちること」まで確認した（2 回目）

- **種類**: 成功手順（**再現**）
- **観測した事象**: 新規テスト追加後に `readOnly` の導出を `false` に、422 の出し分けを
  無効に戻した状態でテストを実行し、**CB-11 / CB-12 / CB-14 / CB-15 の 4 件が FAIL** すること、
  および CB-13 / CB-16（「従来どおり動く」ことの確認）は両方で PASS することを確認した。
- **発生回数**: 累計 **2 回目**。1 回目は project-refactoring 事象 2（S1 回帰テスト UAA-08 を
  `git stash` で旧実装に戻して失敗確認）。
- **対象タスク**: completed-list-check-ui（今回）/ project-refactoring（2026-07-25）
- **原因仮説**: バグ修正・レビュー指摘対応では、追加テストが新実装で通ることは自明に近く、
  「旧挙動で落ちる」ことこそが回帰テストとしての価値を担保する。
  今回は「どのケースが両方で PASS するか」も併せて記録することで、
  「従来どおり動くことの確認」と「不具合を捉えるテスト」を区別できた。
- **改善案**: バグ修正で回帰テストを足すときの手順として明文化する。
  対象箇所だけを旧挙動に戻して実行 → FAIL するケースを記録 → 復帰、の 3 手順。
- **変更対象**: `.claude/skills/quality-gates/SKILL.md` または `create-test-plan`（未定）
- **想定される副作用**: 手順が 1 段増える。対象は「回帰テストを新規に足すとき」に限られる。
- **評価方法**: 次のバグ修正タスクで、回帰テストの失敗確認が行われたかをログで確認する。
- **昇格判定**: **昇格条件の判断を manager に委ねる**。成功パターンの 2 回目で、
  memory-policy.md の「繰り返す → 改善候補」に該当する。

### 事象 5: 必須 Props にして伝播漏れを型エラーで検出させた

- **種類**: 成功手順
- **観測した事象**: `readOnly` を `ShoppingItemRow` / `StoreGroup` の**必須** Props にしたところ、
  `pnpm type-check` が伝播先（クライアント 1 + テスト 2）を漏れなく列挙した。
  `readOnly?: boolean` にしていたら `StoreGroup` の中継漏れは型で捕まらず、
  「一部の行だけ操作可能に残る」不具合になり得た。設計書のリスク表に挙げていた懸念が
  型で潰れた形になる。
- **発生回数**: このタスク内 1 回。
- **対象タスク**: completed-list-check-ui
- **原因仮説**: 「既存呼び出しを壊さないため任意にする」が既定の発想になりやすいが、
  **壊れることが検出したいこと**である場合は必須にするほうが正しい。
  影響範囲が小さい（呼び出し 3 箇所）ことを先に確認できたため採用できた。
- **改善案**: 横断的な状態（読み取り専用・権限・ロック）を親から子へ流す Props は、
  呼び出し箇所が数箇所なら必須にして型で伝播を強制する。
  実装計画のリスク表に「伝播漏れ」を挙げたときの標準の対処にする。
- **変更対象**: `.claude/rules/presentation-layer.md`（未定）
- **想定される副作用**: 呼び出し箇所が多い Props に適用すると修正量が増える。
  「数箇所」という適用条件が要る。
- **評価方法**: 次に親子間で横断的な状態を流すタスクで、必須/任意の判断根拠が記録されるか。
- **昇格判定**: **Memory 留め（昇格せず）**。初観測のため再現を待つ。

### 事象 6: 実装計画の完了条件を満たせず、差分として明記した

- **種類**: 手戻り（軽微）
- **観測した事象**: 実装計画ステップ 1 の完了条件を「既存 8 件が**無修正で**通る」と書いたが、
  `ApiResponseLike` に `status: number` を必須追加したため、テスト側のレスポンス模擬に
  `status` の付与が必要になった。アサーションと期待値は無変更。
  計画を書き換えず「実装との差分」節を追記して残した。
- **発生回数**: このタスク内 1 回。過去に project-refactoring 事象（観点 C の設計前提外れ）で
  同様の「設計 vs 実装の差分を追記で残す」運用を採っており、**運用としては 2 回目**。
- **対象タスク**: completed-list-check-ui
- **原因仮説**: 「無修正で通る」という完了条件は、インターフェースに必須フィールドを足す変更と
  そもそも両立しない。完了条件を書く時点でインターフェース変更の有無を見ていなかった。
- **改善案**: 共通ヘルパのインターフェースを広げる計画では、完了条件を
  「既存テストが**挙動を変えずに**通る」と書く（模擬の形の追随は許容し、
  アサーションの変更は許容しない）。
- **変更対象**: `.claude/skills/create-implementation-plan/SKILL.md`（未定）
- **想定される副作用**: なし。
- **評価方法**: 次のヘルパ拡張タスクで完了条件の書き方を確認する。
- **昇格判定**: **Memory 留め（昇格せず）**。
