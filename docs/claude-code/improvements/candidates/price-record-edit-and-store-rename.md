### 事象 2: `it.each` の範囲表記タイトルが試験 ID 追跡を破壊し、誤って Must 級の欠落を報告した

- **種類**: レビュー指摘（自己検出）/ ハーネスの検証手段の弱点
- **観測した事象**: 受け入れレビューで試験計画 102 件の ID を grep で機械照合したところ、
  `A-UPU-06/07/08` と `D-SRN-03` が未実装と出た。原因は `it.each` のタイトルが
  `'A-UPU-05〜08: …'` / `'D-SRN-02/03: …'` という**範囲表記**だったため、個別 ID の文字列検索に
  一致しなかったこと（実体は実装・pass 済み）。Orchestrator は一次結果をユーザーへ
  「Must 級の欠落」として報告した後、訂正することになった。修正の一次対応
  （`'A-UPU-%s'` + `['05', …]`）も**不十分**で、`%s` の実行時展開はソースコードに ID 文字列を
  残さないため grep で追跡できないままだった。最終的に fixture に ID 全体を literal で持たせて
  解決した（「直した」と思った時点で再検証し発覚）。
- **発生回数**: 1 回目。ただしレビュー記録内で N-1 として「試験計画の ID がすべて実装されているか
  機械的に照合するスクリプトが無い」ことが既に指摘されており、本タスクで使った
  「試験計画から ID 抽出 → 実テストコードの ID と `comm` で差分」という手順は再利用可能。
- **対象タスク**: price-record-edit-and-store-rename
- **原因仮説**: このプロジェクトは試験 ID で要件 ⇔ 試験 ⇔ 実装を追跡する運用だが、
  `it.each` によるパラメータ化テストの命名規約（範囲表記を許すか、ID を literal で
  必ず持たせるか）が定まっていない。加えて、この照合を毎回人手（grep）で行っているため、
  今回のような誤検出・誤報告のリスクが常に残る。
- **改善案**: （評価: **候補として具体化する価値がある**と判断する。理由は 3 点 —
  (1) 本タスクで実際にユーザーへの誤報告という実害が出た、(2) 照合手順は今回のレビューで
  実装済みで自動化コストが低い（抽出 + `comm` のラッパースクリプト化で足りる）、
  (3) ID による追跡はプロジェクト全体の慣習であり毎回の L2/L3 レビューで再利用できる）。
  具体化する場合は 2 段構え: (a) `it.each` のタイトル規約として「範囲表記を禁止し、
  fixture に ID を literal で持たせる」旨を明文化する軽微な追記、(b) 試験計画の ID 一覧と
  実テストコードの ID 出現を機械照合するスクリプト（`check-test-id-coverage.mjs` 相当）を
  `quality-gates` か `validate-deliverables` へ追加する、の両輪。(a) は変更が小さく客観性が
  高いが、(b) はスクリプト新規実装でありそれなりのコストがある。
- **変更対象**: （まだ未定）`.claude/skills/create-test-plan/SKILL.md` または
  `.claude/rules/coding-standards.md` §テスト（(a)）/ `.claude/scripts/`（新規・(b)）
- **想定される副作用**: (b) を Hook 化して毎回強制すると、ID 体系を持たない軽微なテスト追加でも
  実行され無駄になる。L2/L3 の受け入れレビュー工程に限定する必要がある。
- **評価方法**: 次の L2/L3 レビューで、試験 ID の機械照合を行った際に誤検出（範囲表記・
  パラメータ展開による偽陰性）が発生しないかを確認する。
- **昇格判定**: **Memory 留め（昇格せず）**。IMP-2026-030「早期昇格の原則禁止」により 1 回目での
  昇格は見送るが、誤ってユーザーへ Must 級の欠陥を報告するという実害の大きさを踏まえ、
  **次回同型（範囲表記・パラメータ展開による ID 追跡失敗）が起きたら 3 回を待たず昇格を推奨**する
  （shopping-list-price-comparison 事象 1 と同じ「silent failure 系は早期昇格対象」の扱いに倣う）。

### 事象 3: 実画面確認で false PASS が再発した（前タスクの学びの直接再発・二重発生）

- **種類**: 手戻り（自己検出）/ **再発**
- **観測した事象**: MB-03（内容量の単位を変えたときの単価表示）の実画面確認で 2 段階の
  誤判定が起きた。(a) 試験計画の前提記述「編集前の単価表示は 100円/100g」が誤りで、実際は
  `kg` 記録の表示基準が `1kg`（`product-format.ts` の `WEIGHT_BASIS` が `kg` に `factor: 10`）
  のため「1,000円/1kg」だった。前提を検証しない判定にしていたため、一度は PASS が出た。
  (b) PGlite の dev DB を起動中に再シードしたため、dev サーバーが削除済みディレクトリの
  ハンドルを掴んだまま古い状態を返し続け、**前提を満たしていないのに PASS に見えた**
  （実際に一度誤判定した）。いずれも前提の検証を PASS 条件に含めることで是正した。
- **発生回数**: **shopping-list-price-comparison 事象 1 の直接再発（累計 2 回目）**。前タスクの
  候補ファイルは「確認項目の前提条件を満たすデータを用意する手順が無い」「存在確認中心の
  アサーションは前提を外すと空振りがそのまま PASS になる」という原因仮説とともに
  「**次回再発で 3 回を待たず昇格を推奨**」と明記していた。本タスクはそのトリガーに該当する。
  加えて本タスク内で (a)(b) の 2 つの異なる原因（試験計画の前提記述ミス／環境の陳腐化データ）が
  それぞれ独立に false PASS を生んでおり、同じ失敗モードが 1 タスク内でも複数経路から起きる
  ことを示している。
- **対象タスク**: price-record-edit-and-store-rename（今回・MB-03）/
  shopping-list-price-comparison（前回・MB-04）
- **原因仮説**: 前回と同じ — `manual-browser-verify` の「自動化の型」が確認項目の列挙・
  セレクタ規約・PASS/FAIL 出力までは規定するが、**前提条件を満たすデータの用意**と
  **前提が崩れていないことの確認（ネガティブコントロール）**を手順化していない。
  今回はさらに新しい原因（(b) dev サーバー起動中の DB 再作成によるハンドルの陳腐化）が
  加わった。これは前回の原因仮説（データの選択ミス）とは異なる、**環境操作手順**に起因する
  false PASS であり、同じ症状（前提を満たさないのに PASS）でも原因のバリエーションが増えている。
- **改善案**: 前回提案（確認項目と前提条件を対で列挙し、前提を満たさないデータでの FAIL を
  一度確かめてから PASS を採るネガティブコントロールを追加）が**採用されていれば今回の (a) は
  防げていた可能性が高い**（前提記述の誤りを検証工程で検出できたはず）。これに加え、
  (b) 由来の再発防止として「PGlite の dev DB を再シードするときはサーバーを止めてから行う」
  という手順上の注意も `manual-browser-verify` Skill か関連ドキュメントへの追記候補とする
  （レビュー記録にはすでに注記済み・実行可能な形での定着はまだ）。
- **変更対象**: `.claude/skills/manual-browser-verify/SKILL.md`
- **想定される副作用**: 前回と同じ（確認 1 項目あたりの手数が増える）。(b) の手順注意は
  DB 再シードを伴う実画面確認に限定されるため副作用は小さい。
- **評価方法**: 次の L2/L3 タスクで MB 系項目を実施し、(a) 前提条件の明記とネガティブ
  コントロールが実施されているか (b) DB 再シード時にサーバー停止の手順が踏まれているか を確認する。
- **昇格判定**: **昇格条件を満たす**。前タスクが明記した早期昇格トリガー（silent failure の
  再発）が成立した。次に manager が横断分析する際、shopping-list-price-comparison 事象 1 と
  本事象を統合し、`manual-browser-verify` Skill への追記として proposal 化することを推奨する。

### 事象 4: レビュー差し戻し以外の「一次修正が不十分だった」自己検出（技術的教訓）

- **種類**: 実装の技術的教訓（自己検出・小粒）
- **観測した事象**: 事象 2 の一次修正（`it.each` タイトルを `'A-UPU-%s'` + 引数配列 `['05', …]`
  の形にする）は、`%s` の展開が実行時に起きるためソースコード上には ID 文字列
  （`A-UPU-05` 等）が現れず、grep による追跡が引き続き失敗する状態のままだった。
  「直した」と思って再検証したところ発覚し、fixture 側に ID 全体を literal で持たせる形へ
  変更して解決した。
- **発生回数**: 1 回目
- **対象タスク**: price-record-edit-and-store-rename
- **原因仮説**: 「テストのタイトルに ID を含める」という修正方針は正しかったが、
  「grep で追跡できる」という制約（静的な文字列としてソースに現れる必要がある）を
  意識せずに `%s` テンプレートで済ませてしまった。修正の意図（人間が読んだときに ID が
  分かる）と検証手段の性質（静的解析）の両方を満たす必要があることの見落とし。
- **改善案**: 事象 2 の改善案 (a) に統合する — 「`it.each` の ID は fixture 側に literal で
  持たせ、タイトルへ `'%s'` で展開する」という具体的な書き方を明文化すれば、この二度手間は
  防げる。独立した変更対象は設けない。
- **変更対象**: 事象 2 に統合（独立の変更対象なし）
- **想定される副作用**: なし
- **評価方法**: 事象 2 と同一
- **昇格判定**: **Memory 留め（昇格せず）**。1 回目・事象 2 の付随的教訓として記録に留める。

### 事象 5: 姉妹コンポーネント間で縮退処理（エラーハンドリング）の有無が試験計画から漏れた（累計 3 回目相当）

- **発生回数**: 「非同期処理・補助データ取得まわりの縮退観点が試験計画から漏れる」という
  広いテーマで見ると **3 件目**: ① shopping-list-screens 事象 2（refetch 成功時のエラー

  （姉妹コンポーネント）と同じ責務を持つ場合、既存側の観点（エラー処理・縮退動作など）を
  引き写しで確認する」というチェック手順が無い。今回は `StoreRenameDialog` に SRD-05 という
  前例が**同じタスク内**にありながら、`PriceRecordEditDialog` 側の試験計画作成時に参照されず、
  レビュー段階まで見落とされた。
- **改善案**: `create-test-plan` Skill に「新設コンポーネントに類似の既存/姉妹コンポーネントが
  ある場合、その観点一覧（特に縮退・エラー処理）を突き合わせるチェック項目」を追加する案。
  project-refactoring 事象 1（同一ファイル内の refetch 状態遷移）とは対象範囲が異なるため、
  **同一の変更として統合するか、別々の観点として追加するかは manager の判断**に委ねる
  （両者とも「試験計画作成時に "何を見るべきか" のチェックリストが弱い」という同じ根っこを持つ
  可能性がある）。
- **変更対象**: `.claude/skills/create-test-plan/SKILL.md`
- **想定される副作用**: 「類似コンポーネントとの突き合わせ」を機械的に強制すると、
  類似性の判断自体が主観的になり、関係の薄いコンポーネント同士まで比較させて工数が増える恐れ。
  「同一タスク内で新設する複数コンポーネントが同じ責務カテゴリを持つ場合」に限定するなどの
  適用範囲の絞り込みが必要。
- **評価方法**: 次に複数の類似コンポーネントを同時に新設する L2/L3 タスクで、
  試験計画作成の時点で観点の突き合わせが行われ、レビューでの同種 Should 指摘が減るかを確認する。
- **昇格判定**: **manager 判断を推奨**。上位テーマ（縮退・エラー処理観点の脱落）としては
  3 件目に達しており「Reviewer から同種の重大指摘を複数回受けた」に該当しうるが、

### 事象 6: TDD 志向でワークフローを「並行 → 直列」に組み替えた（プロセス変更・ユーザー指摘）

- **種類**: Agent 間認識不一致（というより Orchestrator ↔ development-workflow.md の既定との不一致）
  / ユーザー修正
- **観測した事象**: development-workflow.md の既定どおり「実装計画 ∥ 試験計画」を並行で起動した
  ところ、ユーザーから「テスト駆動ちっくに行いたいので、テスト設計後に実装設計に移る？」と
  指摘され、起動済みの実装計画 Agent を停止し、試験計画 → 実装計画の直列构成に組み替えた。
  結果、実装計画の各ステップが試験 ID を参照する Red → Green 構成になり
  （実装計画書冒頭に「【最重要】本計画の構成方針（TDD・ユーザー指示 2026-08-05）」として明記）、
  TDD の Red が各ステップで実際に確認された（Step 1: 12 件失敗 → 402/402 等）。
- **発生回数**: 1 回目（この形でのユーザー指摘は初めて明示的に記録された）
- **対象タスク**: price-record-edit-and-store-rename
- **原因仮説**: development-workflow.md の並行実行方針は「試験計画と実装計画はどちらも設計書を
  入力にするため独立に進められる」という前提に立つが、**TDD で進めたい場合は実装計画が
  試験 ID を参照する必要があるため、この独立性の前提が成立しない**。並行方針はテスト非依存の
  実装計画を書く場合には合理的だが、Red → Green 構成を明示的に求める場合には直列が必要になる、
  という条件分岐が orchestration-policy.md / development-workflow.md 側に無い。
- **改善案**: （提案止まり）「試験計画 ∥ 実装計画」の並行方針に、「TDD（Red → Green 明示構成）を
  志向する場合は試験計画 → 実装計画の直列に切り替える」という条件を追記する案。
  ユーザーが毎回明示的に指摘しなくても、L3 で TDD 志向かどうかを Orchestrator が要件定義や
  ユーザー原文から判断できるようにする余地がある。
- **変更対象**: （まだ未定）`docs/claude-code/development-workflow.md` §並行実行の指針
- **想定される副作用**: TDD 志向でない L2/L3 まで直列化すると、IMP-2026-007 が導入した並列化の
  効率改善効果を失う。「TDD を明示的に志向する場合のみ」という条件を厳密にする必要がある。
- **評価方法**: 次に TDD 志向のタスクが来たとき、ユーザーの指摘を待たずに Orchestrator が
  直列構成を提案できるかを確認する。
- **昇格判定**: **Memory 留め（昇格せず）**。1 回目。ただし実際に効果があった構成変更
  （Red の確認が全ステップで機能した）であり、次回同種の要求で再現すれば成功パターンとしての
  昇格も検討対象になる。
