## 観測した事象（複数可）

### 事象 1: 正典＋衛星要約の二重化構造が恒常的な同期漏れを生む（構造・P0）

- **種類**: Agent間認識不一致 / 構造
- **観測した事象**: 同一ルールが正典 + CLAUDE.md / Agent 定義 / Skill テンプレへ要約コピー
  され、正典修正のたびに衛星が漏れる。実績: 委譲フロー 5 文書不一致
  （skills-inventory-audit 事象 2）→ default export 例外の衛星 3 文書未同期
  （harness-post-020-audit 事象 1）→ orchestrator ポインタ漏れ（同事象 6）。
  IMP-2026-018（反映先一覧欄）は対症療法で、構造自体は残存。
- **発生回数**: 累計 3 クラス以上（上記）。構造的に再発し続ける。
- **対象タスク**: skills-inventory-audit / harness-post-020-audit / 本診断
- **原因仮説**: 「正典 + 衛星に要約コピー」という設計自体が N 文書同期を必然化している。
- **改善案**: 衛星側の要約コピーを**削除**し、正典への 1 行ポインタへ置換（追記ではなく削除。
  memory-policy の「改善＝削除・移動も含む」に合致）。対象: Agent 定義内のルール要約・
  CLAUDE.md の重複記述・Skill テンプレ内の規約抜粋。
- **変更対象**: CLAUDE.md / Agent 定義複数 / Skill 複数（人間承認必須）
- **想定される副作用**: 衛星単体で読んだときの自己完結性が下がる → ポインタ先を
  1 行で明示すれば実害は小さい
- **評価方法**: 次回正典修正時に同期対象がゼロであること。既存 eval ケースで
  ルール適用（default export 例外等）の判定が悪化しないこと。
- **昇格判定**: 昇格条件を満たす（累計 3 回超）→ proposal 起票推奨

### 事象 2: Orchestrator 多段 background 委譲が実運用で機能せず、補強機構だけが残る（構造・P0）

- **種類**: 手戻り / 構造
- **観測した事象**: 多段 background 委譲の「子 Agent の成果物なし完了」が 2026-07-19
  セッション 2 で 2 回発生し、メインセッションが Orchestrator 役を代行して専門 Agent を
  直接起動する方式へ切替。store-master 事象 1・meal-plan-screens 事象 4 に続く 3 系統目。
  一方、IMP-2026-007/008/009 で積まれた stop/resume・冪等再開・inflight-agents.json の
  複雑さはこの不安定さへの補強であり、orchestration-policy 肥大（harness-post-020-audit
  事象 8）の主因でもある。実際に安定稼働している型は
  「メインセッション直接指揮 + Codex 委譲実装」。
- **発生回数**: 累計 3 系統（昇格条件充足）
- **対象タスク**: store-master / meal-plan-screens / pantry-screens（2026-07-19）
- **原因仮説**: ハーネスの子エージェント通知配送の既知制約（backlog 申し送り参照）に対し、
  Cookpit 側の機構追加で対抗し続けた結果、最も複雑な部品が最も使われない状態になった。
- **改善案**: 「メインセッション直接指揮 + Codex 委譲」を正規ルートとして正典化し、
  多段 background 委譲と stop/resume 機構を凍結扱いに変更。orchestration-policy から
  該当節（stop/resume・通知回避策・既知制約の相当部分）を削減。
- **変更対象**: orchestration-policy.md / orchestrator.md / development-workflow.md
  （設計判断のため人間承認必須）
- **想定される副作用**: 将来ハーネス側の通知配送が改善された場合に機構を再導入する
  可能性 → 凍結（アーカイブへ移動）とし、削除はしない
- **評価方法**: 次の L2/L3 で正規ルートのみで完走すること。orchestration-policy の
  行数削減幅と、初見トレースで迷う箇所の減少（定性）。
- **昇格判定**: 昇格条件を満たす（累計 3 回）→ 提案止まり（運用方針の変更のため
  ユーザー採否が前提）

### 事象 3: 承認マーカーのリモートデッドロックで承認済み変更が滞留（P0・昇格充足済み）

- **種類**: プロセス観察 / 手戻り
- **観測した事象**: guard-dangerous のブロック格上げ（IMP-2026-013）以降、リモート環境では
  `.claude/state/config-change-approved` を Claude が作成できず、**人間承認済みの変更ですら**
  「ローカル適用待ち」で滞留する。IMP-2026-025/026 の SKILL.md・Hook 分が現に未適用。
  obsidian-vault-setup 事象 1 → 2026-07-18 → 2026-07-19（⑤再確認）で反復。
  backlog は既に「再発条件充足・proposal 起票を次サイクルで判断」と記載済み。
- **発生回数**: 累計 3（昇格条件充足）
- **対象タスク**: obsidian-vault-setup / IMP-2026-025・026 適用 / pantry-screens
- **原因仮説**: 安全機構（保護ファイルの書込ブロック）が改善機構（承認済み変更の適用）を
  塞ぐ設計になっており、リモート運用が想定されていなかった。
- **改善案**: 代替承認経路を 1 つ定める。案 A: 承認済み変更は作業ブランチへコミットし
  **PR レビュー承認をもって人間承認とみなす**（適用は PR マージ）。案 B: ユーザーが
  セッション内で明示承認した直後のターンに限りマーカー作成を許可する条件を guard へ追加。
  推奨: 案 A（guard 変更不要・承認の証跡が PR に残る）。
- **変更対象**: improvement-cycle.md §承認境界 /（案 B の場合）guard-dangerous.mjs
  （人間承認必須）
- **想定される副作用**: 案 A は適用がマージまで遅延する → 現状の「ローカル適用待ち」より
  短いため許容
- **評価方法**: 次回の承認済み Skill/Hook 変更が「適用待ち」滞留なしで本適用されること
- **昇格判定**: 昇格条件を満たす（backlog 記載済み）→ proposal 起票推奨

### 事象 4: 低稼働 Agent 5 本の維持コスト（P1）

- **種類**: 構造
- **観測した事象**: logs 全 13 ファイル中の言及ファイル数で、implementer 7 / reviewer 6 /
  reflection-agent 6 に対し、security-reviewer・requirements-analyst・performance-designer・
  e2e-test-implementer・document-reviewer は**各 1**。起動条件が狭く（L3 + 外部 I/O 等）、
  Codex 委譲中心の現運用ではほぼ発動しないが、定義約 330 行 + 正典側の起動条件記述
  （IMP-2026-006/016 ほか）の維持対象であり続けている。
- **発生回数**: 構造的（単発タスクの失敗ではない）
- **対象タスク**: 本診断
- **原因仮説**: IMP-2026-006 で委譲ギャップを埋めるため追加されたが、その後の実装ルートの
  Codex 委譲化で前提が変わった。
- **改善案**: 統合により 15 本 → 8〜9 本へ。performance-designer →
  architecture-designer の条件付きセクション、e2e-test-implementer → test-designer、
  document-reviewer → reviewer、requirements-analyst → orchestrator/設計工程へ吸収。
  security-reviewer は観点の独立性が高いため単独維持も可。
- **変更対象**: Agent 定義複数（削除・移設のため提案止まり・人間承認必須）
- **想定される副作用**: 統合先 Agent の定義が肥大する → 条件付きセクションは
  「発動条件 + 観点リスト」のみに絞る。将来 L3 での再分離は可能。
- **評価方法**: agent-evaluator の既存 eval ケース（security/perf/e2e 追加時の 5 ケース含む）
  で悪化軸ゼロを確認
- **昇格判定**: 提案止まり（ファイル削除・移設は承認境界。ユーザー採否が前提）
- **対応状況（2026-07-25）**: ユーザー「推奨案で ok」→
  [proposals/IMP-2026-030.md](../proposals/IMP-2026-030.md) として本適用
  （15→11、security-reviewer 単独維持、4 Agent を archive 凍結）。

### 事象 5: 改善サイクル自体の自己参照的肥大（P1）

- **種類**: プロセス観察 / 構造
- **観測した事象**: 約 3 週間で IMP 26 件。うち後半の相当数が過去の改善の後始末
  （IMP-018: 同期漏れ対策 / 021: 020 の残差 / 024: スクリプト防御修正 / 026: 020 の
  テキスト修正が 2 日で再発 → Hook 化）。テキスト追記型の改善が効かず機械化が必要になる
  パターンは、指示量が吸収限界を超えたシグナル。改善サイクル関連の構成物
  （meta Agent 2 本・Skill 4 本・Hook 3 本・improvements/ 約 5,000 行超）が
  開発ワークフロー本体より重くなっている。
- **発生回数**: 構造的（IMP 系譜から確認可能）
- **対象タスク**: 本診断
- **原因仮説**: 昇格の例外的早期対応が常態化し（IMP-012 前例の反復）、候補・記録の
  アーカイブ基準がないため追跡記録が単調増加している。
- **改善案**: (1) 例外的早期昇格を原則禁止し 3 回蓄積を厳守、(2) 対応済み candidate を
  `candidates/archive/` へ移動する基準を memory-policy へ追加、(3) metrics に
  「メタ作業がセッション時間に占める割合」を 1 指標追加し、複雑さの再増殖を数字で監視。
- **変更対象**: memory-policy.md / improvement-cycle.md / metrics テンプレ
  （提案止まり・人間承認必須）
- **想定される副作用**: 早期昇格禁止により実害のある単発事象への対応が 1 サイクル遅れる →
  「確証あり・修正極小」の例外条件を 1 行だけ残す
- **評価方法**: 次スプリントの IMP 起票数と「過去改善の後始末」比率が低下すること
- **昇格判定**: 提案止まり（改善サイクルの目的・判断基準の変更のためユーザー採否が前提）
