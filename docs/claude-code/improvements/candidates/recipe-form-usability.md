## 観測した事象（複数可）

### 事象 1: 自動テストを全件 PASS させた状態から、実画面確認で 3 件の不具合が出た

- **種類**: テスト失敗（実機でのみ再現）
- **観測した事象**: `pnpm lint && type-check && test`（1,429 件）を全通過した実装に対し、
  PGlite dev + Playwright の実画面確認で 3 件の不具合が出た。
  1. **capture リスナの登録先が `document` では間に合わない**。Next.js App Router は
     `document` を React のルートコンテナにしてハイドレートするため React の capture リスナも
     `document` に付く。同一ノードのリスナは登録順に走り、ハイドレートは `useEffect` より
     先に終わっているので、Link の `onClick` が先に走って遷移してしまった。→ `window` へ変更。
  2. **リンク内の SVG アイコンをクリックすると素通り**していた。`target` が `SVGElement` に
     なり `target instanceof HTMLElement` で早期 return。→ `Element` へ変更。
  3. **dnd-kit のハイドレーション不一致**。`DndContext` に `id` を渡さないと
     `aria-describedby` をインスタンス連番で採番し SSR/CSR でずれる。→ `useId()` を渡す。
- **発生回数**: このタスク内 3 件（実画面確認の有効性としては累計 3 タスク目 —
  過去に `shopping-complete-stock-selection`（UI テストが実 UX バグ 2 件を検出）と
  `completed-list-check-ui` がある）
- **対象タスク**: recipe-form-usability
- **原因仮説**: 1 と 3 は**テスト環境では原理的に再現できない**類だった。
  RTL は React ルートを**コンテナ div** に作るが、Next.js App Router は **`document`** に作る。
  この差はモック（`vi.mock('next/navigation')`）では埋まらない。
  2 は判定漏れで、テストのフィクスチャがテキストのみのリンクだったため露見しなかった。
  → **「テストが甘い」で片付く（=2）ものと、環境差で原理的に無理（=1, 3）なものが混在**している。
- **改善案**: `manual-browser-verify` スキルに「**RTL では再現できない領域**」の一覧を持たせる。
  現時点で判明しているのは次の 3 つ。
  - React ルートコンテナの位置（`document` vs コンテナ div）に依存するイベント伝播の優先順位
  - SSR と CSR の差（ハイドレーション不一致）
  - `getBoundingClientRect()` を使うレイアウト依存の挙動（happy-dom は常に 0 を返す）
    これがあると「この変更は実画面確認が必須か」を機械的に判断できる。
- **変更対象**: Skill（manual-browser-verify）
- **想定される副作用**: 一覧が古びるリスク。ただし追記型で害は小さい。
- **評価方法**: 過去タスク（`shopping-complete-stock-selection` / `completed-list-check-ui`）で
  検出された不具合が、この一覧のどれに該当するかを後付けで分類できるか確認する。
- **昇格判定**: **改善候補として起票する（→ proposal 候補）**。
  「実画面確認が有効だった」の観測は累計 3 タスク目で、memory-policy.md の
  「繰り返す → 改善候補」を満たす。ただし**今回初めて「なぜ自動テストで無理なのか」の
  類型が言語化できた**ため、Skill への追記という具体的な形に落とせる。

### 事象 2: テスト環境の制約に気づかず、成立しないテストを一度書いた

- **種類**: 手戻り
- **観測した事象**: 材料の並べ替えを RTL のキーボード操作で検証しようとしたが 2 回失敗した。
  1. happy-dom は `getBoundingClientRect()` が常に 0 を返すため、dnd-kit が要素位置を測れず
     並べ替え先を決定できない（ポインタ・キーボードとも）。
     → 兄弟内の位置から縦に積んだ矩形を返すスタブを入れて計測だけ成立させた。
  2. それでも動かず。**dnd-kit の `KeyboardSensor` は `event.key` ではなく `event.code` を見る**
     ため、user-event では物理キーコード記法（角括弧 `[Space]` / `[ArrowDown]`）が必要だった。
     `{Space}` では発火しない。
- **発生回数**: このタスク内 2 回
- **対象タスク**: recipe-form-usability
- **原因仮説**: 試験計画を書く段階で「キーボード操作で検証する」と決めたが、
  **その手段が採用ライブラリと採用テスト環境の組み合わせで成立するかを未確認**だった。
  これは既存の教訓「**ライブラリ API を採用バージョンで未確認のまま指定**」
  （`create-design-document` の悪い例。出典: test-infra-expansion 事象 2）と同型で、
  対象が「設定ファイル・フレームワーク API」から「**テスト手段**」に広がったケース。
- **改善案**: `create-design-document` の悪い例に既にある注意書きの適用範囲を
  「設定ファイル・フレームワーク API」から「**外部ライブラリに依存する検証手段**」まで広げる。
  あるいは `create-test-plan` 側に「新規ライブラリを導入する変更では、**試験手段が
  テスト環境で成立するかを最小コードで先に確認**してから試験計画に書く」を追加する。
- **変更対象**: Skill（create-design-document または create-test-plan）
- **想定される副作用**: 試験計画の作成前に検証コストが発生する。ただし今回のように
  実装後に 2 回失敗するより安い。
- **評価方法**: test-infra-expansion 事象 2 と本事象を同じルールで説明できるか確認する。
- **昇格判定**: **改善候補として起票する（→ proposal 候補）**。
  test-infra-expansion 事象 2 と合わせて**同種 2 回目**であり、
  memory-policy.md の「繰り返す → 改善候補」を満たす。
  なお test-infra-expansion 側は「1 回目のため手順への必須化は保留・再発時に昇格検討」と
  明記されていたため、**その条件が満たされた**ことになる。

### 事象 3: 回帰テストが旧実装で落ちることを確認した（成功手順の再適用）

- **種類**: 成功手順
- **観測した事象**: 実画面で見つけた SVG 判定漏れに対し、回帰テスト LG-15 / LG-16 を追加した後、
  `target instanceof HTMLElement` に戻して**実際に 2 件が FAIL することを確認**してから元に戻した。
- **発生回数**: このタスク内 1 回（累計 2 回目。1 回目は 2026-07-25 の `useApiAction` UAA-08）
- **対象タスク**: recipe-form-usability
- **原因仮説**: 2026-07-25 の教訓「**回帰テストは『旧実装で落ちること』まで確認する**」が
  ログに残っており、それを参照して実行できた。**ログの知見が次セッションで再利用された実例**。
- **改善案**: なし（既に機能している）。ただし**この手順が Skill / Rule に昇格していない**点は
  検討の余地がある。現状は「ログに書いてあるから思い出せた」という属人的な再現に近い。
  `create-test-plan` の完了条件に「回帰テストは旧実装で FAIL することを確認する」を
  加えると恒久化できる。
- **変更対象**: Skill（create-test-plan の完了条件）
- **想定される副作用**: 回帰テスト追加時の手間が増える。適用範囲を「**不具合修正に伴う
  回帰テスト**」に限定すれば過剰にならない（新機能のテストには求めない）。
- **昇格判定**: **改善候補として起票する（→ proposal 候補）**。同種 2 回目で昇格条件を満たす。

### 事象 4: 設計レビューが自分の案への有効な反論として機能した

- **種類**: 成功手順 / レビュー指摘
- **観測した事象**: 実装前の設計レビューで 2 件の指摘を受け、**片方は採用・片方は不採用**とした。
  - **採用**: ボトムナビ（全ページに出る `next/link` 6 本）が最も踏みやすい離脱経路である。
    当初の計画に無く、これが無ければ B-3 の要件自体が漏れていた。
  - **不採用**: dnd ライブラリを入れず Pointer Events で自前実装すべき。
    テスタビリティを決定打とする論だったが、**happy-dom ではどちらの方式でもドラッグを
    再現できず条件は同等**だったため、論拠が成立しないと判断。ユーザー確認のうえライブラリ採用。
- **発生回数**: このタスク内 1 回（累計 2 回目。1 回目は 2026-07-25 の reviewer 指摘の検証）
- **原因仮説**: 2026-07-25 の教訓「**レビュー指摘も検証してから受け入れる**」が機能した。
- **改善案**: なし（既に機能している）。
- **変更対象**: —
- **昇格判定**: **Memory 留め**（既存の教訓が機能した確認であり、新たな変更は不要）。

### 事象 5: `react-hooks/refs` によりレンダー中の ref 読み取りが lint エラーになった

- **種類**: 手戻り（軽微）
- **観測した事象**: 離脱判定の初期スナップショットを `useRef` で保持し、レンダー中に
  `initialSnapshot.current` を読んだところ `react-hooks/refs` の lint エラーになった。
  `useState` の初期化関数（1 度しか走らないので値は不変、かつレンダー中に読める）へ変更して解決。
- **発生回数**: このタスク内 1 回
- **原因仮説**: 「初回レンダーの値を固定したい」という要求に対し `useRef` を反射的に選んだ。
  React 19 系の lint ルールでは `useState` の初期化関数が正解。
- **改善案**: `.claude/rules/presentation-layer.md` に「**初回レンダーの値を固定するには
  `useRef` ではなく `useState` の初期化関数を使う**（`react-hooks/refs` がレンダー中の
  `ref.current` 読み取りを禁止するため）」を 1 行追加する。
- **変更対象**: Rule（presentation-layer.md）
- **想定される副作用**: ほぼ無い。ただし**1 回の観測でルールを増やすのは
  「毎タスク Agent 定義を書き換えない」原則に反する**。
- **昇格判定**: **Memory 留め（昇格せず・再発監視）**。lint が確実に検出するため、
  ルール化しなくても実害が残らない（＝Rule に書く価値が低い）。再発しても lint が止める。
