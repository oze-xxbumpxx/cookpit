## 観測した事象（複数可）

### 事象 1: 棚卸しの母集団を「語」ではなく「形式」で数えて取りこぼした（再発）

- **種類**: レビュー指摘（自己レビューで検出）
- **観測した事象**: 要件 F-7（出典表記の統一）の対象を「出典 38 箇所」と数えたが、実際の
  grep はパス形式（`docs/.../<name>.md`）を拾うものだった。パスを持たない
  `出典: shopping-list-core 事象 2` のような素の feature 名形式 11 箇所が母集団から
  漏れ、うち workflow 層の 7 箇所が未修正のまま「F-7 充足」と判断しかけた。
  レビュー中に `grep "出典[:：]" | grep -v "cookpit/"` で検出し修正した。
- **発生回数**: このタスク内 1 回 / **累計 2 回**。Phase 1（harness-portability）で
  `COOKPIT_TZ` を列挙して探し `COOKPIT_GAP_CAP_MIN` を見落としたのと**同一類型**
  （出典: cookpit/harness-portability 気づき「固有名詞の棚卸しを個別の変数名で grep して
  取りこぼした」）。
- **対象タスク**: harness-plugin-split（過去分: harness-portability）
- **原因仮説**: 「何を全部見つけたいか」（母集団の定義）と「どう探すか」（検索式）を
  分けて考えていない。Phase 1 の振り返りで「プレフィックス単位で grep する」と書いたが、
  それは `COOKPIT_` という**特定の教訓**に閉じており、一般化されていなかった。
- **改善案**: 棚卸し型の作業では、**検索式を書く前に母集団の定義を 1 行で書き、
  検索式がその定義の全体を覆うか確認する**。加えて「網羅したはず」の主張には
  必ず補集合側の検索（`grep -v` で対象外を洗い出す）を 1 本添える。
- **変更対象**: Skill（`audit-skills` に棚卸し手順として追記が妥当か検討）/ まだ未定
- **想定される副作用**: 全タスクに補集合検索を義務化すると過剰。適用範囲を
  「N 箇所を全て変更する」と宣言する作業に限定すべき。
- **評価方法**: `refactoring` / `documentation-only-change` の eval ケースで、
  「全箇所を書き換える」指示に対する網羅性を before/after 比較する。
- **昇格判定**: **累計 2 回で同一類型のため昇格条件を満たす** → proposal 起票を推奨

### 事象 2: 層の割り当てを「役割の見た目」で決めて 2 回訂正した

- **種類**: 手戻り
- **観測した事象**: 層マニフェストの割り当てを 2 度訂正した。①`check-review-coverage.mjs`
  を Standard（workflow）に数えたが、呼び出し元は `check-improvement-cycle.mjs` と
  `close-session` だけで improvement 層だった。②`record-activity` /
  `estimate-session-time` を improvement に置いたが、依存は harness-paths のみで
  `write-work-log`（core）の「所要時間」欄を埋めるため core が正しかった。
- **発生回数**: このタスク内 2 回
- **対象タスク**: harness-plugin-split
- **原因仮説**: ファイル名や説明文から役割を推測して層を決めた。層は
  **依存の向きと利用者**で決まるのに、意味的な分類を先に当ててしまった。
- **改善案**: 層・パッケージ・モジュール境界を決めるときは、**最初に依存グラフ
  （import と呼び出し元）を機械的に取ってから**分類する。名前で判断しない。
- **変更対象**: まだ未定（Plugin 分割は 1 回限りの作業のため恒久ルール化の価値は低い可能性）
- **想定される副作用**: 依存グラフを毎回取るのは小規模変更では過剰。
- **昇格判定**: **Memory 留め**（1 タスク内の 2 回で、作業自体が非反復的。再発監視）

### 事象 3: 依存照合が未知の欠陥を 1 件発見した（成功手順）

- **種類**: 成功手順
- **観測した事象**: 層をまたぐ依存の grep 照合を実行したところ、`classify-change` の
  L2 Agent 早見表が `reflection-agent`（improvement 層）と `contract-designer`
  （cookpit-local）を**無条件で指定**していることを発見した。当初認識していた欠陥は
  `close-session` の 1 件だけで、これは想定外の 2 件目だった。修正せず Phase 3 へ
  進んでいたら「workflow だけ install した環境で存在しない Agent を起動しろと指示する」
  構成を配ることになっていた。
- **発生回数**: このタスク内 1 件検出
- **対象タスク**: harness-plugin-split
- **原因仮説**: 成功要因は「設計時に受け入れ条件を機械照合可能な形（無条件依存 0 件）で
  定義し、それを独立した実装手順（手順 7）として置いた」こと。人手のレビューでは
  早見表の 1 セルは見落としやすい。
- **改善案**: 境界を作る変更（層分割・パッケージ分離・公開 API 縮小）では、
  **境界違反の検出を grep レベルの機械照合に落として受け入れ条件にする**。
- **変更対象**: Skill（`create-design-document` の「テスト方針」節に、境界変更時は
  機械照合可能な受け入れ条件を書く旨を追記する案）/ まだ未定
- **想定される副作用**: なし（既存手順への追加のみ）
- **昇格判定**: **Memory 留め**（1 回目の観測。再現したら昇格検討）

### 事象 4: 検算の数値を一覧表と別に手書きして食い違わせた

- **種類**: レビュー指摘（試験観点で検出）
- **観測した事象**: 層マニフェストで core を見出し「16」、improvement を見出し「12」・
  検算表「16」と書き、`templates/` の新規分も未計上だった。試験計画の観点 11
  （未分類 0 件の照合）を実行して初めて実ファイル 72 との不一致が判明した。
- **発生回数**: このタスク内 1 回
- **対象タスク**: harness-plugin-split
- **原因仮説**: ファイル一覧の表（行数 = 件数）と検算の数値を別々に書いた。
  一覧の行が 1 行 1 ファイルでない箇所（`evals/README.md / evals/rubrics/...` を
  1 行にまとめた等）があり、行数 ≠ 件数だったことにも気づいていなかった。
- **改善案**: 件数を主張する文書では、**一覧と数値を別々に書かず、ディレクトリ別の実数から
  積み上げる**か、照合コマンドの出力をそのまま貼る。
- **変更対象**: まだ未定
- **想定される副作用**: なし
- **昇格判定**: **Memory 留め**（1 回目。事象 1 と根が近い＝「主張と検証手段の乖離」なので
  事象 1 の proposal に含める余地あり）

### 事象 5: 自己レビューで Must を検出したが、独立性は担保できていない

- **種類**: Agent 間認識不一致（の不在による限界）
- **観測した事象**: 本セッションは Subagent 委譲を行わない制約下だったため、reviewer Agent
  ではなくメインセッションが自己レビューを実施した。結果として Must 1 件を検出できたが、
  検出できたのは「自分が書いた要件 F-7 と自分の実装を突き合わせた」ためで、
  設計自体の妥当性や見落とした観点は原理的に検出しにくい。
- **発生回数**: このタスク内 1 回
- **対象タスク**: harness-plugin-split
- **原因仮説**: 実行環境の制約（Agent ツール不使用）。ハーネスの設計上の問題ではない。
- **改善案**: 自己レビューになる場合は**レビュー記録にその旨を明記し、第三者確認を
  PR レビューへ委ねる**ことを運用として固定する（今回は記録に明記した）。
- **変更対象**: なし（運用の記録のみ。恒久ルール化は不要と判断）
- **昇格判定**: **昇格せず**（環境要因）
