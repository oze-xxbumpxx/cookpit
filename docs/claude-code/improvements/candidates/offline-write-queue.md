## 観測した事象

### 事象 1: roadmap のタスク名が実現不可能な技術を指していた

- **種類**: 上流成果物の欠陥（設計着手前に検出）
- **観測した事象**: roadmap の Sprint 9 タスク 1 は「PWA オフライン書き込みキュー（**Background Sync**）」と技術を名指ししていたが、Background Sync API は Chromium 限定で iOS Safari が未対応と見られる。Cookpit の主対象は iPhone の PWA であり、名指しされた技術では完了条件を満たせない。設計方式を案 C（アプリ層のみ）へ変更した
- **発生回数**: このタスク内 1 回 / 類似は累計 2 回（2026-08-10 の P-5 撤回「`TZ` は Vercel の予約環境変数だった」と同型）
- **対象タスク**: offline-write-queue / expiry-alert（P-5 撤回）
- **原因仮説**: **プラットフォームの対応状況・制約がコードにもドキュメントにも現れない**ため、コードベースを読むだけの調査では検出できない。roadmap へ技術名を書いた時点では未検証だった
- **改善案**: roadmap やタスク定義が**特定の Web API・プラットフォーム機能を名指ししている場合、設計フェーズの冒頭で対応状況を一次情報で確認する**工程を明示する。expiry-alert の振り返りで既に同趣旨の学び（「外部プラットフォームの設定に依存する決定は、設計時にその設定が実際に可能かを一次情報で確認する工程が要る」）が出ており、**2 回目の観測**にあたる
- **変更対象**: Skill（create-design-document の手順に「名指しされた外部 API・プラットフォーム機能の対応状況を一次情報で確認する」を追加）または orchestration-policy.md
- **想定される副作用**: 確認工程の追加でリードタイムが伸びる。ただし本件は設計着手前の 1 回の確認で済む粒度
- **評価方法**: expiry-alert（P-5）と offline-write-queue の 2 ケースで、確認工程があれば検出できたかを追試する
- **昇格判定**: **昇格条件を満たす（2 回観測）→ proposal 起票を推奨**

### 事象 2: 一次情報の確認がネットワークポリシーで実行できなかった

- **種類**: 環境制約
- **観測した事象**: 事象 1 の確認のため `developer.mozilla.org` と `vercel.com` を WebFetch したが、いずれも egress プロキシに遮断された（`EGRESS_BLOCKED`）。本番アプリのドメインへの `curl` も CONNECT に 403 が返り到達不能だった。結果、Background Sync の iOS 非対応は**未確認の前提**として設計書に明記したまま進めた
- **発生回数**: このタスク内 3 回（MDN / Vercel Docs / 本番アプリ）
- **原因仮説**: リモート実行環境のネットワークポリシーが許可制で、npm レジストリ等以外への到達を許していない
- **改善案**: 事象 1 の改善（一次情報確認の工程化）と**組み合わせないと機能しない**。工程を足しても環境が遮断していれば実行できないため、「Claude が確認できない場合はユーザーへ確認を依頼し、その旨を設計書へ明記する」までを手順に含める。今回は実際にユーザーへ測定を依頼して成立させた
- **変更対象**: Skill（create-design-document）/ docs/07-dev-rules.md §環境の既知の事実
- **想定される副作用**: なし（既に実施した運用の明文化）
- **昇格判定**: 事象 1 の proposal に統合する

### 事象 3: 下流 Agent が上流の欠陥を検出する構造が再現した（4 件）

- **種類**: 成功手順（工程が機能した例）
- **観測した事象**: 設計・計画の欠陥を下流工程が検出した。(1) test-designer が「`useCheckedSyncQueue` がマウント時に無条件で IndexedDB を開くため、happy-dom で `ReferenceError` となり無関係な既存 dom テストまで壊れる」を検出。(2) test-designer が「設計書はキュー利用可否のガードを要求するが、公開インターフェースに判別手段が無い」という**設計内の矛盾**を検出。(3) reviewer が「`LC-22` が flush 先行化で必ず落ちる」を、`fake-indexeddb` を実際にインストールして実測した上で検出。(4) implementer が実装計画のサンプルコードの不備を 4 件検出
- **発生回数**: このタスク内 4 件 / 累計 3 タスク連続（Unit A・Unit B・本タスク）
- **原因仮説**: 各 Agent が「自分の工程の視点で上流を読む」ため、上流が見落とした前提が露出する。特に**実際に依存パッケージを動かして確かめた**指摘（3）は精度が高い
- **改善案**: 委譲プロンプトの定型「実コードを当たれ・推測で断定するな」は既に効いている。**3 タスク連続で観測**しており、`orchestration-policy.md` と各 Skill へ昇格する条件を満たす
- **変更対象**: orchestration-policy.md / 各 Skill の委譲定型文
- **昇格判定**: **昇格条件を満たす（3 回観測）→ proposal 起票を推奨**。expiry-alert の候補で挙がっていた定型 3 点（実測結果の埋め込み / 実コードを当たれ / 表のセル内改行禁止）と統合する

### 事象 4: セッション上限で implementer が停止し、成果物が中途半端な状態で残った

- **種類**: 手戻り
- **観測した事象**: Step 3 の implementer がセッション上限（`resets 3:30am UTC`）で停止した。実装はディスクに残っていたが、**デバッグ用の `console.log` が production コード（`use-checked-sync-queue.ts`）に 2 箇所、テストに 1 箇所残ったまま**だった。テストは 2 件失敗しており、Orchestrator が引き継いで原因特定・修正した
- **発生回数**: このタスク内 1 回 / 累計 4 回（2026-08-10 に 3 回）
- **原因仮説**: 停止は Agent 側で制御できない。**成果物がディスクに残る**ことは既知（前回の学び）だが、「停止時点の作業が完了形かどうか」の判定手段が無い。今回は `console.log` の残存という形で現れた
- **改善案**: Agent 停止時の引き継ぎチェックとして、**`git diff` に対する機械的な検査**（`console.log` / `DEBUG` / `.only` / `TODO` の混入検査）を Hook もしくは quality-gates スキルへ追加する。lint の `no-console` は今回 `eslint-disable-next-line` を伴っていたため検出できなかった点が重要
- **変更対象**: Hook（pre-commit）または quality-gates スキル
- **想定される副作用**: `eslint-disable` を伴う正当な `console` 利用があれば誤検知しうる。現状のコードベースでは production コードに `console` は無い
- **評価方法**: 本タスクの Step 3 停止時点の差分に対して検査を走らせ、3 箇所すべて検出できるか確認する
- **昇格判定**: **昇格条件を満たす（4 回観測。ただし今回初めて実害が出た）→ proposal 起票を推奨**

### 事象 5: 非決定的なテストが「実装の欠陥」を隠していた

- **種類**: テスト失敗
- **観測した事象**: `LCQ-09` が「`postChecked` が 1 回のはずが 3 回」で失敗し、`LCQ-EX` は実行するたびに成否が変わった。原因は**アンマウント後も `flush()` が走り続け、前のテストの送信が次のテストの呼び出し回数に混入**していたこと。`afterEach` の `cleanup()` と `vi.clearAllMocks()` では止まらない（IndexedDB の解決がマクロタスクで起きるため）。フックに アンマウント検知を足して解消した
- **発生回数**: このタスク内 1 回
- **原因仮説**: 設計・計画のどちらも「flush の生存期間」を規定していなかった。`flushingRef` による二重発火の排他はあったが、コンポーネントの寿命とキュー処理の寿命の関係は未定義だった
- **改善案**: **非同期処理を伴うフックの設計では「コンポーネントのアンマウント時にどうなるか」を設計書の必須確認項目にする**。今回は結果的に実害の少ない箇所だったが、テストの非決定性という形で開発を止めた
- **変更対象**: Skill（create-design-document のチェックリスト）
- **想定される副作用**: 該当しない設計では「対象外」と書くだけで済む
- **昇格判定**: **1 回目の観測。Memory 留め（再発監視）**

### 事象 6: タスク 2 の下調べが、当初の想定と逆の結論を出した

- **種類**: 成功手順
- **観測した事象**: roadmap のタスク 2 は「Function だけ hnd1 へ移すと DB 往復が悪化する」という懸念を前提にしていた。実測（DB を触る API と触らない API の応答時間の差）の結果、**Function と Neon は既に地球の反対側にあり、1 往復あたり 0.18〜0.22 秒**かかっていた。前提が成立しておらず、移設は「悪化リスク」ではなく「改善手段」だと判明した
- **発生回数**: このタスク内 1 回
- **原因仮説**: roadmap の懸念は「両者が同居している」ことを暗黙の前提にしていた。**前提そのものが未検証**だった
- **改善案**: 性能に関する判断は、構成の推定ではなく**差分測定**で確かめる。今回使った「DB を触る API と触らない API の応答時間を比べる」手法は、リージョン名を特定できなくても距離が分かるため汎用性が高い。docs/07-dev-rules.md の環境の既知の事実へ手法ごと記録する価値がある
- **変更対象**: docs/07-dev-rules.md
- **昇格判定**: Memory 留め（手法として記録）
