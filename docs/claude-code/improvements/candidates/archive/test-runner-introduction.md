### 事象 1: turbo キャッシュが既存エラーを不可視化していた

- **種類**: 手戻り（潜在バグの露出）/ テスト失敗（type-check）
- **観測した事象**: `@cookpit/application` の type-check が `node:crypto` 型を解決できず失敗するエラーが、turbo キャッシュによって隠蔽されていた。domain 層の変更によって application の turbo キャッシュが無効化されたタイミングで初めて表面化した。`base コミット b595db6` でワークツリーを再現し、変更前から存在する潜在エラーと確定。原因は application の tsconfig に `@types/node` または `types: ["node"]` が無いこと。本フェーズではスコープ外として未修正。
- **発生回数**: このタスク内 1 回（累計 1 回）
- **対象タスク**: test-runner-introduction
- **原因仮説**: Turborepo のキャッシュは「直前の実行結果」をパッケージ単位で再利用する。あるパッケージ（domain）が変更されると依存パッケージ（application）のキャッシュが無効化され、長期間実行されていなかった type-check が走り、それまで隠れていたエラーが露出する。これは turbo の意図した動作だが、開発者に「変更前から存在するエラーが自分の変更によって生まれた」と誤認させるリスクがある。
- **改善案**: (a) application の tsconfig 修正（直接の根本修正。別タスクで実施）。(b) implementer の Subagent Memory に「キャッシュ無効化で潜在エラーが出た場合は `git stash` または base commit で再現し変更前からの問題か確認する」手順を記録。(c) run-quality-gates.sh に `--force`（キャッシュ無視）オプション付き実行モードを追加し、定期またはリリース前に全パッケージの新鮮な type-check を走らせることを検討。
- **変更対象**: implementer Subagent Memory（手順 b）/ run-quality-gates.sh（手順 c は manager 検討事項）
- **想定される副作用**: (b) は検証手順の追加なので副作用は軽微。(c) は CI 時間増加リスクあり（キャッシュを活用している既存の高速化が失われる）。
- **評価方法**: `aws-integration-change` や `database-schema-change` の eval ケースで「turbo キャッシュが邪魔するシナリオ」を追加観点として確認。定量評価は再現しにくいため、再発時の対処速度で判断。
- **昇格判定**: Memory 留め（昇格せず）。今回 1 回目の発生。発生 3 回、または別タスクでも同様にキャッシュ起因の誤認が発生した場合に改善候補として改めて昇格する。

### 事象 2: テスト網羅性が全軸中最弱（平均 2.6）という構造的弱点の根因が特定・解消された

- **種類**: 成功手順（構造的弱点の解消）
- **観測した事象**: eval ベースライン（INDEX.md）で全 15 軸中最弱と判定されたテスト網羅性（平均 2.6）の根因が「テストランナー未導入」という構造的制約であった。本タスクで Vitest を domain 層に導入し 29 tests が green になったことで、この構造的制約が解消された。 `refactoring`（振る舞い不変の回帰確認が必須）と `external-service-failure`（異常系が核心）でスコア 2 を記録していた軸が、今後のタスクで再採点されるべき状態になった。
- **発生回数**: 構造的弱点の解消は 1 回（単発）
- **対象タスク**: test-runner-introduction
- **原因仮説**: テストランナー未導入という環境制約がテスト網羅性スコアの天井を下げていた。環境制約が解消されたことで、次の制約要因（create-test-plan Skill の観点不足）が顕在化する。
- **改善案**: (a) INDEX.md のテスト網羅性スコアを Phase 2 完了後に再採点し、構造的制約解消後の新ベースラインを確立する。(b) create-test-plan Skill に不足していた観点（冪等性・障害系・フロントエンド固有）を追加する提案を manager に上げる。(c) domain 以外（application / infrastructure / apps/web）のテスト展開を後続フェーズの計画に含める（docs/05-roadmap.md の更新）。
- **変更対象**: (a) .claude/evals/baselines/INDEX.md の更新（evaluator タスクとして別途）/ (b) .claude/skills/create-test-plan.md への観点追加（Skill チェック項目追加 = manager レビュー後可）/ (c) docs/05-roadmap.md（更新）
- **想定される副作用**: (b) Skill への観点追加はテスト計画が詳細化し工数見積もりが増える可能性。一方でテスト網羅性向上には直結する。
- **評価方法**: eval ケース `refactoring` / `external-service-failure` のテスト網羅性スコアが Phase 2 後の再採点で 2 から 3 以上に改善するか。また `create-test-plan` Skill 改善後に `small-bug-fix` / `refactoring` ケースで before/after を比較。
- **昇格判定**: 昇格条件を満たす（→ proposal 起票）。理由: (b) について、INDEX.md が「create-test-plan Skill に冪等性・障害系・フロントエンド固有の観点が薄い問題が重なる」と明示的に指摘しており、ベースライン採点（複数 eval ケース）で繰り返し低スコアが観測されている。これは「複数ケースで同じ原因の弱点が再現」に該当し、昇格条件（Reviewer から同種の重大指摘を複数回受けた）を満たす。

### 事象 3: 作業中断（auto モード安全性判定器の一時障害）からの復旧に有効だったチェックポイントコミット手順

- **種類**: 成功手順（再現性のある回復パターン）
- **観測した事象**: auto モードの安全性判定器が一時障害となり、書き込み・コマンド実行が一定時間不可になった。復旧後にユーザー指示で「チェックポイント commit → 検証 → 完了 commit」の順で再開し、実装が適切に継続された。中断前にコミット（`98dd9c8`）を打っていたため、中断中に完了済みの部分が保全された。
- **発生回数**: このタスク内 1 回（auto モード障害としての発生）
- **対象タスク**: test-runner-introduction
- **原因仮説**: auto モードの安全性判定器は外部依存であり、一時的な障害リスクがある。長時間の実装セッションでは途中コミットがない場合、障害発生時に進捗が失われる（または再確認コストが増大する）。チェックポイントコミットを定期的に打つことで、再開の起点が明確になる。
- **改善案**: implementer の Subagent Memory に「長時間実装タスクでは中間的にチェックポイントコミット（`feat(wip):`等のプレフィックス）を打ち、障害・中断時の再開起点とする」パターンを記録する。ただし CLAUDE.md の「`git commit` は明示指示があるまで行わない」制約との整合を確認すること（チェックポイントコミットはユーザー指示または turbo キャッシュポイントとして扱う）。
- **変更対象**: implementer Subagent Memory（一時的・単発の知見として記録）
- **想定される副作用**: 制約（明示指示なし commit 禁止）との競合リスクあり。ユーザーの明示承認が得られた場面限定で適用するパターンとして記録し、自動化はしない。
- **評価方法**: 再度の auto モード障害時に、チェックポイントコミットの有無が回復速度に影響したか事後確認。定量評価は困難。
- **昇格判定**: Memory 留め（昇格せず）。単発の障害イベント。auto モード障害が複数タスクで再発、またはチェックポイントコミットの有無が実作業時間に 10 分以上の差を生むパターンが 3 回以上観測されたら再検討。

### 事象 4: create-test-plan Skill の冪等性・障害系・フロントエンド固有観点の不足（ベースライン採点で特定）

- **種類**: レビュー指摘（ベースライン採点による構造的指摘）
- **観測した事象**: eval ベースライン INDEX.md の分析で、テスト網羅性の低スコア（平均 2.6）の要因の一つとして「create-test-plan Skill に冪等性・障害系・フロントエンド固有の観点が薄い」という問題が明記されている。本タスク（test-runner-introduction）の試験計画（docs/tests/test-runner-introduction.md）でも、domain の純粋ロジックに限定したため冪等性・障害系の観点は「対象外」として記載されている。ただし本タスクのスコープ（domain 単体のみ）では適切な判断であり、問題は Skill 定義の側にある。
- **発生回数**: ベースライン採点で 8 eval ケース中、テスト網羅性で 3 以下を記録したケースが 8 件（2: 3 件、3: 5 件）。Skill 定義の問題として初回の明示的記録。
- **対象タスク**: test-runner-introduction（採点のタスク）/ 複数 eval ケース横断
- **原因仮説**: create-test-plan Skill が正常系・異常系・境界値の観点は定義しているが、以下の観点が不足している可能性がある: (1) 冪等性（同じ操作を複数回実行した結果が変わらないか）、(2) 障害系（外部サービス停止・タイムアウト・部分失敗のシナリオ）、(3) フロントエンド固有（コンポーネントの状態遷移・非同期ローディング・エラーバウンダリ）。この不足が `external-service-failure`（スコア 2）や `refactoring`（スコア 2）の低スコアに直結している。
- **改善案**: create-test-plan Skill の観点チェックリストに「(4) 冪等性観点: 同一操作の多重実行・重複処理の安全性」「(5) 障害系観点: 外部依存の失敗・タイムアウト・部分失敗のハンドリング」「(6) フロントエンド固有: ローディング状態・エラー表示・楽観的更新のロールバック」を追加する。ただし追加は対象タスクに応じて取捨選択し、不要な観点を全タスクに強制しない（観点の選択基準も Skill に記載）。
- **変更対象**: `.claude/skills/create-test-plan.md`（Skill チェック項目追加 = manager レビュー後可）
- **想定される副作用**: 試験計画が詳細化し、テスト実装の工数が増加する。L1 タスクでは過剰になる可能性。観点の選択基準（変更レベル・対象層によるフィルタリング）を明記することで軽減できる。
- **評価方法**: Skill 改善後に `external-service-failure`（障害系）/ `refactoring`（冪等性）/ `frontend-screen-addition`（フロントエンド固有）の eval ケースでテスト網羅性スコアが 3 以上に改善するか。改善前平均 2.0 → 改善後 3.0 以上を目標。
- **昇格判定**: 昇格条件を満たす（→ proposal 起票）。理由: 8 eval ケース横断で同種の弱点（テスト観点の不足）が複数回観測されており、昇格条件「Reviewer から同種の重大指摘を複数回受けた」および「作業時間またはトークンを継続的に浪費している（テスト品質が低くて手戻りが発生するリスク）」に該当する。なお事象 2 と根本原因が一部重複する（テストランナー未導入 vs. Skill の観点不足）ため、manager による統合・分離の判断が必要。

### 事象 5: contract-designer の起動条件が orchestrator 判断依存で不明確（ベースライン採点で特定）

- **種類**: レビュー指摘（ベースライン採点による構造的指摘）
- **観測した事象**: eval INDEX.md 分析で、契約品質（平均 3.4）の弱点として「contract-designer 起動条件が orchestrator の判断に依存しており、L2 の API フィールド追加（Zod スキーマ変更）で必ず起動するかが不明確」という問題が指摘されている。本タスクでは直接影響がなかったが、将来の API 追加タスクで再現しうる。
- **発生回数**: ベースライン採点で初回記録。本タスクでは発生なし。
- **対象タスク**: 今後の api-field-addition / contract-validation-change 相当のタスク
- **原因仮説**: orchestrator が contract-designer を呼び出すかどうかの判断が暗黙的で、L2 の API フィールド追加でも起動しないケースが想定される。起動条件が明示的なルールとして定義されていないため、orchestrator の判断のブレが品質のばらつきを生む。
- **改善案**: orchestrator agent 定義または orchestration-policy.md に「Zod スキーマ変更 / API フィールド追加 / 外部サービスとの連携変更を含む L2 以上のタスクでは contract-designer を必ず起動する」という条件を追記する（ただし CLAUDE.md / Agent 定義への変更は manager 検討 → 人間承認が必要）。
- **変更対象**: orchestration-policy.md または orchestrator agent 定義（変更対象の確定は manager に委ねる）
- **想定される副作用**: contract-designer の起動頻度増加によるトークンコスト増。ただし契約品質の向上と天秤。
- **評価方法**: `api-field-addition` eval ケースの契約品質スコアが 3 から 4 以上に改善するか。
- **昇格判定**: Memory 留め（昇格せず）。本タスクでは発生しておらず、ベースライン採点での観測のみ。同種の問題（contract-designer が起動しなかった）が実タスクで 2 回以上発生した段階で昇格する。
