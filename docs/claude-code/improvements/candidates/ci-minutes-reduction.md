## 観測した事象

### 事象 1: 実測前に削減率を口頭で提示し、2 回続けて過大だった

- **種類**: ユーザーへの誤情報（自己検出・自己訂正）
- **観測した事象**: ユーザーに削減効果を説明する際、実測前に概算を提示して 2 回訂正した。
  1. 「ジョブ統合で run あたり 3 分前後（約 40%）削減」→ 実際は静的チェック 3 つの統合だけでは
     **約 9%**。GitHub Actions が**ジョブ単位で分単位に切り上げ**課金することを織り込んでおらず、
     `pnpm install` の重複時間だけを見ていた。
  2. 「今日の push 5 回中 3 回が docs のみ。パスフィルタで 33 分削減できた」→ PR の CI は
     前回 push との差分ではなく **base との差分**を見るため成立しない。実測では
     PR 全体がドキュメントのみだったのは直近 25 件中 **3 件（12%）**。
- **発生回数**: このタスク内 **2 回**（同一セッション・同一テーマ）。
- **対象タスク**: ci-minutes-reduction
- **原因仮説**: コスト・性能の削減率は「対象の課金モデル」と「計測の単位」に強く依存するが、
  どちらも確認せずに直感で概算した。しかも数字を出すと相手はそれを前提に意思決定するため、
  概算であることを明示しても実質的に誤情報として作用する。
- **改善案**: **コスト・性能の削減率を数値で提示する前に、必ず実測を取る**。
  実測できない場合は数値を出さず「未計測」と述べる。とくに従量課金の対象では
  課金単位（分単位切り上げ・ジョブ単位など）を先に確認する。
- **変更対象**: `.claude/rules/coding-standards.md` は不適当。CLAUDE.md の行動制約、または
  `quality-gates` / 新規の運用 Skill が候補（**まだ未定**）。
- **想定される副作用**: 「まず測る」ため初動が遅くなる。実測が難しい領域では
  「未計測」と答えることになり、即答性は下がる。
- **評価方法**: 次にコスト・性能の改善提案を行うタスクで、数値提示の前に実測が入ったかを確認する。
- **昇格判定**: **昇格条件の判断を manager に委ねる**。同一セッション内 2 回であり
  「同じ訂正が 2 回」に該当し得るが、テーマが同一（CI 分数）のため独立事象と数えるかは判断が要る。

### 事象 2: 機械判定の正規表現のアンカーミス（同一セッションで 2 件目）

- **種類**: 手戻り（再発）
- **観測した事象**: 変更範囲の判定を `^(docs/|logs/|notes/|[^/]*\.md)$` と末尾 `$` で閉じたため、
  `docs/` という文字列そのものにしかマッチせず、`docs/designs/a.md` が
  ドキュメント扱いにならなかった。前方一致（`^(docs/|logs/|notes/)`）と
  完全一致（`^[^/]*\.md$`）を分けて修正した。
- **発生回数**: 累計 **2 回目**。1 回目は同日の project-refactoring 事象 3
  （`\{([\s\S]*?)\}` が `}` を跨いで隣接 import を巻き込んだ）。
  いずれも「正規表現の境界指定の誤り」で、**同一セッション内での再発**。
- **対象タスク**: ci-minutes-reduction（今回）/ project-refactoring（同日）
- **原因仮説**: 正規表現を「読んで正しそう」で確定させ、実行して確かめていない。
  1 回目は型検査、2 回目はパターン表による検証で検出できたが、いずれも書いた直後ではなく
  適用後の検出だった。
- **改善案**: **機械判定・機械置換に使う正規表現は、書いた直後に代表パターン表で実行検証する**
  （適用前に）。今回は試験計画に 10 パターンを用意していたため、適用前に検出できた。
  この「先にパターン表を作る」手順自体が有効だった。
- **変更対象**: `.claude/skills/quality-gates/SKILL.md` または新規の運用 Skill（**まだ未定**）。
- **想定される副作用**: 小さな置換にも検証を課すと過剰になる。
  「複数ファイルに適用する」「CI の判定に使う」など影響範囲で線を引く必要がある。
- **評価方法**: 次に正規表現で機械判定・機械置換を行うタスクで、適用前の検証が入ったか。
- **昇格判定**: **昇格条件の判断を manager に委ねる**（同種の手戻りが 2 回）。

### 事象 3: 成果物ポリシーの逸脱を独断で決め、Hook に是正された

- **種類**: 手戻り（プロセス）
- **観測した事象**: 変更が CI ワークフロー 1 ファイルであることを理由に、
  「実装計画・試験計画は設計書に内包する」と設計書の冒頭に書いて 1 ファイルで済ませた。
  Stop hook の完了前チェックが `docs/implementation-plans/` と `docs/tests/` の不在を検出し、
  指摘を受けて 3 点に分離した（テスト方針は設計書から試験計画へ移動し、重複は作らなかった）。
- **発生回数**: このタスク内 1 回。
- **対象タスク**: ci-minutes-reduction
- **原因仮説**: `document-policy.md` の「設計書作成自体を目的にしない」「重複作成しない」を
  根拠に規模相応と判断したが、**成果物の点数を減らす判断はポリシーの変更**であり、
  個別タスクの裁量で決めてよい範囲を超えていた。
- **改善案**: 成果物を減らす判断はタスク内で決めず、(a) ポリシーどおり作成する、
  または (b) ユーザーに確認する、のいずれかにする。内容が薄くなる場合は、
  重複を作らないよう**正となる文書を 1 つ決めて他はポインタにする**（今回の是正がその形）。
- **変更対象**: なし（既存の Hook が機能しており、追加の仕組みは不要）。
- **想定される副作用**: なし。
- **評価方法**: 次の L2 タスクで、成果物 3 点が最初から作成されるか。
- **昇格判定**: **Memory 留め（昇格せず）**。Hook が検出できているため仕組みの追加は不要。
  ただし「Hook 頼みで初回から守れていない」点は、再発すれば昇格を検討する。
