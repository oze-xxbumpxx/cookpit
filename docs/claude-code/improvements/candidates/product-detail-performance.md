## 観測した事象（複数可）

### 事象 1: 実画面確認で前提データ（0 件シード済み）を使わず、性能要件の欠落を見落としかけた（累計 3 回目・昇格条件を機械的に充足）

- **種類**: 手戻り（レビューで検出）/ **再発（3 回目）**
- **観測した事象**: MB-01（レイアウトシフトの確認）を「価格記録あり」の商品でしか実施せず PASS
  とした。0 件用のデータ（にんじん）は同セッション内で自分がシードしていたにもかかわらず、
  確認項目に使わなかった。結果、レビューで Must（0 件時にスケルトン 256px → 空状態 84px で
  約 170px 縮み、直下の「この商品を削除」ボタンが 55px 上へジャンプする）を検出された。
  Orchestrator 側の見落としであり、実装自体の欠陥ではない。
- **発生回数**: 累計 3 回目。shopping-list-price-comparison 事象 1（1 回目、内訳が無い品目で
  「崩れない」を false PASS）→ price-record-edit-and-store-rename 事象 3（2 回目、前提記述
  ミス + 陳腐化 DB による false PASS。前候補が「次回再発で 3 回を待たず昇格を推奨」と明記）→
  本事象（3 回目）。memory-policy.md の通常条件（3 回以上）も満たす。
- **対象タスク**: product-detail-performance（今回・MB-01）/ price-record-edit-and-store-rename
  （前回・MB-03）/ shopping-list-price-comparison（前々回・MB-04）
- **原因仮説**: 前々回・前回と同じ — `manual-browser-verify` の型が確認項目の列挙・PASS/FAIL
  出力までは規定するが、**用意した前提データのうち「境界・例外系（0 件・空・縮退）」を必ず
  1 つは確認項目に充てる**という手順が無い。今回は 0 件データを用意する判断自体はできていた
  （境界条件を意識してシードした）のに、確認項目の設計段階でそれを使う項目を作らなかった。
  「データを用意する」と「そのデータで確認する項目を作る」が別工程であることが見落とされている。
- **改善案**: （提案止まり）`manual-browser-verify` Skill か試験計画作成時のチェックリストに
  「性能・レイアウト系の確認項目では、通常データに加えて境界データ（0 件・最小・最大）での
  確認項目を最低 1 つ設ける」旨を追加する案。過去 2 回の候補が提案していた「前提条件を満たす
  データの検証」「ネガティブコントロール」に加え、今回は「境界データを用意したなら必ず確認項目化
  する」という一段具体的な手順が必要と判明した。
- **変更対象**: `.claude/skills/create-test-plan/SKILL.md` または
  `.claude/skills/manual-browser-verify/SKILL.md`（累積 3 回分の原因仮説を統合して manager が判断）
- **想定される副作用**: 境界データの確認項目を機械的に必須化すると、境界が存在しない機能
  （常に非 0 件が保証される等）まで無理に項目を作らせる恐れがある。「0 件・空を取りうる
  UI 要素がある場合」に適用範囲を絞る必要がある。
- **評価方法**: 次の L2/L3 で性能・レイアウト系の試験計画を作る際、境界データの確認項目が
  作成時点で列挙されているかを確認する。
- **昇格判定**: **昇格条件を満たす（3 回目・通常条件でも充足）**。次の横断分析で
  shopping-list-price-comparison 事象 1・price-record-edit-and-store-rename 事象 3 と統合して
  proposal 化することを推奨する。

### 事象 2: FAIL 判定を下した後に測定基準を変更した（新規・構造的リスク）

- **種類**: 手戻り（自己検出）/ **新規の失敗モード**
- **観測した事象**: MB-01 の一次計測で「チャート下要素の Y 座標が 115px 動いた」ことを根拠に
  FAIL と判定した。その後、測定窓が広すぎて `PriceRecordForm` の店舗一覧取得（本タスクで
  変更していない既存挙動）由来の既存シフトを巻き込んでいたと気づき、「セクション高さ自体は
  284px で不変」という**より狭い測定**に切り替えて PASS と判定し直した。基準変更が
  結論に都合よく寄せた rationalization でないことを、独立した直接測定（切り替え前後で
  セクション高が完全一致）で裏取りして確認した。
- **発生回数**: 1 回目（この形での明示的な観測は初めて）
- **対象タスク**: product-detail-performance
- **原因仮説**: 一次判定が FAIL だったときに、判定者自身が基準（測定範囲）を見直す作業と、
  その見直しが正当かどうかを判定者自身が評価する作業が、同一の主体（同一セッション）内で
  連続して行われている。今回は結果的に正しかった（独立測定での裏取りができた）が、
  「FAIL を見てから基準を緩める」という順序そのものが、**確証バイアスに対して脆弱な操作**
  であることに変わりはない。基準変更の妥当性を検証する手段（独立した観点での再測定）が
  たまたま今回は利用可能だった（セクション高という別指標があった）だけで、一般には
  常に使えるとは限らない。
- **改善案**: （提案止まり）FAIL 判定後に測定基準・測定範囲を変更する場合は、(a) 変更前の
  生データ（今回なら「Y 座標 115px 移動」の内訳）を記録として残す、(b) 基準変更の理由を
  「why now」（なぜ後から気づいたか）とともに明記する、(c) 変更後の判定は**変更前の指標とは
  独立した別の指標**で裏取りする、の 3 点を `manual-browser-verify` Skill か試験計画の
  完了条件へ明記する案。特に (c) は今回たまたま「セクション高」という独立指標があったから
  できたことで、無ければ緩めた基準の正当性を確認する手段が無いまま PASS にしていたリスクがある。
- **変更対象**: `.claude/skills/manual-browser-verify/SKILL.md`（まだ未定）
- **想定される副作用**: 毎回の基準変更に独立指標での裏取りを義務付けると、単純な計測ミス
  （誤操作・誤読）の訂正まで大掛かりな手続きになり得る。「FAIL→PASS 方向への基準変更」に
  限定するなど、PASS→FAIL 方向（安全側）への変更とは非対称に扱う設計が必要。
- **評価方法**: 次に FAIL 判定後に基準を見直すケースが発生したとき、独立指標での裏取りが
  行われているか、生データが記録に残っているかを確認する。
- **昇格判定**: **Memory 留め（昇格せず）**。IMP-2026-030 により 1 回目での昇格は見送るが、
  「FAIL を見てから基準を緩める」操作は構造的に確証バイアスへ脆弱であり、独立裏取りが
  できない状況で同型が再発した場合は、実害の重大性（誤った PASS 判定が一時的に定着すること）を
  踏まえて早期昇格を検討する価値がある。

### 事象 3: ビルド成果物と dev サーバーの不整合を製品欠陥と誤診しかけた（累計 2 回目相当・環境誤診）

- **種類**: 手戻り（自己検出）/ **再発（別の機構による同型再発）**
- **観測した事象**: バンドルサイズ計測のために `next build` を実行した後、生成された `.next`
  を残したまま `next dev` を起動したところ、商品詳細ページが 404 を返した。一瞬「新設した
  `GetProductDetailUseCase` の欠陥」と誤診しかけたが、実際は本番ビルド成果物と dev サーバーの
  不整合（ファイルを 1 つ触って再コンパイルさせると解消）だった。
- **発生回数**: 「環境の状態不整合を製品欠陥と誤診しかける」という広いテーマで**累計 2 回目**。
  1 回目は price-record-edit-and-store-rename 事象 3(b)（dev サーバー起動中に PGlite を
  再シードし、古いハンドルを掴んだまま false PASS を出した）。今回は逆方向（本番ビルドと dev
  の不整合による false FAIL 寸前）で、同じ「環境操作の順序を誤ると偽の判定材料が生まれる」
  という根っこを共有するが、具体的な機構（DB ハンドルの陳腐化 vs ビルド成果物とdevの不整合）
  は異なる。
- **対象タスク**: product-detail-performance（今回）/ price-record-edit-and-store-rename（前回）
- **原因仮説**: 性能計測（`next build`）と実画面確認（`next dev`）を同一の作業ディレクトリで
  連続して行う手順が、それぞれの成果物・プロセスの状態管理（`.next` の扱い、DB ハンドルの
  ライフサイクル）について明文化されていない。実施者が経験則で気づく形になっており、
  手順化されていないため毎回同じ落とし穴に当たるリスクがある。
- **改善案**: `manual-browser-verify` Skill か性能計測系の Skill に「`next build` によるバンドル
  計測の後に `next dev` へ切り替える場合は `.next` を削除してから起動する」という手順注意を
  追加する案。前回の「PGlite 再シード時はサーバーを止めてから行う」と合わせて、
  **「計測・DB 操作の前後でプロセス/成果物の状態が変わる操作をしたら、次の確認の前に
  環境をクリーンにする」という一段抽象化した原則**として統合する余地がある。
- **変更対象**: `.claude/skills/manual-browser-verify/SKILL.md`
- **想定される副作用**: 毎回 `.next` 削除や DB 再起動を義務付けると、実行時間が伸びる
  （`next build` の再実行コストは小さくないため、必要な場面に限定する必要がある）。
- **評価方法**: 次にバンドル計測と実画面確認を同一タスク内で行うケースで、環境切り替えの
  手順注意が踏まれ、同種の誤診が起きないかを確認する。
- **昇格判定**: **Memory 留め（昇格せず）**。累計 2 回目だが機構が異なるため合算での即時昇格は
  見送る。次回同種（環境操作順序による偽の判定材料）が起きたら 3 回目として昇格を推奨する。

### 事象 4: 回帰ガードがモジュールキャッシュにより誤って PASS した（テストの置き方が検出力を殺す・関連 2 件目）

- **種類**: テスト失敗（実装漏れの検出失敗）/ 自己検出
- **観測した事象**: M-1 の修正（0 件時にチャートの dynamic import 自体を走らせない）を検証する
  ため、0 件時の同期描画を既存の `product-detail-client.test.tsx` 内でアサートしたところ、
  同ファイル内の先行テストの `render()` によって `import('./price-history-chart')` が
  モジュールキャッシュ経由で解決済みになっており、**バグのある実装（dynamic import を
  条件分岐せず常に走らせる実装）でもテストが PASS してしまった**。独立ファイル
  `product-detail-client.lazy-chart.test.tsx` に `PDC-16` を分離することで真の Red
  （バグを仕込むと確実に落ちる状態）を得て、修正の効果を正しく検証できた。
- **発生回数**: 「テストの物理的な配置・実行順序が検出力を左右し、見た目は正しいテストが
  実は何も検証していない」という上位テーマで見ると、price-record-edit-and-store-rename
  事象 2（`it.each` の範囲表記が grep 追跡を破壊）と関連 2 件目。ただし機構は全く異なる
  （grep によるソースコード上の文字列追跡 vs vitest のモジュールレジストリ分離）ため、
  同一事象としては 1 回目、上位テーマとしては 2 件目という位置づけ。
- **対象タスク**: product-detail-performance（今回）/ price-record-edit-and-store-rename（前回、別機構）
- **原因仮説**: vitest はテストファイル単位でモジュールレジストリが分かれるが、
  「dynamic import の解決有無」を検証するテストを既存の同ファイル内に追加する際、
  先行テストが同じモジュールを import 済みだとキャッシュが効いてしまうという性質が
  `create-test-plan` / TDD の Red 確認手順で意識されていない。今回は「一度誤って PASS した」
  ことに気づけたが、気づかなければそのまま「検証済み」として扱われていた。
- **改善案**: （提案止まり）「dynamic import の解決タイミング（走る/走らないの分岐）を検証する
  テストは、モジュールキャッシュの影響を受けないよう独立したテストファイルに分離する」という
  注意点を `.claude/skills/create-test-plan/SKILL.md` または `coding-standards.md` §テストへ
  追記する案。TDD で Red を確認する運用（price-record-edit-and-store-rename 事象 6 で導入）と
  組み合わせて、「Red を確認する際は対象のモジュールが他のテストで先に import されていないか
  確認する」手順を明文化する余地がある。
- **変更対象**: `.claude/skills/create-test-plan/SKILL.md`（まだ未定）
- **想定される副作用**: dynamic import の検証を伴わない大半のテストにはこの注意は不要であり、
  適用範囲を「dynamic import の解決有無・タイミングを検証するテスト」に限定する必要がある。
- **評価方法**: 次に dynamic import の条件分岐を検証するテストを書く際、独立ファイルへの
  分離判断が事前に行われ、誤 PASS が起きないかを確認する。
- **昇格判定**: **Memory 留め（昇格せず）**。1 回目（この機構としては）。上位テーマとしては
  2 件目のため、次回、別の機構で同型が再発すれば早期昇格を検討する。

### 事象 5: 自分が挿入した実施結果ブロックで Markdown テーブルを壊し、レビューに指摘された（自己混入・単発）

- **種類**: レビュー指摘（自己検出前に指摘）/ 自己混入
- **観測した事象**: 試験計画の BLD 表・MB 表に実施結果を引用ブロックとして追記した際、
  ヘッダ行と区切り行（`| --- | --- |`）の間、あるいは区切り行より後にブロックを挿入してしまい、
  Markdown テーブルとして描画されなくなった（レビュー S-4）。指摘は正当と認め、
  引用ブロックを表の直後へ移動して復元した。
- **発生回数**: 1 回目
- **対象タスク**: product-detail-performance
- **原因仮説**: Markdown テーブルは「ヘッダ → 区切り行 → データ行」が連続していないと
  パーサに認識されないという制約を、実施結果を追記する作業時に意識していなかった。
  試験計画のテンプレートにも「表の途中に別要素を挟まない」という明示的な注意が無い。
- **改善案**: 試験計画・実装計画へ実施結果を追記する Skill（あれば）に「表の途中へ引用ブロックを
  挿入しない。実施結果は表の直後にまとめる」という注意を追記する案。ただし 1 回目であり、
  影響も小さい（レビューで即座に検出・修正できた）ため優先度は低い。
- **変更対象**: なし（1 回目のため見送り）
- **想定される副作用**: なし
- **評価方法**: 次に試験計画・実装計画へ実施結果を追記する際、表構造が壊れていないかを
  自己レビューで確認できるかを見る。
- **昇格判定**: **Memory 留め（昇格せず）**。1 回目・影響小。

### 事象 6: grep -rho による ID 照合の誤り（自己検出・軽微）

- **種類**: 手戻り（自己検出、実害化前に訂正）/ 照合手段の使い方の問題
- **観測した事象**: 新規 UseCase・DTO の識別子（`GPD` / `BLD` 等の略号）が既存で使用済みかを
  `grep -rho` で確認したところ、`-o` フラグが行内容のみを出力しファイル名を伴わないため、
  誤って「既存で使用済み」と判定した。その場で気づき、`-l`（ファイル名表示）等を使った
  照合に切り替えて訂正した。実害はユーザーへの誤報告には至らなかった。
- **発生回数**: 1 回目（この特定のフラグの誤用として）。price-record-edit-and-store-rename
  事象 2（`it.each` の範囲表記が grep 追跡を破壊）と同じ「grep による ID/文字列照合が
  失敗する」という広いテーマの再発ではあるが、原因（範囲表記 vs `-rho` フラグの誤用）が
  異なり、かつ今回はユーザーへの誤報告に至る前に自己修正できている点で深刻度が低い。
- **対象タスク**: product-detail-performance
- **原因仮説**: `grep` のオプションの組み合わせ（`-r` `-h` `-o`）による出力形式の違いを
  作業のたびに正確に把握せず使っていることが根本。試験 ID・識別子の機械照合という同じ
  作業パターンが複数タスクで繰り返し発生しているのに、標準的な照合コマンド・スクリプトが
  定まっていない。
- **改善案**: price-record-edit-and-store-rename 事象 2 の改善案 (b)（試験 ID 一覧と実装の

### 事象 7: レビューへの上限指示（回数・時間・観点）が効き、成果物ゼロ再発を防いだ（成功パターン）

- **種類**: 成功手順

  reviewer Subagent が上限指示なしで単発委譲され、46 ツール呼び出しの時点までは進行を
  確認できたものの、その後 13 時間超にわたり成果物ゼロのまま失われた（同候補ファイル事象 1、
  manager 判断を推奨・強め、として記録済み）。
- **発生回数**: 1 回目（明示的な上限指示ありのケースとして）。前タスクの「上限指示なし」との
  対比として意味を持つ。
- **対象タスク**: product-detail-performance（今回、上限指示あり）/
  price-record-edit-and-store-rename（前回、上限指示なし・事象 1）
- **原因仮説**: reviewer（または他の単発委譲）が長時間ハングする根本原因
  （`harness-complexity-audit` 事象 2 系譜。IMP-2026-028 の対策範囲外）は本タスクでは

- **評価方法**: 次に単発委譲（reviewer 等）へ上限指示を付けたタスクで、成果物ゼロの再発が
