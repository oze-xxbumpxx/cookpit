### 事象 1: 移行要否を実装前に実測ゲート化して、設計を 1 つ省けた

- **種類**: 成功手順
- **観測した事象**: 名前空間を `package.json` の `name` 由来にする設計を書いた段階で、
  「Cookpit では導出結果が現行値 `cookpit-harness` と一致するので移行不要」と気づき、
  実装計画に**手順 3 を独立したゲート**として置いた（「不一致ならここで中断してユーザーへ報告」）。
  実装後にコマンドで実測して一致を確認 → データ移行の設計・スクリプト・試験を一切書かずに済んだ。
  さらに回帰試験（観点 8）で `cookpit-harness` を固定し、将来この前提が壊れたら検出できるようにした。
- **発生回数**: このタスク内 1 回
- **対象タスク**: harness-portability
- **原因仮説**: サフィックス規則を「現行値と一致させる」ことを**設計目標として明示**したため
  （設計書「変更後構成」でサフィックスの理由を 2 つ書いた）。偶然の一致を後から発見したのではなく、
  一致するように規則を選んだ。
- **改善案**: 後方互換・データ移行を伴う変更では、「移行が不要になる設計は選べないか」を
  設計段階で先に検討し、選べる場合は**実測ゲートを実装計画のステップとして独立させる**。
  移行スクリプトを書いてから不要と気づくより安い。
- **変更対象**: （まだ未定 — 成功 1 回目。再現したら create-design-document か
  create-implementation-plan への追記を検討）
- **想定される副作用**: 「移行不要にできる」ことを過度に優先すると、設計として不自然な
  命名規則を選ぶ危険がある。今回はサフィックスに独立した理由（用途が名前で分かる）があった。
- **評価方法**: `.claude/evals/cases/database-schema-change.md`（移行を伴う変更の代表ケース）で
  before/after 比較する。
- **昇格判定**: Memory 留め（昇格せず・成功 1 回目。memory-policy の「成功パターンの複数再現」未達）

### 事象 2: 固有名詞の棚卸しを個別の変数名で grep し、同類型を取りこぼした

- **種類**: 手戻り（軽微・スコープ内で吸収）
- **観測した事象**: 前セッション（同日）の移植性棚卸しと本タスクの初期調査で
  `COOKPIT_TZ|cookpit-harness` という**特定の名前を列挙した grep** を使ったため、
  同じ類型の `COOKPIT_GAP_CAP_MIN` を見落とした。実装中にファイルを開いて初めて気づき、
  設計書の要件 R-3 と実装計画・試験計画を後から更新することになった。
- **発生回数**: このタスク内 1 回（過去の candidates に同種の記録なし）
- **対象タスク**: harness-portability
- **原因仮説**: 「プロジェクト名がコードに残っている箇所を洗う」という**目的**に対して、
  検索式が既知の具体名の列挙になっていた。目的はプレフィックス（`COOKPIT_` / `cookpit`）の
  棚卸しなのに、検索は葉（個別の変数名）を指していた。
- **改善案**: 固有名詞・プレフィックスの棚卸しでは、**まずプレフィックス単位で grep して
  全ヒットを分類する**（`grep -rn 'COOKPIT_'` → 用途ごとに仕分け）。個別名の列挙は
  分類後の確認に使う。棚卸し系タスクの調査手順として有効。
- **変更対象**: （まだ未定 — 1 回目。audit-skills か classify-change への追記を検討）
- **想定される副作用**: プレフィックス grep はヒット数が増え、無関係な箇所の仕分けコストが増える。
  今回は `COOKPIT_METRICS_*` 11 箇所を「利用者が設定しない内部受け渡し」と判断して
  対象外に仕分ける作業が発生した（この仕分け自体は有益だった）。
- **昇格判定**: Memory 留め（昇格せず・1 回目。再発監視）

### 事象 3: Prettier の Markdown 整形が識別子と表セルを静かに書き換えた

- **種類**: テスト失敗（品質ゲート FAIL からの副作用）
- **観測した事象**: `pnpm exec prettier --write` を新規ドキュメント 3 本に当てた結果、2 種類の
  破壊が起きた。
  1. **識別子の変質**: 本文中の `GAP_CAP_MIN` が `GAP*CAP_MIN` に、`'COOKPIT_'` が
     `'COOKPIT*'` になった（`_` を emphasis と解釈し `*` へ正規化）。**内容が変わっている**のに
     ゲートは PASS するため、目視しないと気づけない。
  2. **表の破壊**: 表セル内に書いた `HARNESS_TZ || COOKPIT_TZ || 'Asia/Tokyo'` の `|` が
     セル区切りと解釈され、区切り行に列が 4 つ増えた不正な表になった。
- **発生回数**: このタスク内 2 種類（過去の candidates に prettier 関連の記録なし）
- **対象タスク**: harness-portability
- **原因仮説**: Markdown の記法（`_` = emphasis、`|` = セル区切り）と、技術文書に出てくる
  識別子・シェル式が衝突する。Prettier は Markdown として正しい整形をしており、バグではない。
  設計書に**コードの断片を素のテキストで書いた**のが原因。
- **改善案**: 技術文書で識別子・シェル式・演算子を書くときは必ずバックティックで囲む。
  特に (a) `_` を含む識別子、(b) 表セル内の `|` を含む式。表セルに `|` を含む式を
  書きたい場合は、表の外（本文）へ出すか `\|` へエスケープする。
  **`prettier --write` の後は生成物を必ず目視する**（PASS は内容の正しさを保証しない）。
- **変更対象**: （まだ未定 — 1 回目。create-design-document / create-test-plan /
  create-implementation-plan の共通注意として追記する候補）
- **想定される副作用**: 「バックティックで囲む」を強く言うと、日本語の文中で過剰に
  コードスパンが増えて読みにくくなる可能性がある。適用対象を「`_` を含む識別子」と
  「表セル内の記号を含む式」に絞るのが妥当。
- **昇格判定**: Memory 留め（昇格せず・1 回目）。ただし**内容が静かに変質する**類型で
  発見が遅れると誤情報が残るため、再発時は優先して昇格を検討する。

### 事象 4: `git add` のパス列挙で、実装計画に載っていた変更ファイルを 1 つ取りこぼした

- **種類**: 手戻り（Stop hook が検出）
- **観測した事象**: コミット時に `git add -A .claude docs/designs/... docs/implementation-plans/...
docs/tests/...` とパスを列挙したが、実装計画の「変更対象ファイル」表に載っていた
  `docs/claude-code/harness-state.md` を列挙から漏らした。コミット直前の `git status` にも
  差分として出ていたが照合しなかった。Stop hook の未コミット検出で気づき、追加コミットになった。
- **発生回数**: このタスク内 1 回（過去の candidates に同種の記録なし）
- **対象タスク**: harness-portability
- **原因仮説**: 新規ファイル 3 本を明示的に add する必要があったため個別列挙にしたが、
  そのとき既存変更ファイルの列挙が「`.claude` 配下」だけになった。
  実装計画に**変更対象ファイルの一覧が既にある**のに、コミット前の照合に使わなかった。
- **改善案**: L2/L3 のコミット前に、実装計画の「変更対象ファイル」＋「新規作成ファイル」表と
  `git status --short` を突き合わせる。パスを列挙する `git add` を使うなら照合は必須。
  照合しないなら `git add -A` を単独で使う。
- **変更対象**: （まだ未定 — 1 回目。close-session か definition-of-done への
  チェック項目追加を検討）
- **想定される副作用**: `git add -A` の単独使用は意図しないファイルを巻き込む危険があるため、
  「照合する」側を推すのが安全。チェック項目が 1 つ増える。
- **昇格判定**: Memory 留め（昇格せず・1 回目。再発監視）

### 事象 5: 変更対象モジュールの既存テストカバレッジの穴を発見した（本タスク起因ではない）

- **種類**: 成功手順（試験計画のメソッド網羅チェックが機能した）
- **観測した事象**: 試験計画のメソッド網羅チェック表を埋める過程で、
  `.claude/lib/harness-paths.mjs` の公開 API 14 件のうち **7 件が本変更以前から未テスト**
  だと判明した（`stateDir` / `statePath` / `safeStatePath` / `resolveReadablePath` /
  `hasSafePermissions` / `repoRoot` / `legacyStateDir`・`legacyStatePath`）。
  いずれも状態の永続性を担う関数で、`safeStatePath` は「失敗しても作業を止めない」
  フォールバック経路を持つ。
- **発生回数**: このタスク内 1 回
- **対象タスク**: harness-portability
- **原因仮説**: `harness-paths.mjs` の試験は `resolveStateDir` の**安全境界**（リポジトリ配下拒否・
  シンボリックリンク拒否）に集中して書かれた。安全境界は最重要なので優先順は妥当だが、
  その後の関数追加時に網羅を見直す契機がなかった。
- **改善案**: 本タスクでは依頼スコープ外として追加しなかった（CLAUDE.md「スコープ」）。
  別タスクとして backlog へ起票し、Phase 2 で `harness-paths.mjs` を他プロジェクトへ
  配る前に埋めるのが望ましい（配布後は不具合の影響範囲が広がる）。
- **変更対象**: なし（テスト追加のみ。設定変更を伴わない）
- **想定される副作用**: なし（テスト追加のみ）
- **昇格判定**: Memory 留め（設定改善ではなく個別タスク。backlog へ申し送る）
