### 事象 1: 実画面確認で「前提を満たさないデータ」を使い false PASS を報告した（MB-04）

- **種類**: 手戻り（自己検出）
- **観測した事象**: MB-04 は「**bought 品目の展開パネル（`PurchaseInputForm`）に内訳セクションが
  追加されても**既存入力欄が崩れない」を見る項目。しかし自動化スクリプトは、内訳を持たない品目
  （`productId` が `null` のじゃがいも）を展開して価格入力欄の存在だけを確認し **PASS と報告した**。
  内訳セクションは 1 行も描画されていない状態だった。スクリーンショットを目視して気づき、
  内訳を持つ品目（玉ねぎ）を bought にしてから展開し直して再実施（結果 PASS）。
- **発生回数**: このタスク内 1 回（`manual-browser-verify` Skill 自体は IMP-2026-020 で
  meal-plan-screens → shopping-list-screens の 2 回成功を受けて強化済みだが、**この失敗モードは未カバー**）
- **対象タスク**: shopping-list-price-comparison
- **原因仮説**: Skill の「自動化の型」は「確認項目を先に列挙する」「セレクタは role / label ベース」
  「項目ごとに PASS / BLOCKED / FAIL を機械的に出力する」までは規定しているが、
  **各項目の前提条件を満たす確認データを用意する**手順がない。加えて、存在確認中心の
  アサーション（`count() > 0`）は「対象が無い」と「対象が正しく描画されている」を区別できないため、
  前提を外すと**空振りがそのまま PASS になる**。これは実画面確認の目的（テスト green でも
  分からない問題の検出）を静かに無効化する。
- **改善案**: `manual-browser-verify` Skill の手順 1 を「確認項目を列挙する」から
  「確認項目と**その前提条件**（どんなデータ状態で見るか）を対にして列挙する」へ強化し、
  「自動化の型」に**ネガティブコントロール**を 1 行追加する — 前提を満たさないデータでは
  当該アサーションが FAIL することを一度確かめてから PASS を採る。
- **変更対象**: `.claude/skills/manual-browser-verify/SKILL.md`
- **想定される副作用**: 確認 1 項目あたりの手数が増える（データ準備 + ネガティブ確認）。
  項目数の多いタスクでは実施コストが上がるため、「存在確認型のアサーションを持つ項目」に
  限定するなど適用範囲を絞らないと過剰手順になる。
- **評価方法**: 画面変更を含む次の L2/L3 タスクで MB 系項目を実施し、(a) 各項目に前提条件が
  明記されているか (b) 前提を満たさないデータでの誤 PASS が発生しないか を確認する。
- **昇格判定**: **Memory 留め（昇格せず）**。1 回目であり、IMP-2026-030「早期昇格の原則禁止」に従う。
  ただし本事象は**誤りを PASS として報告する**性質（silent failure）であり、
  次回同型が 1 度でも再発したら 3 回を待たず昇格させることを推奨する。

### 事象 2: 試験計画の項目名より PASS 基準が弱く、実施時に判定が割れた（MB-01）

- **種類**: レビュー指摘（試験計画の品質）
- **観測した事象**: MB-01 の項目名は「総額差の行が本文列で**折り返し・はみ出しなく**収まる」だが、
  同じ行の PASS 基準は「横スクロール・文字の見切れが発生しない」しか書いていない。
  実画面では 390px で「業務スーパーBの方が約10 / 円安い」と**2 行に折り返した**ため、
  **項目名では FAIL・PASS 基準では PASS** という状態になった。基準どおり PASS とし、所見を
  レビュー記録へ残して処理したが、判定の一貫性は担保できていない。
- **発生回数**: このタスク内 1 回
- **対象タスク**: shopping-list-price-comparison
- **原因仮説**: `create-test-plan` Skill の実画面確認節に、**項目名に書いた条件をすべて
  PASS 基準へ落とす**という整合要求がない。項目名は「あるべき姿」を作文しやすく、
  PASS 基準は「機械的に判定できること」に寄るため、両者が自然に乖離する。
- **改善案**: `create-test-plan` Skill の実画面確認（MB 系）節に「**項目名に含めた条件は
  すべて PASS 基準側にも明記する。判定できない条件は項目名から外す**」を追加する。
- **変更対象**: `.claude/skills/create-test-plan/SKILL.md`
- **想定される副作用**: ほぼ無い（文言 1 行）。ただし「判定できない条件は項目名から外す」を
  機械的に適用すると、意図的に定性的な確認項目（見た目の違和感等）を削りすぎる恐れがある。
- **評価方法**: 次に MB 系項目を作る L2/L3 タスクで、項目名と PASS 基準の条件集合が一致しているか確認する。
- **昇格判定**: **Memory 留め（昇格せず）**。1 回目。

### 事象 3: 設計側の指摘を先に処理したら Must の欠陥経路ごと消滅した（成功パターン）

- **種類**: 成功手順
- **観測した事象**: レビューは M-1（Must: 初期値なし `reduce` の `TypeError` で画面が落ちる）と
  S-3（Should: 内訳の基準区分を次元の違う raw 最小単価で決めている）を**独立の指摘**として挙げていた。
  S-3 の修正（基準区分を最頻 kind で決める）を行うと、M-1 の欠陥箇所である `findCheapestRecord`
  自体が不要になり関数ごと削除され、**欠陥経路が消滅した**。M-1 のガードは二重防御として残置。
- **発生回数**: このタスク内 1 回
- **対象タスク**: shopping-list-price-comparison
- **原因仮説**: レビュー差し戻しは重大度順（Must → Should → Nice）に潰すのが自然だが、
  **下位の設計指摘が上位の実装欠陥の原因になっている**ことがある。重大度順に着手すると、
  先に入れた個別ガードが後の設計変更で不要になり、二重の作業になる（今回は結果的に
  二重防御として意味を持ったが、無駄になる場合もある）。
- **改善案**: レビュー差し戻し対応の着手順を「重大度順」ではなく「**依存順（設計 → 実装 → テスト）**」
  とする指針を明文化する。まず Should 以下に設計変更を伴う指摘が無いか走査し、あれば先に確定させる。
- **変更対象**: （まだ未定）`.claude/agents/orchestrator.md` または
  `docs/claude-code/development-workflow.md` の差し戻し節
- **想定される副作用**: Must の修正が後回しに見えることで、マージブロッカーの解消が遅れる印象を与える。
  「設計指摘の確定が Must の修正内容を変えうる場合に限る」と条件を付けないと過剰適用になる。
- **評価方法**: 次にレビュー差し戻しが発生した L2/L3 タスクで、設計指摘の先行確定により
  実装修正の手戻りが減ったかを比較する。
- **昇格判定**: **Memory 留め（昇格せず）**。成功パターンの 1 回目（昇格条件「複数タスクで再現」未充足）。

### 事象 4: 「CI 限定のフレーク」と分類していた失敗が、実体はテストの実装バグだった

- **種類**: テスト失敗（原因の誤分類）
- **観測した事象**: `logs/2026-08-04.md` セッション 2 に「web の RTL テストに **CI 限定の**
  フレークがある」「**CI 環境の遅さによる待ち時間切れ**が疑わしい」と記録されていた。
  本タスクでテストを 8 件追加したところ、**ローカルでも 4 回に 1 回**
  `shopping-list-client.remove.test.tsx` の SDL-05 が落ちるようになった。原因は環境ではなく
  テストの実装で、楽観削除の巻き戻しはエラーバナー表示とは**別の React コミット**で反映されるのに、
  行の復帰アサーションを `waitFor` の**外**に置いていた。アサーションを `waitFor` 内へ移して 6/6 green。
- **発生回数**: このタスク内 1 回（誤分類のまま 1 日運ばれていた）
- **対象タスク**: shopping-list-price-comparison（誤分類の起点は 2026-08-04 セッション 2）
- **原因仮説**: 「再実行で通った」ことから環境起因と結論づけた。**反復実行による再現の試行**を
  していない。テスト件数が少ないうちは実行時間が短く、レースが顕在化しなかったため、
  「CI だけ遅いから落ちる」という説明が一見成立してしまった。
- **改善案**: フレーク遭遇時の切り分け手順を明文化する — 「再実行で消えても環境起因と断定せず、
  **同一スイートを 5 回以上反復実行**して再現を試みる。再現したらテスト側のバグとして扱う」。
  併せて「`waitFor` の直後に置く同期アサーションは、待った条件と同時に満たされる保証がない」を
  コーディング規約のテスト節へ入れる候補とする。
- **変更対象**: （まだ未定）`.claude/skills/quality-gates/SKILL.md` または
  `.claude/rules/coding-standards.md` §テスト
- **想定される副作用**: 反復実行は時間を食う（本リポジトリの web スイートは 1 回 8 秒程度なので
  実害は小さいが、infrastructure の PGlite テストは 200 秒超のため全スイート反復は現実的でない）。
  適用対象を「落ちたファイル単位」に限定する必要がある。
- **評価方法**: 次にフレークを観測したタスクで、反復実行による切り分けが行われ、
  「環境起因」と結論づける前にテスト側の可能性が除外されているかを確認する。
- **昇格判定**: **Memory 留め（昇格せず）**。1 回目。ただし**誤分類が 1 日運ばれた**点は
  「継続的浪費」の芽であり、同種の誤分類が次に起きたら昇格を検討する。

### 事象 5: E2E Smoke は `pull_request` 限定のため「main が緑」という比較対象が存在しない（環境の既知事実）

- **種類**: 成功手順（切り分けの知見）／環境の事実
- **観測した事象**: PR #139 で E2E Smoke が 1 度失敗した。「base ブランチで再現するか」で
  切り分けようとしたが、`.github/workflows/ci.yml` の E2E ジョブは
  `if: github.event_name == 'pull_request'` のため **push では常に skip** され、
  main の最新 run でも実際に skipped だった。**「main が緑だったか」で裏を取ることは原理的にできない**。
  代わりに (a) 差分が当該機能に触れていないこと（プロダクト差分 7 ファイルすべてが
  `shopping-lists/` 配下）(b) ローカル（PGlite）で 2/2 通過すること
  (c) 失敗がアサーション不一致ではなく 5000ms のタイムアウトであること の 3 点で切り分け、
  再実行で緑を確認した。
- **発生回数**: このタスク内 1 回
- **対象タスク**: shopping-list-price-comparison
- **原因仮説**: ハーネスの一般則「CI 失敗が base ブランチでも再現するなら pre-existing」は、
  **その CI が base ブランチで走っていること**を暗黙の前提にしている。イベント条件付きの
  ジョブではこの前提が崩れる。
- **改善案**: `docs/07-dev-rules.md` §環境の既知の事実 に「E2E Smoke は `pull_request` 限定
  （push では skip）。base ブランチの緑実績は存在しないため、切り分けは差分範囲 + ローカル再現で行う」
  を 1 行追記する候補。
- **変更対象**: `docs/07-dev-rules.md`（Rule / Agent 定義ではなくプロジェクト文書）
- **想定される副作用**: ほぼ無い（事実の記録）。
- **評価方法**: 次に E2E が落ちたとき、base 比較を試みて空振りする往復が発生しないか。
- **昇格判定**: **Memory 留め（昇格せず）**。1 回目・事実の記録に留まる。
