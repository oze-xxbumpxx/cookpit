## 観測した事象（複数可）

### 事象 1: リスク受容の前提条件が逆だった

- **種類**: レビュー指摘
- **観測した事象**: 設計書 R-4 は「Pantry が空なら冪等」と書いた。実際は生成時に在庫を引いた品目の買う量が生値より小さく、再同期（在庫は既に空）で生値へ戻る。空のあとで起きやすい。
- **発生回数**: このタスク内 1 回
- **対象タスク**: meal-plan-sync
- **原因仮説**: 品目の `requiredAmount` が買う量なのに、同期の比較対象を集計生値にした。リスク節が「Pantry 非空」側に偏って頻度を見誤った。
- **改善案**: 買う量と生値を同じ列で扱う設計では、リスク節に「生成直後の再同期」を必ず書く。
- **変更対象**: （まだ未定）architecture-designer / create-design-document のチェックリスト候補
- **想定される副作用**: リスク節が長くなる
- **評価方法**: 次回の在庫引き算＋差分更新タスクで、レビューが同じ指摘を繰り返すか
- **昇格判定**: Memory 留め（昇格せず）。単発

### 事象 2: `pnpm --filter … exec vitest` は失敗する

- **種類**: テスト失敗
- **観測した事象**: パッケージの PATH に vitest が無く `ERR_PNPM_RECURSIVE_EXEC_FIRST_FAIL` になる。`pnpm --filter @cookpit/domain test` なら通る。
- **発生回数**: このタスク内 1 回
- **対象タスク**: meal-plan-sync
- **原因仮説**: `exec` はパッケージの node_modules/.bin を前提にするが、root の filter exec では解決しないことがある。
- **改善案**: 実装計画の完了条件コマンドを workspace の `test` script に揃える。
- **変更対象**: Subagent Memory（implementer）
- **想定される副作用**: なし
- **評価方法**: 次回の実装計画が `pnpm --filter <pkg> test` を書いているか
- **昇格判定**: Memory 留め（昇格せず）。単発

### 事象 3: 試験計画の全観点実装を完了条件にすると BLOCK になる

- **種類**: レビュー指摘
- **観測した事象**: 試験計画が「A-1〜A-26 がすべて実装・通過」と書いた。必須分岐（A-16/A-17/A-20）以外の FE 異常系まで含めると、レビューが BLOCK 2 件になった。
- **発生回数**: このタスク内 1 回 / 過去の L3 でも「全部書け」は起きやすい
- **対象タスク**: meal-plan-sync
- **原因仮説**: 試験計画テンプレが観点の網羅を求め、完了条件が「すべて実装」になる。
- **改善案**: 完了条件を「必須観点（正常・異常・冪等・未実行分岐）」と「後続可」に分ける。
- **変更対象**: （まだ未定）create-test-plan Skill
- **想定される副作用**: 必須の定義でもめる
- **評価方法**: 次回 L3 の試験計画完了条件が二段になっているか
- **昇格判定**: Memory 留め（昇格せず）。累計 1 回
