### 事象 1: 計画→実装が手戻りゼロで完走（成功手順）

- **種類**: 成功手順
- **観測した事象**: 実装計画のステップ 1〜8 を順に実施し、lint / type-check / test が
  すべて一発 PASS。手戻り・ユーザー修正・テスト失敗ゼロ。完了条件（新規 9 ファイル +
  package.json ×2・プロダクションコード変更 0・既存テスト退行なし）をすべて充足。
- **発生回数**: このタスク 1 回（orchestrator L2 完走成功は recipe-edit-screen に続き累計 2 例目だが、
  今回は「計画セッションと実装セッションの分離」という新パターン）
- **対象タスク**: test-infra-expansion
- **原因仮説**: 実装計画がリスク（R-1 型非互換 / R-2 DDL / R-3 alias / R-4 happy-dom）と
  回避策を事前列挙しており、実装時の判断が全て「計画に書いてある分岐を選ぶだけ」で済んだ。
  特に R-1（DrizzleClient 型互換）は「まず型キャストを試す→ダメなら中断して確認」の優先順が
  明記されていたため、独断のプロダクションコード変更を避けつつ即決できた。
- **改善案**: 「リスク表に検出タイミングと回避策の優先順位を書く」パターンは
  create-implementation-plan Skill の現行テンプレートで既に機能している。変更不要。
- **変更対象**: （変更不要・成功パターンの記録のみ）
- **想定される副作用**: なし
- **評価方法**: 次回 L2 実装計画でも同形式のリスク表が作られるかを確認
- **昇格判定**: Memory 留め（昇格せず）。成功パターン複数再現の条件は「計画分離型」としては 1 例目。

### 事象 2: 設計書が非推奨 API（defineWorkspace）を指定していた

- **種類**: 手戻り（軽微・実装時吸収）
- **観測した事象**: 設計書 §6.3 / 実装計画ステップ 6 は Vitest の `defineWorkspace` を
  指定していたが、インストールされた Vitest 3.2.6 では workspace 機能が非推奨
  （vitest.config.ts の default export としては機能しない）。実装時に後継の
  `test.projects` へ置き換えて同一の 3 ファイル構成を実現した。
- **発生回数**: このタスク 1 回
- **対象タスク**: test-infra-expansion
- **原因仮説**: architecture-designer が設計時にライブラリの「知識上の API」を書き、
  リポジトリにインストールされる実バージョンの現行 API と突き合わせていない。
  今回は同時に導入する新規依存だったため、バージョン確認の対象からも漏れやすかった。
- **改善案**: create-design-document Skill またはarchitecture-designer の手順に
  「設定ファイル・フレームワーク API を指定する場合は、対象パッケージの採用バージョンでの
  現行 API（非推奨でないこと）を確認する」を追加する。
- **変更対象**: Skill（create-design-document）または architecture-designer 定義（まだ未定）
- **想定される副作用**: 設計フェーズの調査コスト微増。
- **評価方法**: 設定ファイル生成を含む eval ケースで、指定 API の現行性が確認されるか
- **昇格判定**: Memory 留め（昇格せず・1 回目）。同種の「設計書の API 陳腐化」が
  再発したら Skill 昇格を検討。

### 事象 4: リモート（エフェメラル）環境では subagent-log / メトリクス自動補完が機能しない

- **種類**: 重複作業・トークン浪費（計測基盤の欠落）
- **観測した事象**: 実装セッション（リモートコンテナ）に `.claude/state/subagent-log.jsonl` が
  存在せず、record-task-metrics.sh の `agents.calls` 自動補完が働かない。また計画セッション
  （昨日・別コンテナ）の subagent 呼び出し記録も引き継がれないため、タスク全体の
  duration / tool uses / トークンを横断計測できない。
- **発生回数**: このタスク 1 回（リモート環境での L2 フルサイクルは初）
- **対象タスク**: test-infra-expansion（Phase 4 メトリクス運用・IMP-2026-007 計測にも影響）
- **原因仮説**: `.claude/state/` はコミット対象外でコンテナ寿命に紐づく。ローカル前提で
  設計された計測フローがエフェメラル環境を想定していない。
- **改善案**: (a) 計測が必要なタスクでは subagent-log の要約を成果物（metrics yml）に
  セッション終了前に書き出す運用にする、または (b) リモート環境では `agents.calls` 等を
  会話ログから手動記入とし、metrics テンプレートに「リモートは手動」と注記する。
- **変更対象**: Skill（reflect-task）/ record-task-metrics.sh（まだ未定）
- **想定される副作用**: 運用手順の複雑化。
- **評価方法**: 次のリモートセッション実施タスクで metrics yml の欠損値が減るか
- **昇格判定**: Memory 留め（昇格せず・1 回目）。IMP-2026-007 の定量計測にも関わるため
  backlog の申し送りに補記して再発監視。

### 事象 5: 実装後の reviewer / security-reviewer を省略してマージされた

- **種類**: プロセス逸脱（結果影響は未検出）
- **観測した事象**: L2 のワークフローでは実装後に reviewer レビューを挟むのが標準だが、
  今回は実装完了報告の直後にユーザーが PR #21 をマージしたため、reviewer /
  security-reviewer の実装後レビューが実施されていない（docs/reviews/test-infra-expansion.md
  は存在しない）。変更はテスト・設定のみでプロダクションコード変更 0 のためリスクは低い。
- **発生回数**: このタスク 1 回
- **対象タスク**: test-infra-expansion
- **原因仮説**: 実装がテストのみでリスクが低く、ユーザーがレビュー省略を許容できる内容だった。
  また計画（設計・実装計画）は前日にレビュー相当の吟味を経ており、二重レビューの価値が低かった。
- **改善案**: 「テスト・ドキュメントのみの変更（プロダクションコード変更 0）は reviewer を
  省略可」という省略条件を classify-change / validate-deliverables に明文化すると
  判断が安定する。ただし 1 回目なので起票せず様子見。
- **変更対象**: Skill（classify-change / validate-deliverables）（まだ未定）
- **想定される副作用**: 省略条件の乱用（「テストのみ」の判定が曖昧なケース）。
- **評価方法**: 同種のテストのみタスクでレビュー要否の判断が揺れるか観測
- **昇格判定**: Memory 留め（昇格せず・1 回目）
