### 事象 2: 「confirmed」な設計書の技術的記述が下流 3 工程の実測で 8 件誤っていた

- **種類**: Agent 間認識不一致 / 要件見落とし（実装のやり直しではなく、設計フェーズ内での
  記述訂正）
- **観測した事象**: ユーザー確定後 `confirmed` にした設計書に対し、下流の contract-designer・
  test-designer・reviewer が独立に実コードへ実測を当てて計 8 件の誤り・未確定事項を発見した。
  - contract-designer: Zod バリデーション失敗のステータスコードを 422 と記述していたが実際は
    400（`@hono/zod-validator` が `app.onError` を経由しない）。`displayName` 送信時の
    strip 挙動が未定義。
  - test-designer: `StockNotFoundError` を Domain 層が throw すると記述していたが、それは
    Application 層のクラスであり Domain→Application の import は依存方向違反（既存の
    `Pantry.consumeStock` は素の `Error` を投げている）。`Quantity.of()` は `value < 0` のみ
    reject し 0 を許容するが、設計書は「非正数を弾くなら再チェック不要」という成立しない条件付き
    記述をしていた。`UpdateStockDetailsUseCase` の 404/422 発生経路が未確定。既存の
    Infrastructure テストが現状の罠を「正しい挙動」としてアサートしている事実がどの文書にも
    無かった。
  - reviewer（Must-1〜3）: 期限切れ（残日数が負）の緊急度チップの扱いが未定義かつ試験計画に
    overdue 観点が無いため RTL は全件 Green のまま手動確認だけが落ちる構造だった。チップ文言が
    未定義。`/pantry` 375px 表示の検証が抜けていた。
- **発生回数**: このタスク内で 8 件（3 つの独立した下流工程から）。「設計書の技術的記述が
  実コードで未検証のまま流通する」という上位テーマとしては、`test-infra-expansion`
  （設計書が非推奨 API を指定・採用バージョンの現行 API 未確認、1 件・「再発で
  create-design-document Skill 昇格を検討」と申し送り済み）に続く**累計 2 回目**。
- **対象タスク**: stock-edit（今回）/ test-infra-expansion（既存記録）
- **原因仮説**: `confirmed` は「ユーザーが設計判断を確定した」ことのみを意味し、「記述が
  実コードと一致している」ことは保証しない。下流 Agent に設計書を前提として渡す際、
  今回は実測を明示的に指示したため誤りが表面化したが、指示しなければ Codex ブリーフまで
  誤りがそのまま伝播していた可能性が高い。
- **改善案**: `create-design-document` / `create-contract-design` / `create-test-plan` の
  各 Skill に「設計書の技術的記述（エラーコード・例外クラス・層・既存挙動の前提）は下流工程で
  必ず実コードと突き合わせる」旨を明記する案。ただし今回で累計 2 回目のため、
  memory-policy の昇格条件（3 回）には未到達。
- **変更対象**: 未定（3 回目の再発があれば `.claude/skills/create-design-document/SKILL.md` の
  「実測」手順化を検討）
- **想定される副作用**: 実測の義務化が全設計タスクに一律適用されると、小規模変更でも
  過剰な実測コストが発生する可能性。適用範囲（技術的断定を含む記述のみ、等）の絞り込みが必要。
- **評価方法**: 次の L3 タスクで、設計書の技術的記述に対する下流工程での実測実施有無と
  発見件数を記録し、再発パターンかどうかを判定する。
- **昇格判定**: **Memory 留め（昇格せず）**。test-infra-expansion の申し送り事項の
  2 回目の再現として記録し、3 回目の再発条件を待つ。backlog の当該行

### 事象 3: ユーザーが最小推奨案を退けフル機能を選んだことで潜在欠陥が 2 件発覚した（P-1・P-4）

- **種類**: 設計変更（ユーザー判断）
- **観測した事象**: 2 論点でユーザーが推奨案（スコープ最小化案）を退け、より広い機能を選んだ。
  - P-1: 推奨は「期限・保存場所のみ」だったが、ユーザーは数量も含める案を選択。結果、
    `onConflictDoUpdate.set` に `amount_unit` が無いという別の罠（値は反映されるが単位変更は
    反映されない）が判明した。
  - P-4: 推奨は「保存場所ラベルのみ」だったが、ユーザーは緊急度チップも含める案を選択。結果、
    `getExpiryUrgency` が「閾値以内へフィルタ済みの値を渡す前提」の実装であることが判明し、
    `/pantry`（全在庫一覧）側で自前の閾値判定が必要という設計制約が浮上した。
  - 推奨案（最小スコープ）どおりに進んでいれば、どちらの欠陥も設計段階では見つからなかった。
- **発生回数**: このタスク内で 2 回。同型の「推奨案を上回るスコープを選んで初めて欠陥が
  見つかる」という構造の他タスクでの記録は今回確認できなかった（既存 backlog に一致する
  事象なし）。
- **対象タスク**: stock-edit
- **原因仮説**: 推奨案（安全側・最小スコープ）は既知のリスクを避けることを優先するため、
  逆に「広げてみないと気づけない既存コードの罠」を検出する機会を失う。今回はユーザーが
  フル機能を選んだことで偶然発覚した。
- **改善案**: なし（1 タスク内 2 件のみで一般化には材料不足。「推奨案を作る際に、除外した
  スコープに既存コードの罠が隠れていないか軽く当たる」という手順化は過剰適用のリスクが高い）。
- **変更対象**: 未定
- **想定される副作用**: 推奨案作成時に除外スコープまで実測すると、最小化提案のコスト削減効果が
  薄れる。
- **評価方法**: 次回同型（推奨案 vs ユーザー選択の差でリスクが変わる場面）が発生したら記録し、
  2 回目以降で一般化を検討する。
- **昇格判定**: **Memory 留め（昇格せず）**。architecture-designer Subagent Memory へ
  単発の観察として残す。
