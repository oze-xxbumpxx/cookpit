## 観測した事象

### 事象 1: `handleRefetch` 周辺の実行中フラグ・エラーバナーの状態遷移が、再び設計・試験計画から漏れてレビューで初検出された

- **種類**: レビュー指摘（再発）
- **観測した事象**: レビューの Should 2 件が、いずれも `shopping-list-client.tsx` /
  `pantry-client.tsx` の `handleRefetch` 周辺の状態遷移だった。
  (S1) 共有インスタンスの実行中フラグが単一スロットで、並行操作時に奪い合う。
  (S2) 非 silent 再取得でエラーバナーがリクエスト開始時点で消える。
  いずれも設計書の「フロントエンド設計」「エラー処理」節では触れておらず、
  試験計画にも該当ケースが無く、既存テストは**どちらの挙動でも通る**ため検出できなかった。
- **発生回数**: 累計 **2 回目**。1 回目は shopping-list-screens 事象 2
  （S-1「refetch 成功時にエラーバナーが残留」/ S-2「silent refetch でも更新ボタンが disable」）。
  **同一ファイル・同一関数まわりで同じクラスの見落としが再発**している。
- **対象タスク**: project-refactoring（今回）/ shopping-list-screens（2026-07-21）
- **原因仮説**: 「非同期処理中の UI 状態（実行中フラグ・エラーバナー）の遷移」は、
  正常系・異常系・境界値という試験観点の分類のどれにも素直に載らない。
  結果として試験計画の網から落ち、実装者・レビュアーの目視だけが検出手段になっている。
  今回はさらに「複数操作が同じ状態スロットを共有する」という並行性の軸が加わった。
- **改善案**: `create-test-plan` の観点リストに「非同期 UI 状態の遷移」を独立項目として追加する。
  最低限、(a) 実行中フラグの立ち下がり条件、(b) エラー表示の出現・消去のタイミング、
  (c) 同一画面の複数操作が並行したときの独立性 — の 3 点を、対象が Client Component で
  API を呼ぶ場合のチェック項目にする。
- **変更対象**: `.claude/skills/create-test-plan/SKILL.md`
- **想定される副作用**: 試験計画が長くなる。画面を持たない変更（Domain / Application のみ）では
  不要な項目になるため、「Client Component が API を呼ぶ変更のみ」と適用条件を明記する必要がある。
- **評価方法**: 次に `_components/*-client.tsx` を触るタスクで、試験計画に上記 3 点が現れるか、
  およびレビューで同種の Should が出るかを before/after で比較する。
- **昇格判定**: **昇格条件の判断を manager に委ねる**。「同種指摘の複数回」に該当する 2 回目で、
  1 回目（shopping-list-screens 事象 2）は Memory 留めとされていた。同一箇所での再発である点を
  重く見るなら昇格、まだ 2 回である点を重く見るなら留め置き。

### 事象 2: 回帰テストを「旧実装に戻して落ちること」まで確認した

- **種類**: 成功手順
- **観測した事象**: S1 修正で回帰テスト UAA-08 を追加したあと、`git stash` で修正前の
  単一キー実装に一時的に戻し、そのテストが実際に `expected false to be true` で失敗することを
  確認してから復帰した。これにより「指摘を検出しないテストを回帰テストと呼ぶ」事故を防いだ。
- **発生回数**: このタスク内 1 回（過去の candidate に同種の記録なし）。
- **対象タスク**: project-refactoring
- **原因仮説**: 挙動不変リファクタリングでは、追加テストが「新実装で通る」ことは自明に近く、
  「旧実装で落ちる」ことこそが回帰テストとしての価値を担保する。
- **改善案**: バグ修正・レビュー指摘対応で回帰テストを足すときの手順として明文化する。
  `git stash` で対象ファイルだけ戻して失敗を確認 → `git stash pop` の 3 コマンドで済む。
- **変更対象**: `.claude/skills/quality-gates/SKILL.md` または `create-test-plan`（未定）
- **想定される副作用**: 手順が 1 段増える。ただし対象は「回帰テストを新規に足すとき」に限られる。
- **評価方法**: 次のバグ修正タスクで、回帰テストの失敗確認が行われたかをログで確認する。
- **昇格判定**: **Memory 留め（昇格せず）**。成功パターンの初観測のため、再現を待つ。

### 事象 3: 機械置換の正規表現が隣接する import 文を巻き込んだ

- **種類**: 手戻り
- **観測した事象**: 観点 A で 285 箇所の import を機械置換する際、
  `import\s+(type\s+)?\{([\s\S]*?)\}\s*from\s*'@cookpit/domain/src/...'` という正規表現を使い、
  波括弧内に `[\s\S]` を許したため、直前の `import { describe, it } from 'vitest';` を
  飲み込んだ（非貪欲でも `}` を跨いでバックトラックするため）。70 ファイルが壊れたが、
  `pnpm type-check` が即座に検出。該当ファイルを `git checkout` で戻し、
  `[^}]` に限定した修正版で再実行して解決した。
- **発生回数**: このタスク内 1 回。
- **対象タスク**: project-refactoring
- **原因仮説**: 「非貪欲なら最短一致で止まる」という誤解。文字クラスに `}` が含まれる限り、
  後続条件を満たすまで境界を越えて伸びる。
- **改善案**: import 文など「区切り文字が構文上の境界になる」対象を機械置換するときは、
  区切り文字を文字クラスから除外する（`[^}]`）。加えて、大量置換の前に
  **1 ファイルで試して差分を目視**するステップを挟む。
- **変更対象**: （まだ未定。単発のため Memory 留め）
- **想定される副作用**: なし（手順の追加のみ）。
- **評価方法**: 次の大量機械置換タスクで、試行 → 目視 → 全体適用の順が踏まれるか。
- **昇格判定**: **Memory 留め（昇格せず）**。単発かつ type-check で即検出できたため実害が小さい。

### 事象 4: ローカルの `main` ref が古く、検証が偽陽性まみれになった

- **種類**: 手戻り
- **観測した事象**: 観点 G の分割前後でテスト表題が保存されているかを検証する際、
  `git show main:<file>` を基準にしたところ、実在しない差分（表題の不一致 1 件・テスト 8 件の消失）が
  大量に出た。原因はローカル `main` が `origin/main` より前を指していたこと。
  分岐元コミット（`71c0c6c^` = `590dfc2`）を明示指定したところ、42/26/58 件すべて完全一致した。
- **発生回数**: このタスク内 1 回。
- **対象タスク**: project-refactoring
- **原因仮説**: リモートのエフェメラル環境ではブランチが `origin/main` から作成されるが、
  ローカルの `main` ref は clone 時点のまま更新されない。`main` を基準名として素朴に使うと古い。
- **改善案**: 差分比較の基準は常に `origin/<default>` か、`git merge-base HEAD origin/main`、
  あるいは自分の最初のコミットの親（`<first-commit>^`）を明示的に使う。`main` という
  ローカル ref 名を検証の基準に使わない。
- **変更対象**: `.claude/skills/quality-gates/SKILL.md` または close-session 系（未定）
- **想定される副作用**: なし。
- **評価方法**: 次に「分岐元との比較」を行うタスクで、基準の取り方を確認する。
- **昇格判定**: **Memory 留め（昇格せず）**。ただしリモート環境固有で再発しやすいため、
  再発したら早期昇格を検討する。

### 事象 5: 共通ヘルパ化でテストモックの「貧しさ」が露呈した

- **種類**: テスト失敗
- **観測した事象**: 観点 D で `useApiAction` を作った際、成功時に常に `response.json()` を
  呼ぶ設計にしたところ、meal-plan のテストモックが `json()` を持たないため例外になり、
  「通信エラー」として握られて `router.refresh()` が呼ばれず、既存テスト 4 件が落ちた。
  本文を使わない成功時のための `onSuccessWithoutBody` を分けて解決した。
- **発生回数**: このタスク内 1 回。
- **対象タスク**: project-refactoring
- **原因仮説**: 個別実装では「本文を読む経路」と「読まない経路」が自然に分かれていたが、
  共通ヘルパが両者を一本化したことで、モックが実装していない API を触るようになった。
  テストモックは本物の `Response` より常に貧しい。
- **改善案**: 共通ヘルパを新設して既存呼び出しを載せ替えるときは、
  「元の実装が呼んでいなかった API を新たに呼んでいないか」を確認する。
  結果的に「使わない本文をパースしない」という実装上も正しい設計に落ちた。
- **変更対象**: （まだ未定。単発のため Memory 留め）
- **想定される副作用**: なし。
- **評価方法**: 次の共通化タスクで同種のテスト失敗が出るか。
- **昇格判定**: **Memory 留め（昇格せず）**。

### 事象 7: CI の失敗を「インフラ起因」と「実障害」に切り分けられた

- **種類**: 成功手順
- **観測した事象**: PR #110 の CI で 4 ジョブが失敗したが、ジョブ API の
  `runner_id: 0` / `runner_name: ""` / `steps` 配列なし / ログ 404 という特徴から、
  ランナー未割り当て（1 ステップも実行されていない）と判定できた。再実行しても同じ。
  一方、`main` の run では Dependency Audit が実際に走って失敗しており、
  手元で `pnpm audit --prod --audit-level high` を再現して high 3 件（js-yaml / postcss /
  brace-expansion、いずれも推移的依存）を特定した。この PR は依存関係ファイルを
  1 行も変更していないため無関係と確認した。
- **発生回数**: このタスク内 1 回。
- **対象タスク**: project-refactoring
- **判明した根本原因（2026-07-25 ユーザー確認）**: GitHub Actions の課金停止だった。
  UI 上のメッセージは
  「The job was not started because recent account payments have failed or your spending limit
  needs to be increased. Please check the 'Billing & plans' section in your settings」。
  **API 側にはこの理由が一切現れない**（check run の `output.title` / `summary` / `text` は
  すべて空文字、ジョブログは 404）。したがって API だけを見ていると原因不明のまま
  再実行を繰り返すことになる。
- **原因仮説**: 「CI が赤い」だけでは原因が分からない。ジョブのメタデータ（runner_id・steps）で
  「起動したか」を先に切り分けると、無駄な修正コミットを打たずに済む。
  さらに「起動していない」と分かった場合、**API では理由が取れないため、
  ユーザーに Actions の画面表示を確認してもらうのが最短経路**である。
- **改善案**: CI 失敗時の初動として、(a) ジョブ API で `runner_id`/`steps` を確認して起動有無を判定、
  (b) base branch の同一ワークフローの結果と比較して自分の変更由来かを判定、
  (c) 実障害なら CI と同一コマンドをローカルで再現 — の順を手順化する。
  加えて **(d) 「起動していない」と判定できた時点で再実行を打ち切り、
  ユーザーに Actions 画面のメッセージ確認を依頼する**（課金停止・spending limit・
  Actions 無効化などは API から判別できず、待っても回復しない種類の停止であるため）。
  今回は再実行を 1 回試して同症状を確認した時点で打ち切っており、この判断自体は妥当だった。
- **変更対象**: `.claude/skills/quality-gates/SKILL.md`（未定）
- **想定される副作用**: なし。
- **評価方法**: 次に CI が赤くなったタスクで、この順で切り分けられたか。
- **昇格判定**: **Memory 留め（昇格せず）**。成功パターンの初観測。
