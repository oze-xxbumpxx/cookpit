# Memory ポリシー（保存先分類・昇格・肥大化対策）

知見をどこに保存するか、どう昇格させるか、どう削除するかを定める。改善サイクルの全体像は
[improvement-cycle.md](./improvement-cycle.md) を参照。

## 大前提

- **Memory は学習済みモデルではない。** 次回セッションに読み込まれる永続コンテキストに過ぎない。
  誤情報を保存すれば次回以降も誤りを参照する。だから保存は慎重に、削除は迅速に。
- **保存先は知見の「確からしさ」と「適用範囲」で決める。** 単発・検証中ほど局所（Auto Memory）、
  検証済み・全体適用ほど中心（CLAUDE.md / Rule / Skill）。
- **段階を飛ばさない。** `単発 → Memory` / `繰り返す → 改善候補` / `検証済み → Agent・Skill・Rule`。

## 保存先の分類

| 保存先 | 何を置くか | 確からしさ | 変更の重さ |
| --- | --- | --- | --- |
| **Auto Memory** | ビルドコマンド / デバッグで判明した注意点 / ユーザー修正 / プロジェクト固有パターン / 一時的・検証中の知見 | 低〜中（検証中含む） | 自動可 |
| **Subagent 固有 Memory** | Agent 固有の成功・失敗パターン / 担当領域固有の注意点 / 頻出レビュー指摘 / 担当領域の調査方法 | 中 | 自動可 |
| **CLAUDE.md** | 全セッションで必ず必要な原則 / 全 Agent が知るべきルール / 長期有効な方針 / 複数回再現した重要注意 | 高（検証済み） | **人間承認必須** |
| **.claude/rules** | 特定ディレクトリにだけ効くルール（frontend / backend / DB / test 固有） | 高 | 非破壊追加は manager 後可 / 破壊的は人間承認 |
| **Skills** | 複数ステップの作業手順 / 再利用チェックリスト / 成功した設計・実装・レビュー手順 / 成果物テンプレート | 高 | チェック項目追加・テンプレ改善は manager 後可 |
| **Hooks** | 必ず実行する検証 / 保護ファイル変更制御 / 必須成果物確認 / テスト実行確認 / Agent 設定の構文検証 / 改善プロセス起動トリガー | 高（機械的制御） | ブロック条件は人間承認必須 |

### 各 Agent の Memory スコープ

- **orchestrator**: 委譲・統合で繰り返す判断の癖（どの順で委譲すると手戻りが減るか等）。
- **requirements-analyst**: 既存仕様の所在・調査の入口・要確認になりやすい論点。
- **architecture-designer**: このプロジェクトで繰り返す設計判断・既出の設計上の落とし穴。
- **implementation-planner**: 分解の粒度・見落としがちな依存・ロールバック観点。
- **implementer**: ビルド/型/lint の詰まりどころ・Drizzle/Hono 周りの定番注意点。
- **test-designer**: 漏れやすい境界・整合性・冪等性の観点。
- **reviewer**: 頻出指摘の型（タイポ・無限ループ・依存方向違反など）。
- **reflection-agent / manager / evaluator**: 改善メタ知見（昇格判断の精度・評価の限界）。

> Subagent 固有 Memory は「その Agent の担当領域に閉じた知見」だけを置く。全 Agent に効く
> 知見は CLAUDE.md 昇格の検討対象（＝人間承認）であり、勝手に各 Agent へコピーしない。

## 昇格条件（Auto Memory → 改善候補）

Auto Memory の知見を無条件に CLAUDE.md / Skills へ反映してはいけない。以下のいずれかを
満たしたときだけ改善候補へ昇格する。

- 同じ問題が **3 回以上**発生した
- ユーザーから**同じ修正を 2 回以上**受けた
- Reviewer から**同種の重大指摘を複数回**受けた
- **本番障害**または**重大な試験不具合**につながった
- **複数 Agent で同じ認識不足**が発生した
- 作業時間またはトークンを**継続的に浪費**している
- 明確な**成功パターンが複数タスクで再現**した

### 昇格時に記録する項目

観測した事象 / 発生回数 / 対象タスク / 原因仮説 / 改善案 / 変更対象 / 想定される副作用 /
評価方法。記録先は `improvements/candidates/<task-id>.md`（→ 横断分析後 `proposals/`）。

## 肥大化への対策

指示・Memory は増やすほど良いものではない。増えすぎると判断遅延・指示競合・不要作業・
トークン増・重要指示の埋没を招く。次を守る。

- **改善＝追加ではない。** manager は提案時に「不要な指示の削除・適切な場所への移動」を
  必ず検討する。1 提案 = 1 根本原因 = できるだけ 1 変更対象。
- **重複は統合する。** 同じ根本原因の候補は 1 提案にまとめる。
- **CLAUDE.md は痩せ保つ。** 局所ルールは `.claude/rules/`、手順は Skills、メタ記録は
  `improvements/` に分離する。CLAUDE.md には「全 Agent が常時必要な原則」だけ。
- **Auto Memory は定期的に棚卸し**する。検証が終わって恒久化したものは Skill/Rule へ移し、
  Auto Memory 側の重複は消す。古い・一度きりの注意点は削除する。
- **Auto Memory はトピック別に分けてよい（任意）**。索引（MEMORY.md）は簡潔に保ち、詳細は
  `build-and-test` / `architecture-findings` / `debugging` / `reviewer-findings` /
  `user-preferences` などのトピックへ分割すると肥大化を抑えやすい。Auto Memory はマシン
  ローカル前提。チームで共有すべき確定知見は Git 管理の文書（Rule/Skill/ADR）へ昇格する。
- **TTL の意識**: 「一時的・検証中」と明記した Auto Memory は、次の改善サイクルで再評価し、
  再現しなければ削除する。

## 誤った知見の削除手順

Memory はモデル再学習ではないので、誤りは**ファイルを消せば**次回から参照されない。

1. **どこに保存されたか特定する**（Auto Memory / Subagent Memory / Rule / Skill / CLAUDE.md）。
2. **影響範囲を確認する**：その知見を参照している Agent・Skill・Rule をリンクで辿る。
3. **削除または訂正する**。
   - Auto / Subagent Memory: 該当エントリを削除（自動反映可の範囲）。
   - Rule / Skill / CLAUDE.md: **人間承認が必要**。proposal に「誤情報の撤回」として差分を
     起票し、承認後に削除・訂正する。
4. **再発防止**：誤情報を生んだ原因（誰がどの段階で誤判断したか）を `candidates/` に残し、
   必要なら Hook/レビュー観点で検知できるようにする。
5. **記録**：削除も改善の一種。backlog に「撤回」行を残し、なぜ誤りだったかを 1 行で残す。

## 自動化の境界（要約。正典は improvement-cycle.md）

- **自動実行可**: Auto Memory 候補の整理 / 振り返り作成 / 改善候補作成 / 評価レポート作成 /
  重複候補の統合 / フォーマット修正 / リンク切れ修正。
- **manager レビュー後に可（非破壊・軽微）**: Skill のチェック項目追加 / テンプレート改善 /
  Agent description の軽微改善 / 非破壊的な Rules 追加。
- **人間承認なしに変更不可**: CLAUDE.md / Agent の責務・モデル・ツール権限 / Hook のブロック
  条件 / 自動実行シェルコマンド / セキュリティルール / 成果物の省略条件 / 本番影響設定。
