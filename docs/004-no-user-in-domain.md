# ADR-004: ドメインから User 集約を外す

**ステータス**: 採択
**決定日**: 2026-05

## 背景

[ADR-003](./003-no-auth-in-mvp1.md) で MVP1 は認証なしで運用することを決めた。その上で、ドメインモデル上の「ユーザー」概念をどう扱うかを検討。

選択肢は以下の3つ。

- A. ドメインから完全に外す（`userId` を付与しない）
- B. ドメインには残すが、システムユーザー1名で表現（将来入れやすい）
- C. 認証ありの構成を残す

## 決定

**A. ドメインから完全に外す。** ドメインモデルに `User` 集約は存在せず、各集約も `createdBy` 等のユーザー参照を持たない。

## 決定の理由

1. **ドメインモデルが綺麗になる**：5 集約（Recipe / MealPlan / ShoppingList / Pantry / Product）に集中できる
2. **2人利用の本質に合致**：家庭内の共有データという捉え方で、操作主体を区別する必要がない
3. **YAGNI 原則**：必要になってから追加する方が、間違った設計をしにくい
4. **将来の追加コストは大きくない**：認証導入時に DB スキーマに `created_by` カラムを足し、ドメインに反映するのは「監査ログを後付けで入れる」業務の典型パターンと同じ

## 当初の B 案（システムユーザー方式）を選ばなかった理由

一度は B 案（ドメインに残しつつシステムユーザー1名で運用）を選びかけたが、以下の理由で変更。

- 「常に同じ ID が入る `createdBy`」は実質的に意味がなく、コードノイズになる
- 値オブジェクトや集約の引数が増えて、テストや初期化が冗長になる
- 「将来入れやすい」というメリットは、実装時に再検討するコスト（少しの追加実装）と釣り合わない
- ドメインモデルの綺麗さは、実装の理解しやすさに直結する

## 帰結

### ポジティブ
- 集約数が抑えられる（5 集約）
- 各集約の責務が「献立・買い物・在庫の本質」に集中
- 値オブジェクトもユーザー絡みのものが不要

### ネガティブ
- Phase 2 で認証導入する際、各集約に `createdBy` を追加する必要がある
- 既存データに対する `createdBy` のデフォルト値設計が必要

## 認証導入時の移行手順（想定）

1. DB の各テーブルに `created_by` カラム（NULL 許容で追加）を導入
2. 既存データには NULL を入れたまま（または特定のシード値）
3. ドメインモデルに `createdBy` を追加（Optional な値オブジェクトとして）
4. 新規作成・更新ユースケースに「現在ユーザー」を引数で渡すよう変更
5. 既存データを表示する時は `createdBy` が NULL なら表示しない、ある時のみ表示

このパターンは「業務で監査ログを後付けで導入する」状況と同じであり、実践的な学びになる。

## フォローアップ

- Phase 2 認証導入時に本 ADR をレビューし、「廃止」または「上書き」する新 ADR を作成する
- 移行時に発生した課題は、後続のブログ記事や業務知見として整理する
