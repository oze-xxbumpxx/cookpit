# ADR-0013: 店舗マスタを 3 件上限・同名禁止とし、削除は参照ごとカスケードする

- ステータス: accepted
- 日付: 2026-07-27
- 決定者: ユーザー（選択肢提示のうえ確認）
- supersedes: [ADR-0012](./ADR-0012-store-delete-restrict-on-reference.md)

## Context（背景・なぜ判断が必要か）

ADR-0012（同日採択）は「店舗は物理削除し、参照が 1 件でもあれば削除を拒否する」と決めた。
その Consequences には、残るリスクとして次を明記していた。

> **使ってしまった店舗はもう消せない。** 名前を打ち間違えたまま価格を記録した場合、
> 価格記録を全部消さない限り店舗が残る。リネーム機能が無いため回避策も無い。

このリスクが実データで現実になった。本番の店舗マスタは 10 件まで増えている。

| 名前                                  | 件数 | 種別                       |
| ------------------------------------- | ---- | -------------------------- |
| コモディ飯田 / ライフ / 業務スーパー  | 3    | 実在する店舗               |
| `AAAA` / `5555` / `っっっs` / `sssss` | 4    | 試し入力の残骸             |
| 業務スーパー（重複）                  | 3    | 同名チェック不在による重複 |

「業務スーパー」の重複 4 件はすべて 2026-07-27 に作られている。店舗名の一意性を
どこも検査していないため、同じ店舗が何度でも登録できてしまう。

ユーザーからの要求は 2 つ。**(1) 店舗は 3 つまでにしたい。(2) 同名は登録不可にしたい。**
実運用は「2 人で 2 店舗を回る」（`docs/01-overview.md` §ユーザーの実運用）であり、
3 件という上限はこの運用に合わせた実数である。

ここで ADR-0012 との衝突が生じる。上限 3 件だけを導入すると、**実在 3 店舗はいずれも価格記録を
持つため削除できず、10 件から 3 件へ下げる経路が存在しない。**結果として新規店舗の追加が
永久に不可能な詰み状態になる。上限の導入は、削除制約の緩和と不可分である。

## Decision（採用した決定）

**店舗マスタの上限を 3 件・同名禁止とし、店舗削除は参照ごとカスケードする。**

### 1. 上限 3 件（Application 層で強制）

- `CreateStoreUseCase` が作成前に `findAll()` の件数を数え、3 件以上なら
  `StoreLimitExceededError`（`InvalidOperationError` 継承 → 422）を投げる。
- 上限は定数 `STORE_LIMIT = 3` として Application 層に置く。ユーザー設定化はしない。
- **DB 制約では表現しない。**件数制約はテーブル横断で書けず、2 人運用に対して過剰である。
- 上限は**新規作成時のみ**判定する。既存の 10 件は読み取り・削除ともに従来どおり動作し、
  2 件以下まで削除すれば追加が再開できる（自己回復する移行）。

### 2. 同名禁止（正規化後の完全一致）

- 比較は `normalizeStoreName()`（前後空白除去 + NFKC 正規化）後の完全一致。
  `normalizeUnit()` の先例（ADR-0008 / free-text-units）と同じ正規化方針を採る。
- `StoreRepository.findByNormalizedName()` を追加し、一致があれば
  `DuplicateStoreNameError`（422）を投げる。
- 正規化は TypeScript の 1 実装（Domain 層）に寄せ、SQL 側では正規化しない。
  規則を 2 か所に持つと乖離するため。件数上限が 3 件なので全件取得で足りる。
- 大文字小文字の同一視は**しない**。NFKC は `ＡＢＣ` → `ABC` の幅の統一までを担い、
  `Life` と `life` は別店舗として扱う。日本語の店舗名では実害が無く、
  意図的な区別を潰さないため。

### 3. 削除は参照ごとカスケード（ADR-0012 の逆転）

`DeleteStoreUseCase` は「存在確認 → 参照件数 → 0 なら削除」を、次の 3 段に置き換える。

| 段  | 操作                                                   | 対象                           |
| --- | ------------------------------------------------------ | ------------------------------ |
| ①   | `productRepository.deletePriceRecordsByStore(storeId)` | 価格記録を**物理削除**         |
| ②   | 参照リストの `shoppingList.unassignStore(storeId)`     | 店舗指定を**未割当（null）へ** |
| ③   | `storeRepository.delete(storeId)`                      | 店舗を物理削除                 |

- 順序は「参照元 → 参照先」で固定する。逆順は `price_records.store_id` の FK
  `restrict` に当たり生の DB エラー（→ 500）になる。
- **FK の `restrict` は維持する。**カスケードを Application 層の順序制御で実現し、
  FK は順序ミスを検出する安全網として残す。スキーマ変更・マイグレーションは発生しない。
- `StoreInUseError` は発生経路が無くなるため削除する。
- 買い物リストは `completed` のものも対象にする。ユーザー操作ではない後始末であるため、
  `ShoppingList.unassignStore()` は `assertActive` を通さない（`reopen()` に次ぐ 2 例目の例外）。
- **削除前に失われる件数をユーザーへ提示する。**`GET /api/stores/:id/usage` で
  価格記録件数・品目件数を取得し、確認ダイアログに明示する。これが ADR-0012 で
  「undo も無い」として案 A を却下した理由への回答になる。

### なぜ ADR-0012 の判断を覆すのか

ADR-0012 は案 A（カスケード削除）を次の理由で却下していた。

> ユーザーが実際に消したいのは「試し入力で作った未使用の店舗」であり、この案が必要になる
> 場面が無い。

**この前提が実データで否定された。**実際にユーザーが消したいものには、価格記録付きの
重複店舗（業務スーパー ×4）が含まれていた。ADR-0012 は「試し入力の掃除」だけを想定して
おり、「同名チェック不在によって生まれた重複の解消」という用途を見落としていた。

また ADR-0012 は「価格履歴は再入力の効かない蓄積データ」であることを重視したが、
**重複店舗に分散した価格履歴はもともと価値が低い**。同じ業務スーパーの価格が 4 つの
別店舗として記録されていれば、店舗間比較（このアプリの中心価値）はむしろ壊れている。
消して集約し直す方が価値が高い。

## Alternatives（検討した非採用案と却下理由）

### 案 A: 価格記録は残し、店舗名を「店舗未設定」表示に縮退させる（却下）

店舗マスタからは消すが、価格記録は孤立した状態で残り、既存の縮退表示ロジック
（`storeName` が空文字なら「店舗未設定」）で表示される。履歴は失われない。

却下理由: (1) `price_records.store_id` の FK `restrict` を外すマイグレーションが必要になる。
(2) どの店舗の記録だったかが**永久に不明**になり、残った記録は店舗間比較に使えない。
ADR-0012 の案 D と同じ「店舗を剥がした記録は価値を失う」という評価が当てはまる。
(3) 重複店舗を統合する用途では、孤立記録がグラフに「店舗未設定」系列として残り続けて邪魔になる。

### 案 B: ADR-0012 を維持し、上限は新規追加にだけかける（却下）

参照ゼロの試し入力 4 件だけを消せる。ADR の変更が不要。

却下理由: 実在 3 店舗 + 重複 3 件がいずれも価格記録を持つ場合、**7 件から下がらず新規追加が
永久にできない。**上限を入れる意味が失われる。ユーザーの要求(1)を満たせない。

### 案 C: 店舗のリネーム機能（`PATCH /api/stores/:id`）を追加して重複を統合する（却下）

重複店舗を「1 つに統合する」のが本質的な要求なら、リネームではなく**マージ**
（価格記録の store_id を付け替えて片方を消す）が必要になる。削除より実装が重く、
「3 件上限」という要求も別途必要になる。今回の依頼範囲を超える。
リネーム単体では重複は解消しない（名前が同じ店舗が 2 つ残る）。

### 案 D: 論理削除（`stores.archived_at`）(却下)

ADR-0012 で既に却下済み。理由は変わらない — スキーマ変更が必要、`findAll()` の
全呼び出し箇所に分岐が波及、2 人・数件規模に対して仕組みが重い。

## Consequences（良い影響・悪い影響・残るリスク）

良い影響:

- 店舗マスタが実運用の 3 店舗へ収束し、その状態が仕組みで維持される。
- 同名重複が構造的に発生しなくなり、店舗間の価格比較が壊れなくなる。
- どんな店舗でも必ず消せる。ADR-0012 が残した「使ってしまった店舗は消せない」詰みが解消する。
- DB スキーマ変更・データ移行が不要（FK は `restrict` のまま維持）。
- 移行が自己回復する。既存 10 件を消していけば自然に上限内へ収まる。

悪い影響 / 残るリスク:

- **価格記録の消失は取り消せない。**削除ダイアログの件数明示が唯一の防波堤である。
  ユーザーは重複店舗のうち件数が最も多いものを残す運用で被害を抑える。
- 上限チェックと作成が別トランザクションであるため、2 人が同時に店舗を追加すると
  4 件目が通り得る。店舗追加は稀な操作であり、次回の削除で解消できるため対策しない
  （ADR-0012 が「参照件数の確認と削除は別トランザクション」を既知の制約として
  受け入れたのと同じ判断）。
- カスケード 3 段が単一トランザクションではない。途中失敗すると中間状態が残る。
  各段が冪等なので再実行による前方回復で整合させる（`CompleteShoppingUseCase` と同じ方針）。
  順序ミスは FK `restrict` が検出する。
- 未完了リストの `bought` 品目から `actualStore` が消えると、買い物完了時に
  その品目の価格記録がスキップされる（`buildPriceRecord` が null を返す）。
  店舗が存在しないのだから記録先も無く、意図した挙動である。
- `ShoppingList.unassignStore()` が `assertActive` を通さない例外的なメソッドになる。
  ユーザー操作でない後始末であることを JSDoc に明記して区別する。

## Migration（移行が必要な場合の手順）

DB スキーマ・既存データの自動移行はいずれも不要。ただし**リリース後にユーザーが手作業で
店舗を 3 件まで減らす**必要がある。

1. 試し入力 4 件（`AAAA` / `5555` / `っっっs` / `sssss`）を削除する
2. 「業務スーパー」重複 4 件について、削除ダイアログの価格記録件数を確認する
3. 件数が最も多い 1 件を残し、残り 3 件を削除する（残り 3 件分の価格記録は失われる）
4. 実在 3 店舗（コモディ飯田 / ライフ / 業務スーパー）が残った時点で上限内に収まる

上限は新規作成時のみ判定するため、この手順の途中で機能が壊れることはない。

## Rollback（決定を戻す場合の手順）

ADR-0012 の状態へ戻すには次を行う。

1. `CreateStoreUseCase` の上限・同名チェックを削除し、
   `StoreLimitExceededError` / `DuplicateStoreNameError` を取り除く
2. `DeleteStoreUseCase` のカスケード 3 段を、参照件数チェック + `StoreInUseError` に戻す
3. `store-in-use.error.ts` を復活させ、UI の `STORE_IN_USE_MESSAGE` を戻す
4. `GET /api/stores/:id/usage` とルート、`GetStoreUsageUseCase` を取り除く

**ただし、カスケード削除で失われた価格記録は復元できない。**コードは戻せてもデータは
戻らない片道の決定である。DB スキーマは変更していないため、データ側の構造的な
ロールバックは不要。
