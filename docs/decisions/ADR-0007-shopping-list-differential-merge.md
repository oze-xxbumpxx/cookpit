# ADR-0007: 献立変更を買い物リストへ差分マージする（明示トリガの同期 UseCase を追加）

- Status: Proposed（2026-07-24・レビュー待ち）
- Date: 2026-07-24
- 関連 feature: meal-plan-shopping-sync（改善要望 項目7）
- 関連 ADR: ADR-0006（ShoppingList 生成の冪等化。本 ADR はその制約下の続き）

## Context（背景・なぜ判断が必要か）

ADR-0006 で `GenerateShoppingListUseCase` は冪等になった（同一 MealPlan の 2 回目は既存リストを返す・
`created: false`）。この結果、**買い物リスト作成後に献立へレシピを追加しても、その材料が買い物リストへ
反映されない**（ボタンが「買い物リストを開く」に変わり、押しても新材料が増えない）。献立編集はステータス
`shopping` でも可能（`cooking` 以降のみ禁止）なため、「全レシピを揃えてから 1 回だけ作る」運用をしない
限りほぼ確実にこの状態に当たる（改善要望 項目7・`logs/2026-07-23.md` セッション2）。

ADR-0006 は「B3: 再生成（既存を破棄して作り直す）」を**買い物途中のチェック状態が消える危険**を理由に
却下した。したがって単純な再生成は選べない。「差分マージ（既存リストを維持しつつ新規レシピの材料だけ
追加）」が唯一整合する方向で、その具体設計を確定する必要がある。

## Decision（採用予定の決定）

**明示トリガの差分マージ同期 UseCase を新設する。** `GenerateShoppingListUseCase` の冪等挙動は維持し、
別操作として「買い物リストを更新（献立の変更を反映）」を追加する。

1. 新設 `SyncShoppingListFromMealPlanUseCase`（仮）: 対象 MealPlan の現在の材料を再集計し、
   既存 ShoppingList に**まだ無い材料だけ**を新規 ShoppingItem（`source: from_meal_plan`）として**追加**する。
2. **既存の ShoppingItem は一切変更・削除しない**（チェック済み・購入済み状態を完全に保持）。これが B3 却下
   理由への回答。
3. マッチング（「既に有る」の判定）キーは生成時の集計キーと同一: `productId`（無ければ `displayName` の
   trim）× `unit`。同一キーが既存リストにあれば追加しない。
4. **数量の増分は行わない**（MVP の割り切り）: 既存材料と同じキーの材料が新レシピで増えても、既存品目の
   `requiredAmount` は増やさない。理由は、既に bought 済みの品目の数量を書き換えると購入実績と矛盾し得るため。
   数量の正確な合算は将来課題（§Consequences）。
5. 在庫引き算は**新規追加分のみ**に適用する（既存品目は再計算しない）。生成時 `applyPantryDeduction` の
   ロジックを新規材料に対して再利用する。
6. トリガは**明示操作**（買い物リスト画面/献立画面の「買い物リストを更新」ボタン）。レシピ追加時の自動同期は
   行わない（集約間の暗黙結合を避ける・ADR-0006 の「明示的な作り直しは別 UseCase」方針と一致）。
7. MealPlan が `draft` の場合はこの同期を許可しない（まだ生成前）。既存リストが無い MealPlan への同期は
   no-op か 404 相当（実装で確定）。

## Alternatives（検討した非採用案と却下理由）

| 案                                          | 内容                                     | 却下理由                                                                                    |
| ------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------- |
| A: 完全再生成（B3 再訪）                    | 既存リストを破棄して作り直す             | チェック/購入状態が消える（ADR-0006 で却下済み）。再訪しても同じ                            |
| B: レシピ追加時に自動同期                   | AddRecipeToMealPlan が内部でリストも更新 | 集約横断の暗黙結合。部分失敗窓が増える。ユーザーの意図しないタイミングでリストが変わる      |
| C: 数量も合算・既存品目を更新               | 同一材料は既存品目の数量に加算           | bought 済み品目の数量書き換えが購入実績と矛盾。チェック状態保持の原則と衝突。複雑度が跳ねる |
| D: 差分マージ・明示トリガ・追加のみ（採用） | 新規材料のみ追加、既存不変               | チェック状態を守りつつ「追加したレシピが反映されない」問題を解消。最小で安全                |

## Consequences（良い影響・悪い影響・残るリスク）

- 良: 「レシピ追加が買い物リストに反映されない」問題を、チェック/購入状態を失わずに解消。生成の冪等
  （ADR-0006）とも共存（生成＝初回、同期＝以後の追記）。
- 悪/制約: 同一材料の**数量合算はしない**。新レシピで玉ねぎが増えても既存「玉ねぎ」品目の数量は増えない
  （新規キーでなければ追加もされない）。ユーザーは必要に応じ手動で数量調整/手動追加する。
- リスク 1: 削除方向（レシピを外した）には追随しない（追加のみ）。余分な品目はユーザーがチェックしない/
  skip で対応。削除追随は将来課題。
- リスク 2: 表記ゆれ（`displayName` フリー入力材料）でマッチが割れ、重複品目が出る可能性。生成時の集計と
  同じ制約であり本 ADR で新たに悪化はしない。項目3（単位自由記述化）と相互作用する点に留意。

## Migration（移行）

対象外（新規 UseCase・新規エンドポイント追加のみ。DB スキーマ変更なし）。

## Rollback（決定を戻す場合）

1. 新設 UseCase とルート（`POST /api/shopping-lists/:id/sync` 等）を削除。
2. UI の「買い物リストを更新」ボタンを削除。
   既存の生成・完了フローは不変のため、ロールバックは追加分の除去のみで完結する。
