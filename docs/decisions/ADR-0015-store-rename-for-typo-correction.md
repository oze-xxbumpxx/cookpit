# ADR-0015: 店舗のリネームを「誤字訂正」目的で採用する（重複統合は引き続き対象外）

- Status: Accepted
- Date: 2026-08-05
- 関連 feature: price-record-edit-and-store-rename

## Context（背景・なぜ判断が必要か）

Sprint 7 の完了条件「打ち間違えた店舗名・価格記録を画面から修正できる」が未達で残っている。
店舗名を直す手段は API・UI のどちらにも存在せず、`Store`
（`packages/domain/src/shared/store.ts`）は `storeName` を含む全フィールドが
`private readonly` で更新メソッドを持たない。

判断が必要な理由は、**同じ「店舗のリネーム」が 2026-07-27 の ADR-0013 で一度却下されている**
ことにある（`ADR-0013-store-limit-and-delete-cascade.md` §Alternatives 案C）。

> ### 案 C: 店舗のリネーム機能（`PATCH /api/stores/:id`）を追加して重複を統合する（却下）
>
> 重複店舗を「1 つに統合する」のが本質的な要求なら、リネームではなく**マージ**
> （価格記録の store_id を付け替えて片方を消す）が必要になる。削除より実装が重く、
> 「3 件上限」という要求も別途必要になる。今回の依頼範囲を超える。
> リネーム単体では重複は解消しない（名前が同じ店舗が 2 つ残る）。

記録を残さずに実装すると、後から ADR-0013 だけを読んだ人には「却下されたはずの機能が
実装されている」と見える。却下理由の射程を明文化する必要がある。

なお ADR-0012 は「参照が 1 件でもあれば店舗を削除できない」という制約から
「使ってしまった店舗はもう消せない」というリスクを残しており、その Consequences には
**「リネーム機能が無いため回避策も無い」**と明記されていた（`ADR-0012` 90 行目）。
本 ADR はこの記述にも影響する。

## Decision（採用した決定）

**店舗のリネームを `PUT /api/stores/:id` として採用する。ただし目的は「誤字訂正」に限り、
重複店舗の統合（マージ）は引き続き対象外とする。**

決定の内訳は 4 点。

### 1. ADR-0013 案C の却下理由の射程は「重複統合」に限られる

ADR-0013 案C は「**重複店舗を 1 つに統合する**」という当時の要求に対してリネームを評価し、
「リネーム単体では重複は解消しない（名前が同じ店舗が 2 つ残る）」という理由で却下した。
この評価は正しく、**今も有効である**。

今回の採用目的は異なる。「業務スーパー」を「業務スーパ」と打ち間違えて登録し、
その店舗ですでに価格記録を付けてしまったときに、**店舗を消さずに名前だけを直す**ことである。
統合すべき重複相手は存在しない。したがって案C の却下理由は今回の目的には当てはまらず、
**本 ADR は ADR-0013 の結論を覆すものではない**。ADR-0013 の Status は `Accepted` のまま維持する。

重複統合（マージ）の要求が再び生じた場合は、ADR-0013 案C の評価がそのまま適用される
（リネームでは解決せず、価格記録の `store_id` 付け替えを伴うマージが別途必要になる）。

### 2. 同名禁止ルールをリネームにも適用し、自分自身は衝突と判定しない

ADR-0013 が導入した同名禁止（`normalizeStoreName` = trim + NFKC、+
`StoreRepository.findByNormalizedName()`）を、作成時と同様にリネームにも適用する。
リネームを素通しにすると、ADR-0013 が構造的に防いだはずの同名重複が別経路から復活する。

ただし `findByNormalizedName()` の結果が**リネーム対象の店舗自身**であった場合は衝突として
扱わない（`duplicate.id.equals(storeId)` で判定）。これがないと、名前を変えずに保存し直す操作が
自分自身との衝突で失敗する。

検査の置き場所は `RenameStoreUseCase`（Application 層）とする。一意性は集合に対する制約であり、
単一 Entity では判定できないため。`CreateStoreUseCase` と同じ責務分担である。

### 3. `Store` Entity に `rename()` を追加し、`storeName` の `readonly` を外す

`Store` は現在すべてのフィールドが `private readonly` だが、`storeName` のみ `private` へ変更し、
`rename(name: string)` を追加する。空文字列・空白のみの拒否は `create()` と同じ制約を課す。

同一集約内で可変フィールドを持つ前例は `Product`（`update()` が `productName` ほかを変更）に
すでにある。`Store` だけを完全不変に保つ理由はなく、値オブジェクトではなく Entity である以上、
同一性（`storeId`）を保ったまま属性が変わることは正当である。

一方で `PriceRecord` は**不変のまま維持する**（`docs/designs/price-record-edit-and-store-rename.md`
D-3）。価格記録の編集は `Product.updatePriceRecord()` が新しい `PriceRecord` を生成して
配列内を置換する差し替え方式で行う。同じタスクの中で 2 つの扱いが分かれる理由は、
`PriceRecord` が「ある時点の観測値」という**記録**であり、書き換えではなく差し替えの方が
意味論に合うこと、および `PriceRecord.create()` の正数バリデーションを再利用できることによる。

### 4. ADR-0012 の「回避策も無い」という記述は、本 ADR の時点で成立しなくなる

ADR-0012（Status: superseded）は Consequences に「価格記録を全部消さない限り店舗が残る。
リネーム機能が無いため回避策も無い」と書いていた。ADR-0013 のカスケード削除で前段
（消せない詰み）はすでに解消しており、本 ADR で後段（リネームによる回避策）も成立する。

**ADR-0012 の本文は書き換えない。** superseded な ADR は当時の記録として保存する方針であり
（ADR-0012 冒頭の「以下は当時の記録として残す」）、後から事実が変わるたびに過去の ADR を
編集すると、判断の時系列が読めなくなる。本 ADR がその後日談を担う。

## Alternatives（検討した非採用案と却下理由）

### 案 A: リネームを実装せず、削除して作り直す運用を続ける（却下）

ADR-0013 のカスケード削除により、価格記録付きの店舗も削除できるようになっている。
名前を直したければ「消して作り直す」ことは技術的には可能である。ADR も追加不要。

却下理由: **カスケード削除はその店舗の価格記録を全件巻き添えにする**（ADR-0013 の
Consequences「価格記録の消失は取り消せない」）。誤字を 1 文字直すために蓄積した価格履歴を
全部失うのは、代償が目的に対して過大である。Sprint 7 の完了条件「打ち間違えた店舗名を
画面から修正できる」も、履歴を失う手段では満たしたと言えない。

### 案 B: マージ機能（価格記録の `store_id` 付け替え + 片方の削除）として実装する（却下）

ADR-0013 案C が「本質的な要求ならこちらが必要」とした案。重複統合と誤字訂正の両方を
一度に解決できる。

却下理由: 今回の要求は誤字訂正であり、統合すべき重複相手が存在しない。マージは
「移送先店舗の選択 UI」「同一 `observedAt` の記録が同一店舗に集まった場合の扱い」
「付け替えのトランザクション境界」を新たに設計する必要があり、実装コストがリネームより
明確に重い。**ADR-0013 が実施した 3 件上限 + 同名禁止により、そもそも重複が新たに
発生しない構造になっている**ため、マージの需要は当面生じない。必要になった時点で
別 ADR として起票する。

### 案 C: `PATCH /api/stores/:id`（部分更新）として実装する（却下）

ADR-0013 案C が想定していたメソッド。更新対象が `name` 1 つだけなら部分更新の意味論に合う。

却下理由: `Store` の更新可能なフィールドは `name` のみで、部分更新と全体置換が一致する。
既存の `PUT /api/products/:id`（`updateProductSchema` でボディ全体を送る）と揃える方が
一貫性がある。`docs/05-roadmap.md` の Sprint 7 タスク3 の記載も `PUT /api/stores/:id` である。

### 案 D: 独立した店舗管理画面を新設し、そこにリネームを置く（却下）

現在、店舗の一覧・追加・削除は商品詳細画面の `PriceRecordForm` 内の店舗管理カードに
同居している（独立画面は存在しない）。リネームを機に画面を分離する案。

却下理由: 依頼スコープを超える。既存の追加・削除の導線を移設することになり、
Sprint 7 の完了条件に対して不要な変更範囲が増える。店舗管理 UI の独立は、
必要になった時点で独立したタスクとして扱う。

## Consequences（良い影響・悪い影響・残るリスク）

良い影響:

- 打ち間違えた店舗名を、蓄積した価格履歴を失わずに直せる。Sprint 7 の完了条件の
  「店舗名」側が満たされる。
- ADR-0012 が残した「使ってしまった店舗は詰む」というリスク系列が完全に解消する
  （ADR-0013 で削除経路、本 ADR で訂正経路）。
- DB スキーマ変更・データ移行が不要。`DrizzleStoreRepository.save()` はすでに
  `onConflictDoUpdate` で `name` を更新する実装になっている。
- ADR-0013 の同名禁止・3 件上限の構造は維持される（リネームにも同名検査を適用するため）。

悪い影響 / 残るリスク:

- **リネームは過去の全価格記録・買い物品目の表示名を一斉に書き換える。** `price_records.store_id`
  は ID 参照であり、店舗名は表示時に解決されるため、リネーム後は「A 店で記録したもの」が
  すべて新しい名前で表示される。訂正としては正しいが、**違う店舗を選んでリネームすると
  無関係な記録が巻き添えになる**。
  - 緩和策: リネームダイアログで `GET /api/stores/:id/usage` を呼び、影響を受ける価格記録の
    件数をインライン警告として表示する（ユーザー確定・2026-08-05）。削除のような二段階確認は
    設けない。リネームは可逆（再度リネームすれば戻せる）であり、名前を 1 文字直すだけの
    軽微な操作に毎回確認を強いる負担の方が大きいと判断した。
  - 完全には防げないリスクとして受容する。2 人運用・店舗 3 件以内という規模が前提。
- `Store` の完全不変性が失われる。`storeName` のみ可変になるため、以後 `Store` の
  インスタンスを共有する箇所では「途中で名前が変わりうる」前提が必要になる。
  現状 `Store` は UseCase 内で取得して DTO 化するだけで、長命な参照を持つ箇所は無い。
- リネームは変更履歴を残さない（誰が・いつ・元の名前は何だったか）。元の名前は画面から
  確認できなくなる。既存の削除（`removePriceRecord` の「取り消しは無い」）と同じ思想であり、
  監査ログは MVP の対象外。

## Migration（移行が必要な場合の手順。不要なら「対象外」）

**対象外。** DB スキーマ変更・データ移行は不要。新設する `PUT /api/stores/:id` は既存
エンドポイント（`GET` / `POST` / `DELETE` / `GET /:id/usage`）と共存し、破壊的変更を伴わない。

本番 DB に現存する重複店舗（ADR-0013 の背景となった「業務スーパー」4 件など）の整理は、
ADR-0013 が定めた削除経路で行う既存の課題であり、本 ADR のリネームでは解決しない
（同名の店舗が 2 つ残るだけ、という案C の評価がそのまま当てはまる）。

## Rollback（決定を戻す場合の手順）

1. `PUT /api/stores/:id` のルート（`apps/web/src/server/routes/stores.ts`）を削除する。
2. `RenameStoreUseCase` と `RenameStoreInputDto` を削除する。
3. `Store.rename()` を削除し、`storeName` を `private readonly` へ戻す。
4. `StoreRenameDialog` と `PriceRecordForm` 側の編集導線を削除する。

DB スキーマ・保存済みデータへの影響が無いため、ロールバックはコードの巻き戻しのみで完結する。
リネーム済みの店舗名は元に戻らないが、これはデータとして正常な状態であり修復は不要。
