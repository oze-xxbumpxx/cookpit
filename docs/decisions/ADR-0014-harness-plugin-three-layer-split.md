# ADR-0014: ハーネスを 3 層 Plugin として配布し、スタック固有資産は同梱しない

- Status: Accepted
- Date: 2026-07-31
- 関連 feature: harness-plugin-split

## Context（背景・なぜ判断が必要か）

Cookpit の Claude Code ハーネス（設定 7,700 行 + 履歴 17,800 行）を他プロジェクトへ
再利用したいという要求。2026-07-31 の棚卸しで、実行系 3,627 行はほぼ汎用だが、指示系と
実績・履歴はプロジェクト固有度が高いと判明した。

配布方式は Plugin 化を選択済み。残る判断は「どう切るか」と「何を配らないか」。
判断を要した理由は 3 つ。

1. **全部配ると過剰**。L0〜L3 分類・evals 回帰評価・改善サイクルは Cookpit の規模に
   合わせて育ったもので、小規模プロジェクトでは工程が完全に過剰になる。
2. **`.claude/rules/` は Plugin の配布プリミティブに含まれない**。あの自動注入は
   プロジェクトローカルに置いた `.md` が project instructions として読まれる挙動
   （`.claude/rules/README.md` の 2026-07-28 実測）で、Plugin には rules の概念がない。
3. **自動注入は常時トークンを消費する**。移植先のスタックに合わないルールを配ると、
   トークンを払った上で誤った前提を注入する。「配らない」判断も選択肢になる。

## Decision（採用した決定）

**依存が閉じた 3 層の Plugin に分割し、マーケットプレイス 1 本に並べる。**
移植ティアは install 時にプロジェクトごとに選ぶ。

| Plugin                | 行数（実測） | 依存     |
| --------------------- | ------------ | -------- |
| `harness-core`        | 1,919        | なし     |
| `harness-workflow`    | +2,324       | core     |
| `harness-improvement` | +2,149       | workflow |

付随して 3 点を決めた。

- **D-1: スタック固有資産 1,418 行は Plugin へ同梱せず Cookpit ローカルに残す。**
  対象は `check-codex-implementation.mjs`（861 行）/ `manual-browser-verify` /
  `review-codex-implementation` / `create-codex-brief` / `contract-designer` /
  `rules/domain-layer.md` / `rules/presentation-layer.md` / `assert-e2e-results.mjs`。
- **D-2: 汎用ルール（`coding-standards.md` 48 行）は CLAUDE.md テンプレートの断片として配る。**
  Plugin に断片ファイルを同梱し、移植先が自分の CLAUDE.md へ取り込む。
- **D-3: 事象出典はプロジェクト名を前置する**（`出典: cookpit/<feature> 事象 N`）。
  ただし Plugin 同梱ファイルへの参照はパスを維持する（移植先でも生きるため）。

## Alternatives（検討した非採用案と却下理由）

**配布方式**（Plugin 以外）

| 案                             | 却下理由                                                                |
| ------------------------------ | ----------------------------------------------------------------------- |
| テンプレートリポジトリ         | 更新が伝播せず drift する。改善サイクルの成果が他プロジェクトへ届かない |
| git subtree で `.claude/` 共有 | 手動 pull が必要で、層ごとの取捨選択ができない                          |
| `~/.claude/` にグローバル配置  | チーム共有できず、プロジェクト固有 rules と混ざる                       |

**Plugin の分割数**

| 案   | 却下理由                                                                                 |
| ---- | ---------------------------------------------------------------------------------------- |
| 1 本 | ティアの概念が消え、移植先ごとの取捨選択ができない。小規模に改善サイクルが付く           |
| 2 本 | workflow と improvement を統合すると、小規模プロジェクトに evals・メトリクスが付いてくる |

**D-1 の非採用案**

| 案                         | 却下理由                                                                                                                          |
| -------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| 4 本目の stack 固有 Plugin | 将来 Next.js + Tailwind のプロジェクトを作るなら有効だが、現時点で移植先が未定。Phase 3 の作業が 1 本分増える割にリターンが不確実 |
| improvement 層に同梱       | Next.js 以外のプロジェクトが improvement 層を入れると、使えない指示が混入する                                                     |

**D-2 の非採用案**

| 案                      | 却下理由                                                                     |
| ----------------------- | ---------------------------------------------------------------------------- |
| Plugin Skill として配る | 常時トークン消費は減るが、`any` 禁止等の「常時守るべき」ルールが見落とされる |
| 配らず移植先で各自書く  | 汎用ルール 48 行は明確に再利用価値があり、毎回書き直すのは無駄               |

**D-3 の非採用案**

| 案                           | 却下理由                                               |
| ---------------------------- | ------------------------------------------------------ |
| 「他プロジェクト実績」と明示 | Cookpit 自身でも「他プロジェクト」と読めてしまい不自然 |
| 現状維持（フルパス）         | 移植先で dead link になる。根拠の文脈は残るが辿れない  |

**出典を消す案は最初から却下**。出典は指示の根拠であり、削ると「なぜこの指示があるか」が
失われる（改善サイクルの前提が崩れる）。

## Consequences（良い影響・悪い影響・残るリスク）

**良い影響**

- ティアの「選択」が install 時へ後ろ倒しになり、移植先未定でも設計・実装を進められる。
- `harness-core` 1,919 行だけで安全境界（`guard-dangerous`）と品質ゲートが最小構成で効く。
- Cookpit 自身を利用側へ転換すれば（Phase 3）改善サイクルの成果が全プロジェクトへ伝播する。
- D-1 により Phase 2 の作業量が大幅に減った（1,418 行に手を触れない）。

**悪い影響**

- 別の Next.js プロジェクトを作ったとき、スタック固有資産は手でコピーする必要がある（D-1）。
- `close-session` の分割が必要になった。skill 自身が「kickoff-session と対になる」と
  規定しているのに依存先 4 本が improvement 層のため、そのまま切ると
  「開始できるが終了できない」構成を配ることになる。
- D-2 の取り込みが手作業。移植先で CLAUDE.md へ貼る操作が必要。

**残るリスク**

- Plugin の依存宣言がどこまで強制されるか未調査（Phase 3 の調査事項）。強制されない場合、
  core 無しで workflow を install する構成を防げず README 明記に頼る。
- `evals/cases/` 10 件のうち 4 件はスタック前提を含み、汎用/ 固有の線引きが未決（Phase 3）。

## Migration（移行が必要な場合の手順）

**対象外**。状態ファイルの形式・保存先は変更しない（Phase 1 の `harness-portability` で
名前空間の導出が現行値と一致することを確認済み）。Cookpit の現行運用も壊さない。

## Rollback（決定を戻す場合の手順）

Phase 2 の変更は `.claude/` と `docs/` に閉じるため `git revert` で戻せる。Phase 3 で
別リポジトリを作った後に戻す場合は、Plugin リポジトリを削除し Cookpit の `.claude/` を
利用側転換前の状態へ戻す（Phase 3 の設計時に手順を確定する）。

3 分割を 1 本へ戻す判断はマニフェストの統合だけで済む（ファイル自体は同じ）。
