# ADR-0012: 店舗は物理削除し、参照が 1 件でもあれば削除を拒否する

- ステータス: **superseded**（2026-07-27、[ADR-0013](./ADR-0013-store-limit-and-delete-cascade.md) により）
- 日付: 2026-07-27
- 決定者: ユーザー（選択肢提示のうえ確認）

> **この決定は同日 ADR-0013 で覆された。**本 ADR の Consequences に残るリスクとして書いた
> 「使ってしまった店舗はもう消せない」が実データで現実になった（同名チェック不在により
> 「業務スーパー」が価格記録付きで 4 件重複した）。店舗マスタを 3 件上限にする要求と
> 組み合わせると、10 件から 3 件へ下げる経路が存在せず詰むため、削除は参照ごと
> カスケードする方針へ変更した。判断の経緯は ADR-0013 §Decision「なぜ ADR-0012 の判断を
> 覆すのか」を参照。以下は当時の記録として残す。

## Context（背景・なぜ判断が必要か）

店舗（`Store`）には作成 API しか無く、試し入力で作った店舗がプルダウンに残り続ける。
削除を追加するにあたり、店舗を参照している側の扱いを決める必要がある。

店舗 ID を参照している箇所は 2 系統ある。

| 参照元                           | FK                  | 意味                                         |
| -------------------------------- | ------------------- | -------------------------------------------- |
| `price_records.store_id`         | あり（`restrict`）  | どの店舗でいくらだったか。価格比較の元データ |
| `shopping_items.target_store_id` | **なし**（ID 参照） | どの店舗で買う予定か                         |
| `shopping_items.actual_store_id` | **なし**（ID 参照） | 実際にどの店舗で買ったか                     |

買い物リスト側に FK が無いのは、集約をまたぐ参照を ID 参照に留める方針（D-6・C-4 の先例）に
よる。つまり **DB だけでは参照整合性を守れない**。`stores` を単純に `DELETE` すると、
`price_records` は FK の `restrict` で生の DB エラー（→ 500）になり、`shopping_items` は
静かに宙ぶらりんの ID を抱える。

本プロジェクトの中心的な価値は「複数店舗の価格比較」（`docs/01-overview.md` §解決したい課題 1）で
あり、価格履歴は再入力の効かない蓄積データである。

## Decision（採用した決定）

**店舗は物理削除する。ただし削除前に Application 層で参照件数を数え、1 件でもあれば拒否する。**

- `StoreRepository.delete(id)` を追加する（論理削除フラグは持たせない）。
- 参照件数の取得は各集約のリポジトリに置く。
  - `ProductRepository.countPriceRecordsByStore(storeId)`
  - `ShoppingListRepository.countItemsByStore(storeId)` … `target_store_id` と
    `actual_store_id` のどちらかが一致する品目を数える
- `DeleteStoreUseCase` が「存在確認 → 参照件数の合計 → 0 なら削除」の順に実行する。
  参照があれば `StoreInUseError`（`InvalidOperationError` 継承）を投げ、
  既存の `onError` により **422** になる。
- エラーメッセージには内訳の件数を含める。UI はそれを日本語に組み立て直して表示する。

削除の物理削除採用は ADR-0011（買い物リスト品目）と揃う。違うのは「参照があれば拒否する」点で、
これは削除で失われるものが**自分で入れ直せない蓄積データ**だからである。

## Alternatives（検討した非採用案と却下理由）

### 案 A: 参照ごとカスケード削除（確認ダイアログで警告のうえ強制削除）（却下）

どんな店舗でも必ず消せるが、価格履歴が巻き添えで消える。単価の推移は日付をまたいで
少しずつ貯めるデータで、消すと再現できない。ユーザーが実際に消したいのは「試し入力で作った
未使用の店舗」であり、この案が必要になる場面が無い。undo も無い。

### 案 B: 論理削除（`stores.archived_at` 列を追加してプルダウンから隠す）（却下）

データは失われず、過去の記録の店舗名も残る。しかし
(1) DB スキーマ変更とマイグレーションが必要、
(2) `findAll()` の呼び出し箇所すべてに「隠すかどうか」の分岐が波及する、
(3) 2 人利用・店舗数が数件の規模に対して仕組みが重い。
参照ゼロの店舗を消せれば当面の目的（プルダウンの掃除）は達成できる。

### 案 C: DB の FK（`restrict`）だけに任せる（却下）

`price_records` は守れるが、FK の無い `shopping_items` は守れない。さらに FK 違反は
Drizzle が生の例外として投げるため `onError` の 500 経路に落ち、ユーザーには
「なぜ消せないのか」が伝わらない。参照件数も出せない。

### 案 D: 参照を持つ品目・記録を「店舗未設定」に付け替えてから削除（却下）

「どの店舗が安かったか」という情報そのものが価格記録の本体なので、店舗を剥がした記録は
価値を失う。実質的にカスケード削除と変わらない。

## Consequences（良い影響・悪い影響・残るリスク）

良い影響:

- 価格履歴が巻き添えで消える事故が構造的に起きない。
- DB スキーマ変更が不要で、既存データの移行も要らない。
- 拒否時に件数を返すので、ユーザーは「どこで使われているか」を知って対処できる。

悪い影響 / 残るリスク:

- **使ってしまった店舗はもう消せない。** 名前を打ち間違えたまま価格を記録した場合、
  価格記録を全部消さない限り店舗が残る。リネーム機能が無いため回避策も無い
  （今回の対象外。必要になったら別タスクで店舗の更新 API を足す）。
- 参照件数の確認と削除は**別トランザクション**である。確認と削除の間に他方の端末が価格を
  記録すると、`price_records` の FK `restrict` が最後の砦として働き 500 になる。
  2 人・同時操作がほぼ起きない運用のため、追加のロックは入れない（既知の制約）。
- 参照件数の取得メソッドが `ProductRepository` / `ShoppingListRepository` に増える。
  集約をまたぐ問い合わせを Application 層の UseCase が束ねる形は保たれている。

## Migration（移行が必要な場合の手順）

不要。DB スキーマ・既存データともに変更しない。

## Rollback（決定を戻す場合の手順）

`DELETE /api/stores/:id` とルート、`DeleteStoreUseCase`、`StoreInUseError`、UI の削除ボタンを
取り除けば元に戻る。リポジトリに足した `delete` / `count*` は残っていても既存の挙動に
影響しない。DB 変更が無いためデータ側のロールバックは不要。
