#### 方式を roadmap の記述から変更した

roadmap のタスク名は「PWA オフライン書き込みキュー（**Background Sync**）」だったが、
Background Sync API（`SyncManager`）は Chromium 限定で **iOS Safari が未対応**と見られる。
Cookpit の主対象は iPhone の PWA なので、名指しされた技術では完了条件を満たせない。

**ユーザー確定で案 C（アプリ層のみ）を採用**した。IndexedDB に永続キューを持ち、
`online` イベント・フォーカス復帰・マウントで再送する。`sw.ts` には一切触らない
（Sprint 8 で踏んだ `self.__SW_MANIFEST` の terser インライン化の罠を再度踏まないため）。

**この iOS 非対応は一次情報で裏取りできていない。** この環境では `developer.mozilla.org` /
`vercel.com` への egress がポリシーで遮断されている。設計書に「未確認の前提」として明記した。

#### キュー対象をチェック操作のみに絞った根拠

対象 API の冪等性を調べたところ、はっきり二分された。

| API | 送るもの | 再送安全性 |
| --- | --- | --- |
| `POST /items/:itemId/checked` | 絶対値 | 安全（last-write-wins） |
| `POST /items/:itemId/bought` | 絶対値 | 安全 |
| `DELETE /items/:itemId` | — | 安全（404 を成功扱い済み） |
| `POST /stocks/:stockId/consume` | **差分** | **再送で二重消費** |

完了条件はチェック操作だけを求めており、既に冪等な API で満たせる。`consume` をキューに載せるなら
Sprint 9 タスク 3（冪等性キー）が設計上の先行条件になる。

### 非決定的なテストが実装の欠陥を隠していた

`LCQ-09` が「1 回のはずが 3 回」で失敗し、`LCQ-EX` は実行ごとに成否が変わった。原因は
**アンマウント後も `flush()` が走り続け、前のテストの送信が次のテストへ混入**していたこと。
`afterEach` の `cleanup()` と `vi.clearAllMocks()` では止まらない（IndexedDB の解決がマクロタスクで
起きるため）。フックにアンマウント検知を足して解消し、3 回連続実行で安定を確認した。

設計・計画のどちらも**「flush の生存期間」を規定していなかった**。`flushingRef` による二重発火の
排他はあったが、コンポーネントの寿命とキュー処理の寿命の関係が未定義だった。

## Sprint 9 タスク 2: 前提が誤っていたことを実測で確定した

roadmap のタスク 2 は「Function だけ hnd1 へ移すと DB 往復が悪化する」という懸念を前提にしていた。
これは**Function と Neon が同居している**ことを暗黙の前提にしていたが、実測すると成立していなかった。

### 測定方法

DB を触る API と触らない API の応答時間を比べる。差分がそのまま DB 往復のレイテンシになる。
`GET /api/stores` は `findAll()` の**単一クエリ = 1 往復**であることをコードで確認済み。

```
DBなし (/api/push/vapid-public-key): 0.274 / 0.132 秒
DBあり (/api/stores):                0.449 / 0.353 秒
差分 = DB 1 往復:                    0.175 / 0.221 秒
```

**Function ↔ Neon の 1 往復に 0.18〜0.22 秒。**「同居」の想定値（数 ms）の 50 倍以上で、
既に地球の反対側にある。

### チェック操作への影響

チェック操作 1 回は DB を**逐次 4 往復**する（`findById` 1 回 + `save()` 3 回。
`drizzle-shopping-list.repository.ts:44` / `:71` / `:83` / `:99`）。`neon-http` はクエリごとに
独立した HTTPS リクエストを投げるため、往復回数がそのままレイテンシに掛かる。

```
0.2 秒 × 4 往復 + 0.13 秒（利用者→Function） ≒ 0.9 秒
```

**店内でチェックを 1 つ入れるたびに約 0.9 秒。** Sprint 9 のゴール後半「体感速度の実測値が改善する」は、
オフラインキューではなくこの構成が原因だった。

### 結論と残件

「Function だけ移すと悪化する」という懸念は**当たらない**。移設は改善手段になる。ただし
*どちらへ寄せるか* は Neon の場所次第で、**Neon のリージョンは未確認のまま**（ダッシュボードで
確認できず、この環境からは egress 遮断で調べられない）。

`save()` が 3 往復している点（チェック 1 件のために全品目を delete して再 upsert する構造）は
リージョンとは別の増幅要因。Sprint 7 から「非トランザクションで並行書き込みが価格記録を静かに消す」
という申し送りも付いている箇所なので、**Sprint 10 のトランザクション導入と同時に扱うのが筋**。
今回はスコープ外として記録に留めた。
