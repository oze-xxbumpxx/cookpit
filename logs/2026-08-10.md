### 実装フェーズで見つかった問題（3 件）

**1. Domain が Node に結合していた（S-5 の顕在化・設計フェーズの予告どおり）**

`stock-row.tsx` がクライアントから `@cookpit/application` を値 import した結果、バレルが
`@cookpit/domain` を辿って `node:crypto` に到達し、`UnhandledSchemeError` でクライアント
バンドルのビルドが失敗した。`.claude/rules/domain-layer.md:13` は「`packages/domain` は
他のパッケージに依存しない。これが Clean Architecture の核」としており、**Node 固有 API への
結合は本来この層にあってはならないもの**だった。本ユニットが持ち込んだのではなく、
既存の潜在的な違反がクライアントから初めて参照されたことで表面化した形。

`node:crypto` の用途は `randomUUID()` の 2 箇所だけだったため、標準の
`globalThis.crypto.randomUUID()` へ置き換えて解消した（Node 22 / `engines: >=20` / jsdom
いずれでも利用可能なことを実測）。ユーザー確定を経て実施。

**2. 契約設計書のコード例にバグがあった（zod v4 の挙動）**

zod v4 は先行チェック（`.url()` を含む）が失敗しても後続の `.refine()` を短絡しない。
`new URL(value)` を try/catch なしで呼ぶと不正な入力で `TypeError` が送出され、
**`safeParse()` 自体が throw** して `{ success: false }` を返さなくなる。implementer が
実装中に検出し try/catch で解消した。

**3. Serwist の InjectManifest が terser のインライン化に依存していた**

`sw.ts` に `push` / `notificationclick` を足したところビルドが
`Can't find self.__SW_MANIFEST in your SW source.` で落ちた。InjectManifest はビルド後の
JS 文字列中に `self.__SW_MANIFEST` が literal で現れることを前提に置換する。従来は
`sw`（`self` のキャスト済みエイリアス）の参照が 1 箇所だけだったため terser のインライン化で
偶然 literal が残っていたが、参照が 5 箇所に増えてインライン化されなくなった。
`precacheEntries` の 1 行だけ `self` を直接参照する形へ変更して解消。
**ビルド成果物を grep で実測検証**し、既存 4 キャッシュ戦略が 1 回ずつ残り、
`push` / `notificationclick` が注入され、`__SW_MANIFEST` が実マニフェストへ置換されて
いることを確認した。
