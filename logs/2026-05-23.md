## 気づき・メモ

- UseCase 設計の確定事項
  - **戻り値は `RecipeDto`（プレーンオブジェクト）に変換**。Recipe エンティティを Application 層の外（Presentation / Hono）に漏らさない。mapper（`recipe.mapper.ts`）は application 層内部に閉じる
  - **NotFound は専用クラス `RecipeNotFoundError`**。後続の Hono 層で 404 にマッピングしやすくするため
  - 入力 DTO の `Unit` / `RecipeTag` は domain の Union 型を境界でそのまま再利用（raw 文字列の検証は後続の api-contract / Zod 層が担当）
  - DTO の `createdAt` / `updatedAt` は ISO 文字列（`Date` を境界外に出さない）
- アーキテクチャ doc の4ファイル（create / get-recipes / update / delete）に **`get-recipe`（単体取得）を1つ追加**。詳細画面 `/recipes/[id]` が ID 指定取得を必要とするため
- **Update では `baseServings` を変更しない**方針で確定
  - `Recipe` に `updateBaseServings()` が無い。今は2人前前提のため不要と判断
  - 「2人前に合わせる」は将来 MealPlan 側の `scaleIngredients()` で対応する別概念。baseServings 編集とは無関係
  - baseServings は材料量とセットの基準値のため、単独編集はデータ不整合リスクあり。必要になったら不整合の扱いを決めて別タスクで追加（投機的には入れない / YAGNI）
- `packages/application` は現状 `@cookpit/domain` 依存が無いので、UseCase 実装時に追加が必要。import は repository と同じ `@cookpit/domain/src/...` subpath で揃える
