## 気づき・メモ

- **実行系はほぼ汎用だった。** 3,627 行のうち移植を阻む箇所は実測で数点のみ。
  - `.claude/lib/harness-paths.mjs:20` — `STATE_NAMESPACE = 'cookpit-harness'`
  - `COOKPIT_TZ` 環境変数名（`check-improvement-cycle.mjs:102` /
    `session-briefing.sh:13` / `sprint-summary.sh:13`）
  - `pnpm` 決め打ち（`run-quality-gates.sh` / `detect-project-commands.sh`）。ただし
    両者は `has_script` で存在検出する設計なので、パッケージマネージャ検出を足すだけで済む
  - `settings.json` の `hooks` は `$CLAUDE_PROJECT_DIR` 相対で**完全に汎用**。
    固有なのは `permissions`（pnpm / terraform / sst 前提）だけ
- **スタック依存が濃いのは 2 ファイルに集中している。**
  `.claude/scripts/check-codex-implementation.mjs`（固有名詞 10 箇所・Tailwind / Next 前提）と
  `record-task-metrics.sh`（14 箇所）。逆に言えば**この 2 本を切り離せば実行系は移植可能**。
- **`.claude/rules/` は plugin で配布できない。** あの自動注入は「プロジェクトローカルに置いた
  `.md` が project instructions として読まれる」挙動（`.claude/rules/README.md` の 2026-07-28
  実測記録）で、plugin の配布プリミティブには rules ディレクトリの概念が無い。
  汎用の `coding-standards.md` は **plugin skill か CLAUDE.md テンプレート**として配る必要がある。
  `domain-layer.md` / `presentation-layer.md` は Clean Architecture + Next.js 以外に
  持ち込むと**有害**（常時トークンを消費する上に前提が合わない）。
- **事象出典は移植先で dead link になるが、消してはいけない。** `recipe-servings 事象2` 等は
  指示の根拠そのもの。参照形式を「出典: <プロジェクト>/<事象>」へ統一し、移植先では
  「他プロジェクトの実績」として読める形にするのが妥当（Phase 2 の論点）。
- **過剰移植のリスクを明示した。** この構成は設定 7,700 行 + 履歴 17,800 行で、Cookpit の
  規模に合わせて育ったもの。L0〜L3 分類・evals 回帰評価・improvement cycle を全部持ち込むと
  小規模プロジェクトでは工程が完全に過剰になる。**移植先ごとにティアを選ぶ**前提にした。
- Cookpit 自身も plugin 利用側へ転換すると dogfooding になり、改善サイクルの成果が
  全プロジェクトへ伝播する（Phase 3 の狙い）。
