## 気づき・メモ

- **`main` が指す index.ts が空だった**のが観点A の根本原因。`main`/`types` は
  `./src/index.ts` を宣言済みだったので、バレルを埋めるだけで規約が揃った。
  application / infrastructure / api-contract は既にバレルを持っており、domain だけ例外だった。
- **機械置換の正規表現で隣接 import を巻き込んだ**（1 回目の失敗）。
  `\{([\s\S]*?)\}` は貪欲でなくても `}` を跨いで後方の `from '@cookpit/domain/src/...'` に
  マッチしてしまい、直前の `import { describe, it } from 'vitest'` を飲み込んだ。
  波括弧内は `[^}]` に限定すること。type-check が即座に検出したので影響は無し。
- **設計時の前提が 1 件外れた**: 「11 個のエラーは全て 2 基底のいずれかを継承」と書いたが、
  `InvalidStockOperationError` だけ素の `Error` 継承だった。実装前に全件確認する手順を
  実装計画に入れていたため着手時に判明。基底の付け替えでは**メッセージ書式を固定しない
  中間基底**（`InvalidOperationError`）を挟むことで、自由記述メッセージを保ったまま統合できた。
- **テストモックは本物より貧しい**: `useApiAction` が成功時に常に `response.json()` を呼ぶ設計に
  したところ、meal-plan のテストモックが `json()` を持たず「通信エラー」に落ちた。
  本文を使わない成功時のための `onSuccessWithoutBody` を分けて解決。
  「使わない本文をパースしない」のは実装としても正しい。
- **Hono の ClientResponse はステータスごとのユニオン**で、成功側だけ `ok: true` を持つ。
  共通フックで型安全を保つには `Extract<TResponse, { ok: true }>` で成功側を取り出す必要がある。
- **楽観的更新は共通化しない**判断が正解だった。`useOptimistic` + `startTransition` は
  状態更新の順序そのものが挙動（transition 内の通常 setState は保留される）なので、
  フックに寄せると「操作中 item のみ disable」が壊れる。共通化対象は非 optimistic に限定。
