## 気づき・メモ

- **保存値を変えずに表示だけ換算する**のが今回の肝。`unit_price_amount` は店舗間比較の
  正準値なので、ここを単位ごとに変えると 300g の記録と 1kg の記録が比較できなくなる。
  「ユーザーの違和感」は表示の問題であって、計算の問題ではなかった。
- **表示側の単位判定を正規化してはいけない。** `UnitPriceCalculator` は
  `new Set(['g','kg'])` の厳密一致で正準化しており、表示側だけ `toLowerCase()` を足すと
  `'KG'` で「正準値は 1 単位あたり・表示は 1kg 基準」になり**単価が 10 倍ズレる**。
  同じ厳密一致に揃え、理由をコードコメントと PF-06b の試験で固定した。
  正準化と表示は**必ず対で読む**。
- **`formatUnitPrice` の導入で `unitPriceBasisLabel` が死んだ**。金額とラベルは常に対で
  出るため、置き換え後に本番の呼び出し元がゼロになる。テストだけが参照する公開関数を
  残しかけたので削除し、試験は `formatUnitPrice` 経由へ移した。
  **関数を足したら、置き換え元が死んでいないか必ず確認する。**
- **削除の設計は「何が失われるか」で決まる。** ADR-0011（買い物品目）は無条件の物理削除、
  ADR-0012（店舗）は参照があれば拒否。差は「消えるものを自分で入れ直せるか」で、
  価格履歴は日をまたいで貯めるので入れ直せない。同じ「削除」でも判断を揃えるべきではない。
- **Base UI の `Select.Item` に削除ボタンは入れられない。** `role="option"` の内側に
  `<button>` を置くのは ARIA 的に不正で、項目クリックの選択挙動とも競合する。
  ユーザー要望は「プルダウンで削除したい」だったが、**プルダウン直下の既存パネル**
  （元々店舗追加があった場所）を管理パネルに拡張する形で満たした。制約は先に伝えて合意を取った。
- **Hono RPC の型は共通 `onError` 由来の 404 / 422 を知らない。** `response.status !== 404` が
  型エラーになる。`shopping-list-client.tsx` に既存の対処（`const status: number = ...`）が
  あったのでそれに揃えた。**同じ壁に当たったら回避策を発明する前に既存例を探す。**
- **「最近の記録」に内容量を出す**のは要求に明示されていないが、
  どの行が `3001kg` かを画面で見分けられないと削除機能が使えないため入れた。
  スコープ外変更はこの 1 点のみで、レビュー記録に理由を残した。
- リポジトリインターフェースへのメソッド追加で、テスト用 InMemory 実装 6 箇所が
  コンパイルエラーになる。**手順の最初にわざと型エラーを出して波及範囲を確定させる**のが速い。

### 気づき・メモ

- **セッション1 の ADR-0012 を同日に覆すことになった。** ADR-0012 が「残るリスク」として
  明記していた「使ってしまった店舗はもう消せない」が、そのまま現実になっていた。本番の店舗が
  10 件（実在 3・試し入力 4・同名重複 3）で、上限 3 件を入れると価格記録付きの店舗が消せず
  **10 件から下げる経路が存在しない**＝新規追加が永久に不可能な詰みになる。上限の導入と
  削除制約の緩和は不可分だった。ADR に「残るリスク」を書いておいたことが、今回の判断の
  根拠として直接効いた。
- **性能は推測せず実測した。**「描画が遅い」の主因は日本語フォント 4.40MB（JS+CSS 合計
  320KB の 12 倍）で、コードの書き方ではなくアセットだった。Function リージョンが
  iad1（米国東部）なのも `x-vercel-id` で判明。実測しなければ DB クエリや recharts に
  時間を使っていた。
- **unicode-range 分割は実装してから却下した。** 「Google Fonts の日本語方式」を真似たが、
  実測すると 16 スライス全部に到達して転送量が変わらず CSS だけ 73KB 増えた。効くのは
  グリフを頻度順に並べている場合で、JIS（読み）順では意味がない。**やってから測って戻す**
  判断ができたのは、先に測る手段を用意していたから。
- **クライアントから `@cookpit/domain` を値 import できない。** `StoreId.generate()` が
  `node:crypto` を使うため、ブラウザバンドルに混入する。既存のクライアントコンポーネントが
  すべて `import type` だったのは偶然ではなかった。UI 側に複製を置き、node 環境のテストで
  サーバー側実装との一致を固定した（`store-name.node.test.ts`）。
- **実画面確認で実バグを 1 件検出。** 本番に基本単位 `1L` の商品（自由記述単位）が実在し、
  数量を前置して `例：11L` になっていた。ユニットテストは全部通っていた。単位が自由記述で
  ある以上「数字で始まる単位」を想定すべきだった。
- 内容量のバリデーションエラーは `canSubmit` に阻まれて UI から到達不能だと分かった。
  文言の統一は達成したが、到達不能分岐として設計書の未決事項に記録した。
