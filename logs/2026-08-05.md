## 気づき・メモ

- **ADR-0013 で却下済みの機能を、却下理由の射程を切り分けて採用できた。** ADR-0013 案C は
  「店舗のリネーム」を却下しているが、その理由は「重複店舗の統合にはマージが必要」という
  **重複統合の文脈に限られる**。今回の目的は誤字訂正で別物なので ADR-0013 の結論を覆さない、
  という整理を ADR-0015 に残した。**過去の ADR を書き換えずに新しい決定を積める形**になった。
  ADR-0012（superseded）の本文も書き換えず、後日談を ADR-0015 が担う形にした。
- **「実装計画 ∥ 試験計画」の並行はユーザー指摘で直列に組み替えた。** 当初 workflow どおり
  並行起動したが「テスト駆動ちっくに行いたいので、テスト設計後に実装設計に移る？」と指摘され、
  実装計画エージェントを停止して試験計画 → 実装計画の順に変更。結果、実装計画の各ステップが
  **試験 ID を参照する Red → Green 構成**になった。並行だと実装計画が試験 ID を参照できない。
  `development-workflow.md` は L3 を「並行」と定義しているので、恒久化するかは別途判断
  （ワークフロー定義の変更は PR レビューが承認境界のため今回は動かさなかった）。
- **設計書の「将来課題」は着手時に前提を再検証すべき、が再び当たった。** 前タスクでは
  「バルク取得 API が無い」という陳腐化した制約が見つかったが、今回は ADR-0013 の却下理由が
  「別の目的なら当てはまらない」と分かった。**却下記録も、却下理由の射程まで読むこと。**
- **設計レビューの代わりに実物のコードを読ませたのが効いた。** 前タスクで「設計書の文面だけで
  UI を決めて実装と逆になった」失敗があったため、architecture-designer へ
  「`price-record-form.tsx` の実物を読んでから判断すること」を明示した。結果
  「`PriceRecordForm` は編集に再利用しない」判断が、3 つの具体的な理由つきで出てきた
  （店舗管理機能まで同居した複合コンポーネントである等）。
