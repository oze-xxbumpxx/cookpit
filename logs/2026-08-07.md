## 気づき・メモ

- **前タスクの学びが 3 回目の再発をした。** MB-01 を「価格記録あり」の商品でしか測らず、
  **0 件用のデータ（にんじん）を自分でシードしていたのに使わなかった。** 結果レビューが
  Must（0 件時にスケルトン 256px → 空状態 86px で縮み、直下の「この商品を削除」ボタンが
  55px 上へジャンプ）を見つけた。前タスクで既に 2 回記録済みの
  「**確認項目の前提条件を満たすデータを選ばないと、自動化スクリプトは何も無いことを
  PASS と報告する**」と同型。**シードしたデータを全部使ったか、を確認手順に入れる必要がある。**
- **FAIL を見てから PASS 基準を変えるのは構造的に危険。** MB-01 は一次計測で「チャート下要素の
  Y が 115px 動いた」ため FAIL としたが、測定窓が広く既存シフトを取り込んでいた。基準を
  「チャート切替に起因するシフト」へ絞ったが、**これは正当化になり得る**ので独立した直接測定
  （「価格推移」セクション高が 284px で切替前後同一 → 下の要素は動き得ない）で裏を取った。
  実際の原因は `PriceRecordForm` の店舗一覧の非同期取得で、`layout-shift` の `sources` が
  「価格推移セクション**自身**が下へ動いた」＝原因はその上、と示していた。
- **環境の状態不整合が偽の FAIL を作るのは 2 回目。** バンドル計測で `next build` した後の
  `.next` を残したまま `next dev` を起動したら商品詳細ページが 404 になり、旧 UseCase を使う
  編集ページと API は 200 だったので**「新 UseCase の欠陥」と判断しかけた**。実際は本番ビルド
  成果物と dev の不整合で、ファイルを 1 度触って再コンパイルさせると解消（`git diff` 差分なし）。
  前タスクの「dev 起動中に PGlite を再シードして古い状態を掴んだ」と同型。
  → **`next build` の後に dev 確認をするなら `.next` を消してから起動する。**
  これは環境の恒久的な事実なので `docs/07-dev-rules.md` §環境の既知の事実 への追記を検討する。

## 気づき・メモ

- **設計書は下流工程で 8 件の欠陥が見つかった。** 確定済み（ステータス confirmed）でも
  下流が実コードを当たると誤りが出る。内訳は契約設計で 2 件・試験計画で 4 件・レビューで
  Must 3 件（一部重複）。**特に「Zod バリデーション失敗は 422」は明確な事実誤り**で、
  実際は `@hono/zod-validator` が `app.onError` を経由せず自前で 400 を返す。
  → **設計書の記述を下流 Agent に「前提」として渡すときは、実測を指示しないと誤りが伝播する。**
- **P-1 の変更（数量の追加）が罠のもう 1 つの顔を炙り出した。** `onConflictDoUpdate.set` は
  `amountValue` はあるが **`amountUnit` が無い**。期限・保存場所が丸ごと無い元の罠より、
  「値は変わるのに単位だけ変わらない」ほうが**動いて見えるぶん気づきにくい**。
  推奨案どおり期限・保存場所だけにしていたら、この顔は見つからなかった。
- **既存テストが罠を「正しい挙動」として固定していた。** `同一 id の再 save() は amountValue
  のみ更新し不変フィールドを維持する` が `amountUnit === '個'` / `expiresAt === '2026-07-18'` /
  `storedLocation === 'fridge'` をアサートしている。修正すると 3 アサーションが落ちる。
  **これを実装計画に書いておかないと、実装者は「回帰した」と誤診する。**
- **レビュー M-1 が false PASS の構造そのものだった。** 緊急度チップの表示条件で
  「期限切れ（残日数が負）」の扱いが未定義で、下限を付ける実装でも **RTL 観点に overdue が
  無いため全件 Green のまま手動確認だけが落ちる**。累計 3 回起きている型と同じ構造を、
  今度は**実装前に**捕まえられた。SR-EDIT-07 を必須ケースに追加した。
- **上限を明示した Agent 委譲が 4 本連続で機能した。** contract-designer 16 呼び出し /
  test-designer 30 / implementation-planner 32 / reviewer 25。いずれも成果物あり。
  前々タスクの「上限なし reviewer が 46 呼び出しで成果物ゼロ」とは対照的。
- **調査結果をプロンプトに埋め込むと再探索が減る。** Explore 3 本の実測結果を
  architecture-designer のプロンプトに全部貼ったので、設計 Agent は 20 呼び出しで済んだ。
- **セッションが usage 上限で 1 度中断した。** contract-designer の実行中。
  成果物は都度コミット・push していたので失われたのは 1 エージェントの実行分だけだった。
