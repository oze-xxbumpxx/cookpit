## 気づき・メモ

### 候補を並べる前に実データを見たことで、2 つの判断が変わった

**roadmap の「月次の食費分析 / 食材ロス分析」は並記されていたが、実現可能性が正反対だった。**

- 食費分析は**既にデータがある**（`shopping_items.actual_price_amount` × `actual_store_id`
  × `shopping_lists.shopping_date`）。新規テーブル不要
- ロス分析は**記録が一切残らない**。`ConsumeStockUseCase` / `DiscardStockUseCase` は
  `stocks` を減算・削除するだけ。つまりロス分析は「分析機能」ではなく**記録基盤を作る話**で、
  Sprint 8 で未着手だった「消費・廃棄の undo」と同じ根っこ（履歴が無いから undo できない）。
  1 本のスプリントにまとめられた

### 本番データの実測（2026-08-19）がスコープを決めた

| 対象 | 件数 | 判明したこと |
| --- | --- | --- |
| レシピ | 6 件 | うち 2 件（`ユーリンチー` / `マーボーナス`）は**手順が空**。手入力の負担が移行を止めている実証 |
| 商品マスタ | 7 件 | **全件が調味料**。`aliases` は全件空 |
| 在庫 | 1 件 | `productRef` / `expiresAt` とも null |

**在庫 1 件・`productRef` null により「在庫を考慮したレシピ提案」が現状データで動かない**
ことが着手前に分かった。提案を入れる場合も在庫を見ない版（履歴とタグのみ）に限定する判断へ。
候補リストの字面だけで設計に入っていたら、動かないものを作るところだった。

### 「機能を作る」と「移行を済ませる」は別の問題だった

レシピ登録の省力化を Sprint 11 の目玉として設計しかけたが、**ユーザーの提案で
「写真を送って Claude が読み取り登録する」手作業移行へ切り替えた**。目的が
「今ある紙のレシピの移行」であって「継続的な取り込み手段の整備」ではないと確認できたため。

- スプリント 1 本が丸ごと不要になった
- API コストも不要（試算では Opus 5 で 50 品 約 580 円・Batch API で約 290 円だったが、
  それすら払わずに済む）
- **副次効果**: 移行作業自体が、機能実装したときに LLM が詰まる箇所（タグ判断・分量表記の
  揺れ・手書きの癖）の実地調査になる

### コスト議論で「API コスト」と「実装工数」が混ざりかけた

ユーザーが「レシピ提案はコストがかかるので外して」→ 私が「ルールベースなら API コスト 0」と
補足 →「ゼロであれば入れるのも手」と再検討、という往復があった。**「ゼロ」が何のゼロかを
明示しないと判断を誤る**。最終的に「API コスト 0・実装工数はかかる」と分けて示し、
在庫を見ない軽い版として Sprint 13 に同居させる形で決着した。

### 在庫機能が実運用で使われていない可能性（要観察）

在庫 1 件・`productRef` null・`expiresAt` null は、MVP2 で入れた期限入力とアラートが
使われていない可能性を示す。ただし一時点のスナップショットなので断定はできない
（作り置き後に消費して減っただけの可能性）。**MVP2 クローズ時に申し送った
「2 人で土曜運用 1 周の観察が未実施」がここに顔を出した形。** Sprint 12 で在庫イベントの
記録を入れる際に、実際に運用が回るかを併せて確認する。roadmap の Phase 3 節へ要観察として明記。
