# Claude Codeマルチエージェント開発環境の構築依頼

> **ARCHIVED（2026-07-02）**: このファイルは初期構築時の依頼文（歴史的記録）であり、
> 現在の正典ではない。運用の正典は `docs/claude-code/`（usage-guide.md ほか）、
> Agent 実体は `.claude/agents/`、Skill は `.claude/skills/` を参照すること。
> このファイルへの参照は新規に追加しない。

このプロジェクトに、Claude Codeを使用したマルチエージェント開発環境を構築してください。

目的は、ユーザーが機能追加や修正を依頼した際に、指揮役となるOrchestratorがタスクを分析し、専門Subagentへ適切に作業を分配することです。

また、設計や実装計画についてユーザーから明示的な指示がなくても、変更規模に応じて必要なドキュメントが自動的に作成・更新される仕組みにしてください。

## 1. 基本方針

以下の要素を組み合わせて構築してください。

- CLAUDE.md
- カスタムSubagents
- Agent Skills
- .claude/rules
- Hooks
- docs配下の成果物管理

それぞれの責務を重複させないでください。

### CLAUDE.md

プロジェクト全体で常に必要な、短く具体的な原則だけを記載してください。

主に以下を定義します。

- 開発ワークフローの基本原則
- Orchestratorを使用する条件
- Subagentへの委譲方針
- ドキュメント作成方針
- 実装前に設計と計画を確認する原則
- ユーザーへ確認すべき条件
- 完了条件

CLAUDE.mdが肥大化しないようにしてください。

複数ステップの作業手順はSkillsへ、特定のファイルやディレクトリにだけ適用するルールは.claude/rulesへ分離してください。

## 2. モデル構成

モデルは以下のように固定してください。

### Orchestrator

```yaml
model: claude-opus-4-8
```

### その他のSubagents

```yaml
model: claude-sonnet-4-6
```

モデルエイリアスではなく、上記の完全なモデルIDを使用してください。

OrchestratorだけがSubagentを起動できる構成を基本としてください。

OrchestratorのtoolsにはAgentを含め、その他のSubagentには原則としてAgentを含めないでください。

ただし、明確なメリットがある場合に限り、Reviewerなどの一部Subagentから検証用Subagentを起動できる構成を提案しても構いません。

## 3. Orchestratorの責務

Orchestratorは自分で詳細な設計や大量の実装を完結させず、以下を担当してください。

1. ユーザー要求の分析
2. 変更規模の判定
3. タスクの分解
4. 必要なSubagentの選定
5. 実行順序と依存関係の決定
6. 並列実行可能な作業の判定
7. Subagentへの明確なコンテキストの提供
8. 各成果物の統合
9. エージェント間の矛盾解消
10. 最終的な完了条件の確認

Subagentへ依頼する際は、少なくとも以下を伝えてください。

- 目的
- 対象範囲
- 対象外
- 参照すべきファイル
- 期待する成果物
- 出力先
- 完了条件
- 禁止事項

Orchestratorは、Subagentの出力を無条件で採用してはいけません。

要件、設計、実装計画、実装、試験の間に矛盾がないか確認してください。

## 4. 作成するSubagents

まず、以下のSubagentsを作成してください。

### requirements-analyst

担当内容：

- ユーザー要求の整理
- 不明点、制約、前提条件の抽出
- 既存コードの調査
- 既存仕様の確認
- 影響範囲の整理
- 正常系、異常系、境界条件の抽出

原則としてコードを変更しないでください。

### architecture-designer

担当内容：

- 技術設計
- レイヤーと責務の整理
- API設計
- DB設計
- フロントエンド設計
- バックエンド設計
- データフロー
- エラー処理
- ログと監視
- セキュリティ
- 性能
- 後方互換性
- テスト方針

設計結果は会話上の回答だけで終わらせず、以下へ保存してください。

```text
docs/designs/<feature-name>.md
```

原則として実装コードを変更しないでください。

### implementation-planner

担当内容：

- 設計書を実装可能な単位へ分解
- 変更対象ファイルの特定
- ファイルごとの変更内容
- 実装順序
- 依存関係
- 各ステップの完了条件
- テスト追加箇所
- リスク
- ロールバック方法
- ドキュメント更新箇所

結果を以下へ保存してください。

```text
docs/implementation-plans/<feature-name>.md
```

原則として実装コードを変更しないでください。

### implementer

担当内容：

- 承認済みまたは確定済みの設計書を参照する
- 実装計画に沿って実装する
- 必要な単体テストを作成する
- Lint、型チェック、テストを実行する
- 設計から逸脱する必要が生じた場合は、独断で変更せずOrchestratorへ返す

実装前に以下を必ず確認してください。

```text
docs/designs/<feature-name>.md
docs/implementation-plans/<feature-name>.md
```

### test-designer

担当内容：

- 単体試験観点
- 結合試験観点
- 正常系
- 異常系
- 境界値
- 権限
- データ整合性
- 冪等性
- 回帰試験範囲
- 試験データ
- 完了条件

結果を以下へ保存してください。

```text
docs/tests/<feature-name>.md
```

### reviewer

担当内容：

- 要件充足性
- 設計との整合性
- 実装計画との整合性
- コード品質
- 責務分離
- エラー処理
- セキュリティ
- 性能
- テスト不足
- ドキュメント更新漏れ

Reviewerは原則としてコードを変更せず、指摘と修正案を提示してください。

レビュー結果を保存する必要がある変更では、以下へ出力してください。

```text
docs/reviews/<feature-name>.md
```

## 5. Agent Skills

以下のSkillsを作成してください。

### create-design-document

設計書を作成するための手順とテンプレートを定義してください。

必須項目：

- 背景
- 目的
- 要件
- 対象範囲
- 対象外
- 現状構成
- 変更後構成
- データフロー
- API設計
- DB設計
- フロントエンド設計
- バックエンド設計
- エラー処理
- ログと監視
- セキュリティ
- 性能
- テスト方針
- 移行とリリース
- リスク
- 未決事項

対象外の項目は削除せず、「対象外」または「変更なし」と明記してください。

### create-implementation-plan

実装計画を作成するための手順とテンプレートを定義してください。

必須項目：

- 前提となる設計書
- 変更対象ファイル
- 新規作成ファイル
- ファイルごとの変更内容
- 実装手順
- 依存関係
- 各ステップの完了条件
- テスト計画
- リスク
- ロールバック方法
- ドキュメント更新対象

### create-test-plan

試験計画と試験観点を作成する手順を定義してください。

### validate-deliverables

要件、設計、実装計画、コード、テストの整合性を確認するチェックリストを定義してください。

## 6. 変更レベル

すべての変更で重いドキュメントを作成しないよう、変更を3段階に分類してください。

### Level 1：軽微な変更

例：

- 文言修正
- CSSの微調整
- コメント修正
- 単純なnullチェック
- テストコードだけの修正
- 明らかな小規模バグ修正

成果物：

- 設計書は原則不要
- 実装計画は原則不要
- 最終報告に変更理由と確認内容を記載

### Level 2：通常変更

例：

- 既存APIへの項目追加
- 既存画面への機能追加
- バリデーション変更
- 業務ロジック変更
- Lambdaなど既存処理の変更

成果物：

```text
docs/designs/<feature-name>.md
docs/implementation-plans/<feature-name>.md
docs/tests/<feature-name>.md
```

### Level 3：重要変更

例：

- 新規API
- DBスキーマ変更
- 認証または認可変更
- 新規画面
- 外部サービス連携
- AWSサービス間の連携変更
- アーキテクチャ変更
- 既存データの移行

成果物：

```text
docs/requirements/<feature-name>.md
docs/designs/<feature-name>.md
docs/implementation-plans/<feature-name>.md
docs/tests/<feature-name>.md
docs/decisions/ADR-<number>-<title>.md
docs/reviews/<feature-name>.md
```

Orchestratorは作業開始時に変更レベルを判定してください。

判定理由を簡潔に提示してください。

## 7. 自動ドキュメント作成

ユーザーが明示的に「設計書を作ってください」と言わなくても、Level 2またはLevel 3と判定した場合は、必要なドキュメントを作成してください。

ただし、設計書を作成すること自体を目的にせず、実装に必要な判断と後から追跡すべき内容を残してください。

既存ドキュメントがある場合は、新規作成する前に更新対象か確認してください。

同じ内容のドキュメントを重複して作成しないでください。

## 8. Hooks

Hooksを使い、以下を機械的に検証できる構成を提案してください。

- Level 2以上のソースコード変更に対応する設計書が存在する
- 実装計画が存在する
- テスト計画が存在する
- 必須セクションが空になっていない
- コード変更後にテストまたは型チェックが実行されている
- ドキュメントと実装に明らかな不一致がない

Hooksは誤検知が多くならないようにしてください。

すべてのソース変更に対して単純に設計書の更新時刻を要求する方式は避けてください。

可能であれば、作業単位を識別するfeature-nameや作業メタデータを利用してください。

Hooksで完全に判定できない項目は、validate-deliverables SkillまたはReviewerへ委譲してください。

## 9. ツール権限

各Subagentには必要最小限のツールだけを付与してください。

目安：

- requirements-analyst：Read、Grep、Glob
- architecture-designer：Read、Grep、Glob、Write
- implementation-planner：Read、Grep、Glob、Write
- implementer：Read、Grep、Glob、Edit、Write、Bash
- test-designer：Read、Grep、Glob、Write
- reviewer：Read、Grep、Glob、Bash
- orchestrator：Read、Grep、Glob、Agent

Orchestratorが直接コードを書き換えない構成を優先してください。

ただし、成果物の統合に必要なら、限定的なWriteまたはEditを付与する案を比較してください。

## 10. 指示ドキュメントの構成

すべてをCLAUDE.mdへ直接記載しないでください。

次のように分割してください。

```text
CLAUDE.md
docs/claude-code/orchestration-policy.md
docs/claude-code/development-workflow.md
docs/claude-code/document-policy.md
docs/claude-code/agent-responsibilities.md
.claude/rules/
.claude/skills/
.claude/agents/
```

ただし、CLAUDE.mdからインポートする文書は、毎回のセッションで本当に必要なものだけにしてください。

特定の工程でしか利用しない詳細手順はSkillsまたはSubagent定義へ配置してください。

## 11. 作業手順

いきなりファイルを作成せず、最初に現在のコードベースと既存のClaude Code設定を調査してください。

次の順序で進めてください。

1. 既存のCLAUDE.mdを確認
2. 既存の.claude配下を確認
3. プロジェクト構成と技術スタックを確認
4. 既存ドキュメントの配置を確認
5. 現在の開発ワークフローを推測
6. 今回導入する構成案を提示
7. 既存設定との競合を提示
8. 作成・変更予定ファイルの一覧を提示
9. 最小構成と拡張構成を比較
10. 推奨構成を決定
11. 必要なファイルを生成
12. 設定の整合性を検証
13. サンプルタスクで委譲フローを確認

## 12. サンプル検証

構築後、以下のような依頼を想定して動作を検証してください。

```text
既存APIに項目を追加し、画面にも表示してください。
```

期待する流れ：

1. OrchestratorがLevel 2またはLevel 3と判定
2. requirements-analystが既存実装を調査
3. architecture-designerが設計書を作成
4. implementation-plannerが実装計画を作成
5. test-designerが試験観点を作成
6. implementerが実装
7. reviewerが設計、実装、試験をレビュー
8. Orchestratorが成果物を統合
9. HooksまたはSkillで必須成果物を検証
10. ユーザーへ結果を報告

実際のプロダクションコードはサンプル検証のために変更せず、委譲計画のシミュレーションだけを行ってください。

## 13. 最終出力

最後に以下を報告してください。

- 作成したファイル
- 変更したファイル
- 各Agentの責務
- 各Skillの責務
- モデル割り当て
- OrchestratorからSubagentへの委譲フロー
- 自動作成されるドキュメント
- Hooksで保証している内容
- Hooksでは保証できない内容
- 想定されるトークン消費上の注意
- 今後追加可能なAgent
- 運用開始時に人間が確認すべき項目
  Orchestratorの起動方法

Orchestratorを単なるSubagentではなく、メインセッションとして起動する構成がおすすめです。

例えば、.claude/agents/orchestrator.mdを作り、次のように起動します。

claude --agent orchestrator

Orchestrator定義は次のようにします。

---

name: orchestrator
description: >
複数工程を伴う開発タスクを統括し、
専門Subagentへ調査、設計、計画、実装、試験、レビューを委譲する。
model: claude-opus-4-8
tools: Agent(requirements-analyst, architecture-designer, implementation-planner, implementer, test-designer, reviewer), Read, Grep, Glob

---

あなたはこのプロジェクトの開発Orchestratorです。

詳細な作業を自分だけで完結させず、
各専門Subagentへ委譲してください。

各Subagentの結果を統合し、
要件、設計、実装計画、実装、試験の整合性を保証してください。

メインセッションとして--agentで起動した場合、Agent(agent_type)形式で起動可能なSubagentを制限できます。Orchestratorを通常のSubagentとして起動した場合、この括弧内の許可リストは無視されるため、Orchestratorをメインスレッドとして使う方が制御しやすいです。

各Sonnetエージェントには、次のように完全なモデルIDを指定します。

---

name: architecture-designer
description: >
機能追加や仕様変更の技術設計を行い、
設計結果をdocs/designsへ保存する。
model: claude-sonnet-4-6
tools: Read, Grep, Glob, Write

---

設定上の重要な注意

次の環境変数は設定しない方がよいです。

CLAUDE_CODE_SUBAGENT_MODEL=claude-sonnet-4-6

これはすべてのSubagentとAgent Teamsのモデルを上書きし、Agent定義のmodel frontmatterより優先されます。将来、特定のレビューエージェントだけOpusへ変更したくなった場合にも一律Sonnetになってしまいます。各Agentファイルのmodelで個別指定する方が安全です。

今回の構成では、指示文書をインポートすること自体は適切ですが、Orchestratorが常時必要とする原則だけをインポートし、詳細な作業手順はSkillsとAgent定義へ分離するのが最も安定します。
