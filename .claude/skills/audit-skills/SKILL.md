# スキル・指示系棚卸しスキル

指示系の劣化（重複ルール・食い違い・鮮度切れ）を定期的に解消し、実績からの還流で
再現力を上げる。実績: 2026-07-02 に 2 回実施
（第1回: commit c35f78b / 第2回: b7ebf71〔スキル〕+ c8ec43e〔指示系横断〕）。

## 発動条件

- ユーザーが棚卸し・点検・整理を依頼したとき。
- 改善サイクルのトリガー（5 タスクごと等）で manager が指示系の劣化を疑ったとき。
- 使わない場面: 個別スキル 1 件の修正依頼（直接編集でよい）。

## 準備

- 作業ツリーがクリーンであることを確認する（git 管理下なら作業前コミット済み＝復元可能）。
- 実績源を確認する: `logs/`・`docs/{requirements,designs,implementation-plans,tests,reviews}/`・
  `docs/claude-code/improvements/`（candidates / backlog / evaluations）・git log。

## 守り: 診断（全対象を 6 項目で）

まず一覧表（名前 / 役割 1 行 / 最終更新 `git log -1` / 行数）を作り、各対象を診断する。

1. **発動**: description だけで使う/使わない場面を判定できるか。他と発動条件が被らないか。
2. **再現性**: 解釈で結果が変わる指示（「適切に」等）がないか。判断基準とデフォルト値があるか。
3. **例**: 良い例・悪い例が最低 1 つずつあるか（例が挙動を最も強く規定する）。
4. **完了条件**: 観測可能な形で書いてあるか。
5. **鮮度**: 参照パス・ツール・前提が現存するか。**パスは必ず実在確認する**（ls / test -e）。
   「現状」を記述した箇所は日付・出典があるか、現実と一致するかを確認する。
6. **構造**: 本体が肥大化していないか。詳細が参照ファイル・正典に分離されているか。

横断チェック（毎回実施）: 同じルール・フロー・状態が複数文書に書かれていないか grep で確認し、
食い違いがあれば正典を 1 つ決めて他を合わせる（実例: 委譲フローが 5 文書で不一致だった —
`cookpit/skills-inventory-audit` 事象 2）。

## 攻め: 実績からの還流

1. 採用・修正なしで通った成果物を探し、既存例より優れていれば良い例として取り込む。
   修正・却下された成果物からは NG 例と禁止ルールを抽出する。
   **追記には必ず出典（成果物・ログ・candidate のパス）を書く。**
2. ログ上で繰り返されているのにスキル化されていない作業を新スキル候補として挙げる
   （発動条件・手順・完了条件のドラフトつき）。
3. **ログの知識は現行コード・直近コミットで裏取りしてから還流する**（賞味期限切れの
   知識をそのまま定着させない。実例: 「--webpack 必須」は解消済みだった —
   `cookpit/skills-inventory-audit` 事象 4）。

## 変更の扱い（承認境界）

- **そのまま実施**: 客観的修正（デッドパス・矛盾・事実誤り・鮮度切れ）と、実績を出典に
  できる例の追記。
- **提案止まり**: 目的・判断基準・スコープを変えるもの、出典のない改善案、単発事象の
  ルール化（memory-policy の昇格条件に従う）、ファイルの削除・移設。各提案に選択肢と推奨を添える。
- スキル・Agent・Rule・CLAUDE.md を含む変更は作業ブランチへコミットしてよい。承認境界は
  **PR レビュー**（improvement-cycle §承認境界）。`main` へ直接反映しない
  （正典: docs/claude-code/harness-state.md）。

## 完了条件

- 修正した各対象を、初見の AI として頭から実行トレースし、迷う箇所が残っていない。
- 鮮度チェックの grep（古い状態記述のパターン）で残存ゼロ。
- 報告に次が揃っている: 診断一覧表（重症度つき。問題なしも明記）/ 修正の全 diff（攻めは
  出典つき）/ 新スキル候補と提案リスト（選択肢・推奨つき）/ 元に戻す方法（revert 対象コミット）。
