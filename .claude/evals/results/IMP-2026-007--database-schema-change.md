## ケース概要

Recipe に `status`（下書き/公開）を追加する L3 タスク。Drizzle スキーマ変更 + 既存行への
データ移行 + ドメイン状態遷移（Entity）の 3 層設計を伴う。contract-designer の起動は
orchestration-policy.md §contract-designer の必須起動トリガーにより確定（Drizzle スキーマ変更
= トリガー条件 2 に該当）。

改善A の影響: `status` は新規フィールドであり、api-contract（Zod）への追加が発生するため、
contract-designer が architecture-designer と並列先行できる条件（「既存 schema / api-contract
から契約の骨子が立てられる」）に該当するかを判定する必要がある。既存 schema には `status` が
まだ存在しないため、骨子を「既存ファイルから確定」することはできない。→ **集約構造が確定
するまで並列化できないケース**（改善Aの「集約未確定の L3 では並列化しない」ガードが発動する）。

改善B の影響: orchestrator が委譲前に `schema.ts`・既存 repository（例: RecipeRepository）・
関連 api-contract を先読みし、所在情報の要約を各 Subagent に渡す（L3 かつ対象 3 ファイルが
特定可能なシナリオ）。

## after 採点: 改善A のみ適用

### 採点根拠

**設計品質（before=4）**

改善Aで「集約構造が未確定で契約の骨子が立てられない L3 では並列化しない」というガードを
設けている。database-schema-change は新規フィールド `status` の追加であり、そのドメイン設計

contract-designer は骨子を固められない。ガードが正しく発動し、直列実行が維持される。
設計書（`docs/designs/recipe-status.md`）が contract-designer に参照されることも変わらない。
→ 設計品質: 4 維持

contract 先行）が生じないため、契約品質は before の 3 から悪化しない。

**トークン効率（before=4）**

## after 採点: 改善B のみ適用

### 採点根拠

**改善Bの適用条件**: L3 のみ・任意。このケースは L3 判定のため適用対象。
先読み対象ファイル: `schema.ts`（Drizzle スキーマ）・既存 RecipeRepository 実装 1 本・
関連 api-contract 1 本。3 ファイルとも実在し特定可能なシナリオ。

**影響範囲調査（before=4）**

orchestrator が schema.ts（既存カラム構成）・RecipeRepository（既存マッピング構造）・
api-contract（Zod の既存フィールド）を先読みし、所在情報を各 Subagent に渡すことで、
requirements-analyst / architecture-designer が「どのファイルを見るべきか」を
迷わず着手できる。ただし before=4 の根拠は「主要な層・ファイルを特定」であり、
現状でも各 Subagent が自力でファイルを特定できている水準。
所在情報の提供は「既に 4 水準にある」影響範囲調査をさらに底上げする効果はあるが、
「波及まで具体パスで特定」する 5 への到達には、各 Subagent の設計判断の深さが主因であり、
orchestrator の先読みだけでは 1 点の差分を生む根拠が弱い。
→ 影響範囲調査: 4 維持（0 差分）

**Agent 呼び出し効率（before=3）**

orchestrator が Read を 3 回追加で実行する（schema.ts / RecipeRepository / api-contract）。
これにより各 Subagent が同一ファイルを読む回数が減る効果がある。ただし before=3 の根拠は
「L3 フルフロー 6 Agent の本質的コスト」（Agent 起動回数が多い）であり、各 Subagent の
ファイル重複読取り削減は「合計 tool use 回数の削減」ではあるが、Agent 起動回数（6 Agent）は
変わらない。rubric の Agent 呼び出し効率は「起動した Agent 数が必要最小か」を測る軸であり、
ファイル読取りの重複削減は直接この軸に影響しない。
→ Agent 呼び出し効率: 3 維持（0 差分）

**トークン効率（before=4）**

orchestrator が 3 ファイルを先読みするためトークンが増える（orchestrator 側 +）。
一方、各 Subagent が同一ファイルを重複読取りする回数が減り（Subagent 側 -）。
提案書は「並列化により各 Subagent の個別調査量は減るため、トークンの純増は限定的と見込む」
と記している。ただしこれは改善Aと改善Bを組み合わせた場合の見込みであり、改善B単独では
orchestrator の +3 ファイル読取りが純増にならない保証がない。
- 前提：各 Subagent が schema.ts / RecipeRepository / api-contract を重複して読む場合、
  1 ファイルあたり Subagent が複数回読む → その削減効果 > orchestrator の 3 回追加読取り
  ならトークン純減。
- database-schema-change は requirements-analyst / architecture-designer / contract-designer /
  implementation-planner と複数 Subagent が schema.ts 等を参照する可能性が高い。
  4 Subagent × 重複ファイル > orchestrator 3 回追加分であれば純減。
- 要約の文字量が委譲指示に埋め込まれることで各 Subagent の入力コンテキストが増える点も
  考慮が必要。ただし所在情報のみ（設計判断は含まない）に限定しているため、要約文字数は
  最小限。

定性評価の限界上、トークン純減が確認できないため、現状を 4 維持とする。定量実行なしでは
0 差分（悪化なし）とみなすが、純増リスクが消えていない点を留意事項として記す。
→ トークン効率: 4 維持（0 差分、ただし純増リスクあり）

## このケースの総括

**database-schema-change（L3・新規 Entity・データ移行を伴う）** は改善Aの「集約未確定の
L3 では並列化しない」ガードが発動するため、改善Aの主効果（並列化による効率向上）は
このケースには現れない。

改善B は L3 先行調査を追加するが、影響範囲調査・設計品質・契約品質などの品質軸および
効率軸のいずれも悪化なし。ただし効率改善（トークン純減）の定量確認が定性評価では困難。

**全パターン（改善A/改善B/A+B）で悪化軸ゼロ。ただし効率改善も現れていない（0 差分）。**
このケースでは「改善が期待される」軸（Agent 呼び出し効率・トークン効率）の改善が確認できない。
評価の限界として、改善Aのガード発動による直列維持と改善Bの重複削減効果が「別のケース」に
現れる可能性を他のケース評価で確認する。
