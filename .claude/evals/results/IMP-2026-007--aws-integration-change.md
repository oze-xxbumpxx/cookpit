## ケース概要

レシピ画像を外部オブジェクトストレージ（S3 互換）にアップロードする機能を追加する L3 タスク。
`packages/infrastructure` に StorageAdapter を追加し、UseCase はインターフェース経由で呼ぶ。
MVP1 では外部連携未導入のため「設計判断・確認・ロールバック設計の質」を評価する。

orchestration-policy.md §performance-designer の起動条件「L3 かつ Infrastructure 経由の外部
API/外部ストレージへの I/O を新設・変更する」に該当するため performance-designer が起動する。
IMP-2026-003（reviewer 障害設計観点）も適用済み。

改善Aの影響:
- api-contract（Zod）に画像 URL / upload エンドポイントの型追加が想定されるため、
  contract-designer の起動は必須（IMP-2026-004 トリガー条件 1・3 に該当）。
- 既存 api-contract（RecipeSchema 等）と既存の infrastructure adapter 構造（もし既存例があれば）
  から「契約の骨子」が立てられるか判断する必要がある。
- 画像アップロードは「既存スキーマに類似フィールドが存在しない新規追加」であるため、
  「既存 schema / api-contract から確定できる型・nullability・エラー形式」の「骨子」は
  一部立てられる（エラー形式・Zod スキーマの構造パターン等）が、upload エンドポイントの
  レスポンス型・エラーコード体系はドメイン設計に依存する。
- **判定**: 既存 api-contract の構造パターンから一部の骨子（Zod スキーマの形式・エラー形式）
  は確定できるため、**並列化の条件を部分的に満たす可能性がある**。ただし
  architecture-designer が Infrastructure 分離・インターフェース設計を確定するまで
  StorageRepository のインターフェース型は固まらない。
  → このケースはグレーゾーン。改善Aの「判断はオーケストレーターが行う」という設計上、
  orchestrator が「骨子が立てられない」と判定して直列に戻す可能性と、「エラー形式等の
  部分骨子で並列先行する」と判定する可能性の両方がある。
- performance-designer は既に「architecture-designer 完了後、implementation-planner と
  並行可」と明記されており（before 構成）、改善Aでその余地が orchestrator.md の注記に
  追加される（明示化）。

改善Bの影響: orchestrator が schema.ts・既存 infrastructure（もし StorageAdapter の例があれば）
・api-contract の 3 ファイルを先読みする（L3・任意）。

## after 採点: 改善A のみ適用

### 採点根拠

**改善A の主要リスク確認**: 「contract-designer を並列先行させると、設計確定前の契約骨子が
architecture-designer の最終成果物とずれる可能性」。このケースでそのリスクが顕在化するか。

**契約品質（before=3）**

このケースでは architecture-designer が Infrastructure 分離・StorageRepository インターフェース・
upload エンドポイントのレスポンス型を確定するまで、contract-designer が「完全な」契約を
書けない。改善Aでは:
1. 並列化した場合: contract-designer が既存 api-contract の Zod 構造・エラー形式から
   「骨子」を先行作成する。設計確定後に orchestrator が確定差分を追送し、再確認させる。
2. ガード発動した場合（orchestrator が「骨子が立てられない」と判定）: 直列維持。

**ケースのグレーゾーン分析**:
- 既存 api-contract（RecipeSchema 等）の構造パターンは存在する → Zod スキーマの書き方の
  骨子は「立てられる」。
- しかし StorageRepository のインターフェース型・upload URL のレスポンス形式は
  architecture-designer の成果物に強依存する。
- 改善Aの緩和策（設計確定差分の追送 + 整合チェック）が機能すれば、契約品質は
  「骨子作成 → 確定差分追送 → 再確認」というプロセスで最終的な品質は担保される。
  ただし「追送を確実に行う」かどうかは orchestrator の判断精度に依存する。

定性評価として: 改善Aで orchestrator に「追送」という新たな責務が加わる。この追送が
漏れると（orchestrator が設計確定を検知できなかった場合）、contract-designer の契約骨子が
architecture-designer の最終成果物と不整合になるリスクが残る。before=3 の根拠は
「契約は妥当だが浅い」（contract-designer の起動は確定しているが、内容の深さが
architecture-designer の設計書依存）。

改善A の並列化は「追送」の機構を追加することで contract-designer が architecture-designer を
参照できなくなる問題を緩和している。ただし orchestrator による「確定差分を検知して追送する」
という暗黙の責務が正しく機能しなかった場合、before の 3 より悪化する可能性がゼロではない。

**判定**: 改善Aの緩和策（追送・整合チェック・参照リンク）が実際に機能する前提では 3 維持。
ただし「追送漏れリスク」という新たな劣化要因が追加されているため、実際の運用での確認が必要。
定性評価では悪化リスクを「懸念」として記録し、スコアは 3 維持（悪化なし）と判定する。

**Agent 呼び出し効率（before=3）**

## after 採点: 改善A + 改善B 同時適用

### 採点根拠

両改善の複合効果:
- 改善A: 並列化の判断が orchestrator に委ねられる。並列化が発動した場合、architecture-designer
  と contract-designer が同時起動し、設計確定後に追送が行われる。
- 改善B: orchestrator が先読み（schema.ts / api-contract）した要約を、並列起動する
  architecture-designer と contract-designer の双方に渡せる。所在情報を並列起動の両 Subagent
  に共有することで、重複探索が削減される。

A+B の追加効果: 並列起動時に orchestrator の先読み要約を双方に共有することで、重複読取りが
より削減される。ただし Agent 起動数は変わらず（architect + contract の同時起動は「1 本ずつ」
が「同時」になるだけで合計数は同じ）。

追加リスク: 並列化 + 先読み要約の複合で orchestrator の responsibility が増す（先読み → 要約
作成 → 並列委譲 → 確定差分追送 → 整合チェックという多段手順）。orchestrator の判断の
複雑化によりミス発生リスクが単独適用より高い可能性があるが、定性評価では軸スコアに
反映できるほどの差異を定量化できない。

全軸: 改善A・改善B 単独の組み合わせであり、新たな悪化要因は出ない（懸念の積み重ねは残る）。

## このケースの総括

**aws-integration-change（L3・外部I/O・performance-designer 並列あり）** では:

- 改善A: contract-designer の並列化発動が「グレーゾーン」（orchestrator の判断依存）。
  発動した場合でも緩和策（追送・整合チェック）により品質軸の悪化なし。ただし「追送漏れ」
  という新規リスクが定性懸念として残る。全軸スコアは 0 差分。
- 改善B: L3 先行調査を追加。安全性は「所在情報のみ」の制限で維持。全軸スコアは 0 差分。
- A+B: 複合効果は orchestrator の責務増加という潜在的懸念だが軸スコアでは捕捉できない。

**全パターンで悪化軸ゼロ。ただし効率改善も定量確認できない（0 差分）。**

特記: 改善Aの「追送漏れリスク」は設計漏れ指標の「懸念」として記録したが、現在の緩和策
（追送指示・整合チェック・参照リンク必須）が機能する前提でスコアへの影響はないと判定した。
実タスクでの監視が推奨される。
