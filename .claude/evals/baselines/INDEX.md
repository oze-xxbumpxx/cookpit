## 全体傾向の分析

### 現 harness の強い軸（上位3）

**1. 安全性（平均 4.9）**
guard-dangerous.mjs（PreToolUse）と settings.json の deny リストが二層で機能し、全ケースで
秘密情報・破壊的操作・本番デプロイのガードが有効。単一の最強軸。

**2. ユーザー確認の適切さ（平均 4.4）**
CLAUDE.md・orchestrator・各 Subagent・architecture-designer・contract-designer の複数箇所で
「設計判断・後方互換・DB スキーマは確認が必要」と明文化されており、確認の過不足が
ケースに依存しにくい構造。特に L3 ケースで一貫してスコア5を記録。

**3. 不要な作業量（平均 4.2）**
L1/L0 の過剰工程抑制が classify-change Skill と orchestrator で明示されており、
small-bug-fix・documentation-only-change でスコア5を記録。L2/L3 でも
スコープ外変更の禁止が各 Subagent に一貫して徹底されている。

### 現 harness の弱い軸（下位3）

**1. テスト網羅性（平均 2.6）**
最も低い平均スコア。MVP1 でテストランナー未導入という構造的制約が全ケースに影響。
特に refactoring（振る舞い不変の回帰確認が必須）と external-service-failure（異常系が核心）で
スコア2を記録。create-test-plan Skill に冪等性・障害系・フロントエンド固有の観点が薄い問題も重なる。
テストランナーが導入されるまでは構成の変更だけでは改善に限界がある軸。

**2. 契約品質（平均 3.4）**
contract-designer 起動条件が「orchestrator の判断」に依存しており、
L2 の API フィールド追加（Zod スキーマ変更）で必ず起動するかが不明確。
contract-validation-change では専門 Agent（contract-designer）が機能してスコア5だが、
他のケースでは3にとどまる。起動条件の明示化が課題。

**3. レビュー品質（平均 3.7）・影響範囲調査（平均 3.7）・トークン効率（平均 3.7）**
同スコアで3軸が並ぶ。
- レビュー品質：reviewer 定義に障害設計固有観点（リトライ嵐・冪等性欠如）が不足。L1 では reviewer が任意起動。
- 影響範囲調査：L2 では requirements-analyst が任意で、具体パスの洗い出しを強制する仕組みが弱い。
- トークン効率：L3 フルフロー + reflection-agent 必須で、軽量ケースでも大きなコスト。

## 採点上の前提と限界

- 本採点は実コード実行なし。Agent の定義・Skill・Rule・Hook・設計ドキュメントのプロンプトレビューに基づく定性評価。
- 実際の Agent 動作（モデルの応答品質・判断のブレ）は評価に含まれない。
- テスト網羅性の低スコアは構造的制約（テストランナー未導入）によるものであり、後続の改善提案がテストランナー導入を前提とする場合は再採点が必要。
- スコアは根拠から読み取れる範囲での推定であり、同一ケースを複数回実行した際の平均ではない。
