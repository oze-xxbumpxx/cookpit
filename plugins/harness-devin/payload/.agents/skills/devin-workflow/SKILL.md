# Devinの作業手順

共通のルールは`AGENTS.md`。この手順は、Devinに無い仕組み（Claude Codeのフック）の代わりと、Devin固有の約束だけを書く。

## 1. 着手する前

呼び出し側（Claude Code）は、承認済み計画のタスクからIssueを作り、専用クローンのロックを取って起動する。Devinから別セッションを作らず、起動結果不明やstallは呼び出し側へ渡す。

1. `AGENTS.md`と、`logs/`の最新の日付ファイルを読む。
2. `.agents/skills/classify-change/SKILL.md`で変更レベル（L0〜L3）を判定する。
   - L0 / L1（文言、テスト追加、lint修正、小さな修正）: そのまま進める。
   - L2 / L3（複数モジュール、API・DBスキーマの変更、新機能）: `docs/designs/`の設計書がユーザーに承認されていなければ、実装しない。設計案を示して止まる。
   - 技術スタック・アーキテクチャの決定（ADR級）: 候補と比較を示すところまで。決めるのはユーザー。
3. `main`から`devin/<内容>`のブランチを切る。他のツール（Claude Codeの`claude/`など）が使っているブランチにはpushしない。

## 2. 実装

- コーディング規約は`.claude/rules/coding-standards.md`（`any`禁止、名前付きエクスポート、`import type`、値なしは`null`）。`undefined`を使ってよいのはPATCHの入力の「その欄を送っていない」だけ。省略できる欄（`?:`）や`find`の結果を返すときは`?? null`で`null`にそろえる。
- PRの説明・コメント・docsの文章は`.claude/rules/writing-style.md`（結論を先に、具体的に、抽象語を並べない。和文と英字のあいだにスペースを入れない）。
- テストは各workspaceの`tests/`に置き、`src/`の構造をミラーする。
- 例外（DBドライバー・外部ライブラリ）の`message`には、接続先のURLやトークンが入っていることがある。ログ・標準出力・APIの応答にそのまま出さず、許可した項目（種類やコード）だけを出す。テストでは、実際に出た文字列に秘密が無いことを確かめる（`JSON.stringify(error)`は`message`を含まないため、それだけでは確かめられない）。
- テストは本番と同じ組み立てで、Issueのテスト項目の経路を最後まで通す。HTTPのテストは本番と同じ組み立ての関数でアプリを作る（素のHTTPサーバーや別の設定にしない）。モックした呼び出し（例: `router.replace`）の先で起きること（再描画など）が項目に含まれるなら、`rerender`などでその状態まで進めて確かめる。
- 観点のテストは、試験計画のその観点の「前提」と「試験データ」の節のとおりのデータで作る。assertは、確かめたい処理を壊したら落ちるものにする（常に真の比較や、確かめたい値を含まない比較にしない）。403 / 404など拒否の規則は、同じ規則を持つすべての経路（読み取りと書き込み）で確かめる。
- リクエストで受け取る配列と、外から来る値をたどるループ（`cause`など）は、設計書の上限と重複の決まりを実装する。設計書に上限が無ければ、自分で数を決めて拒否を足さない。PRの説明に「上限が設計書に無い入力」として挙げる（数を決めるのはユーザー）。
- 依頼の範囲外のリファクタリングはしない。気づいたことはPRの説明に書く。
- 存在しない設計書・コマンド・レビュー結果をあるものとして扱わない。

## 3. PRを出す前の品質確認

次をすべて通す。

```bash
bash .claude/scripts/run-quality-gates.sh
```

- 品質コマンド（lint・型チェック・テスト・ビルド）は`AGENTS.md`に書いたものを通す。上のスクリプトはロックファイルからパッケージマネージャーを選び、実在するコマンドだけを実行する。
- ハーネス（`.claude/`・`.agents/`）を変えたら`node --test .claude/tests/*.test.mjs`も通す。
- 手元で動かせない試験（Dockerが要るものなど）はCIに任せ、PRに「未確認」と書く。
- 画面を変えたら、変えた画面をブラウザで開き、設計書かIssueが示す見本と見比べる。見本が無ければ、実装を止めて報告する。ブラウザを開けなければPRに「画面は未確認」と書く。
- 通らないテストをスキップ・無効化してCIを通さない。

## 4. PR

- タイトルは既存に合わせる（`feat:` / `fix:` / `docs:` + 日本語）。
- 説明に「変更レベルと、ユーザー承認: 必要 / 不要」「何を・なぜそう設計したか・別の方法との比較」「実行した品質確認と結果」を書く。L1の説明は3行以内の要約でよい。
- Issueが設計書の表（エラーのcodeと表示・状態の遷移・契約の経路など）を参照していたら、説明に表の**行ごと**の対応（実装の場所・テスト）を書く。正常系以外の行（403 / 404 / 401、結果不明、空の入力など）を汎用の扱いでまとめない。対応を書けない行があれば、実装を変えずに止まって報告する。
- マージはユーザーが行う。Devinはマージしない。

## 4.5 PRを出した後（コメントとCIの監視）

PRを出したらセッションを終了せず、コメントとCIを監視して自分で対応する（クラウドのDevinと同じく、ローカルでもコメントとCIの失敗に反応するため）。

- `sleep 300`程度の間隔で`gh pr view <n> --comments`を実行し、前回確認時以降の新しいコメントを見る。
- 同じ確認で既存のCIも見る。CIが失敗していれば、コメントが無くても原因を調べて修正し、pushする。
- 指摘（`<!-- claude-review -->`のコメントを含む）は修正をcommitして同じブランチにpushする。質問にはPRへのコメントで返信する。
- 修正のたびに §3の品質確認を通してからpushする。Claudeの新しい完了は呼び出し側が確かめる。短いSHAや旧レビューの印を成功の証拠にしない。
- 終了条件: PRがマージ・クローズされた、または最後に活動（新しいコメント・自分のpush）があってから4時間経過。
  PR作成時刻ではなく直近の活動から数える。レビュー投稿が遅れても、その投稿で時計がリセットされ、呼び出し側の`wait-for-pr-update.mjs`（投稿から4時間待つ）の中で対応できる。
  終わるときは「監視を終了した理由」と「最後に確認した時刻」を報告する。
- 監視中も「やってはいけないこと」の制約は変わらない（force push・mainへのpushはしない）。レビュー中のブランチに他者がコミットしていたら、上書きせず報告する。

## 5. 作業ログ

`logs/`は編集しない（PRに含めない）。並行するPRが同じ日のログに追記すると、毎回衝突するため。
やったこと・検証結果・未完了・気づきはPRの説明に書く。日次ログには、Claude CodeがPRのレビューとマージの後に、委譲の記録とPRの説明から書く。

## やってはいけないこと

次はユーザーの確認なしに実行しない。

- `main`への直接push、履歴の書き換え（force push）、ブランチの削除
- データの削除、migrationの本番適用、本番環境への操作
- `.env`や秘密情報のコミット（`.env.example`に本番の値を書かない）
- `.claude/`・`.agents/`・`AGENTS.md`・`CLAUDE.md`の変更（ハーネスの構成。変えるならPRで理由を書き、重点レビューを依頼する）
- 他のリポジトリのスキルをこのリポジトリの作業に使うこと。使うのは、このリポジトリの`.agents/skills/`にあるスキルとDevin組み込みのスキルだけ。
