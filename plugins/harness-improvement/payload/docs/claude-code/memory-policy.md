# Memoryポリシー（保存先分類・昇格・肥大化対策）

知見をどこに保存するか、どう昇格させるか、どう削除するかを定める。改善サイクルの全体像は
[improvement-cycle.md](./improvement-cycle.md)を参照。

## 大前提

- **Memoryは学習済みモデルではない。** 次回セッションに読み込まれる永続コンテキストに過ぎない。
  誤情報を保存すれば次回以降も誤りを参照する。だから保存は慎重に、削除は迅速に。
- **保存先は知見の「確からしさ」と「適用範囲」で決める。** 単発・検証中ほど局所（Auto Memory）、
  検証済み・全体適用ほど中心（CLAUDE.md / Rule / Skill）。
- **段階を飛ばさない。** `単発 → Memory` / `繰り返す → 改善候補` / `検証済み → Agent・Skill・Rule`。

## 保存先の分類

| 保存先                 | 何を置くか                                                                                                 | 確からしさ           | 変更の重さ                                  |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- | -------------------- | ------------------------------------------- |
| **Auto Memory**        | ビルドコマンド / デバッグで判明した注意点 / ユーザー修正 / プロジェクト固有パターン / 一時的・検証中の知見 | 低〜中（検証中含む） | 自動可                                      |
| **Subagent固有Memory** | Agent固有の成功・失敗パターン / 担当領域固有の注意点 / 頻出レビュー指摘 / 担当領域の調査方法               | 中                   | 自動可                                      |
| **CLAUDE.md**          | 全セッションで必ず必要な原則 / 全Agentが知るべきルール / 長期有効な方針 / 複数回再現した重要注意           | 高（検証済み）       | **人間承認必須**                            |
| **.claude/rules**      | 特定ディレクトリにだけ効くルール（frontend / backend / DB / test固有）                                     | 高                   | 非破壊追加はmanager後可 / 破壊的は人間承認  |
| **Skills**             | 複数ステップの作業手順 / 再利用チェックリスト / 成功した設計・実装・レビュー手順 / 成果物テンプレート      | 高                   | チェック項目追加・テンプレ改善はmanager後可 |
| **Hooks**              | 必ず実行する検証 / 必須成果物確認 / テスト実行確認 / Agent設定の構文検証 / 改善プロセス起動トリガー        | 高（機械的制御）     | ブロック条件の変更はPRレビューで確認        |

### 知見を置く場所

役割ごとの子エージェントは畳んだ。知見はスキルか、検証役の定義か、CLAUDE.mdに置く。役割の名前でMemoryを分けない。

- 手順の癖（設計の落とし穴、計画の粒度、テストの境界、ビルドの詰まり）は、対応するスキルに足す。
- `reviewer`と`security-reviewer`にだけ効く指摘の型は、その定義に足す。
- どの作業でも効く注意は、CLAUDE.mdへ上げる候補にする。PRのレビューで人が見る。
- 改善のメタ知見は`improve-harness`が読む文書に残す。

> 全員に効く知見を、検証役の定義へコピーしない。

## 昇格条件（Auto Memory → 改善候補）

Auto Memoryの知見を無条件にCLAUDE.md / Skillsへ反映してはいけない。以下のいずれかを
満たしたときだけ改善候補へ昇格する。

- 同じ問題が **3回以上**発生した
- ユーザーから**同じ修正を2回以上**受けた
- Reviewerから**同種の重大指摘を複数回**受けた
- **本番障害**または**重大な試験不具合**につながった
- **複数Agentで同じ認識不足**が発生した
- 作業時間またはトークンを**継続的に浪費**している
- 明確な**成功パターンが複数タスクで再現**した

### 早期昇格の原則禁止（IMP-2026-030）

上記の回数条件を満たす前にproposal化・本適用しない。例外は次の**1行だけ**:

- **確証あり・修正極小**: 手動再実行等で再現が確定し、変更が1ファイル程度の客観的バグ修正
  （例: Hookの誤検知修正）。例外適用時はproposalまたはbacklogに「例外理由」を1行残す。

個人開発ライトモードでは、例外を常用しない（改善サイクルの自己肥大を防ぐ）。

### 昇格時に記録する項目

観測した事象 / 発生回数 / 対象タスク / 原因仮説 / 改善案 / 変更対象 / 想定される副作用 /
評価方法。記録先は`improvements/candidates/<task-id>.md`（→ 横断分析後`proposals/`）。

## candidateのアーカイブ（IMP-2026-030）

対応済み候補は`improvements/candidates/archive/`へ移し、現行一覧を痩せ保つ。
`archive/`が無ければ移すときに作る。移動基準はこの節を正典とする。

移してよい条件（すべて満たす）:

1. 紐づくIMPが`accepted`または`rejected`で決着している
2. backlogの当該行ステータスが更新済み（candidateのまま残っていない）
3. 未解決の再発監視がcandidate本文に残っていない（残すならbacklogのMemory留めへ）

## 肥大化への対策

指示・Memoryは増やすほど良いものではない。増えすぎると判断遅延・指示競合・不要作業・
トークン増・重要指示の埋没を招く。次を守る。

- **改善＝追加ではない。** managerは提案時に「不要な指示の削除・適切な場所への移動」を
  必ず検討する。1提案 = 1根本原因 = できるだけ1変更対象。
- **重複は統合する。** 同じ根本原因の候補は1提案にまとめる。
- **CLAUDE.mdは痩せ保つ。** 局所ルールは`.claude/rules/`、手順はSkills、メタ記録は
  `improvements/`に分離する。CLAUDE.mdには「全Agentが常時必要な原則」だけ。
- **Auto Memoryは定期的に棚卸し**する。検証が終わって恒久化したものはSkill/Ruleへ移し、
  Auto Memory側の重複は消す。古い・一度きりの注意点は削除する。
- **Auto Memoryはトピック別に分けてよい（任意）**。索引（MEMORY.md）は簡潔に保ち、詳細は
  `build-and-test` / `architecture-findings` / `debugging` / `reviewer-findings` /
  `user-preferences`などのトピックへ分割すると肥大化を抑えやすい。Auto Memoryはマシン
  ローカル前提。チームで共有すべき確定知見はGit管理の文書（Rule/Skill/ADR）へ昇格する。
- **TTLの意識**: 「一時的・検証中」と明記したAuto Memoryは、次の改善サイクルで再評価し、
  再現しなければ削除する。
- **メタ作業を測る**: `metrics/<task-id>.yml`の`process.meta_work_ratio`（セッション時間に
  占める改善・棚卸し・承認待ち等の割合。不明ならunknown）で再増殖を監視する。

## 誤った知見の削除手順

Memoryはモデル再学習ではないので、誤りは**ファイルを消せば**次回から参照されない。

1. **どこに保存されたか特定する**（Auto Memory / Subagent Memory / Rule / Skill / CLAUDE.md）。
2. **影響範囲を確認する**：その知見を参照しているAgent・Skill・Ruleをリンクで辿る。
3. **削除または訂正する**。
   - Auto / Subagent Memory: 該当エントリを削除（自動反映可の範囲）。
   - Rule / Skill / CLAUDE.md: proposalに「誤情報の撤回」として差分を起票し、
     作業ブランチで削除・訂正して **PRレビュー**で確認を得る。
4. **再発防止**：誤情報を生んだ原因（誰がどの段階で誤判断したか）を`candidates/`に残し、
   必要ならHook/レビュー観点で検知できるようにする。
5. **記録**：削除も改善の一種。backlogに「撤回」行を残し、なぜ誤りだったかを1行で残す。

## 自動化の境界（要約。正典はimprovement-cycle.md）

- **自動実行可**: Auto Memory候補の整理 / 振り返り作成 / 改善候補作成 / 評価レポート作成 /
  重複候補の統合 / フォーマット修正 / リンク切れ修正。
- **managerレビュー後に可（非破壊・軽微）**: Skillのチェック項目追加 / テンプレート改善 /
  Agent descriptionの軽微改善 / 非破壊的なRules追加。
- **独断で確定しない（PRレビューで確認）**: CLAUDE.md / Agentの責務・モデル・ツール権限 /
  Hookのブロック条件 / 自動実行シェルコマンド / セキュリティルール / 成果物の省略条件 /
  本番影響設定。
