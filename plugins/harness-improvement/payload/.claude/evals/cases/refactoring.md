# 評価ケース: リファクタリング（L2）

## 想定レベル

L2（複数ファイルに触れるが**外部から見た振る舞いは不変**）。

## シナリオ

`packages/application/src/recipe` の UseCase 群に重複した組み立て/変換ロジックがある。
振る舞いを変えずに整理する（共通化・命名整理・責務の置き直し）。公開インターフェースと
API 契約は変更しない。

## 期待される進め方

- 変更レベルを **L2** と判定（振る舞い不変の構造変更）。
- **スコープを厳守**する。依頼範囲外のファイル・機能には触れない（気づきはコメントで報告）。
- 1 ユースケース = 1 クラス・`execute()` の原則を保つ。手動 DI の構造を壊さない。
- 公開 API・Zod 契約・DB スキーマを変えない（変えるなら別タスク・要確認）。
- 変更後に `pnpm lint` / `pnpm type-check`。テスト導入後は回帰テストで振る舞い不変を確認。

## 期待成果物

- `docs/designs/...`（何を/なぜ整理するか・振る舞い不変の根拠・対象外の明記）。
- `docs/implementation-plans/...`（対象ファイル・各ステップ・ロールバック）。
- `docs/tests/...`（回帰観点：整理前後で入出力が同一であること）。

## 評価で特に見る軸（rubric）

- **不要な作業量 / スコープ厳守**: 依頼範囲を超えた「ついで改善」をしていないか。
- **実装整合性**: 公開インターフェース・契約・振る舞いを変えていないか。
- **テスト網羅性**: 振る舞い不変を担保する回帰観点があるか。
- **トークン効率**: 最小の変更で目的を達しているか。

## 失敗パターン

- リファクタに乗じて仕様変更・API 変更を混ぜる（振る舞いが変わる）。
- スコープ外のファイルまで「改善」して差分を膨らませる。
- 集約境界・依存方向を崩す形で「共通化」する。
