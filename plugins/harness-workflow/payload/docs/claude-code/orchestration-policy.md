# 検証と探索のポリシー

機能の追加と修正は、メインのセッションが`develop-feature`スキルで進める。設計、計画、実装、試験計画は子エージェントに渡さない。

子に渡すのは、別の文脈が要る仕事だけ。

- `reviewer`。実装のあと。品質と整合性。
- `security-reviewer`。下の起動条件に当たるとき。`reviewer`と並行してよい。
- 広い探索。当たった場所と結論だけを持ち帰らせる。Claude Codeの`Explore`を使う。

プロジェクト内の定義が`Agent`ツールを持つことは想定しない。検証役は互いを起動しない。

## 検証役に渡すこと

- 目的
- 対象範囲と対象外
- 参照するファイル（設計書があるならそのパス）
- 返してほしい形（指摘の表と、見なかった範囲）

設計の全文や、実装中の試行は貼らない。返ってきた指摘は、メインのセッションがコードと突き合わせてから直す。無条件では採用しない。

## レベルごとの流れ

手順の本体は`develop-feature`スキル。ここは分岐だけを書く。

### Level 0

読んで答える。実装しない。

### Level 1

このセッションが直す。設計書は作らない。振る舞いが変わるなら`reviewer`。`security-reviewer`は起動しない。

### Level 2

問い、設計、実装計画、試験計画をこのセッションで書く。設計の承認のあと実装する。そのあと`reviewer`。`security-reviewer`は起動条件に当たるときだけ。当たらなければ省略理由を1行書く。

### Level 3

Level 2に、要件定義書を足す。外部入出力か大量データなら、設計書の性能の節を厚く書く。契約が変わるなら設計書にContract節を書く。`security-reviewer`は原則起動する。結合やE2Eは、試験計画に観点があり`e2e/playwright.config.ts`があるとき、このセッションがテストを足す。

改善サイクル（振り返り、横断分析、回帰評価）は`AGENTS.md`で休眠。ユーザーが頼んだときだけ`reflect-task`と`improve-harness`をこのセッションで読む。

## 実装ルート

実装はこのセッションで行う。`harness-devin`を入れていれば、Issue起点のL0 / L1はDevinへ渡せる（`review-devin-pr`）。

作業ブランチは必須。`main`への直コミットは禁止。マージの判断はユーザーが行う。

`review-readiness`とGate Bは休眠（`docs/reviews/README.md`は未作成）。指摘と検証結果はPRと日次ログに残す。チャットとPRに`受け入れ可`、`PASS`、`APPROVED`を書かない。

## 再開したとき

ログと、期待するファイルの有無で、済んだ工程をやり直さない。設計書がすでにあれば設計からやり直さない。検証役を、成果が残っているのに起動し直さない。

## 契約を設計書に書く条件

専用の契約役は無い。次のどれかに当たる変更は、設計書のContract節に書く。L2の項目追加も当たれば書く。

1. 公開API、イベント、CLIの入出力に項目の追加、変更、削除がある。
2. DBスキーマに列、制約、型の追加、変更、削除がある。
3. 層をまたぐDTOの形が変わる。
4. 必須と任意、null、enum、最大長などの検証境界が変わる。
5. エラーの形や、同じ要求の再送で二重に作られないためのキーが、外から見て変わる。

契約の形が変わらない内部の整理、文書だけ、L1の軽微な修正には書かない。

## security-reviewerの起動条件

L1では起動しない。L3は原則起動する（文書だけは除く）。L2はセキュリティの触点があるとき起動し、省略条件に当たれば省いてよい。

### 必ず起動する（L2/L3）

1. 認証、認可、セッション、Cookie、セキュリティヘッダーの新設や変更がある。
2. トークン、APIキー、個人情報の扱いが変わる、またはログの出力経路が変わる。
3. 外部APIや外部ストレージへの入出力を新設、変更する。
4. 依存パッケージの追加やメジャー更新がある（`package.json`やlockfile）。
5. 入力の境界を新設、変更し、未検証の値が業務ロジックに届きうる。
6. L3の、新しいAPI、DBスキーマ、データ移行を含む変更。

### 省略してよい

次をすべて満たすL2は省略してよい。省略したら報告に理由を1行書く。

- 画面だけ、または契約・DB・認証に触れない内部の整理、テスト基盤だけ。
- 依存の追加やメジャー更新が無い。
- 秘密情報、外部入出力、認証認可に触れていない。

L2/L3とも、文書、コメント、表示文言だけの変更は省略してよい。

判断に迷うときは起動する。

役割の分担は次のとおり。

- `reviewer`は品質、整合性、責務の境界、エラー処理、テスト不足を見る。
- `security-reviewer`はOWASP Top 10、認証と認可、秘密情報の漏れ、依存の脆弱性を見る。

## 性能の節（L3、条件付き）

次のどれかを含むL3だけ、設計書の性能の節を厚く書く。単独の性能役は無い。

1. 外部APIや外部ストレージへの入出力を新設、変更する。
2. 一覧や集計など、大量データを扱うクエリを新設、変更する。
3. 性能の要件が明示された改善。

## ツールごとの起動方法とモデル

起動方法は共通スキル[develop-feature](../../.claude/skills/develop-feature/SKILL.md#ツールごとの起動方法)に従う。次のモデル指定はClaude Codeだけに適用する。

| 仕事                                | モデル                                                                                        |
| ----------------------------------- | --------------------------------------------------------------------------------------------- |
| 広い探索                            | Exploreを`haiku`で起動                                                                        |
| 検証（reviewer、security-reviewer） | 各定義の`claude-opus-5-5`                                                                     |
| 設計、計画、実装                    | メインのセッション。L3の方針決めではFableへの切り替えを提案してよい。切り替えはユーザーが行う |

`CLAUDE_CODE_SUBAGENT_MODEL`は設定しない。設定すると検証役の`model`まで一律で上書きされる。

探すだけの作業を検証役に渡さない。
