# このセッションで実装する

確定した設計と計画に沿って実装する。実装役の子エージェントは起動しない。

規約の詳細は[coding-standards.md](../../rules/coding-standards.md)。品質コマンドは[definition-of-done.md](../../../docs/claude-code/definition-of-done.md)。

## 着手前

- L2/L3は`docs/designs/<feature-name>.md`と`docs/implementation-plans/<feature-name>.md`を読む。どちらかが無い、または必須の節が空なら、コードを変えない。
- L1は設計書が無い前提で、依頼の範囲だけ直す。
- レベルに試験計画（`docs/tests/<feature-name>.md`）があれば、その観点をテストにする。

## やること

- 計画の手順に沿って実装する。
- 計画の「ドキュメント更新対象」を、コード変更と同じ完了条件として実施する。
- 実在するlint、型チェック、テストだけ実行する。未導入のコマンドは`unknown`。ハーネス自身を変えたときは`node --test .claude/tests/*.test.mjs`。
- 変更したpublicメソッド、staticファクトリ、ゲッターに、最低1つのテストを置く。状態を変えるメソッドは、変えたあとの値を検証する。
- EntityやValue Objectを変えたときは、防御的コピー、不正な引数、状態変更後の`updatedAt`を検討する。計画に無い観点を足したら、報告に差分を書く。

## L3の結合とE2E

L3で、試験計画に結合やE2Eの観点があり、`e2e/playwright.config.ts`があるときだけ、その基盤にテストを足す。基盤が無い観点は`docs/tests/<feature-name>.md`の「未実装観点（基盤待ち）」に残す。プロダクションコードを、テストのためだけに増やさない。

## 設計と食い違ったとき

実装を止める。食い違いと選択肢をユーザーに出す。設計を独断で変えない。

## しないこと

- 依頼の範囲外のリファクタ。気づきは報告に書く。
- `main`への直コミット、force-push、ブランチの削除。作業ブランチへの通常のcommitとpushは、PRのレビューが承認の境界。
- 設計と計画に無いファイルの追加。必要ならユーザーに確認する。

## 報告

変えたファイル、実行した確認と結果、設計からの逸脱の有無、ドキュメント更新の実施状況。L2/L3は何を変えたか、なぜその構成か、検討して採らなかった案。L1は理由を3行以内。L0は省略してよい。
