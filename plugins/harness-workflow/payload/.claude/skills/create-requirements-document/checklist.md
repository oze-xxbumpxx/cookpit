# 要件定義の調べる観点

要件定義書を書く前に、この観点で「決まっていないこと」を探し、[ask-questions](../ask-questions/SKILL.md)の問いにする。
全部の観点に問いを作る必要はない。設計資料や既存の決定で答えが出ているものは、根拠を書いて飛ばす。

立場（操作した人・相手・運用する人など）ごとに分けて考える。エンジニアの目だけで見ると、相手側の画面・通信が切れたとき・あとから見返すときの観点が抜けやすい。
プロダクトに固有の立場（お金を払う側と受け取る側など）は、導入先で下の表に足す。

## 1. なぜ作るか（要求）

- この機能が無いと、使う人は今どう困っているか。設計資料のどこに書いてあるか。
- 今回の段階でどこまで作り、どこを次の段階に回すか（画面だけ・APIだけ・ふつうの流れだけ、など）。
- 設計資料の案から変えたい値はあるか（上限・件数・期間など）。変えるなら理由。

## 2. 何が変わるか（使い方）

立場ごとに、操作の前後で何が見え、何ができるかを追う。

| 立場                           | 見る観点                                                                             |
| ------------------------------ | ------------------------------------------------------------------------------------ |
| 操作した人                     | 操作のあと、画面に何が出るか。間違えたとき戻せるか（取りやめ・取り消し）             |
| 相手                           | 相手の操作をいつ・どこで知るか。同時に同じものを触ったら（競合）                     |
| 通信が不安定な人               | 電波が弱い・切れたときに保存できるか（結果不明・同じ要求で確かめる）                 |
| あとから見返す人               | 記録を見返したとき、取り消した記録や誰が何をしたかが分かるか                         |
| 運用する人（自分）             | 使う人から「おかしい」と言われたとき、どの記録で原因を追えるか                       |

- 既存の機能のうち、この変更で振る舞いが変わるものはどれか。`path`で挙げる。
- 個人情報（名前・メール・位置）を新しく持つか、見せる範囲が変わるか。

## 3. 何を作るか（要件）

- 機能: 入力・出力・状態の移り方。状態ごとに、できる操作とできない操作。
- 異常系: 権限がない、相手が先に変えた、二重に送った、途中で失敗した、ときの振る舞い。
- 境界: 0・空・上限・下限・日付の切り替わり・期間の開始前と終了後。
- 性能・保存: 件数の上限、オフラインのとき、再読み込みしたときに残すもの。
- 受け入れ条件: 自動の試験で確かめるもの、手で確かめるもの、E2Eに足すもの。

## このチェックリストの育て方

設計・実装・レビューの段階で「要件定義のときに聞いておけばよかった」問いが出たら、その観点をここに1行足す。
`ask-questions`の記録で「推奨と同じか」が「違う」だった問いも、足す候補にする。
