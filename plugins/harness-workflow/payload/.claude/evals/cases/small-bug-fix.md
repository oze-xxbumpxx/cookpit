# 評価ケース: 小さなバグ修正（L1）

## 想定レベル

L1（単一ファイル・単一層の軽微修正。設計書・実装計画は作らない）。

## シナリオ

`packages/domain/src/recipe` の Recipe Entity / Value Object のバリデーションに 1 件の不具合が
ある（例：調理時間が 0 分でも `create()` が通ってしまう／タイトルの空白のみを弾けていない）。
ユーザーは「このバリデーションのバグだけ直して」と最小修正を依頼する。

## 期待される進め方

- 変更レベルを **L1** と判定し、理由を簡潔に提示する。
- Orchestrator は実装を **implementer に直接**委譲する（設計書・実装計画・ADR を作らない）。
- `.claude/state/current-feature` は設定しない（Hook を黙らせ誤検知を防ぐ）。
- ドメインロジックは Entity / Value Object 内に閉じ込めたまま直す（UseCase/Repository に
  バリデーションを漏らさない）。
- 修正後に `pnpm lint` / `pnpm type-check` を実行する。

## 期待成果物

- 該当 Entity / Value Object の最小修正。
- 最終報告に「変更理由・確認内容・lint/型チェック結果」。

## 評価で特に見る軸（rubric）

- **不要な作業量**: 1 件のバグに対し設計書・実装計画・大量調査をしていないか（L1 を L2 に
  膨らませないか）。
- **不要な質問回数**: 自明な最小修正で過剰に確認していないか。
- **実装整合性**: 依存方向・集約境界・コーディング規約（`any` 禁止・`===` 等）を守っているか。
- **トークン効率**: 必要最小の Agent 呼び出しで完了しているか。

## 失敗パターン（after で増えていたら減点）

- L1 なのに設計書・実装計画を作って手戻り・トークンを浪費する。
- バリデーションを Entity の外へ出してしまう。
- スコープ外のリファクタを混ぜる。
