# 文章の書き方

人が読む文章はすべてこの書き方にする。対象はユーザーへの報告、`logs/`、`docs/`、Issue、PRの説明、レビューのコメント、コードのコメント。
目的は、読んだ人がすぐ意味をつかめること。整って見えることではない。

このルールは、ユーザーが指定した文章スキル`shizen-nihongo`の要点をリポジトリに写したもの。Claude Codeは書くときにスキルも読み込み、新しく書く文章は執筆の手順、既存の文章は推敲の手順で扱う。Devinにはスキルが無いので、このファイルだけで同じ書き方になるようにしてある。

## 書く前に

- 誰が読むかを決める。決まらないときは「この会話を見ていない、明日のユーザー」とする。
- 言いたいことを1文で言えるか確かめる。言えないなら、まだ書かない。書き方ではなく材料が足りないので、調べるかユーザーに聞く。
- 文書の立場（勧め・決まり・説明）を先に決め、文末をそろえる。敬体と常体を混ぜない。

## 直すときは意味を変えない

既存の文章を直すときは、次の4つを変えない。ほかのルールはこの範囲でだけ使う。

- 主張と論理のつながり。「本質」を「目的」のような別の言葉にすり替えない。
- 何を一番大事にしているか。否定していたものを「AとB」と並べない。
- 言い切りの強さ。断定は断定のまま、推量は推量のまま書く。
- 文の働き。評価・説明・依頼・予定の区別。

元の文から分からない動作主・数・例・原因は足さない。足りなければ、書いた人に聞く。

## 書き方

- 結論を最初の1文に書く。前置き・あいさつ・「まとめると」は書かない。
- 何が・いくつ・どれかを具体的に書く。「多くの」「様々な」「一部の」は、数か名前に置き換える。置き換えられないなら、その文を消す。
- 誰が・何を・どうしたが、その文だけで分かるように書く。「これ」「それ」は指す先がすぐ分かるときだけ使う。
- 1文に言いたいことは1つ。目安は30〜45字。分けるのは、理由や順序のつながりを次の文のつなぎ言葉で残せるときだけ。
- 見出しには中身を書く。読み手が見出しだけで結論がわかるようにする。
- 漢語より和語。「実施する」→「する」、「確認を行う」→「確かめる」、「〜することが可能」→「〜できる」。
- 専門用語は、何をするものかを先に説明してから名前を出す。
- 箇条書きは、並べるものが本当に並列なときだけ使う。理由と結論のつながりは文で書く。
- 確かめた事実・推測・意見を混ぜない。推測は「推測ですが」と書き、語尾のぼかしで逃げない。
- 同じ主張を言い換えて繰り返さない。説明の後に要約を重ねない。
- 書いたあと、消しても意味が変わらない言葉を全部消す。

## 記号の使い方

- 和文と英数字・インラインコード・リンクのあいだに半角スペースを入れない（「AWS の設定」→「AWSの設定」、「`npm test` を」→「`npm test`を」）。URLの直後と、太字・強調の記号（`**`）の隣は、表示が崩れるのでスペースを残す。自動生成のコード（`apps/*/src/**/generated/`）は生成元の書き方のまま触らない。
- 絵文字、文末のコロン、ダッシュ（——、―）は使わない。ダッシュは助詞でつなぐか、文を切るか、括弧にする。
- 太字は読み落とされると困るところだけ。段落ごとに置かない。
- 情報が増えない言い換えの括弧（「設計（デザイン）」）は消す。

## 使わない書き方

| 使わない | 理由 | 直した例 |
| --- | --- | --- |
| 160本の検証で見えた限界と本質 | 抽象名詞を並べて、中身を見出しに書いていない | 160本で試した。敬語は直せたが、段落のクセは残った |
| 〜が見えてきた / 〜が浮き彫りになった | 発見の演出。何がわかったかを書けばよい | 〜とわかった |
| 〜の本質は〜 / 〜という観点で | 言葉を大きくしているだけ | 何の話かを直接書く |
| 〜することが可能です | 長い | 〜できます |
| 様々な観点から検討した結果、Aとした | 何と比べたかがない | AとBを比べて、〜なのでAにした |
| 重要なのは〜という点です | 前置き | 〜が大事です（または本題から書く） |
| 速く・安全で・使いやすい | 語呂のために3つ並べている | 本当にある利点だけを書く |
| 理由は3つあります / ポイントは以下の通りです | 数の宣言。中身が無い | 中身から書く。無理に3つに丸めない |
| 〜と言えるでしょう / 〜かもしれません（根拠なし） | ぼかし。言い切れないなら理由を書く | 〜です / 〜は試していないのでわからない |
| 一概には言えませんが / あくまで一例ですが | 予防線 | どの条件で成り立つかを書く |
| 実は / 驚くべきことに | 共感の演出 | 意外さは事実の差で伝える |
| 非常に重要 / 不可欠 / 鍵となる / 包括的 | 強調語で根拠の代わりにしている | 根拠そのものを書く |
| 解像度を上げる / 腹落ち / 温度感 | 何がどこまで分かったかが無い | 分かったことを具体的に書く |
| 効く / 〜側に倒す / 1つずつ潰す / 踏み込む / 深掘りする | AIが好む比喩の動詞 | 役に立つ / 〜を優先する / 1つずつ直す / 詳しく調べる |
| 静かに〜 / 〜した瞬間 | 比喩 | 気づかないうちに〜 / 〜するとすぐに |
| 落とし穴 / 土台 / 入口 / 核心 / 定石 / 別物 | 最近増えた決まり文句 | 見落としやすい点 / 基本 / 手始め / 肝心なところ / いつものやり方 / まったく違うもの |
| コードが語る / データが教えてくれる | 道具に意志を持たせている | 人を主語にするか、事実を書く |
| いかがでしたか / 参考になれば幸いです | 定型の結び | 消す。次に何をすればよいかで終える |
| ——（ダッシュ）での言い換え・付け足し | 翻訳調 | 文を切るか、括弧にする |
| 絵文字・太字の多用 | 目立たせたいところがわからなくなる | 太字は読み落とされると困るところだけ |
| 正本の案どおり / 正本の実装順序の次の段階 / 業務の規則 | AIしか使わない言葉 | 設計資料の案どおり / 設計資料の作る順番で次にあたる回 / アプリの決まり |

人が読む文章では「正本」と書かない（AIしか使わない言葉で、わかりにくい）。基本設計・詳細設計は「設計資料」と書き、必要なら資料の名前と節を添える。

## 出す前に見直す

1. 最初の1文で、聞かれたことに答えているか。
2. 見出しと各段落の先頭の文だけを読んで、話が通るか。
3. 同じ型の文（書き出し・定義・箇条書きの組み方）を3回続けていないか。
4. 上の表の言葉と、和文と英字のあいだのスペースが残っていないか。
5. 太字・箇条書き・見出しが、中身の量に対して多すぎないか。短い報告なら見出しは要らない。

## この表の育て方

ユーザーが「AIっぽい」「わかりにくい」と言った書き方は、この表に1行足す。
足すのは、実際に出てきた文と直した文のペアにする。一般論は足さない。
